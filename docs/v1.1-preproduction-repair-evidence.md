## 3. E-2: do SQLite reads write Library files?

Script (`probe1.py`):

```python
# Q: do read transactions write any Library file, in WAL vs rollback (TRUNCATE) mode?
import sqlite3, os, hashlib, shutil, time
def state(d):
    out={}
    for n in sorted(os.listdir(d)):
        p=os.path.join(d,n); st=os.stat(p)
        out[n]=(st.st_size, st.st_mtime_ns, hashlib.sha256(open(p,'rb').read()).hexdigest()[:12])
    return out
for mode in ['wal','truncate']:
    d=f'lib_{mode}'; shutil.rmtree(d, ignore_errors=True); os.makedirs(d)
    db=os.path.join(d,'library.sqlite3'); open(db,'xb').close()
    w=sqlite3.connect(db, isolation_level=None)
    w.execute(f'pragma journal_mode={mode}'); w.execute('pragma synchronous=FULL')
    w.execute('create table t(a integer primary key, b blob)')
    w.execute('begin'); w.executemany('insert into t(b) values(?)', [(os.urandom(64),) for _ in range(20000)]); w.execute('commit')
    # a second, long-lived connection = the writer's own session connection stays open
    time.sleep(0.05)
    before=state(d)
    changed_after=[]
    for i in range(5):
        r=sqlite3.connect(db, isolation_level=None)   # UI reader opens, reads, closes (not last connection)
        r.execute('begin'); r.execute('select count(*), sum(length(b)) from t').fetchone(); r.execute('commit'); r.close()
        time.sleep(0.02)
        after=state(d)
        changed_after.append([n for n in set(before)|set(after) if before.get(n)!=after.get(n)])
    print(mode, 'files at rest:', {k:v[0] for k,v in before.items()})
    print(mode, 'files changed by 5 reads (not last close):', changed_after)
    w.close()
    print(mode, 'after writer (last) close:', {k:v[0] for k,v in state(d).items()})
```

Output:

```

wal files changed by 5 reads (not last close): [['library.sqlite3-shm'], ['library.sqlite3-shm'], ['library.sqlite3-shm'], ['library.sqlite3-shm'], ['library.sqlite3-shm']]
```

**Finding.** In WAL mode, **every read transaction rewrote `-shm`** (content and modification time), and the last
close checkpointed and deleted `-wal` and `-shm` (as the review's P5). In rollback-journal `TRUNCATE` mode, reads
changed **no** file, and the journal stayed as a 0-byte file after commit and after close. Used by D-37 and OBS-03.

## 4. E-3: one-transaction import, journal peak and insertion order

Script (`probe2.py`, run with `N=1000000`): a `file_obs`-shaped `WITHOUT ROWID` table, two full-snapshot imports each
in **one** transaction, then deletion of snapshot 1 in one transaction, then a third import into the freed pages.
"key" inserts in primary-key order; "traversal" inserts the same rows shuffled (a stand-in for traversal order that
does not match interned-ID order). `cache_size` 8 MB.

```python
# Q: one-transaction import of a full snapshot: side-file peak, time, and ordering effect (WAL vs TRUNCATE).
import sqlite3, os, shutil, time, threading, random
N=int(os.environ.get('N','1000000'))
DDL='''create table file_obs(snapshot_id integer not null, folder_path_id integer not null, name_id integer not null,
 size_bytes integer not null, modified_utc integer, created_utc integer, accessed_utc integer, attributes integer not null,
 primary key(snapshot_id, folder_path_id, name_id)) strict, without rowid'''
def rows(sid, order):
    keys=[(f, n) for f in range(N//4) for n in range(4)]   # ~4 files per folder
    if order=='traversal':
        rnd=random.Random(7); rnd.shuffle(keys)                # stand-in for DFS order not matching interned-id order
    for f,n in keys:
        yield (sid, f, n*1000+f%997, 1234+f, 638000000000000000, None, None, 32)
def peak_watch(paths, stop, out):
    m={p:0 for p in paths}
    while not stop.is_set():
        for p in paths:
            try: m[p]=max(m[p], os.stat(p).st_size)
            except FileNotFoundError: pass
        time.sleep(0.005)
    out.update(m)
for mode in ['truncate','wal']:
  for order in ['key','traversal']:
    d=f'imp_{mode}_{order}'; shutil.rmtree(d, ignore_errors=True); os.makedirs(d)
    db=os.path.join(d,'library.sqlite3'); open(db,'xb').close()
    c=sqlite3.connect(db, isolation_level=None)
    c.execute(f'pragma journal_mode={mode}'); c.execute('pragma synchronous=FULL'); c.execute('pragma temp_store=memory'); c.execute('pragma cache_size=-8000')
    c.execute(DDL)
    res=[]
    for sid in (1,2):
        stop=threading.Event(); peaks={}
        t=threading.Thread(target=peak_watch, args=([db+'-journal', db+'-wal'], stop, peaks)); t.start()
        t0=time.time(); c.execute('begin immediate')
        c.executemany('insert into file_obs values(?,?,?,?,?,?,?,?)', rows(sid, order))
        c.execute('commit'); dt=time.time()-t0
        stop.set(); t.join()
        res.append((sid, round(dt,2), round(os.stat(db).st_size/2**20,1), {os.path.basename(k)[-8:]:round(v/2**20,1) for k,v in peaks.items()}))
    if mode=='wal': c.execute('pragma wal_checkpoint(truncate)')
    # delete snapshot 1 in one transaction: journal/WAL peak
    stop=threading.Event(); peaks={}
    t=threading.Thread(target=peak_watch, args=([db+'-journal', db+'-wal'], stop, peaks)); t.start()
    t0=time.time(); c.execute('begin immediate'); c.execute('delete from file_obs where snapshot_id=1'); c.execute('commit'); dt=time.time()-t0
    stop.set(); t.join()
    res.append(('del1', round(dt,2), round(os.stat(db).st_size/2**20,1), {os.path.basename(k)[-8:]:round(v/2**20,1) for k,v in peaks.items()}))
    # re-import into freed pages (snapshot 3)
    stop=threading.Event(); peaks={}
    t=threading.Thread(target=peak_watch, args=([db+'-journal', db+'-wal'], stop, peaks)); t.start()
    t0=time.time(); c.execute('begin immediate'); c.executemany('insert into file_obs values(?,?,?,?,?,?,?,?)', rows(3, order)); c.execute('commit'); dt=time.time()-t0
    stop.set(); t.join()
    res.append(('sid3-after-delete', round(dt,2), round(os.stat(db).st_size/2**20,1), {os.path.basename(k)[-8:]:round(v/2**20,1) for k,v in peaks.items()}))
    c.close()
    print(mode, order, 'N=',N, res)
```

Output. Each tuple is (step, seconds, database MB after the step, peak side-file sizes in MB during the step):

```
truncate key N= 1000000 [(1, 3.48, 31.4, {'-journal': 0.0, 'ite3-wal': 0.0}), (2, 3.22, 63.9, {'-journal': 0.0, 'ite3-wal': 0.0}), ('del1', 0.41, 63.9, {'-journal': 31.5, 'ite3-wal': 0.0}), ('sid3-after-delete', 2.61, 65.0, {'-journal': 0.1, 'ite3-wal': 0.0})]
truncate traversal N= 1000000 [(1, 8.02, 30.6, {'-journal': 0.0, 'ite3-wal': 0.0}), (2, 8.24, 62.0, {'-journal': 0.0, 'ite3-wal': 0.0}), ('del1', 0.74, 62.0, {'-journal': 30.7, 'ite3-wal': 0.0}), ('sid3-after-delete', 7.28, 62.9, {'-journal': 0.1, 'ite3-wal': 0.0})]
wal key N= 1000000 [(1, 3.25, 31.4, {'-journal': 0.0, 'ite3-wal': 31.6}), (2, 3.28, 63.9, {'-journal': 0.0, 'ite3-wal': 32.7}), ('del1', 0.38, 63.9, {'-journal': 0.0, 'ite3-wal': 31.6}), ('sid3-after-delete', 3.18, 65.0, {'-journal': 0.0, 'ite3-wal': 32.7})]
wal traversal N= 1000000 [(1, 9.39, 30.6, {'-journal': 0.0, 'ite3-wal': 30.8}), (2, 8.67, 62.0, {'-journal': 0.0, 'ite3-wal': 31.6}), ('del1', 0.39, 62.0, {'-journal': 0.0, 'ite3-wal': 30.8}), ('sid3-after-delete', 9.06, 62.9, {'-journal': 0.0, 'ite3-wal': 31.7})]
```

**Findings.**
1. A one-transaction import that **appends** a snapshot journals almost nothing in rollback mode (peak 0.0–0.1 MB),
   including when it reuses pages freed by a deletion. In WAL mode the same import needs a WAL about the size of the
   snapshot (31–33 MB per 1M rows here).
2. Deleting a snapshot journals about the snapshot's size in either mode.
3. **Insertion order dominates import time:** primary-key order was 2.3–2.9 times faster than shuffled order in both
   modes. Used by IMP-03.
4. Throughput is similar in both modes (about 300k rows/s in key order on this machine). These are relative numbers
   on Linux; Windows numbers are Q-17 (C4).

## 5. E-4: crash during import, and a separated hot journal

Script (`probe3.py`): a child process opens a TRUNCATE-mode database, inserts 300,000 rows and modifies existing
pages inside one transaction with a small cache (so SQLite spills pages to the main file), then exits without
committing.

```python
# Q: crash in the middle of a one-transaction import (TRUNCATE mode): what is left, and what does reopening do?
import sqlite3, os, shutil, subprocess, sys
d='crash'; shutil.rmtree(d, ignore_errors=True); os.makedirs(d); db=os.path.join(d,'library.sqlite3'); open(db,'xb').close()
c=sqlite3.connect(db, isolation_level=None); c.execute('pragma journal_mode=truncate'); c.execute('pragma synchronous=full')
c.execute('create table t(a integer primary key, b blob)'); c.execute('begin'); c.executemany('insert into t(b) values(?)', [(b'x'*100,)]*10000); c.execute('commit'); c.close()
child = r'''
import sqlite3, os
c=sqlite3.connect(%r, isolation_level=None); c.execute('pragma journal_mode=truncate'); c.execute('pragma synchronous=full'); c.execute('pragma cache_size=-500')
c.execute('begin immediate'); c.executemany('insert into t(b) values(?)', [(b'y'*100,)]*300000)
c.execute('update t set b=x\'00\' where a<=5000')   # modify pre-existing pages too
os._exit(9)   # crash: no commit, no close
''' % db
subprocess.run([sys.executable, '-c', child])
ls=lambda: {n: os.stat(os.path.join(d,n)).st_size for n in sorted(os.listdir(d))}
print('after crash:', ls())
# hazard: set aside ONLY the main file, then create a new empty Library at the same name while the hot journal is still there
shutil.copytree(d, d+'_hazard')
h=os.path.join(d+'_hazard','library.sqlite3'); os.rename(h, h+'.damaged'); open(h,'xb').close()
try:
    x=sqlite3.connect(h, isolation_level=None); print('hazard: new empty db sees tables:', x.execute("select name from sqlite_schema").fetchall()); x.close()
except Exception as e: print('hazard: error', e)
print('hazard dir after opening new db:', {n: os.stat(os.path.join(d+'_hazard',n)).st_size for n in sorted(os.listdir(d+'_hazard'))})
r=sqlite3.connect(h+'.damaged', isolation_level=None)
try: print('hazard: quarantined main file rows:', r.execute('select count(*) from t').fetchone(), r.execute('pragma integrity_check').fetchone())
except Exception as e: print('hazard: quarantined main file error:', e)
# normal recovery: reopen in place
r=sqlite3.connect(db, isolation_level=None)
print('reopen rows (expect 10000):', r.execute('select count(*), sum(b=x\'00\') from t').fetchone(), r.execute('pragma integrity_check').fetchone())
r.close(); print('after recovery:', ls())
```

Output:

```
after crash: {'library.sqlite3': 34414592, 'library.sqlite3-journal': 572648}
hazard: new empty db sees tables: []
hazard dir after opening new db: {'library.sqlite3': 0, 'library.sqlite3.damaged': 34414592}
hazard: quarantined main file rows: (10027,) ('ok',)
reopen rows (expect 10000): (10000, 0) ('ok',)
after recovery: {'library.sqlite3': 1118208}
```

**Findings.**
1. In place, recovery is correct: the hot journal is rolled back at the next open, the 10,000 committed rows remain,
   the uncommitted rows and updates are gone, and the file shrinks back.
2. **A main file separated from its hot journal exposes uncommitted data as if it were valid:** the set-aside main
   file shows 10,027 rows, 27 of them from the interrupted transaction, and `integrity_check` reports `ok`.
3. Creating a new empty database under the old name made SQLite **delete** the leftover hot journal (the database has
   zero pages, so the journal is treated as a remnant; E-5). The rollback-mode analogue of the review's H02.
4. After recovery by a connection in SQLite's default `DELETE` mode, the journal file was deleted rather than
   truncated. Journal mode is per connection in rollback modes.

Used by LIB-02, LIB-07, LIB-09, D-28, D-47 and TEST-L4/L6.

## 6. E-5: SQLite source citations

`src/pager.c` fetched from `github.com/sqlite/sqlite` (master, 7,910 lines) on 2026-09-30:

| Lines | Behaviour |
|---|---|
| 2127–2136 | `journal_mode=TRUNCATE` commit: `sqlite3OsTruncate(jfd, 0)`, then, when `fullSync`, `sqlite3OsSync(jfd)` "so the journal cannot resurrect following a power loss and cause the last transaction to roll back" (Mozilla bug 1072773). So TRUNCATE plus `synchronous=FULL` makes the commit durable |
| 5232–5245 (`hasHotJournal`) | "If the database is zero pages in size, … the journal is a remnant from a prior database with the same name … the journal file can be deleted." The journal is then deleted with `sqlite3OsDelete` |

## 7. E-6: world-model soundness of the absence rule

The probe builds random directory trees in which **each directory is either case-sensitive or case-insensitive**,
evolves them (deletions, creations, case-only and other renames, file/folder replacement, folder/link replacement,
toggling case sensitivity where Windows would allow it), observes both worlds as a v1 scan would (Ok, Partial listings
of a random prefix, Unreadable folders, links never entered), and classifies the two observations. A **Missing**
verdict is unsound if the item's namespace position in the newer *world* is occupied by an entry of the same type or
lies behind a link; **Added** symmetrically against the older world.

The filesystem fold folds ASCII letters only. Key `wide` also folds U+017F (long s) to `s`, as .NET casing does, so it
is strictly wider than the filesystem's fold. Key `exact` is the `c0c031f` definition. Rules:

- `strict` is spec §12.2 (D-38): case-fold matching only under two Listed parents and only when the name's key class
  has exactly one same-type member on **each** side, counting matched members; Missing (Added) only when the Listed
  counterpart folder has **no** same-type child with the same key, matched or not.
- `strict1` is an earlier draft of this repair: uniqueness counted among **unmatched** children only.
- `review` is the review's §10.6 text (i)+(ii)+(iii) as implemented here. It shares the Listed-parents restriction on
  case-fold matching, without which it would do worse.

Script (`absence_probe.py`):

```python
"""World-model soundness probe for the case-aware absence rule (spec section 12.2, D-38).
usage: [BIASED=1] [OPS=n] python3 absence_probe.py WORLDS KEY RULE
  KEY:  wide | fs | exact        RULE: strict (spec 12.2) | strict1 (earlier draft) | review (review 10.6)
World: each directory is case-sensitive or case-insensitive; the filesystem fold FS folds ASCII letters only.
KEY=wide also folds U+017F (long s) to 's', as .NET casing does, so it is wider than FS; KEY=exact is the
c0c031f definition. A Missing (Added) verdict is UNSOUND if, in the newer (older) world, the item's namespace
position is occupied by an entry of the same type, or lies behind a link and so cannot be known.
BIASED=1 restricts names to s, S, U+017F, t; OPS sets the maximum number of changes between the two worlds."""
import random, sys, os
NAMES = ["s","S","\u017f","t"] if os.environ.get("BIASED") else ["a","A","b","B","ab","AB","Ab","s","S","\u017f"]
FS = lambda n: n.lower()
KEYS = {"wide": lambda n: n.lower().replace("\u017f","s"), "fs": lambda n: n.lower(), "exact": lambda n: n}
K = KEYS[sys.argv[2] if len(sys.argv)>2 else "wide"]
RULE = sys.argv[3] if len(sys.argv)>3 else "strict"
GEN = KEYS["wide"]   # how the world generator picks case-only renames: independent of the key under test
class D:  # world directory
    def __init__(s, cs=False, link=False): s.cs=cs; s.link=link; s.ch={}   # name -> D or 'F'
def key(d,n): return n if d.cs else FS(n)
def free(d,n,excl=None): return all(key(d,m)!=key(d,n) for m in d.ch if m!=excl)
def rand_tree(r, depth=0):
    d=D(cs=r.random()<0.3)
    for _ in range(r.randint(0,4 if depth<3 else 0)):
        n=r.choice(NAMES)
        if not free(d,n): continue
        if depth<3 and r.random()<0.45: d.ch[n]=rand_tree(r,depth+1) if r.random()>0.1 else D(link=True)
        else: d.ch[n]='F'
    return d
def dirs(d, acc=None):
    acc = [] if acc is None else acc
    acc.append(d)
    for v in d.ch.values():
        if isinstance(v,D) and not v.link: dirs(v,acc)
    return acc
def clone(d):
    e=D(d.cs,d.link); e.ch={k:(clone(v) if isinstance(v,D) else v) for k,v in d.ch.items()}; return e
def evolve(r, w):
    w=clone(w)
    for _ in range(r.randint(1,int(os.environ.get('OPS','6')))):
        d=r.choice(dirs(w)); op=r.random()
        if op<0.2 and d.ch: del d.ch[r.choice(list(d.ch))]
        elif op<0.4:
            n=r.choice(NAMES)
            if free(d,n): d.ch[n]='F' if r.random()<0.6 else rand_tree(r,3)
        elif op<0.6 and d.ch:                                  # rename (often case-only)
            o=r.choice(list(d.ch)); n=r.choice([x for x in NAMES if GEN(x)==GEN(o)] if r.random()<0.7 else NAMES)
            if n!=o and free(d,n,excl=o): d.ch[n]=d.ch.pop(o)
        elif op<0.7 and d.ch:                                  # replace with the other type
            o=r.choice(list(d.ch)); d.ch[o]='F' if isinstance(d.ch[o],D) else rand_tree(r,3)
        elif op<0.8 and d.ch:                                  # folder <-> link
            o=r.choice(list(d.ch))
            if isinstance(d.ch[o],D): d.ch[o]=D(link=True) if not d.ch[o].link else rand_tree(r,3)
        elif op<0.9:                                           # toggle case sensitivity when legal
            if d.cs and len({FS(m) for m in d.ch})<len(d.ch): pass
            else: d.cs = not d.cs
    return w
# ---- observation: what a v1 scan would record ----
class O:  # observed folder
    def __init__(s,status): s.status=status; s.ch={}   # name -> O or 'F'
def observe(r, d, root=True):
    if d.link: return O('Link')
    st = r.choices(['Ok','Partial','Unreadable'], [0.75,0.12,0.13])[0]
    if root and st=='Unreadable' and r.random()<0.7: st='Ok'
    o=O(st)
```

An earlier run of the rule **without** the restriction of case-fold matching to pairs of Listed folders gave 4

than any filesystem fold. Its clause (i) lets a case variant that is already matched to another item fail to block the
proof, which is unsound when case sensitivity changed.

**Findings.**
1. The file change counter (header offset 24, big-endian) and the page count (offset 28) are unchanged by read
   transactions, advance with every committed write transaction, and are unchanged after a rollback. They are a
   **commit generation** read from the file's contents, not from directory-listing metadata.
2. They do **not** reveal a write transaction that was rolled back: inside the large transaction the main file grew
   from 1,118,208 to 6,668,288 bytes (cache spill), and the rollback restored it byte for byte. Only the process that
   ran the transaction knows it happened. The specification therefore uses the in-process mutation epoch as the
   authoritative detector of StorageInventory's own Library mutations and the header only as a secondary check of
   commits by any connection (spec OBS-04).
3. In `TRUNCATE` mode the journal is truncated to 0 bytes, not deleted, both at commit and at rollback.
4. A read-only connection that meets a hot journal fails with `SQLITE_READONLY_ROLLBACK` and changes no file (confirms
   the re-review's source reading R4 by measurement).
5. A new read-write connection whose first statement is `PRAGMA journal_mode=truncate` recovers a hot journal and
   **deletes** the journal file (the re-review's R3); the journal reappears as a 0-byte file at the next committed
   write transaction.

What this cannot show: Windows file-sharing behaviour of the header read, and NTFS metadata. The header read opens the
main file for reading with full sharing (spec OBS-04); the Windows confirmation is part of Q-21 and TEST-W1.

**Findings.**
1. In Unicode 16.0.0 exactly one case class mixes combining classes: {U+0345, U+0399, U+03B9, U+1FBE}. This agrees
   with the re-review's census R1 on Unicode 14.0.
2. The key of `c0c031f`/`456b233` (NFD first, then per code point case class) does not equate `α U+0345 U+0301` and
   `α U+0399 U+0301`, which a per-code-unit fold following Unicode simple case mapping equates. The corrected key
   `R(NFD(R(n)))` equates them.
3. Property: over 100,000 pairs of names that are equal under one of 2,000 random per-code-unit folds contained in the
   case classes, the old key was unequal for 147 pairs and the corrected key for **none**. This is the per-unit width
   argument of spec NAME-04 exercised on random multi-code-point names (combining marks, Greek iota forms, Hangul).
4. The table-driven NFD equals Python's NFD on every code point assigned in Unicode 14.0.
5. Canonically equivalent strings drawn from the same pool (a string and its NFC form) got equal corrected keys in
   98,893 of 98,893 cases. Soundness on verified filesystems does not depend on this (they do not normalise); it is
   recorded because the key is also used to suggest spelling-only renames.
6. Full case folding (`ß`/`ss`, `ﬁ`/`fi`) and default-ignorable characters (U+200B) are **not** equated by the key.
   A filesystem that equates such a pair is therefore not covered by the key; spec Q-14's sequence census tests these
   pairs, and a filesystem class for which any such pair collides stays `Unverified` (NAME-04).

**proof gap in the key's construction**, not an observed NTFS or exFAT defect. Real filesystems are measured by the
