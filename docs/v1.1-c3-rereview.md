## 3. Methodology and limitations

**What was done.**

1. Verified refs, ancestry, trees and the diff (sections 1 and 4).
2. Read both documents in full and every changed file. Cross-read the changed tests against the specification text (ID-01, ID-02, ID-04,
   ID-05, ID-13, TEST-I3) and the production lines each mutant touches.
3. Ran the repository's own scripts on a Linux container (Ubuntu 24.04, .NET SDK 10.0.112, PowerShell 7.6.6), in scratch clones of this repository
   at each commit (this repository was never built in or modified): the C3 mutant script against both the review tree and the repair tree, and the
   script-safety fixtures and guard mutants against the repair tree.
4. Wrote independent probes (Appendix B): 30 checks of the `-Work` and `-Out` handling (including an injected-exception run and an ordering trace),
   38 checks of the teardown, and 10 malformed manifests through the real `-Remove` entry point. Wrote an independent mutation harness (Appendix A): the nine mutants re-derived by
   hand, 27 neighbouring mutants, 7 direct-variant audit mutants, 3 scope probes, a culture matrix, and 14 guard mutants against the script
   fixtures.
5. Read the hosted Windows runs from the raw job logs through four read-only delegated agents that returned verbatim excerpts. I treated their
   reports as data, cross-checked the lines I could reach myself (the tail of the `ci.yml` job log: the integration `RESULT` line, the publish
   hash and size, the clean-target summary) and the git facts behind the flake, and compared every number with my own local reproduction. All agree.

**Limitations.**

* No Windows machine and no elevation. Windows-only behaviour (VHDX, diskpart, SMB, drive letters, ACLs, the real WPF integration suite, PowerShell 5.1)
  rests on the hosted logs. The full solution including the WPF App could not be built here (`NU1100`, the Windows Desktop reference pack is not
  resolvable under this container's package-source mapping), so the hosted build is the authority for it. `Provision-IdentityMedia.ps1` cannot
  provision here; its `-Remove` entry point was exercised through an adapted copy in which only the elevation check, the `kernel32` long-path call
  and the table of real side-effect actions were replaced. The `-Remove` block and `Invoke-MediaTeardown` are the shipped code.
* The log archive host (`results-receiver.actions.githubusercontent.com`) is refused by the session's egress policy (403). I did not route around it;
  job logs were read through the GitHub tools instead.
* The reviewer's scripts live in the scratchpad and are not part of the repository, as in the original review. Appendices A and B describe them.

## 5. C3-H01: unsafe `-Work`

**Original.** `Invoke-IdentityExperiments.ps1 -Work` created inside and then recursively deleted any caller-supplied folder, and `-Out` was overwritten silently.

**Repaired design (verified in code).**

| Requirement | Where | Verdict |
|---|---|---|
| `-Work` is a parent only; the script makes its own uniquely named child | `Resolve-WorkParent` (`IdentitySafety.ps1:85`), `New-ScratchChild` (`:94`, `SiIdentityWork_` plus eight hex digits, a marker file written with its fixed text) | yes |
| only that child is eligible for deletion | `Remove-OwnedScratch` (`:108`): direct child of the parent, name pattern, marker present with the exact text, not a reparse point | yes |
| marker validated before the recursive delete | `:116` and `:117`, then `[IO.Directory]::Delete` at `:121` | yes |
| link and reparse paths fail closed | `Test-IsReparsePoint` (`:64`), used at `:118`; any error in the checks is caught and means "left alone" | yes |
| dangerous and general roots refused | `Test-PathTooGeneral` (`:59`): a filesystem root or a path under 8 characters; a file is refused | yes |
| `-Out` validated before work starts | `Invoke-IdentityExperiments.ps1:51` (`Resolve-OutputFile`, `IdentitySafety.ps1:73`): a folder, a missing folder, or an existing file without `-Overwrite` is refused; the default name is timestamped | yes |
| cleanup on an exception | `try {` at `:71`, `finally { Remove-OwnedScratch … }` at `:459` to `:461` | yes |

**Destructive-order check.** The script's order is: dot-source the guards; `Resolve-OutputFile` (line 51); `Resolve-WorkParent` (52); the `-CheckArgumentsOnly`
branch (53); build and tool checks, the elevation test and the manifest read (58 to 69, all read-only or process-environment only);
`New-ScratchChild` (70); `try`. The report is written at line 456, inside the `try`, after everything else. There is no point at which a recursive delete,
a child creation under an unvalidated root, or an output overwrite precedes validation. A confirmation prompt is not relied on anywhere.

I proved the order with a trace rather than by reading alone: a logging line was injected as the first statement of each of the four functions in a copy, and the
script was run with hostile arguments.

| Run | Functions that ran (in order) | Scratch child created or removed? |
|---|---|---|
| `-Work /` | `Resolve-OutputFile`, `Resolve-WorkParent` | no |
| `-Out` an existing file | `Resolve-OutputFile` | no (and `-Work` was never looked at) |
| accepted arguments | `Resolve-OutputFile`, `Resolve-WorkParent`, `New-ScratchChild`, `Remove-OwnedScratch` | once each, in that order |
| full flow with an exception injected after the child exists | the same four, once each | removed by `finally`; the caller's data byte-identical; no report written |

**Independent exercise** (Appendix B, 30 checks, all PASS), covering the five cases the brief named:

1. valid generated work directory: the child is made and removed and the parent, including a decoy `.si-identity-scratch` planted in it, is byte-identical;
2. unmarked caller directory (hidden and nested content with a decoy marker planted in it; `-Work` a symlink to user data): contents retained. The repository's fixtures add a relative `.`, the default with a data-filled temp folder and read-only content (1.02, 1.03, 1.01);
3. dangerous roots (`/`, `//`, `/./`, `/tmp/../`, short paths, empty and whitespace): refused with a reason;
4. marker tamper (text plus an extra line, altered text, emptied, removed, replaced by a directory, a non-hex name suffix, a marked grandchild): all refused, payload kept;
5. link: the child replaced by a symlink to a folder that carries a valid marker is refused and the victim is intact; `-Out` as a symlink to an important file is refused.

The repository's fixtures: 28 PASS, 0 FAIL, 1 SKIP as root; 29 PASS, 0 FAIL, 0 SKIP as an unprivileged user (fixture 2.14 executes, section 11).
Hosted: 29 PASS, 0 FAIL, 1 SKIP under both Windows PowerShell 5.1 (`Desktop 5.1.26100.33438`) and PowerShell 7.6.6, including 1.13 (links).
Guard mutants S9 to S14 (the scratch-cleanup, `-Out` and `-Work` guards) are killed locally and on the hosted runner.

**Verdict: CLOSED.** One note on evidence strength: the `finally` path is proved by my injected-exception run, not by the repository's fixtures (C3R-O03).

## 6. C3-M01: `-Remove` order and ownership

**Original.** `-Remove` detached, dismounted, unmapped, unshared and deleted before it checked ownership, and never validated `-Manifest`.

**Repaired order (verified in code).** `-Remove` (`Provision-IdentityMedia.ps1:79` to `:86`) calls `Invoke-MediaTeardown` (`IdentitySafety.ps1:169`). Every side effect is an injected action
called only after all of the following have been checked, and any doubt returns a refusal (exit 2) with no action called:

| Check (before the first action) | Where |
|---|---|
| the manifest parses as JSON | `:181` to `:183` (catch means refuse) |
| it says it was written by this script: `madeBy`, `schema`, a non-empty `root` | `Test-ProvisionManifest` (`:142`), `:184` |
| an explicit `-Root` agrees with the manifest's root | `:195` |
| the root is not a filesystem root and is not too general | `:203` |
| the root is an existing folder holding the marker with its exact text | `:204` to `:208` |
| the root is not a link | `:209` to `:210` |

Then, and only then, each action is still checked against the manifest: a mapping is unmapped only while it still points at the manifest's share (`:216` to `:225`); a share
is removed only while it serves a folder inside the volume the manifest names for it (`:230` to `:236`); only the five image names the script gives its disks, directly
inside the marked root, are detached or dismounted (`:152`, `:239` to `:243`); the folder is deleted after its marker is re-read (`:246` to `:248`); the manifest is deleted only if it passed
validation (`:250`). The diskpart script file is written only by the detach action, inside the marked root. Provisioning refuses a folder that cannot be listed (`:129` to `:137`).

**Independent replay of bad cases** (Appendix B). Each case asserts a refusal, zero actions of any kind (stricter than "no state-changing call": not even a look-up), nothing on disk changed:

| Case | Result |
|---|---|
| unrelated JSON as `-Manifest` (appsettings-like, a JSON array, a scalar, `null`, an empty file, binary) | refused, 0 calls |
| manifest of another tool; wrong `schema` | refused, 0 calls |
| valid-looking manifest whose root is an unmarked folder with mounted-looking images | refused, 0 calls |
| manifest root is the parent of a marked folder; explicit `-Root` is the root's parent or a subfolder | refused, 0 calls |
| unmarked root; wrong marker text; the marker is a directory | refused, 0 calls |
| marked root reached through a symlink | refused, 0 calls |
| a `..` that leaves the marked folder for an unmarked one | refused, 0 calls |
| eleven odd root strings (NUL, `<>\|"?*`, 5,000 characters, `\\?\C:\x`, `NUL`, `CON`, whitespace, `.`, `..`, `/`, `//server/share`) | refused, 0 calls |
| through the real `-Remove` entry point (adapted copy): an unmarked `-Root`, foreign JSON, mismatched marked roots, and ten malformed manifest roots | exit 2, `REFUSED`, 0 actions, files intact |
| positive control: a genuine marked root | torn down in the safe order; only the manifest's own mapping and share, only the five image names; a re-mapped letter, a share serving another volume, `user.vhdx`, `Installer.iso` and `sub\ntfsA.vhdx` untouched |

The malformed-input cases matter because `-Remove` runs under `$ErrorActionPreference = 'Continue'` (line 80) with no enclosing `try`: a .NET exception inside a check is then skipped,
not fatal. I tested that context directly and every case still refuses with no action.

**Real media.** Hosted fixture 2.16 attached a real VHDX named `ntfsA.vhdx` in an unmarked folder, ran the real script's `-Remove` against that folder and against an unrelated JSON file, and
required exit 2, the disk still attached and both files present: PASS under both PowerShell hosts. In the real-media job, after real provisioning of five VHDX volumes, a UDF image and two SMB shares,
`-Remove -Manifest appsettings.json` and `-Remove -Root %RUNNER_TEMP%` exited 2 with `REFUSED` and the volume list was identical before and after (`C NTFS;D NTFS;E UDF;M NTFS;N NTFS;O FAT32;P exFAT;Q ReFS`).

**Verdict: CLOSED.** The teardown link check, the recursive-image guard and the marker re-read have no fixture of their own (C3R-O03); my probes show the shipped code enforces them.

**What the new tests pin, point by point.**

* **T1, T2 (Moderate clones).** `A_Moderate_clone_mounted_beside_its_original_asks` proves that ID-05 applies to Moderate: a mounted volume with the same filesystem, 32-bit serial, label and capacity makes the matcher ask (`CoMountedClones`) and
  never attach silently, while the capture's own entry (the same mount point) is not a clone. `A_mounted_volume_is_a_Moderate_clone_only_when_every_corroborating_item_matches` varies each item. The filesystem test covers Moderate (FAT32 against exFAT)
  and Strong (ReFS against NTFS), the case-insensitive name comparison, and an unknown filesystem.
* **T3 (exact root, culture).** The pairs are non-ASCII and linguistically equal but different code units: a soft hyphen, precomposed against decomposed `é`, a Hangul syllable against its jamo; lone surrogates; an all-equal hostile key that may only make the matcher ask.
  I ran the unmutated repair suite under eight cultures (default, `tr-TR`, `az-AZ`, `lt-LT`, `de-DE`, `ja-JP`, `ko-KR`, `sv-SE`): 107/0/0 in each. I ran all nine mutants under `tr-TR`: 9 of 9 killed. Five culture and case-folding formulations of the root comparison
  (`InvariantCulture`, `CurrentCulture`, `CurrentCultureIgnoreCase`, `InvariantCultureIgnoreCase`, `OrdinalIgnoreCase`) and a culture-sensitive suggestion comparison are all killed, in both the default and the `tr-TR` runs. The tests do not depend on ASCII.
* **T4 (UserAsserted creation).** The test builds a real ambiguity (two volume rows with one serial), answers `SameVolume` for a volume with no source at that root, and asserts that the created source's basis is `UserAsserted`. It is the creation path, not an attach to an existing source.
  The second test follows the answer into the case-variant question and asserts the basis of the suggested alternative.
* **Later matching does not rewrite the fixed creation basis (brief item 12).** In production nothing can: `SourceCandidate` is an immutable record, `InMemoryIdentityStore.Apply` only refreshes a volume's label and capacity on an attach, and basis is written only by `AddLocalSource` at creation.
  The regression net pins it generally (my mutant "any attach rewrites the stored basis to the decision's basis" is killed by an existing test) but not for one direction, a source created on the user's word that is later attached on evidence (C3R-O04, mutant X4d).
* **T5 (zero serial).** Matches the frozen rule: ID-13 makes Save unavailable only when an item "cannot be obtained"; ID-01 makes a serial of 0 PathOnly. The test asserts that a zero 32-bit and a zero 64-bit serial are obtained items (`Sufficient`, `CanSave`), cost the source its confidence (PathOnly, basis Location),
  and that the capture is matched, not refused. The distinction from unavailable and failed is pinned by earlier tests (my mutant "a `CallFailed` serial counts as obtained" is killed). "Not provided" is not pinned separately (C3R-O04, mutant X5b).
* **T6, T7 (labels).** Exact label; a case-only difference; an unknown label on either side; two unknown labels; an empty label equal to an empty label and not equal to an unknown one. The ignorable-character form of T3 does not exist for labels (C3R-O04, mutant X6).
* **T8 (underivable canonical path).** Seven shapes (a volume GUID path, `\\.\x`, `\\?\x`, `\\.\C:\Media`, `\\server`, a relative path, empty) for local and network kinds. The mutant's failure message shows the canonical path was available and non-null, so the test exercises "available but not representable", not "missing"; each case must be `Sufficient == false` with the single missing item `CanonicalPath` and `SaveUnavailable` from the matcher.
* **T10c (device namespace).** `TryDerive` of every `\\?\` and `\\.\` spelling is refused, and `\\.x\share` and `\\a.b\share` (servers that merely start with or contain a dot) are accepted. The production code is unchanged, and `GetFinalDirectoryPath` strips `\\?\` and `\\?\UNC\` before the canonical path reaches `TryDerive` (`NativeMethods.cs:215`), so the test pins existing fail-closed behaviour and does not broaden path rejection.

**Neighbouring mutants (my own, 27).** 23 killed, 4 survived, identically under the default culture and `tr-TR`. The survivors are listed in C3R-O04; none is one of the nine and none is a production defect.

**Verdict: CLOSED.**

## 8. C3-M03: the A-08 reflection bypass

**Original.** `Enum.ToObject(m.GetParameters()[1].ParameterType, 5)` through `MethodInfo.Invoke` asked `GetFileInformationByHandleEx` for another class and passed every audit rule, and the comments said the text rule closed every spelling.

**Reproduced.** On the review tree the audit passes with the original mutant C7 (16 of 16 tests), and also with C7b (whitespace inside every token) and C7c (a call written so that no text pattern matches). On the repair tree all three are killed:

| Mutant | Review tree | Repair tree | Rule that fires (message) |
|---|---|---|---|
| C7 (the review's) | survives | killed | text rule: "reflection in src: …/NativeMethods.cs" |
| C7b (whitespace) | survives | killed | text rule (whitespace tolerant) |
| C7c (namespace imported by an XML character reference, no `typeof`, no `GetMethod`, no `Enum.ToObject`) | survives | killed | compiled rule only: "StorageInventory.Core refers to reflective members: MemberInfo.get_DeclaringType, MethodBase.Invoke, TypeInfo.get_DeclaredMethods, …" |

The existing variants stay caught.
