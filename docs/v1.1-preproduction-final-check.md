## 2. Focused scope and method

**Scope.** G0-B01; RR-01 to RR-10 as the re-review's §15 defines them; what `121358c` changed; regressions those
changes caused. Accepted architecture (SQLite, rollback `TRUNCATE`, `%LOCALAPPDATA%` Library, out-of-source spool,
post-observation atomic import, exact names, strict Missing/Unknown, single writer, internal observer API, full
snapshots, the C1 to C13 structure) was not reopened. One pre-existing defect is reported because the corrections
leave it in place and it violates the acceptance criterion on deletion claims (G0F-H01).

**Independence.** The corrections of `121358c` were written in the same working session as this check. To keep
the check independent, three reviewers with no part in the corrections read the specification separately, each
attacking one area: the interlock, locking and detector; the comparison key and identity; and the spool, SQLite,
packages, mechanics and regressions. Every finding below was then re-verified against the specification text, v1
source, SQLite source or a probe before being kept. Claims the reviewers made that did not survive that check were
dropped.

**Evidence classes.** [SPEC] the specification at `121358c` (line numbers refer to it); [SRC] v1 source at
`c63c6d6`; [SQL] SQLite `src/pager.c` and `src/os_win.c` (master, fetched for this check); [PROBE] a disposable probe
run for this check (Python 3.11, SQLite 3.45.1, the Unicode 16.0.0 files of E-9), kept outside the repository; [INF]
reasoning from these.

**Probes run for this check.**

| Probe | Result |
|---|---|
| K against its own canonical decomposition, over every BMP code point assigned in Unicode 14 | **34 code points** have `K(c) ≠ K(NFD(c))`, for example U+03AF ί gives `0345 0301` but `ι U+0301` gives `0301 0345`; also U+0130 İ against `I U+0307`. ## 3. G0-B01 closure

**Classification: CLOSED.** No specified path lets an observation window and a Library mutation overlap within
one process. Three precision gaps remain in how the rule is enforced; they are medium (G0F-M02, G0F-M03) and do not
re-open an overlap under the normative rules.

**Design checked.** D-51 and OBS-07 to OBS-13 [SPEC 1551-1567]: one state machine (Idle, Mutating, Observing,
Faulted); every mutation needs a mutation lease (OBS-08, exhaustive, including SQLite's hot-journal rollback at open,
creation, set-aside and future migration, backup and compaction as new lease kinds); a window opens only from Idle or
by a capture's own hand-off; grants are non-blocking tries under one monitor (OBS-09); requests that arrive in an
incompatible state are refused and start nothing (OBS-11, O28, O29); the writer connection exists only inside a
mutation lease (OBS-12). It is a service invariant in `LibrarySession` with lease-typed APIs (A-25), not a button
state; UI-13 only derives availability from it.

**Original sequence re-run, both directions.**

| Sequence | Result under the corrected spec |
|---|---|
| Scan A finishes; its save (V, T-IMPORT, T-OUTCOME) starts; user asks for scan B of `C:\` (Save on or off) | Scan A's window hands over to its Save lease atomically at P4 (OBS-10); the interlock is never Idle in between, so B's request is refused (O28) and creates no report file and no attempt. B becomes possible only when the Save lease ends after the commit or rollback, the outcome write, the writer close and the spool close |
| Same with a snapshot deletion running | Delete lease held; B refused. Conversely, Delete during B's window is refused (O29) |
| Same with open-time recovery (hot-journal rollback, T-RECOVER) | Open lease held from App start; Scan unavailable ("Opening the Library…"). See G0F-M01 for the start-up ordering gap |
| Same with set-aside | SetAside lease held; Scan unavailable; set-aside during a window is refused |
| Library creation on the first save | Inside the capture's Prepare lease, before P2, handed over atomically to Observing |
| Migration, backup, compaction (later releases) | OBS-08 requires each to be a new lease kind; A-25 makes a lease-less writer unreachable |
| T0 failure; Stop scan; Stop saving; close during save | Prepare hands over to Observing and the window ends at Idle; Stop scan returns Cancelled then the hand-off records the outcome; Stop saving rolls back within PERF-16 and the lease ends normally; closing during save asks "Stop saving and close / Keep saving" and the lease always ends in `finally` |
| Class C failure during a mutation | OBS-13 requires Faulted (no further lease, scans unavailable). The entry mechanism is under-specified: G0F-M02 |

**Cross-process (RR-02).** Another StorageInventory process that cannot take `library.lock` never opens a
connection and never creates, renames or deletes a member (CONC-02, LIB-07 step 3, LIB-08 step 2, LIB-13 step 2).
Its scans can observe the owner's mutations; that process never publishes, so no snapshot is affected (L-OBS1). An
external, non-StorageInventory writer belongs to the tamper model: committed changes during a window advance the
commit generation and make the capture NotEligible; rolled-back external writes are not detected, as OBS-04 states.
A system-wide observation coordinator is not needed for correctness. One disclosure gap: a second instance whose
open found no Library directory shows "Not created" rather than In use, so its scans run without the L-OBS1 notice
(G0F-O06).

## 5. Comparison-key verdict

**What holds.** Stored names stay exact UTF-16 (NAME-01, NAME-02); `K` is a separate, never-stored candidate key
except `network_root_key` (NAME-03). The per-unit condition of NAME-04 implies width for any per-code-unit fold that
satisfies it, surrogates included: such a fold maps surrogates to themselves at the same positions, so two
fold-equal names are both well-formed or both ill-formed and equal after `R`. Every class is `Unverified` until Q-14
passes, so Missing cannot rest on an unverified key. The rule was walked through:

| Case | Result | Sound? |
|---|---|---|
| Case-only rename, both parents Listed, singleton classes | Unchanged {NameSpelling} | Yes |
| NFC in O, NFD in N (NTFS, which does not normalise) | Case-fold match when `K` is equal; for the 34 iota-family code points `K` differs and the NFC item is Missing. Correct on NTFS, which treats the two spellings as different names | Yes on `Verified` per-unit classes |
| U+0345 reordering pair | Equal `K`; T49 Unknown under an Unreadable folder | Yes |
| `ß`/`ss`, `ﬁ`/`fi`, U+200B | Not equated; a class whose census equates them stays `Unverified` (Q-14 part 3) | Yes, gated |
| Two names in one key class (T23, T40) | NameVariantPresent | Yes |
| Partially listed parent (T42) | No case-fold match; Unknown | Yes, but §12.8 computes `K` only when both folders are Listed (G0F-O04) |
| Per-directory case sensitivity and changes to it (T41) | Exact matching is contained in any per-unit fold; rule needs no flag | Yes |
| Characters outside Unicode 16.0.0 | `Dom` fails, Unknown (T52) | Yes |
| Network share (`Unverified`) | Missing only from an exactly aligned, Listed folder with no child of that type | **No when the server hides entries** (G0F-H01) |

**Verdict.** The key's construction and width are closed; uncertainty in **name matching** can no longer create
Missing on correctly classified sources. Two defects in the new tiering remain (G0F-M04, G0F-M05), and the network
proof rests on listing completeness, which access-based enumeration breaks (G0F-H01). The product decision that
network deletions may appear as Unknown is respected and is the natural fix for G0F-H01. E-9 finding 5 ("98,893 of
98,893" canonical equivalents equal) is a sampling artefact and the capability table's "`K` also folds
normalisation" [SPEC 1010] is overstated (G0F-O02); neither affects soundness on `Verified` per-unit classes.

## 6. Identity verdict

**Closed.** E1 and E2 are read through a handle opened on the enumerated path (v1's `RootFullPath`,
`InventoryScanner.cs:50`) and held; E3 is a fresh open of the same path; the canonical path is only an identity item
read from a handle, never the thing re-opened. This is consistent in §7.2, ID-10, ID-13, §10.1, §10.2, D-42, TEST-I5
and the C3 text. A drive letter, SUBST or mapped letter re-pointed and still re-pointed at P4 changes E3; a replaced
medium invalidates the held handle (E2 fails; Q-19 confirms on media); a renamed or deleted source folder changes E2
or makes E3 fail; a source that cannot supply the ID-13 items is never saved (O24). A letter re-pointed away and back
within one scan remains undetectable by start and end evidence and is disclosed as L-ID2; the same is true of the
source folder itself replaced and restored during the scan, which L-ID2 does not yet mention (G0F-O05).

## 7. Library detector and locking verdict

**Detector (RR-05): closed.** No directory-listing metadata is used as proof anywhere. The authoritative signal is
the interlock's mutation epoch; the secondary signal is the header file change counter (offset 24) and page count
(offset 28), which E-8 shows unchanged by reads, advanced by every commit and restored by a rollback. That
interpretation is right for rollback `TRUNCATE` mode with `NORMAL` locking. A capture is NotEligible when either
changes, or when the interlock left the capture's Observing state. Not detected, as stated: a rolled-back external
write (tamper model). Two precision gaps are observations (G0F-O07): a failed header read must make the capture
NotEligible rather than read as "absent", and M2 must be recorded before the epoch increment of the P4 Save grant.

**Locking (RR-07): partially closed.** Lock-before-inspection now holds for concurrent races: two processes racing
to create end with one lock holder and one In use, and set-aside requires the lock and a lease. The residual is
sequential (G0F-M01): a process whose start-up open found no Library directory keeps a stale "Not created" state
without the lock; after another process creates a Library and exits or crashes, the stale process's first save takes
the now-free lock and then LIB-07 classifies the valid Library as Leftover files (hot journal) or refuses the existing
main file, instead of opening it.

## 8. Spool integrity and low-space verdict

**Integrity (RR-06): closed in substance.** The physical byte sequence is defined and append-only (SPOOL-07,
SPOOL-20); the digest covers exactly bytes `[0, L − 32)` in write order and is written last (SPOOL-12); V reads the
whole file sequentially before any record is used, rebuilds and compares the run index, and checks counts, offsets
and totals (SPOOL-23); key-ordered reads happen only afterwards and never feed the digest (IMP-05 (a)). Changed byte,
truncation, appended bytes, a run split, reordered run-index entries and a wrong digest are detected and named in
TEST-SP7 (C1) and TEST-SP4 (C5). C1 can build the codec without inventing an integrity protocol. Two corrections
remain: TEST-SP7 and §22.3 require V to reject two swapped records of the **same** folder with a recomputed digest,
which format 1 cannot detect (G0F-M07); and C1 must still freeze ordinary layout details, including how trailer
record counts map to `ScanTotals`, since error records include the informational reparse rows (G0F-O03).

**Low space (RR-08): partially closed.** Automatic deletion stays restricted to the spool's own delete-on-close
handle (SPOOL-11, SPOOL-18, INV-22, A-02, RX-02); the source is untouched; reports keep v1 validity; the snapshot
becomes NotEligible with a clear message. The reserve does not yet deliver its purpose (G0F-M06): no check happens
before the spool reaches 16 MiB, and the reserve of three times the spool's size is below what v1 still writes after
the last check in sorted mode (about 3.2 to 3.3 times, from the measured Files CSV, plus the Folders report). The
"after the last finalised folder" check is implementable: the root is finalised first and its total subfolder count
gives the last index (`FolderAggregator.cs:73`); the specification should say so.

## 9. SQLite, package and native verdict; regressions; mechanics

**SQLite journal (RR-10, G0-O02): closed with one wrong detail.** The model no longer assumes WAL, a permanently
present journal, or that SQLite never deletes it: §6.3 lists the hot-journal recovery deletion at open (inside the
Open lease) and the zero-page remnant case; read-only connections cannot delete (`winLock` refuses `RESERVED`). The
wrong detail: LIB-07 step 4 [SPEC 691] and TEST-L8 [SPEC 2508] say SQLite deletes a **0-byte** journal beside a
zero-page main file; SQLite treats a zero-length journal as absent and never deletes it (G0F-M07). Only a non-empty
journal beside a zero-page main file is deleted, and LIB-07 refuses creation in that state, so the case is not
reached in normal flows.

**Packages and native loading (RR-09): closed.** RX-03 and RX-04 document the widening; TEST-R2 and BLD-10 check the
module actually loaded (path and SHA-256) and both planted-file negatives (native `e_sqlite3.dll`, managed
`SQLitePCLRaw.batteries_v2.dll`); Q-11 and Q-22 are C4 stop conditions. The model verifies runtime loading in the
published app rather than assuming the extraction location.

**Regressions: none found.** Source access stays metadata-only and read-only; StorageInventory does not mutate the
observed tree; v1 reports are unchanged with and without a capture; finished incomplete scans keep their completeness
evidence (LIFE-09); cancelled and failed scans never publish (LIFE-08, LIFE-10); SQLite is used only before and after
observation; Library writes stay narrow and audited (LIB-02, A-01 to A-26); the observer, fan-out and spool stay
internal (SINK-09, A-13); full snapshots remain the model; no content reading, hashing, telemetry, cloud or account
behaviour appears.

**Mechanics: pass.** Re-counted independently: 75 test IDs defined in §18.1 and none undefined; 51 decisions (D-01
to D-51), 22 questions, T1 to T53, O1 to O30, all resolving; 24 internal links, none broken; every normative ID is in
§18.2 except family, deferred (LIB-11, SREQ-04 to SREQ-10) and retired (PERF-09) ones; superseded wording appears only
in §22.1, §22.2 and the stale-term table. Measured and projected figures are labelled, apart from E-9 finding 5
(G0F-O02).
