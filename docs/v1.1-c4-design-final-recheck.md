## 3. C4DRR-M01: the workload class function

### 3.1 Closure worksheet

| Original defect (review §5.5) | Required correction (review §16) | Final repair claims | Verified here? |
|---|---|---|---|
| Nested upper bounds with "the hardest of them": the representative class was empty, and re-scans of non-representative sources or with δ or α above 5% had no class | Classes as a total function of the parameters; a class for every R(n, d, m; ρ, δ, α); D-53 records how the re-scan of a high-novelty source is bounded; a boundary table that gives the matrix labels | Disjoint bands per parameter; an ordered function (named informational families, then named adversarial families, then the hardest band); re-scans carry their source's `d` band; tie-break removed; a stress cell R(2M, 60%, data; 1%, 0.5%, 0.5%); D-53 restated; `workload_class.py` 59 checks | **Yes** (§3.2 to §3.6) |

### 3.2 The rule as written (read in §15.4)

| Parameter | Representative | Stress | Worst-case |
|---|---|---|---|
| `d`, model system | 0 < d ≤ 25% | 25% < d ≤ 60% | 60% < d ≤ 100% |
| `d`, model data | none | 0 < d ≤ 60% | 60% < d ≤ 100% |
| `ρ` | 0 ≤ ρ ≤ 1% | 1% < ρ ≤ 10% | 10% < ρ ≤ 100% |
| `δ` | 0 ≤ δ ≤ 0.5% | 0.5% < δ ≤ 5% | 5% < δ ≤ 100% |
| `α` | 0 ≤ α ≤ 0.5% | 0.5% < α ≤ 5% | 5% < α ≤ 100% |

The domain is `d` in (0, 100%], each churn ratio in [0, 100%], with ρ + δ ≤ 100%. The class is decided in this order:

1. **Informational**: N1 append at any size, or any cell of more than 2M files.
2. **Worst-case**: N2 or N3 into an existing source, or a re-scan of an N2 source.
3. **Otherwise** the hardest band among the cell's parameters:
   - a first save has its `d` on its model's row;
   - a re-scan has its source's `d` and its ρ, δ and α.

Each row's bands are adjacent, half-open intervals that start at the range's lower end and end at its upper end. So every
parameter value lies in exactly one band, and the maximum over a cell's parameters is a single value.

**Properties:**

| Property | Holds? |
|---|---|
| Total over the generator domain | yes |
| Deterministic | yes |
| Mutually exclusive in the final class | yes |
| Uses the cell's input parameters only | yes ("Every cell is defined by numeric input parameters fixed before it runs … never from its result") |
| Independent of any measured result | yes (realised statistics are recorded, never classified; C4DRR-O10's wording is in place) |

### 3.6 D-53 (read exactly)

D-53 now states each of the following.

| D-53 statement | Matches the function? |
|---|---|
| The class follows "by a **total function**": disjoint bands, the hardest band among a cell's parameters, after the named families | yes |
| PERF-01 is judged on first saves at ≤ 25% distinct on the system model, and on re-scans of such sources with ρ ≤ 1%, δ ≤ 0.5% and α ≤ 0.5% | yes |
| High-novelty sources are stress sources: "their first saves **and their routine re-scans** are stress cells, because the dictionary a re-scan imports into is part of its workload" | yes |
| "A re-scan's class follows the parameters of the dictionary it imports into, not a label inherited from the first save" | yes |
| Sources above 60% distinct, churn beyond the stress bands and adversarial distributions are worst-case | yes |
| The nested-bound rule is listed under "Rejected" (C4DRR-M01) | yes |

**The re-scan decision is deliberate, not inherited.** The text gives a reason: the source's name range is looked up and extended
by every re-scan. §15.4 adds a separate "Re-scans of high-novelty sources" bullet with a sizing argument: about 30 MiB of name
index for a representative 2M source against the 64 MiB cache, and about 3.5 times as many pages for a 60% data-model source
(inferred). The decision is backed by a matrix cell and by `workload_class.py`.

Whether this is the right product decision is not reopened. It is coherent and complete: every re-scan has a class and a budget,
and PERF-01 is not extended to high-novelty sources.

**One wording looseness (C4DRRR-O01).** D-53's parenthesis "(above 25% and up to 60% distinct names, or the data name model)" could
be read alone as making every data-model source stress. Two things settle it: the next sentence ("Sources above 60% distinct … are
worst-case cells") and §15.4's band table.

**One seam at the named families (C4DRRR-O01).** N2 or N3 into a *new* source, which was a worst-case cell in the D-52 design
review, and a re-scan of an N1 or N3 source are neither generator cells nor named families. With the catch-all removed, the text
gives them no class. `workload_class.py` classifies any N2 or N3 cell as Worst-case whatever its target, and it raises an error on
an unlisted family. None of these cells is in the matrix, and a cell outside the matrix gates nothing. Every generator parameter
combination is classified. This is an observation, not an open M01.

### 4.2 Outcomes and exit codes (from source: `journal_ranges.py`)

- **Starting state.** `check()` starts at `INVALID`.
- **INVALID, by every other path.**
  - Any reason recorded during validation leaves it INVALID.
  - `Invalid`, `OSError` and `sqlite3.Error` are caught as INVALID.
  - A usage error exits 2 through the parser's `error` override.
  - Any other exception is caught at the top level and exits 2.
- **PASS and FAIL.** They are reached only when the reason list is empty:
  - PASS when there is no REMOTE page and no level over the SHARED cap;
  - FAIL otherwise.
- **Exit codes.** `EXIT = {PASS: 0, FAIL: 1, INVALID: 2}`.
- **The one exit 0 that is not a verdict** is `--help`, which prints usage. A port should read the verdict, not only the exit code
  (C4DRRR-O02).

### 4.7 Wrong-copy binding

The brief asks that a journal paired with a different pre-import copy be INVALID through an authoritative binding, not because
the stored fixture happens to differ.

**What the fixture shows (measured here).** The smoke copies of F and R are both 28,856,320 B with the **same change counter
(8)** and an **identical page 1**. They differ in **one page only, page 8**: the root (and only page) of `scan_attempt`, which holds
the attempt rows, the run's own T0 attempt among them (inferred: that row is the difference). R's import journals page 8. So self-test case 23 ("another run's database") is INVALID through that one page, an
incidental property of the harness. Page 1 does not catch it.

**What each binding covers:**

| Binding | What it binds | Covers a separately built Library with the same commit count? |
|---|---|---|
| Page 1 journalled and equal | The copy's commit state within one Library lineage (change counter, page count, free list). Case 24, the same Library one commit later, is INVALID through it | **No** |
| Every journalled image equal to the copy | The copy's journalled pages | **No**: it misses a copy that differs only in unjournalled pages (§4.6: PASS without a hash) |
| **The SHA-256 recorded when the copy was taken** | The whole copy, byte for byte | **Yes** (§4.6: INVALID) |

The hash is the authoritative binding. The authority makes it normative:

- §15.4's Binding bullet (the record holds it, and the checker takes it from the record);
- the INVALID list ("or its SHA-256 differs from the record");
- TEST-P1 ("the copy's SHA-256 from the run's record");
- §15.4's per-run record list;
- D-R4 (the run record carries "the copy's length and SHA-256").

Taken together with "valid only when the checker validates its evidence completely", a record without the hash cannot give a
valid attribution. **The authority's gate is therefore safe.**

The reference tooling is looser than the authority, in three ways:

- `--expect-copy-sha256` is optional, while `--expect-journal-bytes` is required;
- `journal_ranges_rerun.py` computes the hash from the copy it checks, which proves nothing about binding;
- the self-test has no case for a missing hash, and no wrong-copy case that the fixture cannot help.

The final repair document's claim that "a wrong pre-import copy cannot PASS" (§13) holds only when the hash is given. A literal port
of the reference's interface could drop the gate the specification sets. **C4DRRR-O02** asks the C4 port to make the hash mandatory
and to add the two cases. That is guidance for implementation work the authority already requires, not an open M02.

### 4.8 Target binding: an accepted limitation

**Measured here:** valid evidence checked against a wrong but existing target fails unless that target's range borders the true
target's insertion point:

- F checked as source 1: FAIL;
- R checked as source 2: FAIL;
- F checked as source 2, which borders the new source's right edge: PASS.

The checker cannot know the run's target, so the remedy is binding. The authority binds the target to the run's record, written by
the harness and read by the checker, "never from the analyst" (§15.4, TEST-P1). D-R4 as supplemented requires the record to carry
it.

The design repair's reference harness records only `TargetSource` = `existing` or `new`, not the id; its port adds the id. The
binding is explicit and unambiguous. **Recorded as an accepted limitation.** C4DRRR-O02 suggests that the port read the record

### 5.4 The definition of `U` (read in §15.4)

- **Definition.** "Other load `U` = whole machine − own, per collection, in percent of the machine. `U` alone decides validity."
- **Collections.** A fixed 500 ms schedule, 120 collections a minute, with each value covering the interval since the previous one,
  so the collections tile the window. The committed idle sessions hold 120 collections in 60.0 s; the old 118 is gone.
- **Negative and noisy samples.** The authority does not say how a negative per-collection `U` is treated. One can arise when the
  job's tick-granular CPU accounting and the idle-based machine counter straddle an interval edge differently. The reference keeps
  such values unclamped, which leaves the mean unbiased: the per-collection errors telescope over a window. Clamping or dropping
  them would bias `U` upwards, which is conservative. **No committed collection has a negative `U`** (minimum 23.99% on this loaded
  machine), so the case is untested. Stating the treatment is C4DRRR-O03.

### 5.5 The quiet check and run validity (read in §15.4)

**Quiet check:**

- **Condition:** no benchmark operation running, only the probe, whose own time is subtracted.
- **Window:** 60 s, 120 collections.
- **Thresholds:** `U` mean ≤ 5% and 95th percentile ≤ 15%.
- **When:** before the session (a failure refuses the session and is recorded) and after every round (a failure invalidates the
  round; its runs are kept and marked, and receive replacements).

**Run validity:**

- **Thresholds:** `U` mean ≤ 10% and 95th percentile ≤ 25%.
- **Window:** "over the collections of its measured operation". This is the operation itself, not a check before and after it.
  `load_harness.py` takes the collections wholly inside `StartedUtc` to `StartedUtc + ImportSeconds`, and an operation with none is
  INVALID. The authority does not say how a collection that straddles the operation's edge is treated (C4DRRR-O03).
- **The benchmark's own load:** "The benchmark's own processes never count against it, however busy they are". They are
  subtracted, so a CPU-bound benchmark cannot invalidate itself.
- **Induced work** (Defender scanning the run's files, the System process's cache writes, DPC and interrupt time) stays inside `U`
  conservatively, within the 5-point gap between the two thresholds. A scan the run did not cause counts like any other load
  (C4DRR-O07).

The machine being loaded during development is not a design failure. The rules refuse it, as they must.
