# StorageInventory v1.1 C4 design final repair: the three findings of the design repair review

The bounded correction that the focused review of the C4 design repair (`docs/v1.1-c4-design-repair-review.md`, verdict
`C4 DESIGN REPAIR REQUIRES REVISION`) requires. It addresses exactly that review's three Medium findings, C4DRR-M01 to
C4DRR-M03, in the authoritative sections of `docs/v1.1-preproduction-spec.md` and in the reference tools under
`docs/evidence/c4-design-review/`, and corrects those of the review's 13 observations that are wording errors, contradictions or
safe tooling fixes.

It is **not** the C4 implementation repair. No file under `src/`, `tests/` or `.github/` changes, nor any build or project file.
The C4 review's findings C4-H01 and C4-M01 to C4-M17 stay open exactly as stated, C5 does not start, and D-52's architecture is
not reopened.

Units: **MiB = 2^20 bytes, MB = 10^6 bytes**. Labels:

- **measured**: run here; the raw data is in `docs/evidence/c4-design-review/final-repair/`;
- **from source**: read in SQLite's or StorageInventory's code;
- **defined**: a value the specification sets;
- **inferred**: argued, not measured.

## 4. C4DRR-M01: the workload class function

### 4.1 The defect (review §5.5)

The repaired class table had rows of nested upper bounds: representative `d` ≤ 25%; stress `d` ≤ 60%, "as representative, but ρ
≤ 10%, δ ≤ 5%, α ≤ 5%"; worst-case `d` > 60%, ρ > 10%. Its tie-break was "a cell whose parameters fit several rows takes the
hardest of them". Read literally:

- F(·, 25%, system) and R(·; 1%, 0.5%, 0.5%) fit the representative and the stress rows, so both were stress, and PERF-01 applied
  to no cell;
- the stress re-scan row inherited "the dictionary of a representative first save", so R(2M, 60%, data; 1%) fitted no row; nor
  did a re-scan with δ or α above 5%; both fell to "Informational: every cell outside the matrix".

### 4.2 The correction (§15.4)

**Bands.** Each parameter of a generator cell lies in exactly one band of its row:

| Parameter of the cell | Representative band | Stress band | Worst-case band |
|---|---|---|---|
| `d`, name model **system** | 0 < d ≤ 25% | 25% < d ≤ 60% | 60% < d ≤ 100% |
| `d`, name model **data** | none | 0 < d ≤ 60% | 60% < d ≤ 100% |
| `ρ` | 0 ≤ ρ ≤ 1% | 1% < ρ ≤ 10% | 10% < ρ ≤ 100% |
| `δ` | 0 ≤ δ ≤ 0.5% | 0.5% < δ ≤ 5% | 5% < δ ≤ 100% |
| `α` | 0 ≤ α ≤ 0.5% | 0.5% < α ≤ 5% | 5% < α ≤ 100% |

The domain is `d` in (0, 100%], each churn ratio in [0, 100%], with ρ + δ ≤ 100%.

**The function**, in this order:

1. **Informational**: a named informational family (N1 append at any size; any cell above 2M files). No budget is judged on it.
2. **Worst-case**: a named adversarial family (N2 or N3 into an existing source; a re-scan of an N2 source).
3. Otherwise, the **hardest band among the cell's parameters** (representative < stress < worst-case):
   - a first save F(n, d, m) has one parameter, its `d` on model m's row;
   - a re-scan R(n, d, m; ρ, δ, α) has four: its source's `d` on m's row, and ρ, δ and α.

**Mathematical statement.** Let `b(p)` be the band of parameter `p`, ordered R < S < W. For a generator cell with parameter set
`P`, class = max over `p` in `P` of `b(p)`. Because each row's bands partition its range, `b` is a function, so class is a
function: it is defined for every valid cell and has one value.

**Proof that the representative cells stay representative.** F(1M or 2M, 25%, system) has `P` = {d = 25%, system}, and 25% is in
the system row's representative band (0, 25%]; so max = R. R(1M or 2M, 25%, system; 1%, 0.5%, 0.5%) has d = 25% in (0, 25%], ρ =
1% in [0, 1%], δ = 0.5% in [0, 0.5%] and α = 0.5% in [0, 0.5%]: every band is R, so max = R. The script checks the same
mechanically.

**The tie-break is gone.** "Hardest" now ranges over one band per parameter, never over overlapping rows; the phrase "the hardest of
them" no longer occurs in the specification (checked by `spec_check.py`).

### 4.3 Why a re-scan's class includes its source's band

The review's option was: classify the routine re-scan of a high-novelty source as stress (with a cell), or state that it is bounded
by the stop thresholds only. This repair takes the first, because it is what D-53 already said ("high-novelty real sources … are
stress cells, bounded by PERF-14's engine target and the 5 s Stop budget") and because the source's dictionary is part of a
re-scan's workload:

- every file name of the re-scan is looked up in the source's name range, and its new names land in that range's leaves;
- a representative 2M source holds about 520,000 names, about half of the 15,232 name-index pages measured for L2's two sources
  (from the evidence: `repair-structure.jsonl`), so about 30 MiB, which fits the 64 MiB import cache;
- a 60%-distinct data-model source holds about 1.2M names, each about 1.7 times as long (mean 34.6 against 20.8 code units), so
  about 3.5 times the pages, more than the cache (**inferred**).

So a low-churn re-scan of a 60%-distinct source is not a representative workload, and it gets the stress budgets: PERF-14's 45 s
engine target and the 5 s / 4.75 s Stop. **This is the intended product behaviour**, stated in D-53: the class follows the
parameters of the dictionary the save imports into, not a label the source inherits from its first save. PERF-01's representative
acceptance is not extended to high-novelty sources. The added matrix cell R(2M, 60%, data; 1%, 0.5%, 0.5%) measures it; it is
expressed by `ObjSnapshot`'s existing parameters (`d=0.60;model=data;rho=0.01;delta=0.005;alpha=0.005`), with no generator change,
and was not run here (no new workload evidence is part of this repair). Whether a C4 implementation meets 45 s in it is an
implementation risk for the C4 repair's gate session, like C4DRR-O11's stress first save.

### 4.4 D-53 alignment

D-53 now says: the class follows "by a total function" (bands of disjoint intervals, the hardest band among a cell's parameters,
after the named families); PERF-01 is judged on representative first saves and on re-scans of such sources with ρ ≤ 1%, δ ≤ 0.5%
and α ≤ 0.5%; high-novelty sources are stress sources, "their first saves and their routine re-scans"; "a re-scan's class follows
the parameters of the dictionary it imports into, not a label inherited from the first save"; sources above 60% distinct, churn
beyond the stress bands and adversarial distributions are worst-case. Its "Rejected" list names the nested-bound rule
(C4DRR-M01). The classifier implements exactly this text.

### 4.5 Boundary tests (measured: `python workload_class.py docs/v1.1-preproduction-spec.md`)

Full output: `final-repair/classes.md` (59 checks, 0 failures). The cases the brief names, at 2M files; ε is one millionth of a
percentage point, in exact rational arithmetic:

| Case | Class |
|---|---|
| F d = 25%, system / data | Representative / Stress |
| F d = 25% + ε, system | Stress |
| F d = 60%, system / data | Stress / Stress |
| F d = 60% + ε, system / data | Worst-case / Worst-case |

25% (system) in two bands, so no single class; R ρ = 1% with every parameter in two bands; the 1% re-scan of a 60% data-model
source with every churn parameter in two bands; ρ 1%, δ 8% with δ in no band.

## 5. C4DRR-M02: the fail-closed journal checker

### 5.1 The defect (review §7.6)

The verdict was `PASS if remote == 0 and not defects and not shared_over`. Checksum failures, image mismatches and truncation were
counted but never changed it, and an empty or unparseable journal gave zero records and so PASS. Seven of the review's thirteen
altered inputs passed. A port of the tool would have certified PERF-15 (a) on a journal copied after `COMMIT`, truncated, or paired
with the wrong copy.

### 5.2 Outcomes and exit codes

| Outcome | Exit | Meaning |
|---|---:|---|
| **PASS** | 0 | The evidence is complete and valid, and every journalled page meets PERF-15 (a) |
| **FAIL** | 1 | The evidence is complete and valid, and a page violates PERF-15 (a) (REMOTE, or a level over the SHARED cap) |
| **INVALID** | 2 | The evidence cannot be trusted or interpreted; every reason is listed. Also any usage error (the argument parser exits 2 with "INVALID: usage") and any internal error (caught at the top, exit 2) |

**INVALID is never PASS** (§15.4): the cell's PERF-15 (a) is NOT MEASURED, which counts as MISSED, until the run is captured again
and its attribution is valid. INVALID evidence is an objective invalidation, so the rerun is allowed by §15.4's rerun rule.

### 5.3 What is validated

**Binding to the run (new in §15.4).** The run's record holds the target (a source id, or a new source), the journal's length read
through the live handle immediately before `COMMIT`, and the copy's length and SHA-256 taken when the copy was made. The checker
takes them from the record (`--source`/`--new-source`, `--expect-journal-bytes`, `--expect-copy-sha256`), never from the analyst.
`--expect-journal-bytes` is required.

**The journal** (format: SQLite's `pager.c`; the checksum is `pager_cksum`, the segment's nonce plus every 200th byte of the image
from the end):

- its length equals the recorded pre-`COMMIT` length;
- every segment header is complete (a full sector), its magic is SQLite's or the zero form SQLite writes on purpose for a segment
  not synced yet (magic and record count zero, nonce, original size, sector and page size present), and its sector size (32 to
  65,536, a power of two) and page size (512 to 65,536, a power of two) are valid;
- every segment's page size equals the copy's, and every segment's original database size equals the copy's page count;
- a synced segment holds all the records it declares; the unsynced last segment ends exactly on a record boundary (a trailing
  partial record is INVALID, never ignored);
- every record's page number is between 1 and the original size and appears once; every checksum matches; every original image
  equals the copy's page byte for byte;
- page 1 is journalled. SQLite journals page 1 before it allocates a page (to record the new database size, or the free-list count
  when it reuses a free page), and every T-IMPORT of the matrix allocates pages; page 1's image then ties the copy's change counter,
  size and free list to the journal. **From source:** `allocateBtreePage` in `btree.c` of 3.53.3 (SHA-256
  `c0982890…7a94`, the hash the review cites) calls `sqlite3PagerWrite` on page 1 before it decrements the free-list count
  (lines 6570 to 6572) and before it extends the database and writes the new size at offset 28 (lines 6776 to 6800).
  **Measured:** page 1 is journalled in all nine analysed journals, 100k to 2M.

**The copy**: an SQLite database whose length is a whole number of pages; in-header size valid and equal to the file; no auto-vacuum;
UTF-8; `application_id` 0x53494E56 and `user_version` 1 (StorageInventory's, `LibraryNames.cs`); `PRAGMA quick_check` = ok; exactly
the Library schema's 21 trees; the name index keyed as `--layout` declares (`source_id, utf16` per source; `utf16` for the negative
control) and `folder_path_child` and `folder_path_root` keyed by `source_id` first; the free list's count equal to the header's;
the SHA-256 equal to the record's when given.

**Decoding and placement.** Every page of every tree decodes (page type, cell pointers, records, child and overflow pointers in
range, no page reached twice); every dictionary key's first column is a source id (per source) or a name (the control); every
journalled page is placed in a tree, the free list or an overflow chain.

**The target.** An existing target has keys in the copy's dictionary (per source) or references names (the control); a new target
has no key at or past its id.

### 5.4 Empty-journal semantics

The normal `TRUNCATE` journal is 0 bytes after `COMMIT`; that is what a copy taken too late gives. PERF-15 (a)'s evidence is the
journal **before** `COMMIT`. So:

- a 0-byte or record-less journal is INVALID unless the run is declared, separately, to journal nothing
  (`--expect-no-records`, with a recorded length of 0); then only a 0-byte journal is valid, and the verdict is PASS vacuously;
- **no TEST-P1 cell declares this**: every T-IMPORT of the matrix allocates pages and so journals page 1 (§15.4 says so);
- records present in a run declared empty are INVALID.

## 6. C4DRR-M03: the whole-machine load source

### 6.1 The defect (review §10.4)

The repaired §15.4 decided validity from `\Process(*)\% Processor Time` summed by class, and forbade any other source. A process
that lives less than one 500 ms interval never has a rate, and PDH renumbers the instances of an executable when one exits, so
the sum misses short-lived work: in the review, 261 short processes raised the whole machine by 31.2 points and the counted
external share by 2.4. A machine running a build or a script of short processes could pass the quiet check.

### 6.2 The counter (research and measured)

| Candidate | Semantics | Used? |
|---|---|---|
| `\Processor Information(_Total)\% Processor Time` | Busy time of all logical processors (100% − idle), from each processor's idle accounting; counts every process however short-lived, and DPC and interrupt time. The `Processor Information` object covers every processor group (systems above 64 logical processors); the older `Processor` object reports only the first group's processors | **Yes: the one validity counter** |
| `\Processor(_Total)\% Processor Time` | The same quantity for group 0 only | Recorded for comparison |
| `\Processor Information(_Total)\% Processor Utility` | Busy time scaled by delivered frequency over base frequency: it reads above 100% under turbo and is what Task Manager shows (Microsoft: "CPU usage exceeds 100% in Task Manager and Performance Monitor if Intel Turbo Boost is active") | No: not comparable with processor time, so own time cannot be subtracted from it |
| `GetSystemTimes` | Idle, kernel and user time of the whole machine | Recorded for comparison |
| Summed `\Process(*)` counters | Misses short-lived processes and renumbered instances | Diagnostics only |

**Measured agreement** on this machine (16 logical processors, one group), over the idle sessions: `Processor Information` 56.75%
mean, `Processor` 56.76%, `GetSystemTimes` 56.74%; `% Processor Utility` 65.5% (frequency-scaled). Sources:
[Microsoft, CPU usage exceeds 100%](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/cpu-usage-exceeds-100);
[Microsoft, processor groups](https://learn.microsoft.com/en-us/windows/win32/procthread/processor-groups);
[Zabbix, notes on Windows CPU counters and processor groups](https://www.zabbix.com/documentation/7.0/en/manual/appendix/items/system_cpu_util).

### 6.3 The benchmark's own time, and `U`

A whole-machine counter includes the benchmark. Its own time is subtracted exactly:

- the orchestrator (the probe here) creates a **job object** and puts itself in it; every process it starts, and everything those
  start, inherits the job;
- `QueryInformationJobObject(JobObjectBasicAccountingInformation)` returns the cumulative user and kernel time of every process
  ever in the job, exited ones included (measured: a 2 s child's time stays in the total after it exits), unelevated;
- each collection's own share is the change in that total over the interval, divided by the interval and the number of logical
  processors;
- **`U` = whole machine − own**, per collection.

`U` needs no process enumeration, so a process cannot hide from it by being short-lived. The per-process counters stay as
diagnostics: own by process ID (it agrees with the job's figure), induced (`System`, `MsMpEng`), external, and the **unattributed**
CPU (`U` less the counted induced and external shares), recorded as CPU, as the review required.

### 6.4 The rules (§15.4)

| Check | Window | Rule on `U` |
|---|---|---|
| **Quiet check**, before the session and after every round | 60 s, 120 collections on a fixed 500 ms schedule, nothing of the benchmark running but the probe | mean ≤ 5%, 95th percentile ≤ 15% |
| **Run validity** | the collections of the measured operation | mean ≤ 10%, 95th percentile ≤ 25% |

Between the quiet check, where no benchmark runs and `U` measures the machine directly, and a run, where the benchmark's own
processes are subtracted, the 5 and 10 points are the allowance for the work a run causes outside its own processes: Microsoft
Defender scanning its files, the System process's cache writes, and the interrupt and DPC time of its I/O, which Windows charges to
no process. That induced work now counts against a run (C4DRR-O07): a scan the run did not cause is not distinguishable from one it
did, so all of it counts, and the allowance is sized by measurement (§6.6). A CPU-bound benchmark is never rejected for its own
load, because its own time is subtracted (§6.5, "bench").

## 8. The cancel-point correction

The design repair listed four cancel points for PERF-15 (c), PERF-16, TEST-P1 and TEST-P2, the fourth "immediately before `COMMIT`
(after the final statements and IMP-11's final check)". The final check is the last token check (CAN-01d) and nothing runs between
it and `COMMIT` (IMP-11), so a cancellation there is never observed: the save publishes (CAN-01e). That point could not roll back.

The fourth point is now **during the final statements**: after the token check that follows the verification, before IMP-11's final
check, which is the last token check before `COMMIT` and detects it. The four points are each a place where a later token check sees
the cancellation and the transaction rolls back:

1. immediately after a token check during row insertion;
2. at the start of the in-transaction verification;
3. at its middle;
4. during the final statements, detected by the final check.

The same wording is in PERF-15 (c), §15.4 (cancellation and recovery), PERF-16, TEST-P1 and TEST-P2. CAN-01d adds that the last check
before `COMMIT` is IMP-11's final check and a cancellation after it is not observed, and UI-10 reports a Stop that came too late as
"Saved to History (it had finished before Stop took effect)". The budgets are unchanged. No text claims that a point after the final
check rolls back.
