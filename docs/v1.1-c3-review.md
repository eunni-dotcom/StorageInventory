## 3. Methodology and limitations

**What was done.**

1. Read every changed production file in full, and the tests that exercise them (`SourceIdentityTests`,
   `SecurityAuditTests`, the History tests, `IdentityEvidenceTests`, `FakeWorld`, `IdentityProbe`).
2. Built and ran the whole suite on the exact head (`.\build.ps1 -Target Test -Configuration Release`) and the reproducible
   publish (`.\build.ps1 -Target Publish`).
3. **Mutation experiments** on a scratch copy of the exact head (`git archive`; the review repository was never mutated):
   63 deliberate defects across the matcher, classifier, re-verification, hold, source-location and native layers, each
   built and run against the History, Core and the C3 integration tests (Appendix A). These replace counting tests with
   asking whether the tests can fail.
4. Ran the product's own read-only probe (`--identity-probe`, zero access, no hold) on the review machine's local
   volumes, and an ancestor-rename experiment with the held handle and the implementer's own control (Appendix B).
5. Replayed the audit's own regular expressions against a reflection-based call to try to defeat A-08 (section 5).
6. Delegated four read-only investigations to sub-agents, whose reports were treated as data and spot-checked: (a) the
   hosted CI logs and artifacts through `gh` (counts, hashes, attempts, the experiment matrices); (b) a safety audit of
   `tests/identity`; (c) a test-adequacy audit of TEST-I3 and TEST-I5; (d) a documentation overclaim audit. Findings
   marked **[reviewer-verified]** below were re-checked by me against the code, the logs I read, or an experiment I ran;
   items from (a) are marked **[CI agent]** and were confirmed from raw logs by that agent, and I re-derived the numbers
   that could be reproduced locally (suite counts, publish hash, the platform matrix on this machine).

**Limitations.**

* The review machine is the implementer's development machine (Windows 11 Pro 10.0.26200, not elevated). It is not
  independent hardware. No elevated provisioning script was run; the VHDX, FAT32, exFAT, ReFS, UDF-image and SMB results
  rest on the hosted run artifacts, which a delegated agent read.
* I did not hold the handle on, or eject, any removable or physical medium. I did not run the physical "Safely Remove"
  experiment or any test that needs hardware the machine does not have.
* The mutation experiments cover the History, Core and C3 integration suites; the UI suites were not mutated.
* Labels and serials of the review machine's volumes are withheld from this public document, as the implementer's
  evidence withholds its own.

## 5. Native API and the zero-access model

### 5.1 The six P/Invokes (A-08)

By reflection and by reading `src/StorageInventory.Core/Paths/NativeMethods.cs`, the first-party surface is exactly six
P/Invokes, all `kernel32.dll`, all in `NativeMethods`. **[reviewer-verified]**

| # | Function | Reviewed signature and handling | Verdict |
|---|---|---|---|
| 1 | `CreateFileW` | `string` path (Unicode, `ExactSpelling`), `uint` access, share, disposition and flags, returns `SafeFileHandle`; `SetLastError = true`; one call site (`OpenZeroAccess`, line 85) with the literal `0`, share `0x7`, `FILE_FLAG_BACKUP_SEMANTICS`, `OPEN_EXISTING` | correct |
| 2 | `GetFinalPathNameByHandleW` | `[Out] char[]` buffer, grown when the result is not smaller than the buffer; last error read immediately; v1's loop unchanged | correct |
| 3 | `GetVolumeInformationByHandleW` | eight parameters match the Windows signature; 261-char buffers (label and filesystem name are far shorter); returns an error code instead of throwing | correct |
| 4 | `GetFileInformationByHandleEx` | class is a one-member private enum (`FileIdInfo = 18`); `out FileIdInfoNative` is 24 bytes (`ulong` serial, then the 16 identifier bytes as two little-endian `ulong`s), `bufferSize = Unsafe.SizeOf<>() = 24` | correct |
| 5 | `GetVolumePathNameW` | extended path in, buffer `length + 8`; result prefix stripped | correct |
| 6 | `GetDiskFreeSpaceExW` | three `out ulong`; clamped to `long`; mount point or canonical path with a trailing separator | correct; capacity is per-user-quota aware (documented limit 6 of the evidence) |

Integer widths (`uint` for `DWORD`, `ulong` for `ULARGE_INTEGER`), `SetLastError`, `Marshal.GetLastWin32Error()` read
before any other call (including before `Dispose` of an invalid handle), buffer lifetimes and `SafeFileHandle` ownership
are all correct. The caller of `ToExtendedPath` must pass a validated path; for `\\?\` and `\\.\` inputs it produces
`\\?\UNC\?\...`, which fails closed (Win32 53, section 7 and C3-O13), and `PathPolicy` already refuses device paths
(`DevicePath`).

### 5.2 Can the audit rule be defeated? (TEST-A1)

`The_only_native_calls_are_six_read_only_kernel32_functions` reflects over Core, History and the App for exactly six
`kernel32` P/Invokes, forbids declarations outside `NativeMethods.cs`, requires one `CreateFile` call site whose second
argument is the literal `0`, one `GetFileInformationByHandleEx` call site whose second argument is exactly
`FileInfoByHandleClass.FileIdInfo`, a one-member enum, and the enum's name in only three kinds of place.
`The_native_rules_reject_violating_fixtures` is the negative self-test (A-21).

| Attack | Result | How |
|---|---|---|
| a seventh P/Invoke, write-capable (`DeleteFileW`) | **rejected** | mutant C6 killed by the A-08 test; the negative test also runs the reflection rule over a real fixture type |
| a P/Invoke from another DLL | rejected | negative self-test (`MessageBoxW` fixture) |
| `CreateFile` with `GENERIC_READ` | rejected | mutant C2 killed by the A-08 test **and** by the granted-access test |
| second enum member | rejected | mutant C5 killed |
| another information class value (`= 1`) | rejected | mutant C4 killed |
| cast, `default(...)`, `Enum.ToObject(typeof(FileInfoByHandleClass), n)`, `Unsafe.As<int, FileInfoByHandleClass>` | rejected | the type's name may appear only in three places; each has a negative fixture |
| alternate wrapper | rejected | a second call site breaks the count; a second P/Invoke breaks the six |
| **`Enum.ToObject(m.GetParameters()[1].ParameterType, 5)` through `MethodInfo.Invoke`** | **not rejected** | mutant C7: the A-08 and A-12/A-13 audit and all 36 filtered C3 tests still pass with such a call in `NativeMethods.cs`. The rule's regular expressions find neither `GetFileInformationByHandleEx(` nor `FileInfoByHandleClass` in that code, and A-18's dynamic-code rule bans `Assembly.Load`, `Activator.CreateInstance` and `Type.GetType(` but not `MethodInfo.Invoke` |

The negative self-tests are meaningful: they run the real rule over real violating input and the reflection rule over real
declared fixtures. They are not complete. The doc comment that says the text rule closes the cases "whatever the spelling"
(`SecurityAuditTests.cs:153-156`) and the commit subject "reject every way to conjure a FileIdInfo class value" overstate it
(C3-M03). The practical risk is bounded (a deliberate reflection call inside Core would show in any review), and the six
functions themselves cannot grow.

### 5.3 The zero-access handle

* **Desired access exactly 0:** one `CreateFile` call site in `src`, passing the literal `0` (audited, and mutant C2 shows
  the audit and the test both fail when it is changed).
* **Backup semantics, share read, write and delete, the enumerated path:** `OpenZeroAccess` passes
  `FileFlagBackupSemantics` and `FileShareReadWriteDelete`; `WindowsEvidenceSource.Open` passes the enumerated path
  (`WindowsEvidenceSource.cs:22`) through `TryOpenDirectoryZeroAccess`.
* **No path obtains a data right:** no other `CreateFile`, `FileStream` (A-03), `File.OpenHandle` or `Directory.Enumerate*`
  appears in the new code.
* **The granted-access test measures the production open.** `TEST_I1_the_handle_the_product_opens_is_granted_no_list_read_write_or_delete_right`
  (`SourceIdentityTests.cs:569`) calls `NativeMethods.TryOpenDirectoryZeroAccess`, the same function
  `WindowsEvidenceSource.Open` calls, reads the mask back with `NtQueryInformationFile`, asserts only `SYNCHRONIZE |
  FILE_READ_ATTRIBUTES` (`0x00100080`), asserts none of twelve list, read, write, delete and security bits, and shows with a
  `GENERIC_READ` contrast handle (`0x00120089`) that the probe can see rights. It does not read the private `_handle` of
  `WindowsEvidenceHandle`; the single-call-site rule is what ties the two together. Acceptable.
* **Share mode is not what keeps the handle from blocking anyone (C3-O05).** Mutant C3 removes `FILE_SHARE_DELETE` from the
  constant and every C3 integration test, including the rename and delete tests, still passes. A handle that holds no
  read, write or delete access does not take part in Windows share-access checking, so its share mode changes nothing
  observable. The documents attribute the non-blocking to the share mode ("shared read, write and delete, so it never
  blocks a rename"). The share mode is what §7.2 specifies and is harmless; the claim and the test are about something else.

## 6. VolumeEvidence

`EvidenceItem<T>` (`Core/Identity/EvidenceItem.cs`) keeps four states apart: `Available`, `Unavailable` (the default value,
so an item nobody filled in is never mistaken for a value), `CallFailed` and `NotProvided`
(Win32 1, 50, 87, 120 or 124, kept with the raw error). `VolumeEvidence` carries every item as an `EvidenceItem`, so:
**[reviewer-verified]**

* a Win32 failure is never converted into a zero or null: the failing item becomes `CallFailed` or `NotProvided` with the
  call name and the error; `WindowsEvidenceSource.NoHandle` fills every item with `Missing(call, reason)` when the handle
  could not be opened, and the missing-folder test asserts nothing is available;
* **serial 0 is a value**, `Available(0)`, distinct from a failed call and from an unavailable item; the classifier
  refuses to make a zero serial Strong or Moderate (mutants M16b and M17b killed), and the matcher never looks one up;
* a filesystem name of the empty string is treated as unavailable;
* `EvidenceItem` is a record struct whose generated equality includes `Call`, `Win32Error` and `Detail`, but no production
  code compares items as a whole: `Reverification.Check` compares `Status` and `Value` only (`Reverification.cs:114-128`),
  the classifier reads `.Value`, and the matcher uses explicit ordinal comparisons.

`NotProvided` is classified from the error (87 on FAT32, exFAT and UDF was measured). No decision treats `NotProvided`
differently from `CallFailed`; it changes the explanation only. Judgement call 8 of the evidence is sound.

## 7. Source-kind and location derivation

One rule decides local or network (`VolumeEvidence.ResolvedKind`, `Core/Identity/VolumeEvidence.cs:48`): the canonical path
returned by `GetFinalPathNameByHandleW` on the opened handle is split by `SourceLocation.TryDerive` into a drive-letter
volume or a UNC share; `ID-13`'s minimum evidence, `ID-01`'s confidence and `ID-10`'s comparison all call it (they used
two derivations before `ab3d5d6`). The drive-letter syntax of the input is never used while a canonical path exists.
**[reviewer-verified]**

| Case | Result | Evidence |
|---|---|---|
| `C:\` | local, root `\` | `IdentityEvidenceTests`, `TEST_I1_the_system_drive_*` |
| local subfolder | local, `\Media\Music` | tests; integration subfolder test |
| SUBST letter | local, the target's canonical path and volume | integration SUBST tests; hosted matrix row `Z:\` |
| UNC `\\nas\share\x` | network, share `\\nas\share`, root `\x` | `IdentityEvidenceTests` (6 UNC shapes) |
| mapped drive letter | canonical `\\server\share\...`, so **network**, never Strong | hosted rows `R:\`, `S:\`; mutant M15 killed (a network share cannot be made Strong) |
| extended input `\\?\C:\x`, `\\?\UNC\...`, device `\\.\C:\` | refused: `PathPolicy` blocks device paths; the evidence layer, called directly, fails closed (Win32 53, Save unavailable) | `PathPolicy.cs:234`; reviewer probe, Appendix B |
| canonical path with neither shape (`Volume{GUID}\x`, `\\.\x`, empty) | `TryDerive` false, so `MinimumEvidence` makes the source unsaveable | code; **but untested** (mutants T8, T10c survived, C3-M02) |

Root exactness: `RootBelow` drops the trailing separator only, `\` for a volume or share root, no case folding and no
normalisation (mutants M40c and M46c killed; the integration test keeps Korean, a surrogate-pair emoji and precomposed and
decomposed accents as different exact roots). Unpaired surrogates survive `new string(buffer, ...)` and the ordinal
comparisons by construction and are untested.

Two small imprecisions remain (C3-O01): `VolumeEvidence.ResolvedKind` falls back to the reading's own `Kind` when the
canonical path is **available but underivable**, whereas its documentation and judgement call 24 say "only when no
canonical path was obtained"; and `Kind` itself is still produced by `SourceLocation.ClassifyKind`, a second derivation.
Both are neutralised because an underivable path is unsaveable, and no test pins the branch.

## 8. Confidence and basis

**Strong** needs a local source, NTFS or ReFS (by name, case-insensitively) and a non-zero 64-bit serial;
**Moderate** a local FAT, FAT32 or exFAT volume with a non-zero 32-bit serial; everything else is **PathOnly**
(`IdentityClassifier.Decide`). Confidence is keyed by the filesystem name (mutant M18, exFAT as Strong, is killed), network
is decided first (M15), and a zero serial is PathOnly (M16b, M17b). No fallback weakens the rules silently. The stable codes
equal §9.4 (Strong 1, Moderate 2, PathOnly 3; Evidence 1, UserAsserted 2, Location 3; LocalVolume 1, Network 2).

**Mutable metadata is never identity.** The label, capacity, free space, flags and mount point are recorded, never
compared by `Reverification` (mutants M27 and M28 killed), and not used for Strong matching (M44 killed). They appear in the
matcher in exactly three allowed places: the Moderate corroboration (label exact, capacity ±1%), the Moderate co-mounted
check (`SameIdentity`), and the mount point as the alias filter. The whole-volume root `FILE_ID_128` is used in one place
only, the E0 to E3 comparison (`Reverification.cs:109`); it is not read by the classifier or the matcher (grep). **[reviewer-verified]**

**Basis and confidence are separate and fixed at creation.** `IdentityConfidence` and `IdentityBasis` are distinct
enums; `InMemoryIdentityStore` has no API that changes a stored source's or volume's confidence or basis (it refreshes only
a volume's latest label and capacity); `Confidence_and_basis_are_fixed_when_a_source_is_created_and_never_change`
(`MatchingTests.cs:733`) snapshots every row. A later weaker capture is never attached silently (`WeakerThanSource`, mutant
M13 killed; `PathOnlyMayBelong` for the NTFS-with-failed-`FileIdInfo` case, M11 killed).

**Judgement call 1 (C3-O02).** "Any evidence call failed" in the PathOnly row is read as "a call whose value the applicable
rule needs". The literal reading would make Moderate unreachable (`FileIdInfo` is not provided on every FAT volume) and would
give an NTFS volume a new source whenever a label query failed. The reading is reasonable and is pinned by
`ClassifierTests.Informational_failures_do_not_change_the_confidence`, which therefore enshrines a reading the owner has not
ratified in the specification. It should be ratified when the specification is next revised.

## 9. Matching and clone semantics

The matcher (`IdentityMatching`) is a set of pure functions of an `IdentityAssessment`, an `IIdentityCandidates` view, an
`IComparisonKey` and a required list of mounted volumes. It reads no filesystem, clock, process or registry (a grep of
`src/StorageInventory.History` for `System.IO`, `File.`, `Directory.`, `DateTime`, `Process`, `Environment`, `Registry`,
`System.Net`, `Thread` and `Console` finds only prose in comments).

**Outcomes** (`MatchOutcome`, `IdentityDecision`, `PromptReason`, `IdentityAnswer`): existing source attached automatically
(`Decided(AttachToSource)`), a new source (`Decided(CreateSource)`), ask the user (`Ask` with six reasons), a suggested source
(`CaseVariantRoot`, `PathOnlyMayBelong`), an explicit user assertion (`SameSource`, `SameVolume` with basis
`UserAsserted`), don't save (`SkipSaving` leading to `DoNotSave`), treat as new (`IfDifferent`, `TreatAsNewSource`), and
`SaveUnavailable`. No UI wording is in the layer. I found no contradictory state; `WeakerThanSource` is reachable only

## 10. The E0, E1, E2, E3 lifecycle

This is the most important correctness review, and it passes.

* **E0** (`PreflightEvidence.Collect`): open the enumerated path, read, close.
* **E1** (`RootIdentityHold.Open`): open the enumerated path, read E1 through that handle, keep it.
* **E2** (`Finish`, step 1): read through **the same held handle**.
* **E3** (`Finish`, step 2): `_source.Open(EnumeratedPath)`, a **fresh open of the enumerated path**, read, dispose.
* The held handle is then closed. `Reverification.Evaluate` refuses readings taken on different enumerated paths.

The canonical path is never the path of any `CreateFile` call (the only call site takes the enumerated path), and the two
by-path display queries (`GetVolumePathNameW`, `GetDiskFreeSpaceExW`) take the canonical path and the mount point as §7.8
specifies ("no handle"), are not identity items and are never compared (C3-O07). `TEST-I5`'s wording "the canonical path
is never opened" is true of handles.

**Call order is proved by the fake provider.** `FakeWorld` logs every open, read and close with the handle id, the path and
the stage; `E1_and_E2_come_through_one_held_handle_and_E3_through_a_fresh_open_of_the_enumerated_path`
(`LifecycleTests.cs:47`) asserts the exact sequence Open1, Read1(E1), Read1(E2), Open2, Read2(E3), Close2, Close1, and
`Every_open_uses_the_enumerated_path_and_the_canonical_path_is_never_opened` (`:79`) asserts every open path equals the
enumerated path and exactly three opens. My mutants M31 (E3 opens the canonical path), M32 (E2 through a fresh open) and
M33 (E3 through the held handle) are each killed by 6 to 8 tests. **[reviewer-verified]**

**ID-13 minimum evidence.** `MinimumEvidence.Check`: the canonical path for every source (plus, conservatively, that it has
a drive-letter or UNC shape), and for a local volume the filesystem name and 32-bit serial. When it is missing,
`IdentityAssessment.CanSave` is false, `IdentityMatching.Match` returns `SaveUnavailable` before anything else, and
`Reverification.Evaluate` returns `SaveUnavailable` without comparing; there is no "the path still exists, so identity is
fine" fallback (mutants M14, M29, M30 killed).

**Conditional items.** `Check` requires an item at E1, E2 and E3 whenever it was available at E0, which implements ID-13
(3) (`FileIdInfo`'s 64-bit serial and root file ID) and (4) (a network provider's filesystem name and serial) with one
rule. A later value that **changed** is rejected (M19 to M23 killed), a later value that **became unavailable** is rejected
(M25c killed), and an item **unavailable at E0 is not required** later (M26 killed). **Equality** is over identity items
only (the five items plus the source kind); a label, capacity, free space, flags or mount point that changes between
readings does not reject (`The_mutable_items_are_recorded_but_never_compared`; M27, M28 killed).

**SUBST (TEST-I5).** `TEST_I5_a_SUBST_letter_re_pointed_during_the_window_is_not_eligible`
(`SourceIdentityTests.cs:281`) uses a real SUBST letter re-pointed from A to B during the window and asserts: E2's canonical
path is unchanged (the held handle still designates A), E3's canonical path ends in `\B` (so E3 really reopened the
**letter**; a reopen of the canonical target would read `\A`), and the failure is reported at E3. The test cannot pass by
opening the canonical path. Away-and-back is pinned as `Verified` (L-ID2).

**Rename, delete, replace (TEST-I5).** Rename: E2 reports the new name, E3 cannot open the old path. Case-only rename,
delete, replaced-and-left and replaced-and-restored (L-ID2) are separate tests. The tests record what Windows does and
require only that the decision rejects the capture; they do not insist on one Win32 error. **[reviewer-verified]**

**L-ID2.** The implementation and the documents state it without overclaiming, including the source-folder extension
requested by G0F-O05, and pin both undetectable cases with tests (`TEST_I5_a_SUBST_letter_re_pointed_away_and_back_*`,
`TEST_I5_a_source_folder_renamed_away_replaced_and_restored_*` and the unit equivalents). Minor wording nuance:
"on every filesystem" for E2 in the architecture and security documents rests on NTFS real folders and a FAT32 **fake**

## 15. Q-19 and the stop-condition judgment

**The stop condition (§19 C3):** "holding the root handle has a user-visible effect beyond blocking 'safely remove' during a
scan (a design review is needed first)".

**What was observed while the handle is held (hosted artifact, plus the implementer's development machine and my own
experiment):**

| Effect | Evidence |
|---|---|
| the orderly volume lock that "Safely remove" and Eject begin with is refused (Win32 5); it succeeds before and after | **[CI agent]** hosted artifact, virtual NTFS volume |
| the same lock is refused while only an ordinary open folder listing is held (control) | hosted artifact |
| a mapped drive's normal disconnect asks "open files and/or incomplete directory searches pending... Is it OK to continue disconnecting and force them closed?" | hosted artifact (loopback mapped letter) |
| the same confirmation appears with only an open folder listing held (control) | hosted artifact |
| renaming or deleting the **source folder itself**, listing and scanning it: not blocked; a scan's reports are byte-identical | `SourceIdentityTests` (rename, delete, report hashes), reviewer-verified |
| **renaming an ancestor of the source folder is blocked (Access denied)** | **reviewer experiment** (Appendix B), with the identical result for an open listing (control); not in the implementer's records |
| detach, swap, forced disconnect, re-point, rename, delete are detected by E2 or E3 | experiments and tests (section 10) |

**Judgment.** The candidates were: (1) the identity handle introduces a materially new user-visible effect, so the stop
condition is triggered; (2) the effects are ordinary directory-enumeration behaviour already inherent in scanning, so it is
not; (3) inconclusive.

**It is (2): the stop condition is not triggered.** The reasoning:

1. **Same kind, same cause.** Every user-visible effect of the held handle (a refused volume lock, the "open files"
   confirmation on a mapped drive, a blocked rename of an ancestor folder) is produced identically by an ordinary open
   directory listing. The controls are valid: the `--identity-enumerate` control opens a `DirectoryInfo` enumeration and
   leaves it part-way, and the v1 scanner does exactly that. `ScanEngine.Run` (`ScanEngine.cs:60-131`) walks the tree
   iteratively with one `FileSystemEnumerable` at a time, so **throughout the enumeration phase a directory handle is
   already open on the source tree**. Windows' own message text for the mapped drive names "incomplete directory searches
   pending" as one of the two causes. The scan itself, not the identity handle, is what makes these effects visible.
2. **The only increment is duration.** The held handle spans the observation window (P2 to P4), which is longer than the
   enumeration: it adds the moments before the first listing and after the last one. For a removable volume that is the
   accepted effect ("blocking 'safely remove' during a scan"); for a mapped drive and for ancestor folders it is the same
   effect for the same extra time. No new category of effect appears.
3. **No spontaneous effect.** Nothing happens to the user unless the user tries to remove a volume, disconnect a mapped
   drive or rename an ancestor folder during a scan, and in each case Windows' standard "in use" refusal or confirmation
   applies.
4. **The scan is unchanged** (reports byte-identical with the handle held), the handle blocks no rename or delete of the
   source folder itself, and every change that is made is detected, except what is undone (L-ID2).

The mapped-drive confirmation is therefore **within the accepted effect**, and so is the ancestor-folder rename. This is a
judgment about the stop condition, not a claim that the record is complete: the record **omits** the ancestor-folder effect
and states elsewhere that the handle "never blocks a rename" (C3-M04), and the specification row asks the reviewer to decide
a point that this section now decides. The later UI gate's identity help should say that removing, disconnecting or renaming
a parent of a source while a scan runs is refused (a note for C8).

### C3-H01 (High): an unguarded recursive delete of a caller-supplied folder

* **Authority / requirement.** The review brief (item 37): "Any dangerous path/volume-selection bug is a serious finding even
  though the scripts are test tooling", and the hardening the implementer itself applied to the sibling script in `6ba7402`
  (`-Root` is deleted only if created by the script).
* **Evidence.** `tests/identity/Invoke-IdentityExperiments.ps1:27` takes `[string] $Work`; line 44 runs
  `New-Item -ItemType Directory -Force $Work` (no error if it exists); line 407 runs
  `try { [IO.Directory]::Delete($Work, $true) } catch { }`. There is no emptiness check, no marker and no refusal. The
  synopsis (line 12) describes `-Work` as the folder whose scratch content "is removed", and `tests/identity/README.md`
  never mentions the parameter. The default is a fresh `%TEMP%\SiIdentityWork_<6 hex>`. [reviewer-verified]
* **Failure mode.** `.\Invoke-IdentityExperiments.ps1 -Work C:\Users\Jack\Documents\results` (or `-Work $env:TEMP`, or
  `-Work .`): the script creates its folders inside the user's existing folder and then deletes the whole folder
  recursively, including everything that was there before; the `catch { }` swallows partial failures. `-Out` is likewise
  overwritten silently (line 408).
* **Consequence.** Irreversible deletion of user data on a plausible mis-use. With the default arguments the scripts are safe;
  neither script is run by CI.
* **Required correction.** Refuse an existing non-empty `-Work` or, better, always create and later delete a unique child
  folder of whatever path is supplied, and delete only a folder the script created (a marker, as `Provision-IdentityMedia.ps1`
  does). Refuse an existing `-Out` or document the overwrite.
* **Closure evidence.** A recorded run of the script with `-Work` pointing at an existing non-empty folder that is refused (or
  leaves the folder's original contents intact), and the changed lines.

### C3-M01 (Medium): `-Remove` acts before it checks ownership

* **Authority.** Same brief item; `6ba7402` claims "teardown deletes only a marked folder".
* **Evidence.** `Provision-IdentityMedia.ps1`: `-Remove` returns at line 88, before `Assert-ScratchRoot` (line 90). In
  `Remove-All` (lines 69-86), for every `*.iso` in `$Root` it runs `Dismount-DiskImage` (line 76) and for every `*.vhdx` a
  diskpart `detach vdisk` (lines 77-79) **before** the marker test (line 81), after writing a `dp_*.txt` script into `$Root`
  (lines 62-65); it force-disconnects the letters the manifest names (line 74), removes shares named `SiEvidenceA/B` (line 75)
  and deletes the file given as `-Manifest` (line 84), which is never validated (any JSON passes, line 71). The folder
  guard also fails open when the folder cannot be listed (`-ErrorAction SilentlyContinue`, line 52). [reviewer-verified]
  The detail of the mis-supply scenarios was supplied by the safety sub-agent.
* **Failure mode.** `-Remove -Root D:\VMs` detaches the user's own mounted VHDX and dismounts their ISOs before warning that

* **Consequence.** No data is deleted, but unrelated volumes and mappings are disturbed; the documents ("deletes only a
  marked folder") are true of deletion only.
* **Required correction.** Test the marker (and apply the root guard) before any dismount, detach or write; validate that a
  manifest was written by the script (a signature field) and that each letter is still backed by the script's own image;

* **Closure evidence.** The reordered teardown and a run of `-Remove` against an unmarked folder holding a mounted image that
