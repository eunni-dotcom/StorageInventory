## 7. A-09 and the 164 versus 150/141 discrepancy

**A-09 itself is satisfied.** In the four package assemblies only `SQLitePCLRaw.provider.e_sqlite3` has an ImplMap table (the `Microsoft.Data.Sqlite` assemblies and `SQLitePCLRaw.core` have none); every import in the selected asset
(`lib/net6.0-windows7.0`) targets module `e_sqlite3`; there are no framework-module imports.

**Why 164 versus 150/141.** The implementation's numbers are correct: 150 P/Invoke declarations (ImplMap rows) and 141 distinct entry points; the nine extra declarations are overloads of `sqlite3_config` (×5) and `sqlite3_db_config` (×6) that share entry points.
The specification's **164 is the number of distinct `sqlite3_[a-z0-9_]+` string tokens in the provider file**, not an entry-point count: 141 entry points + 23 other identifiers (11 overload method names such as `sqlite3_config_log` and `sqlite3_db_config_charptr`, five type names
`sqlite3_stmt`, `sqlite3_blob`, `sqlite3_backup`, `sqlite3_snapshot`, `sqlite3_vfs`, and seven member references to SQLitePCLRaw.core API that are not P/Invokes, such as `sqlite3_key` and `sqlite3_create_function`). I reproduced the 164 myself by scanning the three provider assets
(164 for `net6.0-windows7.0` and `netstandard2.0`, 163 for `net6.0`); the 150/141 are pinned by the passing audit test, which reads the metadata tables. It is not a different asset or version, a missed function-pointer import, or an audit omission. All 141 entry points
are exported by `e_sqlite3.dll` (371 exports, 312 `sqlite3_*`). §5.3, §5.5 and §16.2 carry the wrong figure; this is a documentation erratum (C4-M15), not a design change.

## 8. Library states and precedence

All nine states are produced by deterministic fixtures in `LibraryStateTests`, `LifecycleTests` and `ProcessTests`; the derivation order in `LibrarySession.DeriveCore` follows §6.7 steps 1 to 3 and the first-matching-row rule of LIB-07 step 4. Combinations reasoned through from the code:
absent main + zero journal → Not created or Missing (journal untouched); absent main + non-empty journal → Leftover; zero main + non-empty journal → Leftover; foreign main (+ journal) → Not a Library from the header, SQLite never opened (untested, C4-M08);
valid main + unknown extra file → ignored (only owned names are inspected); lock only → Not created/Missing by the lock flag; `-wal`/`-shm` first; incompatible version + malformed schema → Incompatible from the header before SQLite.

Judgement calls:
- **Zero-byte main with no side files = uninitialised, Not created:** correct. §6.6 step 7, §6.8 (Not created row) and TEST-L3 say so. **But §6.6 step 7 has a second clause, `application_id = 0`, `user_version = 0` and no schema objects, which is not implemented** (C4-M01).
- **`_lockPreExisted` / `_everHadLibrary`:** LIB-07 step 3 says the flag is recorded **once**, at the process's first acquisition; LIB-08 step 3 says "existed **before this open**" and §6.8 Missing says "existed before this open". The code follows the once-recorded reading and adds `_everHadLibrary` so a Library this process created and
  then lost reads as Missing. That is the only reading under which both rules hold after this process has created the lock. The persistent lock file is expected owned state; it is not used as evidence of missing *data* except as the specification dictates. A one-sentence clarification in the specification is advisable (C4-O01).
  A consequence the specification accepts: an empty directory opened by a second process reads as Missing.
- The agent's claim that no test covers the lock-pre-existing quirk across two processes is confirmed.

## 9. Lock-first creation (LIB-07, CONC-01)

Traced from `Derive` (`LibrarySession.cs:151`): lease check → `AssertEngineLoaded` (no file access) → `ValidatePath` (directory chain only) → `DirectoryExists` (the directory itself, permitted by §6.7 step 2) → `AcquireWriterLock` → `InspectMembersUnderLock`, which throws if the lock is not held;
`CreateEmptyDatabase` and `QuarantineSet` carry the same guard. No directory enumeration or member access exists before the lock. **Verified.** I also ran mutant R-03 (inspect the main file before the lock), §20.

`library.lock`: existing lock opened `FileMode.Open`, `FileAccess.Read`, `FileShare.None`; absent lock created `CreateNew`, `FileShare.None`, with one retry open on a create collision; sharing violation → In use; held for the process lifetime; `_lockHandle` stays null on failure. **Verified**, with one latent point: the handle is an ordinary
`FileStream`, so the lock lasts only as long as the owning object is reachable (C4-O02).

Process races (TEST-K1): real child processes, six rounds, exactly one Available and one In use, never Leftover, only owned members afterwards; sequential cases (Library created by another process after this one started) are sound. **But the race is not shown to be contested** (C4-M06):
both children poll `File.Exists(barrier)` every 10 ms, the whole pre-lock path is about a millisecond, nothing records whether the loser hit a sharing violation on the open or the `CreateNew` collision, and the parent uses `Thread.Sleep(1500)` instead of a handshake. The six rounds can pass without ever reaching the arbitration they claim to test.
Production logic is correct by reading. The "second process scans a source containing the fixture Library" clause and the second-logon-session run are C5 or an environment limit.

## 10. Header pre-check (SEC-32, LIB-08 step 4)

`HeaderCheck.Classify` (`LibraryStore.cs:341`) matches the specification byte for byte: 16-byte magic, bytes 18 and 19 both 1, `application_id` at offset 68, `user_version` at offset 60 (newer → Incompatible, below 1 → Not a Library), fewer than 100 bytes → Not a Library. The zero-byte case is handled earlier. SQLite opens a file only after the check
(`LibrarySession.cs:290` then `:314`). **Gaps:** the tests assert "no journal created, bytes unchanged", which cannot tell a pre-check refusal from SQLite opening the file and refusing it; the combination that matters, a suspect file **beside a non-empty hot-looking journal**, is untested, as are single-byte magic and
byte-18-alone corners (C4-M08). The check and path validation run only at open; later writer opens (T0, T-OUTCOME, T-IMPORT, T-DELETE) do not repeat them (C4-M11). A vacuous assertion (`LibraryStateTests.cs:434`, a length compared with itself) means "nothing deleted" is not tested in that case.

## 11. Journal semantics, recovery, SQLite configuration

- Journal: TRUNCATE; a 0-byte journal remains; a non-empty journal is recovery material and is never deleted by StorageInventory; no `-wal`/`-shm` is created (A-23 holds in the lifecycle and K1 tests). Real-process evidence: `ProcessTests` kills a child mid-import (non-empty journal asserted, database file already written), the next open under an Open lease rolls back and deletes the journal
  (then re-creates it at 0 bytes within the same open; the test says so), committed data survives, uncommitted data is gone. A reader facing a hot journal fails with extended code 776. I accept this as real crash evidence (an external kill of a child process, not a managed exception).
- T-CREATE is one `BEGIN IMMEDIATE` with the pragmas, DDL and `library_info`; a failure rolls back and leaves a 0-byte main. **A crash during T-CREATE is not tested**, and the recovery path of that crash is the one affected by C4-M01.
- T-RECOVER changes only `outcome = 1 AND session_token <> $token`; idempotent; best effort with "recovery pending" (TEST-L7).
- Writer pragmas: `journal_mode=TRUNCATE`, `synchronous=FULL` (read back as 2), `locking_mode=NORMAL`, `busy_timeout=5000`, `temp_store=MEMORY` (2), `foreign_keys=ON`, `trusted_schema=OFF`, import `cache_size=-65536`, each set from a constant and read back (A-22). `application_id` and `user_version` are written in T-CREATE and re-read at open.
  No WAL, VACUUM, VACUUM INTO, ATTACH or extension loading appears in `src/` (`max_page_count` is in the test-fault constants only). Reader connections set only `temp_store` and `trusted_schema`; they keep the default busy timeout and do not read back `journal_mode` (C4-O03).
- Engine assertion: `AssertEngineLoaded` runs at the start of every derive and `AssertEngine` on every connection, exact `3.53.3` and exact source id; a mismatch gives Unavailable with nothing written (a test proves no directory or lock is created and a real Library's hashes are unchanged).
- Connection strings: only `Mode=ReadWrite` (writer) and `Mode=ReadOnly` (readers), `Pooling=False`; `library.sqlite3` is first created by `FileMode.CreateNew`. Verified. The A-06 audit enforces it; I ran mutant R-04 (§20).
- Temp files: `temp_store=MEMORY` is asserted by read-back only; no test watches `%TEMP%` for `etilqs_*` files (C4-O12).

## 12. Schema and stable codes (§9, TEST-S1, S2)

- Schema: an agent extracted the spec's SQL block (lines 1088–1247) and compared it with every `CREATE` constant in `SchemaSql.cs` after stripping comments and whitespace: all 18 statements (11 tables, 7 explicit indexes) are identical (columns, types, `NOT NULL`, `CHECK`s, `STRICT`, `WITHOUT ROWID`, PKs, `UNIQUE`, partial indexes), no defaults,
  views, triggers or extra columns; with the two autoindexes the object count is 20, matching the full-suite log. Observation FKs are not declared (Q-07, §22). I accept this; I did not repeat the diff line by line myself.
- Fingerprint: canonical text `type|name|tbl_name|sql` per `sqlite_schema` row, ordinal order, CRLF→LF only, SHA-256; `rootpage` excluded. The frozen hash and object list are asserted; trigger, view, extra index, extra table and `ALTER TABLE ADD COLUMN` each flip the state. `ALTER TABLE ADD COLUMN` covers a definition change with an unchanged object set (mutant R-07 is killed); no test removes an expected object.
- Stable codes: every enum maps through an explicit `switch`; no `(int)` enum persisted; unknown codes throw `LibraryDataException`; `ToCode(Catastrophic)` throws so 207 is never written; TEST-S2 pins the table, asserts ordinals differ from codes, and rejects unknown codes. ## 13. The raw SQLitePCLRaw importer

Reviewed `LibraryDatabase.WriterConnection`/`WriterStatement` and `SnapshotImporter`. It runs on `_connection.Handle`, the same approved engine and connection (no second engine, no extension API, no new `DllImport`); ADO.NET `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` run on the same connection; statements are `using`-disposed before the writer on every path;
errors are built from `sqlite3_errmsg` and `sqlite3_extended_errcode` **before** `sqlite3_reset` and thrown as `SqliteException`, so classification equals the ADO path (13 → DiskFull/`LibraryFull`, 19 → InvariantViolation, busy, IO/corrupt/cantopen); binds are exact (int64, null, blob/zeroblob, text; unsupported types throw); all SQL is a `const string`; every `WriterStatement`
operation takes a `MutationLease` and calls `Guard`; the A-25(a) audit confines `sqlite3_step`/`prepare` to `WriterStatement`/`WriterConnection`. **Verdict: sound**, with these notes: the lease-currency checks tolerate a `default` lease (C4-M05); statements are not finalised if a caller forgets `using`
(mutant R-08, §20); `Rollback` deliberately does not require a current lease (permitted by OBS-13). The real-engine fault path I accept is the two `SQLITE_FULL` tests (§19).

## 14. Import, deletion, set-aside

- **Import** (`SnapshotImporter.Run`): one `BEGIN IMMEDIATE`, everything inside, in-transaction verification, three final statements each required to change exactly one row (IMP-06), commit; any exception rolls back; no data is visible to the gate's readers before commit; older snapshots are never touched (checksums asserted after success, planted failure, thrown row source and `SQLITE_FULL`).
  The OBS-15 check runs at begin, every statement, every 16,384 rows and immediately before `COMMIT` (the T0 commit-time hook is tested; T-IMPORT commit-time invalidation is not, and mutant R-12 is killed only incidentally, so the periodic row check has no test of its own).
  Defects: **cancellation is not checked after verification and before `COMMIT`** (C4-M02); **the in-transaction verification gate is untested for most invariants** (C4-M03); **invariant 13's `run_id` is not enforced** (C4-M09).
- **Delete** (T-DELETE): one `BEGIN IMMEDIATE`; `UPDATE … WHERE state = 2` must change exactly one row; then the four observation tables and the snapshot row; commit; failure rolls back; the attempt row is kept; other snapshots checksum-identical. **The rollback test cancels immediately after `BEGIN`, before any delete statement** (C4-M12).
- **Set-aside** (LIB-13): explicit `SetAside` lease; writer lock held (a process without it cannot rename); gate taken as writer first, readers preempted and closed; unique stem over all four target names, up to 16 draws; main renamed **first**, then journal, wal, shm, each `File.Move(overwrite: false)`; nothing deleted; a failed rename stops the sequence and re-derives (Leftover);
  the lock is never released. Tests: crash between renames, an open reader, a second process, byte-identical moves. `SetAsideAsync` does not call `ValidatePath` (C4-O04). The `overwrite:false` flag is not observable because the stem search already guarantees absence, so mutant R-09 (§20) is expected to survive.
- Real `SQLITE_FULL`: hosted run `37006608313`, step "SQLITE_FULL on a really full volume": a 200 MB fixed VHDX, NTFS quick-formatted, 193.8 MB free before; a 2M-row import (about 270 MB needed) failed as `LibraryFull (201)` via the engine's own primary code 13, rolled back in 7.07 s, database again 37.8 MB measured through a handle, three snapshots counted, invariants 1–12 hold. This is distinct from the
  page-cap tests (`LimitDatabaseToTwentyThousandPages`, 80 MiB; and the unit test at 2,048 pages, which has the stronger assertions). Thinner points: "re-opened as Available" and `quick_check` are not asserted on the real-volume run, a single run, and deleting a snapshot on a full volume (needs about 128 MB of journal) is untested (C4-O10).

## 15. Interlock, W2, Faulted, gate

Reviewed `LibraryInterlock`, `Leases`, `ReaderWriterGate`, `LibrarySession` and the tests.

- Initial state is `Mutating(Open)` with lease id 1 by field initialisers, never observable as Idle; refusal text "Opening the Library…"; a second `TakeStartupLease` faults. **Verified.**
- Ids come from `_nextLeaseId++` under the monitor, never reused; Faulted sets `_leaseId = 0` and id 0 is rejected; owner is checked by reference in `CheckLocked`, `CheckObservationLocked` and `IsCurrent`; stale, disposed, handed-off and wrong-kind leases are rejected; a stale second `Dispose` does not end a later lease. **Verified.**
- Lock order interlock → gate → SQLite holds: the monitor is never held while the gate or SQLite is entered; `Notify` runs outside it. The gate is writer-preferring, gives back a grant that lost a race with cancellation, and is tested for coexistence, exclusion, preemption and close.
- Faulted: `FaultLocked` is the only entry, idempotent, no exit path in any transition method; a release exception faults; ending a lease with a resource open faults; writer disposal precedes gate and lease disposal on every session path, so no clean-end race on one thread. I ran mutant R-02 (Faulted exit, two edits) (§20).
- TEST-W2: the model in `InterlockTests.cs:19–76` restates the §11.6 table (state, kind, owner, epoch, resources, unclean) and is not a mechanical copy of production, although it mirrors the fault condition; every state × request pair, the hand-offs, wrong-owner and the random sequential test (seed retained) exist. **Gaps:** the random sequential test keeps only stale *mutation* leases (observation leases are dropped, so a stale observation hand-off is never replayed);
  the concurrent tests check grant exclusivity and terminal Faulted but do not run hand-offs or assert the snapshot invariant after every step; **class C is never injected through production code** (C4-M04); the writer-release failure is exercised only by calling `ReleaseFailed` directly.
- **Defects:** a default lease is accepted by every writer operation after open (C4-M05); T0, T-OUTCOME and T-DELETE do not report class C (C4-M04); open, create and recover bypass the gate (C4-M10). Latent (C4-O05 to O07): `End` compares ids only (not reachable except through `Dispose`); state notifications are raised outside the monitor without a sequence number, so a UI could end on a non-Faulted state after
  Faulted (relevant from C8); `Publish` raises `StatusChanged` inside `SetAsideAsync` while the gate's writer ticket is held (a handler that reads synchronously would deadlock); `_flaggedUnclean` is never set true (dead code).

## 16. A-25 interpretation (decisive)

**Frozen text (A-25 (a), §16.4):** *every method that calls a Library mutation primitive takes a `MutationLease` parameter, or is private and called only from methods of its own type that take one.* The primitives are the operations A-01, A-03, A-04 and A-06 confine to `LibraryStore.cs`/`LibraryDatabase.cs` plus `BeginTransaction`, `BEGIN IMMEDIATE`, `COMMIT` and
**any command executed on the writer connection**. It applies to **every first-party assembly** (Core, History, Library, App).

**What the implementation's audit (`IlAudit.MutationViolations`) allows instead** (`IlAudit.cs:321-345`): a method has authority if it (1) takes a lease, **or** (2) calls a lease producer (`TryBeginMutation`, `TakeStartupLease`, `HandOffToSave`), **or** (3) is an instance method of a *lease-bound type* (any type with a `MutationLease` field), and a private helper
inherits authority **transitively** through any chain of allowed private methods (the spec says "called only from methods … that take one": one hop).

**Judgement: the "lease-bound type" category is not permitted by the frozen wording**, and neither are the producer clause or the transitive chain. The evidence document's own phrasing ("member of a lease-bound type") is a reinterpretation, not terminology. Concretely, the Library has three lease-bound types:

| Type | Lease-less mutating member reachable | Safe at run time? |
|---|---|---|
| `WriterConnection` (field `_openedBy`) | `Configure(bool)` (`LibraryDatabase.cs:210`) takes **no lease**, is `internal`, and executes commands on the writer through `SetAndReadBack` (the first statement on the database, which triggers hot-journal rollback and deletion). It has no currency check of its own; only the `Require` in `OpenWriter` precedes it. It passes the audit only through clause (3). | Yes in practice: the only caller is `OpenWriter` after `Require`. |
| `SnapshotImporter.NameCache` (field `_lease`) | `Intern`, `LookUp` run INSERT/SELECT through the stored lease, which reaches `WriterStatement` methods that take it and `Guard` each statement. | Yes. |
| `WriterQueryRunner` (primary-constructor capture) | `Scalar`, `Rows` execute arbitrary constant SQL on the writer the same way. | Yes. |

**Outcome:** *static audit weaker than A-25, runtime OBS-15 safety preserved today*. This is a **High** finding, not a Blocker: no concrete unleased write exists (the runtime `Guard` rejects every stale lease before I/O, and the IL audit still confines `sqlite3_step`/`prepare` to two classes), but the rule that is supposed to make a future unleased write impossible does not,
and the audit also has these evasions or narrowings, each verified by reading `IlAudit.cs`:
- the primitive list lacks `BeginTransaction`/`SqliteTransaction.Commit` (named by the spec), `ExecuteNonQueryAsync`/`ExecuteReaderAsync`/`ExecuteScalarAsync`, `SqliteConnection.OpenAsync`, `File.OpenWrite`/`Open`/`OpenHandle`, `FileInfo`/`DirectoryInfo` operations, `StreamWriter(path)`; `calli` is not decoded;
- calls are matched by `Type::Name`: a `callvirt` through an interface (`IQueryRunner.Rows`) matches nothing, so `SnapshotVerifier.Verify(IQueryRunner …)` (static, no lease) runs commands on the writer unseen (today it runs only SELECTs);
- `ReaderConnection::*` is exempted wholesale and `LibraryDatabase::AssertEngine` runs a command on the writer connection while exempted;
- overloads are merged by name;
- part (a) runs on the Library assembly only; the check for the other assemblies is "does not reference the Library".
Genuinely sound: async state machines, lambdas and local functions fold into the host method, `ldftn` counts as a call, generic instantiations resolve by name, part (c) catches `newobj`/`initobj` of the lease types outside the interlock, and the negative self-tests do reach their rules (private helper reachable from a lease-less public method; async; lambda).
There is **no negative self-test for any of the three relaxations**, and the fixtures `LeaseBound::Create` and `ObtainsItsOwnLease::Run` are asserted as *must be accepted*. Two reviewer mutants test this directly (§20): **R-20** (a lease-less method on `WriterConnection` executing a constant command on the writer) **survives** the audit, and **R-19** (the audit reduced to the frozen wording) **fails on the real Library code and on the fixtures**, which proves the relaxations are load-bearing. (R-13, a lease-less `File.Move`, is killed, but by the separate "exactly these callers" assertion.)

**Required correction:** give `Configure` a `MutationLease` and a `Guard`; delete the lease-bound and producer clauses (or amend A-25 by a reviewed specification change, which this review does not do); one-hop private rule; dispatch-aware matching; the spec's full primitive list; negative self-tests for each; run part (a) over every first-party assembly.

## 22. PERF-01 judgement

**`PERF-01 EVIDENCE INCONCLUSIVE`.**

What the specification says: PERF-01 is "import throughput ≥ 100,000 file rows/s in key order" (§15.3, "proposed; each confirmed or revised with measured justification at its gate"). §15.4 defines the C4 benchmark (fresh process per run, warm cache, same SSD, full schema with interning, into a Library that already holds other snapshots and sources)
and a **stop condition** when PERF-01, PERF-14's engine share or PERF-15 is missed by more than 50%. §19 says C4 is done when "the engine benchmark meets PERF-01 and PERF-15". **The specification gives no aggregation statistic: not a median, not every run, no exclusion rule for noisy runs, no quiet-machine requirement.** I therefore do not silently redefine it as "median ≥ 100k".

The evidence: ten workstation runs of the P1 configuration (3×1M, 3×2M, 1×10M, three no-FK Q-07 runs): 78.2, 80.5, 95.8, 100.5, 107.0, 109.8, 114.3, 127.3, 127.5, 127.6 k rows/s: three of ten below 100k, median about 108k. The document's "median 109,768 at 2M" uses three runs and drops three same-configuration runs; its "two of six runs were below 100k (78k to 107k)" is wrong (106,971 is above 100k; one of the six is below). The
slow runs are attributed to machine load, "an inference, not a measurement" (the document says so); no CPU counters or process list were recorded; the "quiet machine" 130k/127k runs exist only in prose. Hosted runs are 6/6 above 100k (123k to 212k) but identical code differed by 1.5× between hosted runs, and a hosted runner is not the reference machine. The slow runs are within the literal §15.4 method (nothing excludes them). The >50% stop condition did not fire on these data (minimum 78k) —
that avoids a forced design review; it does not turn a sub-budget measurement into "met", and the budget row was neither confirmed nor revised as §15.3 requires.
All of these runs use names that append to the end of the dictionary indexes (§23), so even the 100k statement is for a best-case data set. In the **reviewer replay** (§23) throughput was 89.5k files/s at 1M and 82.3k at 2M with a 250k×3 prefill, and **40.8k files/s at 1M with a 1M×3 prefill: a miss of more than 50%.**

Required: state the criterion in a reviewed specification change (or the evidence), re-run on a quiet machine with load recorded and every run reported, on data that exercises the dictionary indexes.

## 23. PERF-15 judgement and the stop condition

**PERF-15 is not demonstrated, and a reviewer replay shows it missed by more than 50%.**

*What the implementation measured:* peak journal 0.19 MB at 1M, 2M and 10M, "0.142% / 0.070% / 0.014% of growth", sampled by a thread polling `FileInfo.Length` every 5 ms plus once per 16,384 rows. Spec PERF-15/IMP-09/§15.4 require the measurement on the full schema in a Library that already holds other sources **because the `name` and `folder_path` `UNIQUE` indexes modify existing pages, and those pages are journalled (G0-O03)**.

*Why the figure says nothing about that case:* the synthetic names (`SyntheticSnapshot.FileName`) are `file_<label>_<folder>_<k>` for the unique half and `common_<n>` for the rest. The measured import has label `target`; the prefill snapshots have labels `p1`–`p3`. In UTF-16 byte order `file_t…` sorts after every existing name (`common_…`, `dir…`, `file_p…`), so every new name lands past the right edge of the `name` index; new pages are not journalled
(the specification itself says appended pages are not, §11 CAN text). Folder names are `dir<i % 997>` with ascending ids, also append-shaped. 0.19 MB is about 48 pages at every scale, with and without FKs: an append-only workload.

*Reviewer replay* (scratch copy; only `FileName`'s unique branch changed to `img<hash>_<n>`, and the journal sampled through a `FileStream(FileShare.ReadWrite|Delete)` every 1 ms; prefill labels and target both hash-distributed so they interleave; machine otherwise idle):

| Run | Library before | Snapshot growth | Peak journal | Journal / growth | Files/s | Notes |
|---|---:|---:|---:|---:|---:|---|
| Control: original names, new sampler, 1M target, 3×250k prefill | 98.2 MB | 140.0 MB | 0.19 MB (198,176 B) | 0.14% | 101,397 | the new sampler reproduces the implementation's figure: the sampler is not the cause |
| Interleaved names, 1M target, 3×250k prefill | 103.7 MB | 137.3 MB | **23.4 MB** (23,402,536 B) | **17.0%** | 89,509 | limit 5% → missed by 3.4× |
| Interleaved names, 2M target, 3×250k prefill | 103.7 MB | 278.3 MB | **23.4 MB** (23,402,432 B) | **8.4%** | 82,284 | limit 5% → missed by 1.7× |
| Interleaved names, 1M target, 3×1M prefill (larger Library) | 411.6 MB | 130.9 MB | **92.9 MB** (92,932,104 B) | **71%** | **40,788** | PERF-01 missed by 59%; PERF-15 by 14× |

The journal is bounded by the pre-existing dictionary pages that get touched, so it scales with the Library's size, not with the snapshot's: it is a small fraction only for a snapshot much larger than the Library. A first snapshot of a new source with unfamiliar file names into an established Library is exactly the case that makes it large, and that is the case G0-O03 asked C4 to measure.
The 10M replay was not run; the bound suggests about 23 MB (1.6%) for the 250k prefill. The replay's data are synthetic and chosen to interleave; real names will share more with existing names (fewer new names, smaller journal) but a new source's names are not append-shaped either.

*Conclusion:* the C4 acceptance statement "meets PERF-15" is not supported; the §15.4 benchmark as the specification words it, run on a data set that exercises the dictionary indexes, misses PERF-15 by more than 50% in three of three interleaved runs and PERF-01 by more than 50% in the larger Library. That is the C4 stop condition: "C4 stops and §11.8 is amended by review". Whether the
answer is revised budgets (§15.3 allows "confirmed or revised with measured justification"), a relative budget, or the prepared staging alternative is a design decision that this review does not take. **Journal measurement method:** `FileInfo.Length` reads directory-entry metadata, which NTFS may not keep current for open files (the authors saw exactly that staleness on the main database: 186.6 MB after rollback in
the first hosted run versus 37.8 MB through a handle; the specification treats listing sizes as unreliable, OBS-04c); a TRUNCATE journal only grows within a transaction, so sampling interval cannot miss a *spike*, the risk is lag. The replay used a handle.

Peak working set (`Process.PeakWorkingSet64`, process-lifetime, baseline `WorkingSet64` after a forced collection) is +120/+138/+319 MB workstation, +101/+125/+312 MB hosted at 1M/2M/10M; PERF-11b (300 MB at 2M) is not breached. Deletion of the 2M snapshot: 2.4–2.6 s workstation, 3.3–3.9 s hosted, peak journal 128 MB (about the size of the snapshot's `file_obs`), against PERF-10 (≤ 10 s, confirmed later);
measured on the just-imported tail snapshot in a warm session, a best case. PERF-14's engine share is met (≤ 25.6 s workstation, ≤ 14.4 s hosted, limit 60 s). **PERF-03 (≤ 90 B per file observation) is 140–145 B per file in every run**, unreported against the budget in the document (C4-O09); it is confirmed at C5 and not a C4 stop condition.

**C4-B01: PERF-15 (and PERF-01 at scale) not measured on the case G0-O03 names; the replay trips the §15.4 stop condition.**
