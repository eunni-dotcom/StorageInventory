## 4. The six native calls and the zero-access handle

| # | Function | Called on | Used for |
|---|---|---|---|
| 1 | `CreateFileW` | the enumerated path (extended form) | the directory handle: desired access **0**, share read, write and delete, backup semantics, `OPEN_EXISTING` |
| 2 | `GetFinalPathNameByHandleW` | the handle | the canonical path of the opened object |
| 3 | `GetVolumeInformationByHandleW` | the handle | filesystem name, 32-bit serial, label, flags |
| 4 | `GetFileInformationByHandleEx`, class `FileIdInfo` (18) only | the handle | 64-bit serial and the 128-bit root directory file ID |
| 5 | `GetVolumePathNameW` | the canonical path | the mount point (display) |
| 6 | `GetDiskFreeSpaceExW` | the mount point | capacity and free bytes (display, and Moderate corroboration) |

Nothing else is native: no write-capable function, no other DLL, no COM, WMI, registry probing, process or PowerShell
fallback, or name-resolution API.

**Zero access, measured.** `CreateFileW` adds `SYNCHRONIZE` and `FILE_READ_ATTRIBUTES` to a desired access of 0. The access mask
a handle opened that way was actually granted was read back with `NtQueryInformationFile` (`FileAccessInformation`), in test
tooling that is not product code (`tests/identity/Invoke-IdentityExperiments.ps1`, part 1b):

| Handle opened with | Granted access mask | Meaning |
|---|---|---|
| desired access 0 (**the product**) | `0x00100080` | `SYNCHRONIZE` and `FILE_READ_ATTRIBUTES`: no list, read, write or delete right |
| `FILE_READ_ATTRIBUTES` | `0x00100080` | the same: asking for it adds nothing |
| `GENERIC_READ` (for contrast) | `0x00120089` | adds `READ_CONTROL`, `FILE_LIST_DIRECTORY` and `FILE_READ_EA` |

The mask was identical on every volume the experiments probed (section 9). The first reading of it was made earlier with a
throwaway script on the development machine's system drive (`0x00100080` against `0x00120089`); the committed script
reproduces it per volume, and `SourceIdentityTests.TEST_I1_the_handle_the_product_opens_is_granted_no_list_read_write_or_delete_right`
asserts it in the suite (on every machine the suite runs on), through the handle the product's own open function returns,
with a `GENERIC_READ` contrast handle so the probe is known to see rights when they exist.

**The audit (A-08, TEST-A1).** `The_only_native_calls_are_six_read_only_kernel32_functions` reflects over Core, History
and the App and requires exactly the six functions above, all in `kernel32.dll`, all declared in `NativeMethods`; no
`[DllImport]`, `[LibraryImport]` or `extern` anywhere else in `src`; exactly one `CreateFile` call site, passing the literal
0; exactly one `GetFileInformationByHandleEx` call site, passing `FileInfoByHandleClass.FileIdInfo`, whose enum has that
single member (`= 18`) and whose name may appear in exactly three kinds of place (its declaration, the P/Invoke's
parameter, the `.FileIdInfo` argument), which also rejects a cast, `default(...)`, `Enum.ToObject` and `Unsafe.As`.
(Every information class is a read-only query; the claim is about the reviewed surface being exactly one, not about
safety.) `Native_functions_cannot_be_bound_any_other_way` forbids `NativeLibrary`, `GetProcAddress`, `LoadLibrary`,
function pointers and similar. **Negative self-tests (A-21):** `The_native_rules_reject_violating_fixtures` runs the real
reflection rule over fixture types that declare a seventh kernel32 function that can write (`DeleteFileW`) and a function
from another DLL (`MessageBoxW`), and the text rules over snippets with a wrong desired access, another information
class, a cast, `default`, `Enum.ToObject`, `Unsafe.As` and a second enum member: each is rejected, a removed function is
noticed, and the permitted shapes are accepted.

## 5. The evidence model

`VolumeEvidence` (internal, `Core/Identity`) holds one reading: the kind (local or network, from the resolved canonical
path), the canonical path, filesystem name, flags, 32-bit serial, 64-bit serial, root directory `FILE_ID_128`, label, mount
point, capacity and free bytes, and whether the handle opened. Each item is an `EvidenceItem<T>` whose status is one of:

| Status | Meaning | Example measured |
|---|---|---|
| Available | the value was obtained | `NTFS` |
| Unavailable | nothing was attempted or reported (for example the handle could not be opened) | every item of a missing folder |
| CallFailed | the call ran and Windows returned an error, kept as `Win32Error` | `GetFinalPathNameByHandleW` Win32 59 on a forcibly disconnected mapped drive |
| NotProvided | the source type answered that it does not implement the query (Win32 1, 50, 87, 120 or 124) | `FileIdInfo` Win32 87 on FAT32, exFAT and UDF |

The default item is *Unavailable*, so an item nobody filled in is never mistaken for a value. The distinction between the
last three only changes the explanation: no decision treats them differently (section 15, item 8). Label, capacity and free
space are recorded and never compared (ID-13). The drive letter plays no part: the source kind comes from where Windows
says the opened object is, so a mapped letter whose canonical path is `\\server\share` is a network source and a SUBST
letter is the local folder it points to.

## 7. The E0 to E3 lifecycle

```
 E0  PreflightEvidence.Collect(path)   open the ENUMERATED path, read, close                       (P0)
 E1  RootIdentityHold.Open(path)       open the ENUMERATED path, read, KEEP the handle              (P2, before enumeration)
     ... the scan runs; the handle stays open ...
 E2  hold.Finish()  step 1             read through the SAME held handle                            (P4)
 E3  hold.Finish()  step 2             open the ENUMERATED path AGAIN, read, close that handle      (P4)
     hold.Finish()  step 3             close the held handle        (Dispose does the same on cancel, failure or exception)
 Reverification.Evaluate(E0, E1, E2, E3)  ->  Verified | SaveUnavailable | IdentityChangedDuringScan
```

The required items are exactly ID-13's: the canonical path (every source); for a local volume the filesystem name and 32-bit
serial (without them, at E0, the result is *SaveUnavailable*, with the failure kept, and nothing is compared); the 64-bit
serial and the root directory ID when `FileIdInfo` succeeded at E0; for a network source the filesystem name and serial when
the provider returned them at E0. Each must be obtained, and equal by UTF-16 code units, at E1, E2 and E3. Label, capacity,
free space, flags and the mount point are never compared. The four readings must have been taken on the same enumerated
path or `Evaluate` refuses them: that is exactly the mistake ID-10 forbids (opening the canonical path), made impossible to
make quietly.

What each reading detected, by scenario. "Unit" means the fake provider, "integration" a real folder or SUBST letter in the
test suite, "experiment" a real run of the committed experiments (sections 9 and 11). The actual behaviour was recorded, not
assumed.

| Scenario | E2, through the held handle | E3, fresh open of the enumerated path | Outcome | Evidence |
|---|---|---|---|---|
| Nothing changes | equal | equal | Verified | unit, integration, every probe |
| SUBST letter re-pointed to another folder | still the original folder | the new folder | **NotEligible, caught by E3** | unit, integration, experiment (local and hosted) |
| SUBST letter re-pointed away and back | equal | equal | Verified: **L-ID2**, as documented | unit, integration, experiment |
| Source folder renamed | the new canonical name | cannot open (Win32 2) | NotEligible | unit, integration, experiment |
| Source folder renamed away, another folder given its name, and left like that | the original's new name (every filesystem) | the other folder under the same name: the same canonical path, a different root file ID where the filesystem provides one | NotEligible (E2; E3 too on NTFS and ReFS) | unit (an NTFS and a FAT32 variant), integration |
| The same, and everything put back before the window closes | the original's name again | the original again | Verified: **L-ID2 as extended by G0F-O05**, as documented | unit, integration |
| Renamed in letter case only | the new spelling | the new spelling | NotEligible (the path is compared exactly) | unit, integration |
| Source folder deleted | a `$Extend\$Deleted\…` name | cannot open | NotEligible | unit, integration, experiment |
| Virtual disk detached (a stick pulled) | Win32 21, device not ready | cannot open (Win32 3) | NotEligible | unit, hosted experiment |
| Another volume at the same letter | Win32 21 | another serial pair | NotEligible | unit, hosted experiment |
| Disc image dismounted with `Dismount-DiskImage` (no volume lock; not what Eject does on a physical disc) | Win32 21 | cannot open (Win32 3) | NotEligible | hosted experiment |
| Mapped drive forcibly re-pointed to another share | Win32 59 on every item | the other share and its serials | NotEligible | unit, experiment (local and hosted) |
| Mapped drive: a normal disconnect, declined | equal | equal | Verified | experiment (local and hosted) |
| Share's backing folder renamed on the server's own filesystem (loopback; not another client) | the new canonical name | cannot open | NotEligible | experiment (local and hosted) |
| A required item missing at E0 | not compared | not compared | **SaveUnavailable**, with the reason | unit, integration |

An invalid handle, a failed required call or any difference makes the capture not eligible, and no scenario above needed a
watcher or polling. The undone-before-the-end cases are left exactly as the specification documents them: **L-ID2**,
which the specification's own acceptance check (G0F-O05, assigned to C3) says must name the source folder replaced and
restored as well as a letter re-pointed away and back. C3 states both in the architecture and security documents and
asserts both with tests; the identity help text itself is a later gate's (TEST-U1), and §19 proposes the wording.

1. `CreateFileW` at access 0, `GetFinalPathNameByHandleW`, `GetVolumeInformationByHandleW`, `GetVolumePathNameW` and

2. `FileIdInfo` is **provided** on NTFS and ReFS (also when the share is served from NTFS) and **not provided** (Win32 87,

## 15. Judgement calls for the reviewer

Places where the specification is silent or open to two readings, and what C3 chose. Each is easy to change if the review
disagrees.

1. **"Any evidence call failed" means a call whose value the applicable rule needs** (ID-01, PathOnly). Strong needs the
   filesystem name and the 64-bit serial; Moderate the filesystem name and the 32-bit serial. A failure of an informational
   item (label, capacity, free space, flags, mount point, root file ID) does not lower the level. The other reading, "any
   call at all", would make Moderate unreachable on every FAT volume (measured: `FileIdInfo` is not provided there) and
   would give an NTFS volume a new source each time a capacity query failed once. A Moderate volume whose label or capacity
   is unknown simply cannot be corroborated, which the matcher answers by asking.
2. **The basis of a new local PathOnly source is `Location`.** The specification fixes the basis of an explicit user pick
   (`UserAsserted`) and of a network source (`Location`) but not of a new source with no evidence at all. `Location` is the
   only accepted basis that says "all we know is where it was seen"; `UserAsserted` is reserved for an actual answer.
3. **Which existing sources a PathOnly local capture may be explicitly attached to:** local sources with the same root
   (exactly, or apart from letter case) on a volume of the same filesystem. Serial, label and capacity are not consulted: that
   would be inventing a heuristic where the specification asks for the user.
4. **ID-05's "two currently mounted volumes" is an input, not a probe.** The matcher takes an optional list of the *other*
   mounted volumes and never reads a drive itself; building that list is a later gate's job, on demand (ID-07, D-32). The
   specification's test (TEST-I3) lists "co-mounted clones (ask)" as a matching case, so the seam exists now.
5. **Moderate corroboration details.** Labels are compared exactly (UTF-16 ordinal); capacity within ±1% of the *recorded*
   capacity, inclusive, in exact integer arithmetic, with both values known and positive; no volume with the same
   filesystem and 32-bit serial means a new volume (nothing to ask about), whereas candidates that fail corroboration, or two
   that satisfy it, mean ask.
6. **The case-variant suggestion also applies to the path inside a network share** (§7.5 step 5 is stated for any source).
7. **The comparison key is a seam.** `IComparisonKey` is injected; History contains no case folding or normalisation. The
   tests use a stand-in that folds ASCII only (`AsciiFoldKey`), which is not NAME-03's key and is labelled so. C7 supplies the
   real one.
8. **`NotProvided` is classified from the Win32 error** (1, 50, 87, 120, 124), measured for 87 on FAT32, exFAT and UDF. The
   raw error is always kept, and every non-available status is treated alike by every decision, so the classification can
   only change an explanation.
9. **One conservative addition to ID-13:** a canonical path that is neither a drive-letter nor a UNC path cannot be split into
   a root inside a volume or share, so no source key can be formed, and it counts as missing evidence. Normal sources never
   hit it.
10. **A zero serial counts as *obtained* for ID-13's minimum evidence** (equality of four zeros is still checked) and costs
    the source its confidence instead (PathOnly, and a zero serial is never matched on).
11. **`Reverification.Evaluate` refuses readings taken on different enumerated paths** (an `ArgumentException`), and readings
    given under the wrong stage. It is a programming-error check that turns "opened the canonical path by mistake" into a
    failure at the first test.
12. **A case-only rename of the source folder is a rename** (not eligible): the canonical path is compared exactly (ID-02).
13. **Everything in History is internal**, shared only with History.Tests and the integration tests. Making it public is a
    later gate's decision (a stop condition here).
14. **The kind fallback.** When Windows cannot report a canonical path (so the source cannot be saved anyway) the kind falls
    back to v1's own `PathPolicy.IsNetworkPath` (a UNC path or a mapped network drive).
15. **The root inside the volume is derived from the canonical path's shape**, not from `GetVolumePathNameW`. A drive-letter
    path always has the root `X:\`; a UNC path's share is its first two components. `GetVolumePathNameW` is still called and
    recorded as the mount point (observed location), and never decides identity.
16. **A temporary evidence branch was pushed** to obtain Windows evidence (the C2 precedent). The implementation branch is
    pushed only after the evidence is complete.
17. **The specification's §21 rows for Q-02, Q-13 and Q-19 are updated, and nothing else in it.** §19 C3's Docs bullet says
    "§21 updated with the Q-02, Q-13 and Q-19 results", and the brief allows either that or a separate evidence document where
    repository policy prefers one; no policy against it exists (C1 and C2 had no scheduled §21 question, so they set no
    precedent either way), so the specification's own instruction was followed, restricted to the status and evidence cells
    of those three rows (three lines; no normative text; no question promoted to RESOLVED where evidence is missing: Q-02 and
    Q-19 read PARTIALLY ANSWERED with the unmeasured parts named, Q-13 reads ANSWERED with the Dev Drive substitution
    stated). It is one commit that the owner can drop, and section 19 carries the same wording. Q-10 is left as it is.
18. **The published executable's hash changes** (Core gained code that nothing calls yet): section 13.
19. **The mounted-volumes input of the matcher is required and carries mount points.** ID-05 asks about *two volumes*, and a
    SUBST letter or a second drive-list entry for the captured volume is one volume under two names. Each entry carries its
    mount point, read the way the capture's was (so every name of one volume reports the same one), and the matcher drops the
    entries that report the capture's own; an entry whose mount point is unknown is kept, which can only cost an extra
    question. The parameter has no default, so clone protection cannot be left off by omission.
20. **With no saved volume there is nothing to ask about.** §7.5 step 2 says "None: a new volume", and ID-04's prompt asks
    about a last-seen drive that does not exist yet, so the first of two never-saved clones becomes a new volume and the
    second, scanned while the first is still mounted, finds its row and asks. A reviewer who reads ID-05's "asks" as applying
    from the first scan can change `OnMatchedVolume` in one place; the outcome would only gain a question.
21. **A network capture is never "weaker than" its source.** Network captures and network sources are always PathOnly, and
    the location is the identity, so ID-12's weaker-evidence question is local only; the branch that would have built a second
    source with the same share and root (which the schema's unique key forbids) was unreachable and is removed.
22. **ID-06's "Treat as a new source is always available"** is read as: every prompt carries it (`IfDifferent`), and for a
    capture the matcher settled automatically `TreatAsNewSource` returns the same decision for a local capture (a new volume
    and source), and null for a network share (its identity is its location, so a second source with the same key cannot
    exist) and for an unsaveable source: there the alternative is not to save.
23. **L-ID2 is extended to the source folder** (G0F-O05, assigned to C3 by the specification's own acceptance check): a source
    folder renamed away, replaced and restored is as undetectable as a letter re-pointed away and back. The wording is in
    `docs/architecture.md` and `docs/native-security-review.md`, both cases are pinned by tests (unit and real folders), and the
    user-facing identity help text belongs to the UI gate (TEST-U1).
24. **One derivation of "local or network".** `VolumeEvidence.ResolvedKind` (the canonical path's shape, falling back to the
    reading's own kind only when there is no canonical path) is used by ID-13's minimum evidence, ID-01's confidence and
    ID-10's comparison, which had derived it in two ways.

## 16. Known limitations and open items

1. **No physical removable media, no Samba server, no remote Windows server.** The removal experiments used virtual disks
   and a mounted image; SMB was a Windows server on the same machine (loopback), reached by UNC and by a mapped letter.
   The specification's USB "Safely Remove" experiment (Q-19) and the Samba and mapped-drive-to-another-machine cases (Q-02)
   are open manual acceptance evidence; the exact steps are in `tests/identity/README.md`. The refused volume lock that
   was measured is the mechanism "Safely remove" begins with, but the dialog itself was not observed.
2. **No ReFS Dev Drive.** The ReFS volume was a standard ReFS format on a VHDX (a Dev Drive needs a Windows 11 development
   machine and elevation). Its root directory ID is recorded (section 10), so Q-13 is answered for ReFS, but a Dev Drive is
   not claimed.
3. **Windows 10 was not tested.** Evidence is from Windows 11 Pro 10.0.26200 (non-elevated) and Windows Server 2025
   10.0.26100 (a hosted runner, elevated). Third-party antivirus, indexers and backup tools were not exercised beyond what
   those images run.
4. **A held handle was only held for seconds** (a scan of a small tree, an experiment's action). Behaviour over a scan of
   hours, with the volume under real load, was not measured.
5. **The mapped drive of a remote server was not measured**; the loopback SMB stack is the same code but a different
   topology. A DFS namespace (whose canonical target can change) and a NAS were not measured.
6. **Per-user disk quotas** change what `GetDiskFreeSpaceExW` reports as capacity. Quotas are an NTFS feature and Moderate
   matching concerns FAT-family volumes, so the effect is not expected, but it was not measured; a difference would make
   the matcher ask, not merge.
7. **A volume with no drive letter** (or a mount-point-only volume) has no canonical DOS path, so it cannot be a source
   (`PathPolicy` already blocks sources through a mount folder). Not exercised.
8. **L-ID1 and L-ID2** are limitations of the design, asserted by tests exactly as the specification states them, and not
   mitigated. L-ID2 covers both a letter re-pointed away and back and, per G0F-O05, a source folder renamed away, replaced
   and restored (section 7); a replacement left in place is detected. The user-facing identity help text is the UI gate's
   (TEST-U1); section 19 proposes its wording.
9. **A Windows SMB server reports the underlying volume's identity** (including for a share on FAT32): the evidence is
   recorded but never used to match a network source, and never makes it Strong.
10. **The in-memory store is not the Library.** It models the two tables the matcher reads and the identity step of an
    import; locking, persistence, the real comparison key and the real `volume`/`source` rows arrive with C4, C5 and C7.
11. **C3 is not wired into a scan.** Nothing calls the hold in v1's scan path (that is C5), so there is no identity work in
    any scan today, and no performance cost to measure.
