## 4. Shell architecture

```
App.OnStartup ── new ScanSession() ─────────────────────────────── app lifetime (UI-12)
      │                     ▲ owns: scanner, scan task, cancellation, clock,
      │                     │       Progress (ScanProgressViewModel), Stage, Results (ResultsViewModel)
      └─ new MainWindow(session)  ← the shell
           DataContext = MainViewModel(session)          (v1's contract: tests and automation reach the scan here)
           ShellRoot.DataContext = ShellViewModel([ShellPage("Scan", MainViewModel)])
           ┌──────────────┬───────────────────────────────────────────────┐
           │ ListBox      │ ContentControl PageHost                       │
           │ "Pages"      │   Content = Current.ViewModel                 │
           │  • Scan      │   DataTemplate MainViewModel → ScanPage       │
           │ (200 px)     │     ScrollViewer › Grid (v1's page)           │
           │              │       header · SetupView | ScanProgressView | │
           │              │                ResultsView                    │
           └──────────────┴───────────────────────────────────────────────┘
```

- **One view per page, one view model per page, a small navigation model (UI-01).** `ShellViewModel` holds the pages
  and the page shown; the page host shows a page's view model through its view (an implicit `DataTemplate`), so a page
  is a view model plus a template and nothing in the shell knows the scan. In C2 the list has one entry, Scan.
- **The window's `DataContext` stays the scan's view model.** v1's UI tests (unchanged, TEST-B1) cast
  `MainWindow.DataContext` to `MainViewModel`; so does any automation that relied on it. The shell's own chrome binds
  to `ShellViewModel`, which is set on the shell's root *before* the window's `DataContext`, so the shell's bindings
  never see the page's view model (no transient binding error).
- **The page keeps v1's size.** The navigation column is a fixed 200 pixels and the window's default and minimum widths
  grow by exactly 200 (1080 and 760), so the page region is v1's 880 × 820 window client area. 200 is a multiple of 8,
  so the column edge is a whole device pixel at 100 %, 125 %, 150 %, 175 % and 200 % scaling.
- **No access key on the page names**, so v1's access keys (including its two uses of S) behave as before.
- **A page is always shown**: `ShellViewModel` refuses to show no page, so clearing the list's selection (Ctrl+click,
  Ctrl+Space) leaves the Scan page in place (tested on the view model, §12).
- **No UI package** (A-11): WPF only.

## 6. ScanSession: ownership and lifetime

**What moved.** Everything v1 kept in `MainViewModel.Scanning.cs` to run a scan: the scanner, the scan task, its
`CancellationTokenSource`, the stopwatch and the one-second `DispatcherTimer`, the `ScanProgressViewModel`, the
`ResultsViewModel` (with its exploration load), and the stage (Setup, Scanning, Results). A line-by-line diff of v1's
`StartScan`/`RunScanAsync`/`CancelScan`/`NewScan` against the session's `Start`/`RunScanAsync`/`Cancel`/`Clear` shows
only these differences:

| v1 | C2 | Effect |
|---|---|---|
| `StartScan()` read the inputs and `Preflight.CanScan` itself | `MainViewModel.StartScan` still checks `Preflight.CanScan \|\| IsBusy` and builds the same options; `ScanSession.Start(options, createWorkbook)` | None |
| `if (… IsBusy) return;` | `if (IsBusy) return false;` | None; a refused start is now reported to the caller |
| `NewScan()`: `Results = null; Stage = Setup; ScheduleValidation();` | `Clear()` does the first two, unless a scan is running; `MainViewModel.NewScan` then calls `ScheduleValidation()` | None in any reachable v1 path: New scan is enabled only in Results, when no scan runs |

Change notification is unchanged: the session raises `Stage` and `Results`, and `MainViewModel` re-raises them under
v1's names (`Stage`, `IsSetup`, `IsScanning`, `IsResults`, `Results`) in v1's order, followed by v1's
`CommandManager.InvalidateRequerySuggested()`.

**Lifetime.** `App.OnStartup` creates one `ScanSession` before the shell and hands it to `MainWindow(session)`; the
session is never created by a view, a page or a page view model. A `MainWindow()` built on its own (v1's UI tests do
this; so would a designer) creates its own session: each such window is the shell of its own app session, so each v1
test window still starts fresh. `MainViewModel` subscribes to the session through WPF's `PropertyChangedEventManager`
(a weak event), so the app-lifetime session never keeps a page view model or a view alive.

**What the C2 session does not yet own** (later gates, not invented here): the save token and the save outcome
(CAN-02, C5), the class C boundary (CAT-04), the `ObservationLease`/Prepare lease and the refusal before the start-up
open or in Faulted (OBS-07 to OBS-15, C4/C5), and `InventoryRun` (A-25). `LibrarySession`, `ICatalogue`,
`ICompareService` and `ISourceStatus` do not exist. §14.2's table still describes the final `ScanSession`; C2 builds
the part v1's flow needs and the app-lifetime boundary the rest will join.

**Proved by tests** (all on Windows CI; §12): the window, the page, every stage view and the page view model share one
session; stage changes recreate no view and no session; the page's view can be taken away during a scan and the scan
neither stops nor restarts (one call to Core), and a new view shows the same progress and then the same scan's result;
closing another window that hosts the page leaves the scan running; a second start is refused; after the shell closes,
the session (still referenced) and the page view model do not keep the replaced view alive.

## 8. TEST-U4: screenshots

**Reference.** `tests/StorageInventory.IntegrationTests/V1Baseline/MainWindow.v1.xaml` is v1's `MainWindow.xaml` from
the frozen base, byte for byte: `ShellParityTests.The_v1_reference_is_v1s_MainWindow_xaml_byte_for_byte` computes its
git object id and requires `d29fd70170a137dafb1981b8a24c3cbfccfd377d`, which is
`git rev-parse bf3fa36:src/StorageInventory.App/MainWindow.xaml`. The test loads it as loose XAML with two mechanical
edits that never reach the visual tree (drop `x:Class`; name the assembly of the `vm:` namespace) and does what v1's
constructor did that affects what is shown (the view model as `DataContext`, focus on the source box when loaded).
Nothing in the C2 tree was regenerated or accepted as a new "golden" image: the authority is v1's own markup, rendered
live next to the shell.

**Method.** For each theme (Light, Dark), the shell and v1's window are created together, both over **one**
`MainViewModel` (so both show the same data at the same moment), before the first scan (so even the animated
indeterminate progress bar starts in the same layout pass in both). A test scanner holds the real scan at a gate when
a frame needs a running scan. The synthetic tree is the docs screenshot's layout (seven folders, 931 files, no real
names), built under the test fixture's folder and removed with it. Eight frames cover the three stages:

| Frame | State |
|---|---|
| `setup-initial` | Nothing chosen (NOT READY) |
| `setup-blocked` | Reports inside the source (BLOCKED, with the reason and its expander) |
| `setup-ready` | A valid pair (READY TO SCAN, with the "will be created" note) |
| `scanning` | Enumerating: indeterminate bar, counters, current folder |
| `scanning-writing` | Writing the Files report: determinate bar |
| `scanning-stopping` | After Cancel: "Stopping safely…", Cancel disabled |
| `results-cancelled` | SCAN CANCELLED with the incomplete files listed |
| `results-complete` | SCAN COMPLETE with the report actions and the loaded results tabs |

Each frame is rendered in one dispatcher operation for both windows (the elapsed-time clock cannot tick in between),
twice: (1) **the masked window diff**: the shell's whole client area is rendered, the content region is located from
the page host's position (it must start at x = 200, y = 0 and be exactly as large as v1's whole client area), cropped,
and compared with v1's client area; (2) **the whole page**: the Scan page's scrollable page and v1's page are rendered
in full (not just the visible part) and compared. Comparison is exact (every channel of every pixel). Differences
outside the mask are by construction the shell chrome (the navigation column); there is nothing to compare them with.

**Keyboard focus.** Only one element per process holds keyboard focus. With two windows, a caret and the Fluent text
box's clear button appeared in one window only (the first Windows run found this: 20 to 189 differing pixels in the
Setup frames, all at the source box). Frames are therefore rendered with keyboard focus cleared in both windows; each
Setup frame is then compared again with each window's own source box holding keyboard focus while that window is
rendered (`-focused`), which is how the app starts. Both windows are also checked to give logical focus to the source
box when they load.

**Window size on the CI screen.** Windows limits a window to the screen; the runner's screen allows 1044 pixels, less
than the shell's 1080. Both windows are then shrunk by the same amount (v1's to 844, the shell's to 1044), which keeps
the content regions equal (828 × 749). The default sizes are checked separately on unshown windows
(`The_shell_window_is_v1s_window_plus_the_navigation_column`: 880 + 200, 560 + 200, the same height, title, automation
name and start-up position).

**Results** (CI run [36890700671](https://github.com/eunni-dotcom/StorageInventory/actions/runs/36890700671) on
`f1db346`; the same in evidence run 1 on `ca7d3f5`):

| Theme | Frames | Content region (masked window diff) | Whole page |
|---|---|---|---|
| Light | 8 + 3 focused | **0** differing pixels in all 11 (828 × 749 each) | **0** differing pixels in all 11 (828 × 749 to 828 × 1092) |
| Dark | 8 + 3 focused | **0** differing pixels in all 11 | **0** differing pixels in all 11 |

**Negative control.** The same comparison with one word changed in v1's Setup markup only ("Reports are always new
files." → "…new file.") finds **1,285** differing pixels in both the window and the page diff
(`TEST_U4_the_masked_comparison_notices_a_one_word_change_in_the_page`). Further preconditions checked in every pass:
the same window style object, font family, font size and foreground at the page root in both windows.

The PNGs (v1, shell with chrome, and a diff image whenever a frame differs) are written to the test work folder, or to
`SI_SCREENSHOTS\test-u4`; evidence run 1 uploaded them as the artifact `screenshots-1` of run
[36891303309](https://github.com/eunni-dotcom/StorageInventory/actions/runs/36891303309) (30-day retention).

## 9. Binding diagnostics

`BindingErrorRecorder` attaches to `PresentationTraceSources.DataBindingSource` at Warning level after
`PresentationTraceSources.Refresh()` (WPF traces bindings only after a refresh or under a debugger).

- **The channel is live:** `The_binding_diagnostics_are_live` creates a deliberately broken binding and requires the
  recorder to see it (it does).
- **No new binding error:** `The_shell_adds_no_binding_error_to_v1s` drives v1's window alone through all eight frames,
  then the shell alone through all eight frames plus a re-host of the Scan page view, and requires every message the
  shell produces to be one v1 also produced (hash codes normalised). Result on every run: **v1's window 0 distinct
  messages, the shell 0, none new.**

Nothing suppresses or filters binding errors in the product.

## 10. Accessibility, keyboard, theme and DPI

**UI Automation.** The four views return a peer (`ViewAutomationPeer`) that takes no part in the control and content
views, so a screen reader or UI Automation client sees the page's controls exactly where v1's single window had them;
WPF's default `UserControl` peer would wrap the page and each stage in an unnamed "custom" element.
`Every_frame_has_v1s_accessibility_tree_and_tab_order_inside_the_page` walks UI Automation's control view of both
windows at every frame (control type, name, automation id, help text, live setting, enabled, keyboard-focusable,
access key, labelled-by) and requires the shell's tree, minus the navigation list, to equal v1's line for line, and the
navigation list (a List "Pages" with a ListItem "Scan") to be present. It holds at all eight frames (24 to 53 elements
per frame). The same comparison, out of process on the published exe, is in the evidence run's UI Automation dump: the
C2 control view equals base's except the three navigation lines; with WPF's default peers it does not (the page is
re-nested under extra custom nodes).

**Keyboard.** The same test walks the Tab order as the Tab key does (`MoveFocus(Next)` from the window's first stop
until focus comes back round) and requires the shell's order without the navigation list's stop to equal v1's, and
that the navigation list is a stop (0 to 41 stops per frame inside the page; 0 while stopping, when Cancel is
disabled). Initial focus is still the source box; the one new stop, the page list, comes before the page, so Shift+Tab
from the source box now reaches it. No access key was added.

**Live regions, labels, word + icon + colour.** All inside v1's unchanged markup and covered by the tree comparison
(live settings, names, help texts, labelled-by, access keys) and by the pixel comparison (icons, colours).

**Theme.** `ThemeMode="System"` is unchanged in `App.xaml`. TEST-U4 passes in Light and in Dark. The navigation column
uses the theme's own brushes and the Fluent list style.

**DPI.** The manifest (`PerMonitorV2`, `asInvoker`, long paths) is unchanged. The navigation column is 200 DIPs, a whole
device pixel at the common scaling factors (§4). The UI tests ran at the runner's 96 DPI only (§19).

**Not done here (C8):** chart data tables and virtualised diff tabs (UI-09's v1.1 additions) belong to the pages that
need them.

## 11. Closing behaviour

v1's flow, unchanged, now asks the session: if a scan (or its workbook step) is running, closing asks "Stop the scan?";
Yes cancels through Core and the window waits until Core has closed every report file, then closes; No keeps the scan
running; a second close while waiting asks nothing more. Covered by v1's `UiScanTests` (run with the trees, §13) and by
`ShellTests.Closing_the_shell_during_a_scan_stops_it_through_the_session_and_waits` and
`Declining_to_close_the_shell_keeps_the_session_scanning`, which run on every CI build because the gate holds the scan
open without a large tree. No Save-to-History, deletion, open or Faulted close states were added (§14.3 and C4 to C8).

## 18. Judgement calls for the reviewer

1. **The window's `DataContext` is still `MainViewModel`.** TEST-B1 requires v1's UI tests to pass unchanged at C2 and
   every later gate, and they read `(MainViewModel)window.DataContext`. The shell's chrome therefore has its own
   `DataContext` (`ShellViewModel`) on the shell's root. C8 will need to keep that contract or keep v1's tests passing
   another way.
2. **`MainWindow()` without a session creates one.** Only `App.OnStartup` creates the app's session; the parameterless
   constructor exists because v1's tests construct the window directly and expect a fresh app each time.
3. **The window is 200 pixels wider (1080, minimum 760)** so the page keeps v1's exact size. On a screen narrower than
   about 1100 pixels Windows limits the window, and the page is narrower than v1's by the difference (36 pixels on the
   CI runner's 1024-pixel screen), reflowing as v1's page would at that width. The alternative, v1's 880-pixel window,
   would make the page 200 pixels narrower on every screen.
4. **`ViewAutomationPeer`.** Without it, every view adds an unnamed custom element to the accessibility tree. With it,
   the tree is v1's (in process and out of process, §10). It is the only product code added purely for accessibility
   preservation.
5. **UI-02's "Scanning…" label in the navigation list is left to C8.** UI-02 is a C2 prerequisite, but the label tells
   a user on another page that a scan runs; with one page the user is always on the Scan page, and the brief excludes
   C8's navigation-during-scan behaviour. C2 delivers UI-02's other half: the scan survives re-hosting of its view.
6. **The temporary evidence branch** carries a workflow file in `.github/workflows`; it runs only on pushes to that
   branch and is not part of C2.
7. **`ScanSession` owns two v1 view models** (`ScanProgressViewModel`, `ResultsViewModel`) because §14.2 makes it own the
   progress and the result and §14.6 requires the existing view models; moving them unchanged keeps the exploration
   load and the report actions exactly v1's.

## 19. Known limitations and open items

1. **One smoke-test failure in 24 C2 runs, cause not established** (§14). It did not recur in 23 later runs (two in
   the failing run's exact conditions) or in 450 targeted UI Automation probes. The reviewer should run the smoke test
   locally on Windows as well (about 10 minutes, `docs/release.md`).
2. **The README screenshot** (`docs/images/results.png`) still shows v1's window without the navigation column. Its
   content region is identical to C2's (TEST-U4); regenerating it needs a Windows desktop. `--docs-screenshots` now
   renders the shell's visible client area rather than v1's whole page.
3. **DPI.** The UI tests and the smoke test ran at 96 DPI only. PerMonitorV2 is unchanged and the column edge is
   pixel-aligned at common scales, but no rendering at 125 % or more was compared.
4. **Screen size.** TEST-U4 ran on a 1024-pixel screen with both windows shrunk equally (§8); on a large screen it uses
   the default sizes. Judgement call 3 describes the small-screen layout.
5. **`App.OnStartup`** is not reached by in-process tests (the test host never calls `Application.Run`); the smoke test
   exercises it by starting the published exe, and a test checks there is no `StartupUri`.
6. **Reference-machine benchmarks** were not re-run (no Core change).
7. **A v1 long-scan UI test is timing-sensitive on CI runners**, on the frozen base too (§13): with `tree_60000`, the
   close-during-scan test can see a Folders report because the scan outruns the cancellation. A larger tree would make
   it robust; changing v1 tests or their fixtures is outside C2.
