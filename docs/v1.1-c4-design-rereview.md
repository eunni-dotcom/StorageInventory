# StorageInventory v1.1 C4 design re-review: decision D-52

An independent review of the C4 blocking design decision D-52 (`docs/v1.1-c4-design-review.md`) and of the specification amendments
that integrate it (`docs/v1.1-preproduction-spec.md` at `7d85d78`). It is a design and specification review only. It does not repair
C4, does not start C5, and changes no production code, test, evidence file or specification text. The blocked C4 implementation
stays blocked whatever this review concludes.

The question answered is the one the brief states: **does D-52 provide a sound, testable and safe authority for repairing C4 after the
§15.4 stop condition?** It is not whether the current C4 implementation is acceptable; it is not.

Units in this document: **MiB = 2^20 bytes, MB = 10^6 bytes**. Decisive figures are also given in bytes. Labels: **measured here**
(run or computed in this re-review), **from the evidence** (recomputed from the committed raw data), **inferred** (argued, not
measured).

## 2. Independence

The same assistant wrote the C4 implementation, the C4 review, the C4 design review and this re-review, in separate sessions.
**Organisational independence is therefore limited**, and the design review's own author note says the same. This review treats
`docs/v1.1-c4-design-review.md` as a proposal and an evidence report, not as authority, and mitigates the limitation as follows:

- **Raw evidence recalculated** with a script written for this review (not the committed `tables.py`), with per-record consistency
  checks: every rate, ratio, growth and journal figure is recomputed from the JSONL fields (§4).
- **Journals parsed independently.** A rollback-journal parser and B-tree walker written here from the SQLite file-format document
  (not from the design review's C# code) checks each record's checksum, compares each record's original page image byte for byte
  with the pre-import database, attributes each page to its B-tree, locates it by level and distance from the right edge, and decodes
  the first key column of every name-index page to test source-range confinement, which the design review never tested (§6).
- **Targeted reruns** from the committed patches, built in two fresh worktrees of `035dc90` (one with `harness.patch` only, one
  with `harness.patch` + `probes.patch`), with two clearly marked reviewer-only instrument lines (§21).
- **Vocabulary statistics recomputed** from the harvested name file, and an aggregate-only name census of this machine's whole system
  drive (§7).
- **The specification read in full** in every affected section at both `035dc90` and `7d85d78`, plus a mechanical comparison of every
  requirement-ID row (§3).
- **The design session's scratch directory** (build logs, chain scripts, `overlap.py`, prefill caches) was inspected read-only as
  evidence of how the runs were made; nothing in it was trusted without a check.
- **Every Blocker, High and Medium finding below was verified first-hand** by measurement or by reading the cited text. No separate
  agent was used; the independent parser, reruns and recalculation are the substitute.

## 4. Evidence integrity

### 4.1 Recalculation

The committed JSONL holds **137 records**: 119 normal runs (118 published; one is the planted-failure staging probe), 11 cancel runs
and 7 crash runs (killed child plus recovery open). Recomputed with this review's script:

- **Internal consistency: 0 defects.** For every record: growth = after − before; file rows/s = files ÷ `ImportSeconds`; insertion
  rate; journal ÷ growth; journal ÷ Library; page size × page count = Library size before; the importer's coarse journal figure never
  above the handle figure; the sampled peak never below the exact end-of-insertion length.
- **Every per-cell figure in the design review's §4, §6, §7, §8 and §10.2 tables reproduces** (medians, min–max, journals to the
  byte, growth, working set, load). `b1_table.py` reproduces §10.2's B1 table exactly. `tables.py` reproduces the remaining tables but
  **fails with `UnicodeEncodeError` under the Windows console code page** and needs `PYTHONIOENCODING=utf-8` (C4DR-O04).
- **Units.** The design review declares MB = 2^20 bytes and mostly keeps to it: 23,402,536 B = 22.32 MiB = 23.40 MB and
  92,932,104 B = 88.63 MiB = 92.93 MB, so the C4 review's decimal "23.4 MB / 92.9 MB" and the design review's "22.3 / 88.6 MB" are the
  same bytes, as it says. **Two exceptions:** the staging table prints its peaks in binary (104.8 = 109,840,680 B) but its totals in
  decimal ("798 MB" = 798,324,032 B = 761.3 MiB; "2,195 MB" = 2,093.5 MiB; "380 MB" = 362.5 MiB); and the amended specification prints
  binary figures labelled MB without stating a convention (for example "57 pages (0.23 MB)" for 235,016 B = 0.224 MiB = 0.235 MB)
  (C4DR-O06).
- **Run counts.** The design review's "in all 92 normal runs" handle = `FileInfo` is stale: the committed evidence has 118 published
  normal runs, and the property holds in all **130** non-crash records (stronger than stated). "28% to 75% over 130 runs" is correct
  (27.6% to 75.1%).
- **Load annotations.** The per-run whole-machine figure is in the JSONL. The plan-level "other readable processes 1.9 to 7.2 of 16
  CPUs" figure is only in the `results/*.log` files, which the evidence README lists as evidence but which `.gitignore` (`*.log`)
  kept out of the commit; it is confirmed here from the local copies (1.86 to 7.19) but cannot be checked from the repository
  (C4DR-O02).
- **Private data.** No harvested file name, user path or process name is in any committed file; the JSONL `Probe` field and the
  harness use `<scratch>` placeholders; the harvested name file was never committed. Only aggregates are reported, here too.

### 4.2 Build-overlap markings

### 4.3 Prefill contamination of the per-source cells (C4DR-M06)

The harness caches each prefill under the key `<family>-<size>[-persource]` and builds it in a child that inherits **the triggering
run's whole environment**. In the design session the per-source prefills `hash-1000000-persource`, `hash-2000000-persource`,
`mixed-1000000-persource` and `append-1000000-persource` were all first built by `probe:combined` runs (`persource+chunked … r1`),
that is **with `SI_DR_PRESORT=chunk` active** (the plan logs show "building prefill …-persource" directly under those runs). Every
later "B1 alone" run on those sizes reused them.

Verified here: the design session's `hash-1000000-persource` prefill and the one this review built with the committed harness and
probes have the same name set and the same file observations (equal content hashes over strings), but **different `name_id`
assignment** (different content hashes over ids) and a different page count (101,792 against 102,237 pages): key-ordered ids
instead of first-seen ids.

Consequence. The **journal** conclusions survive: this review's clean rerun of the existing-source cell journals 62,927,656 B
(60.01 MiB) against the design review's 62,291,928 B (59.41 MiB), and the new-source cell is identical (247,328 B peak, 57 pages).
The **throughput** statements for B1 on an existing source are not clean B1 measurements: `persource hash existing` at 1M and 2M,
`persource rescan 1%`, the 2M cancel and crash cells, and `persource mixed new-source 1M` ran on B2-built prefills. The design review's
reading "B1 bounds the cost, it does not make the same-source work cheaper (39k rows/s either way)" and the "D-52's alike" half of
PERF-14's basis rest mainly on these; the one clean worst-case existing-source cell is `persource mixed existing 2M/6000k`
(37,441 rows/s, 53.3 s). The harness is named as the starting point of the repair's TEST-P1 (D-R4), so the defect would carry over.

### 4.4 Other evidence observations

- **An undisclosed failed-state record.** `probe-combined-analyse`'s crash cell recovered the hot journal correctly (main file
  1,040.1 → 796.6 MiB, exact) but the start-up open then derived **`NotALibrary`** (schema fingerprint). It ran on the first probe
  build (`bin-probes`), whose recovery child did not receive the run's `SI_DR_PERSOURCE`, so the per-source schema failed the normal
  fingerprint: a harness-version artefact, not a product defect. The design review does not mention it. The harness also records
  `OlderSnapshotsVerify = true` when verification was skipped because the state was not Available (C4DR-O01).
- **The pre-import copy predates T0.** In every analysed journal of this review exactly one record (page 1) differs from the
  pre-import copy, because the harness copies the database before the attempt insert (T0) commits. Attribution is unaffected; the
  repair's harness should copy after T0 (C4DR-O12).

### 4.5 Journal measurement integrity

- The handle sampler ran at **60.9 to 65.5 samples per second** (median 64.2): Windows' 15.6 ms timer, as the design review says.
- In 113 of the 116 single-transaction published runs the sampled peak exceeds the exact end-of-insertion length by **exactly three
  4,104-byte records** (the final statements' pages), in the other three by 3.18 records. `FileInfo` equals the handle in all 130
  non-crash records.
- **Why the sampler cannot miss the peak:** a `TRUNCATE` journal only grows within the transaction, and its final size is held
  through the in-transaction verification and the whole `COMMIT` write-out (phase timings 0.2 to 3.9 s for `COMMIT` alone; 1.7 to
  12.2 s for verification in the unmodified and per-source runs, 17.2 s in a key-ordered probe) before it is truncated. A 15.6 ms sampler sees a plateau of hundreds of milliseconds at least.
- The proposed method, the exact length through a live handle **immediately before `COMMIT`** plus sampling at least every 20 ms,
  removes the remaining few-page uncertainty. **Remaining blind spot:** only failure paths (guard stop, `SQLITE_FULL`), where the peak
  is not held; it is not acceptance-relevant. The pre-`COMMIT` read needs an importer hook; IMP-11's guard hook "immediately before
  `COMMIT`" (D-R3) can carry it. "At least every 20 ms" cannot be guaranteed by `Sleep(1)` on a loaded Windows machine; the pre-`COMMIT`
  read should be the reported figure and the sampled series a cross-check with its actual maximum interval recorded.

**Verdict on evidence integrity: sound for the journal and mechanism conclusions** (deterministic, reproduced to the byte here);
**defective in one material respect** (C4DR-M06) and several presentational ones (C4DR-O01 to O06, O12).

## 6. SQLite mechanism

Independent parse of every journal this review produced: pristine append 1M / 3×250k, interleaved 1M / 3×250k and 1M / 3×1M,
interleaved new-source 1M / 3×1M; per-source new-source and existing-source 1M / 3×1M.

| Check | Result |
|---|---|
| Segment structure | Two segments, the first synced (magic and record count present), the second unsynced (zero magic, records to end of file), sector 512, page 4,096 |
| Record checksums (`pager_cksum`: initial value + every 200th byte from the end) | **All pass**: 66,430 records in the six journals |
| Repeated page numbers | None |
| Original image equals the pre-import page, byte for byte | Every record except page 1 (explained in §4.4) |
| Pages beyond the original end | None |
| Attribution to B-trees | Identical to the design review's walker in every cell (for example 22,611 / 22,811 name-index pages, 10 `file_obs`, 10 `folder_obs`, 5 `name`, five one-page catalogue trees) |

The brief's six-step explanation is **correct**:

1. **Original images only.** The rollback journal holds the original image of each pre-existing page changed in the transaction,
   once: zero repeats, and images equal to the pre-import pages.
2. **New pages are not journalled.** No record lies beyond the original end of the file.
3. **C4's names appended.** C4's generator names (`file_target_…` after `file_p1…` to `file_p3…`) sort past the right edge.
4. **So almost nothing was journalled.** In the append control every journalled page of every growing tree lies on the right edge.
5. **Interleaved names touch the existing leaves they land in.** In the interleaved cells 96.6% to 99.1% of the name index is
   journalled.
6. **So the journal follows the existing dictionary footprint and the insertion distribution, not the snapshot:** the same
   22,611 pages at 1M and 2M rows into the same Library.

**Additions the mechanism needs (none contradicts D-52):**

- **About one page per new name even before saturation, because of rebalancing.** The 1% re-scan journals 9,928 name-index pages
  for 10,187 new names, where the occupancy formula *E*·(1 − e^(−N/E)) predicts 8,217. Splits at about 93% fill rewrite siblings and
  parents. The design review's "about one 4 KiB page per new name" is therefore the better summary than its formula.
- **Append-shaped trees: the rightmost page of each level and at most two left siblings, at every level including interior ones.**
  In every analysed journal and every append-shaped tree (`file_obs`, `folder_obs`, `name`, `folder_path`) no journalled page is more
  than two places from the right edge at its level.
- **A new source's dictionary is append-shaped.** Its journal holds, in the name index, the rightmost page of each of the four levels
  plus two left siblings at each of the three lower levels (10 pages), and the same pattern in `folder_path_child`; 57 pages in all
  (235,016 B at the end of insertion), identical to the design review's figure on a clean prefill.
- **An existing source's journal is confined to its own range.** This was never tested by the design review, whose walker attributes
  pages to B-trees only. Decoding the first key column of every name-index page: source 1's keys occupy leaves 0 to 15,248 of 23,198.
  Of the 15,051 journalled leaves, **15,050 hold only source 1's keys and one is the border leaf** holding both sources' keys. **No
  leaf holding only the other source's keys was journalled.** 249 interior pages were journalled: 247 are ancestors of journalled
  leaves; the other two are interior pages rewritten by rebalancing at level 2, one inside source 1's range and **one adjacent to it
  holding only source 2's keys**. That is real SQLite behaviour the PERF-15 (a) wording must allow (C4DR-M02).
- **"Append-shaped" workloads can still touch a mid-index page.** In the pristine append control one name-index leaf 4,943 places
  from the right edge was journalled, because an in-folder collision suffix ("… (1)") produced a name that sorts mid-index. So the
  rule for an existing source must stay range-based, not edge-based.

**Verdict: the B-tree mechanism is correct**, and the source-range confinement on which D-52 rests is confirmed here page by page.

| N4 real vocabulary | Names harvested from `C:\Program Files` (source A), `C:\Program Files (x86)` (source B) and `C:\Windows` (target), **assigned to the generator's slots in order, cycling the list** (`RealName`: `list[slot % list.Length]`) | **acceptance** | **Not objective; the "about one name in ten new" statistic is an artefact of cycling (C4DR-H01)** |
| N5 re-scan | The source's previous snapshot with 1% renamed: of an N4 source (acceptance) or of an N2 source (worst-case) | acceptance / worst-case | 1% is a reasonable routine-change rate; the N4 source behind it is unrealistically small (C4DR-H01) |

### 7.4 Is the split defensible?

**In principle, yes.** PERF-01's 100k target is derived from PERF-02b's 250k-file tree, and PERF-14 bounds every 2M save. Holding
adversarial distributions to PERF-14 rather than PERF-01 is a legitimate product choice.

**As specified, no.** The boundary between "acceptance" and "worst-case" is not drawn by objective properties:

- N4 is defined only as names "harvested from real system trees", which depends on the machine and is not reproducible on the hosted
  runner. Its outcome is driven by a parameter the specification never states (the list's distinct count against the target size).
- The justifying statistic in §15.4 ("about one name in ten new to the source on a first save") is the cycling artefact.
- A real source can resemble the worst-case cells: real system trees are 52% to 67% distinct at natural size, a whole system drive
  21% to 23%, and media or music archives more (the design review itself names "a media archive, a cache folder"). Its established
  dictionary is far nearer the worst-case N2 source than the N4 source.

A later implementation could meet PERF-01 on N4 while a plausible real source behaves like an adversarial cell. That is exactly what
the brief warns against: an inconvenient plausible workload labelled "worst-case" by construction. This is **C4DR-H01**.

**Re-scan rate.** 1% is a defensible routine-change figure. The 5% re-scan stays informational. A 10% cell should be added as
informational. The acceptance re-scan must run against a source dictionary of realistic size.

**Verdict: the workload families are well designed except N4. The acceptance/worst-case division is defensible only once N4 and
N5's source are defined objectively (C4DR-H01).**

## 9. Schema and query implications; source identity

- **Key structure.** `name (name_id INTEGER PRIMARY KEY, source_id INTEGER NOT NULL REFERENCES source (source_id), utf16 BLOB NOT NULL,
  UNIQUE (source_id, utf16)) STRICT`.
  - **Rowid table:** correct, because `name_id` lookups by id (verification, browsing) need it; `WITHOUT ROWID` would make `name_id`
    a secondary key.
  - **Automatic index `(source_id, utf16, rowid)`:** serves interning, the source's range scan for search, the footprint aggregate
    of IMP-11 (count and `length(utf16)`) and future source deletion.
- **Foreign key.** `foreign_keys = ON` (§5.8), so every name insert checks that the source exists. The source row is created or
  re-read at IMP-03 step 1 inside the same transaction, so the check always succeeds and costs one page-cached lookup.
- **Observation references.** `file_obs.name_id` and `folder_path.name_id` stay plain integers. Invariant 4 now requires the
  referenced row's `source_id` to equal the snapshot's source. That is one rowid lookup per distinct id, which the closure check
  already performs; D-R1's negative test (a `name_id` of another source must fail) and its mutant cover it.
- **No ambiguity and no expensive join.** `name_id` is globally unique; every query that needs a name has the source in hand.
- **Source identity dependency (C3).**
  - **New sources append:** a new source's `source_id` is max + 1 (rowid allocation), so its keys sort past every existing key in the
    name, `folder_path_child` and `folder_path_root` indexes. That is the append behaviour verified in §6.
  - **Existing sources:** an existing source's range is wherever its id sorts, and its imports touch only that range (§6).
  - **C3 decisions:** Strong, Moderate, PathOnly, UserAsserted, same-source matching, renamed or moved roots, network sources and
    new-versus-existing decisions all decide only *which* source an import goes into.
  - **No cross-contamination:** a name row is an exact string, so a wrong source decision cannot corrupt any name; it can only add
    names to the wrong source's dictionary (larger future journals). Invariant 4 prevents any snapshot from referencing another
    source's names. D-52 neither conflicts with C3 nor makes a C3 error more harmful than it already is.

**Verdict: the schema change is sound and has no ambiguous key or join.**

## 10. Storage-growth trade-off

**What the evidence shows.** Real-vocabulary new source at 2M: 195.1 MiB growth with D-52 against 193.3 MiB with the Library-wide
dictionary (+0.9%). That figure says almost nothing about duplication, because the target's vocabulary overlaps the other sources' by
1.5% (§7.2).

**Estimate (inferred from measured costs).** A new name costs about 2 × its UTF-16 bytes + 25 B (row and index entry; 117 B for the
46-byte interleaved names, from the evidence). Per-source dictionary size is (distinct names) × (2 × mean bytes + 25 B):

| Source | Distinct names | Mean length | Dictionary | One snapshot of the source (PERF-03: 64 to 90 B per file) |
|---|---:|---:|---:|---:|
| Reference drive, SRCH-02 figure | 250,000 | 20.8 code units (41.6 B) | about 26 MiB | 2M files: 122 to 172 MiB |
| This machine's system drive | 673,791 | 20.8 code units | about 70 MiB | 2.58M files: 158 to 222 MiB |
| `C:\Windows`-like names | 102,236 | 52.6 code units (105 B) | about 23 MiB | – |

- **Two similar sources** (two PCs' system drives, or a drive and a clone registered as separate sources) that share most of their
  vocabulary duplicate up to one dictionary: about 26 to 70 MiB, that is 15% to 45% of one snapshot, amortised over the second
  source's snapshots (2% to 5% at ten snapshots).
- **Ten similar sources** with ten snapshots each: about 0.23 to 0.62 GiB extra against about 12 to 22 GiB of snapshots (2% to 3%).
- **Many small sources** (USB sticks scanned once): small dictionaries (they scale with distinct names, not files), so a small
  absolute cost. The worst ratio is a single-snapshot source with a large, fully shared vocabulary (up to about 45% of that one
  snapshot).

Against the product's growth goals:
- PERF-03 (≤ 90 B per file observation) is measured in C5 on one real drive, normally the first source, which pays its full
  dictionary under either design. The duplication affects only second and later sources.
- CAP-01 and CAP-02 trigger on totals and would show any surprise.

The trade-off buys a journal and rollback bounded by the source (§6, §14) and a cheap, exact-scope IMP-11 projection.

**Verdict: acceptable.** The cost grows with distinct names per source, never with observations, and is a few percent in a Library
with history. The design review's "storing a name once per source costs almost nothing" should be restated with this estimate
(C4DR-O08).

## 11. IMP-11: the space preflight and guard

### 11.1 The rule

- **Inputs:** `F_L` and `Cap_L` from `GetDiskFreeSpaceExW`; at P5 the spool's `n_f`, `n_d` and name bytes `B_n`; the target source's
  footprint `E_n`, `E_b`, `E_p` (all zero for a new source).
- **Growth projection:** `G_p` = 110 B·`n_f` + 120 B·`n_d` + `B_n`.
- **Journal projection:** `J_p` = min(2·(`E_b` + 16·`E_n` + 24·`E_p`), 4,104 B·(`n_f` + `n_d`)) + 1 MiB.
- **Margin:** `M_L` = max(256 MiB, 1% of `Cap_L`), at most 2 GiB.
- **Check points:**
  - **P0** (read-only): `F_L` < `M_L` + `G_p` + `J_p`, or the query fails → Save to History unavailable (O24).
  - **P5**: the same with the exact counts → T-IMPORT does not start (O13).
  - **Guard**: at `BEGIN`, after every 4,096 inserted rows and immediately before `COMMIT`: `F_L` < `M_L` + `I_L` with
    `I_L` = 2·max(16 MiB, `D`), or the query fails → `ROLLBACK` (O13).

### 11.2 What is conservative

- **Query failure** is treated as insufficient space at every point.
- **Exact threshold:** strict "<", so equality continues; TEST-L9's "one byte above continues" is consistent with that.
- **Another process** filling the volume faster than `I_L` per interval is honestly left to `SQLITE_FULL`, with the same outcome.
- **The rollback returns all the space.** Original pages are restored in place, the main file is truncated to its size at `BEGIN`
  and the journal to 0 bytes. Every cancel run in the evidence and in this review returned the main file to its exact size before.
- **`J_p` against the measured existing-source journal:** for source 1 of the 1M / 3×1M per-source Library, `E_n` = 1,018,610,
  `E_b` = 44.4 MiB, `E_p` = 250,000 give `J_p` = 132.3 MiB, against a measured 60.01 MiB. Conservative by 2.2×.
- **`G_p` against measured growth:** 133.4 MiB + `B_n` against a measured 125.6 MiB. Conservative.
- **Margin size:** `M_L` ≥ 256 MiB keeps the system drive far from full.

### 11.3 What is not covered: the `COMMIT` write-out (C4DR-M01)

SQLite keeps new pages in its page cache (64 MiB for the import) and writes them to the main file when it spills or at `COMMIT`. When
the guard runs its last check "immediately before `COMMIT`", up to a page cache of *new* pages has not reached the file yet; `COMMIT`
then extends the main file by that amount after the last check.

**Measured.** Main-file growth that lands after the end of row insertion, almost all of it at `COMMIT`:

| Cell | After the end of row insertion | Source of the figure |
|---|---:|---|
| C4 append control, 1M / 3×1M (crash cell: main file at the kill against the twin normal run's final size) | **54.1 MiB** | committed evidence |
| Append control, 1M / 3×250k | **54.1 MiB** | rerun here |
| **D-52 new source**, interleaved, 1M / 3×250k and 1M / 3×1M | **33.4 MiB** (both) | rerun here |
| D-52 existing source, interleaved, 1M / 3×1M | 3.2 MiB | rerun here |
| Library-wide dictionary, interleaved, 1M / 3×1M | 0.0 to 0.8 MiB | rerun here and committed |

Append-shaped imports, which is what D-52 makes every new source's first save, defer the most: the cache then holds new pages rather
than journalled old ones. At the last check `D` is the drop since the previous check, which spans the in-transaction verification:
no rows, no growth, so `D` ≈ 0 and `I_L` = 32 MiB. `COMMIT` then writes 33 to 54 MiB measured, up to 64 MiB bounded by the cache.

Consequences:
- **The guarantee is false as written.** IMP-11 states that "while T-IMPORT runs it does not take the Library's volume below `M_L`
  free, provided the volume loses at most `I_L` between two checks". The import itself, with no other program writing, can take the
  volume **22 MiB below `M_L` (measured) and up to 32 MiB below it (bounded)**.
- **The arithmetic omits it.** "4,096 rows add at most about 21 MiB" leaves out the deferred write.
- **Q-24's experiment cannot see it.** "The largest free-space drop between two guard checks" never spans `COMMIT`.
- **C5 cannot pass as written.** C5's acceptance text ("an import never takes the Library's volume below IMP-11's margin") and
  TEST-L9's end-to-end VHDX case would fail on a small volume.

The safety hazard itself stays small, because `M_L` ≥ 256 MiB leaves at least 224 MiB free. But a normative safety guarantee and its
acceptance test are wrong, and the fix touches C4's primitive (D-R3). It must be corrected before implementation.

**Required correction (bounded, no architectural change).** Make the final check account for the deferred bytes. Either:
- **(a)** flush the page cache inside the transaction (`sqlite3_db_cacheflush`) before the last guard check, so the main file has
  reached its final size; or
- **(b)** add the deferred bytes, `PRAGMA page_count` × page size − the main file's length through a handle, or simply the import
  cache size, to the final check's allowance.

In either case: restate the guarantee and its arithmetic; extend Q-24's experiment and TEST-L9 to measure the drop across `COMMIT`;
update D-R3's hook definition.

### 11.4 Minor (C4DR-O10)

- **`J_p`'s per-row term is not a strict bound.**
  - A new folder inserts into two content-keyed indexes (`name`, `folder_path_child`).
  - Rebalancing can journal more than one page per insertion.
  - So 4,104 B·(`n_f` + `n_d`) can be exceeded for a small snapshot of all-new names into a large source.
  - The guard covers it, but the text should not call it a bound.
- **`G_p` counts name bytes once**, while a new name is stored twice (row and index).
  - For snapshots of all-new names longer than about 13 characters, actual growth exceeds `G_p`.
  - The guard covers it.
  - Q-24's experiment should include an all-unique long-name cell and a small-snapshot-into-large-source cell; the TEST-P1 cells
    never exercise either.
- **Rollback after `SQLITE_FULL` took 3.56 s (page-capped) and 7.07 s (real full volume) in the C4 evidence**, with an
  append-shaped journal of about 0.2 MiB. So a guard-stop or full-disk rollback has a fixed cost that the per-MiB model of §14 does
  not capture, and no budget covers it. TEST-L9 should record it.

**IMP-11 verdict: the right control in the right places.** Its constants are conservative except for the `COMMIT` write-out, which
must be accounted for (C4DR-M01).

## 12. Full-disk safety

- **One transaction, rollback journal, `synchronous = FULL`:**
  - A page is changed only after its original image is in the journal.
  - The journal is synced before any database page is written.
  - Rollback writes original images in place and truncates; no allocation is needed.
  - The hot-journal recovery at the next open does the same and deletes the journal.
  - So a rollback stays reliable even when the journal's own growth caused the exhaustion: the page whose record could not be
    written was never modified.
- **Existing evidence:**
  - a page-capped `SQLITE_FULL` (80 MiB cap);
  - a real full 200 MB NTFS VHDX on the hosted runner (run 37006608313): `LibraryFull`, main file back to 37.8 MB, older snapshots
    verified, re-opened Available.
- **What that evidence does not cover:** both cases had an append-shaped journal of about 0.2 MiB, so the failure was a spill or
  `COMMIT` write of the main file. D-52's existing-source case (a large journal, failure while appending a journal record) and a
  failure during the `COMMIT` write-out after the journal sync are untested. SQLite's design makes them safe (*from source*), but the
  repair's TEST-T1/TEST-L9 should force all three failure points (C4DR-O11).
- **Staging would have been worse:** a failed batch keeps earlier batches' pages (§18).

**Verdict: full-disk safety is bounded and D-52 does not weaken it.** IMP-11 adds a margin in front of `SQLITE_FULL`, once
C4DR-M01 is corrected.

## 13. PERF-15 replacement

What the old "≤ 5% of the snapshot" protected, and its replacement:

| Protected property | Replacement | Sufficient? |
|---|---|---|
| Structural correctness: no unexpected page churn; catches a regression to a Library-wide dictionary or a content-keyed index over observations | (a) the journal's allowed pages | Yes in kind; **wording not yet machine-testable as specified (C4DR-M02)** |
| Free space on the Library's volume | (b) IMP-11 | Yes once the `COMMIT` write-out is accounted for (C4DR-M01) |
| Rollback latency | (c) cancel within 2 s (acceptance) / 5 s (worst-case) | Yes in kind; **measurement point ambiguous, and PERF-16 / CAN-03 inconsistent (C4DR-M03)** |
| Crash-recovery cost | (c) next open within 5 s | Yes (§14) |
| Transient journal amplification | (b) `J_p` bounds it before the import; (a) bounds it structurally | Yes |
| Write amplification | reported (journal bytes per row), not budgeted | Acceptable |

**C4DR-M02, the structural rule.** PERF-15 (a) has three problems:

1. **It cannot be asserted by B-tree attribution.** §15.4 and TEST-P1 say "every journalled page attributed to its B-tree: PERF-15
   (a) is asserted". But (a) allows only pages that "hold an entry of the target source" within the name and folder-path indexes. A
   page of another source's range is in the same B-tree. B-tree attribution, which is all the design review's walker did, cannot see
   the difference. Asserting (a) requires decoding the first key column of each index page (§6 shows it is easy).
2. **It does not cover interior-level rebalancing.** The wording allows "the pages bordering that key range and their ancestors".
   This review observed an interior page holding *only the other source's keys*, adjacent to the range, rewritten by rebalancing
   (§6). It is not an ancestor and, read as "the leaf next to the range", not bordering. A literal implementation would report a
   defect on correct SQLite behaviour.
3. **The new-source clause is ambiguous.** "For a new source, only those indexes' right edge" does not say that the right edge
   includes two left siblings per level, as the append-table clause does. Measured: 10 name-index pages = the rightmost page of each
   of 4 levels + 2 siblings at each of 3 levels.

**Required precise rule.** For each content-keyed index:
- At every level, the pages holding a key in the target source's range, plus **up to two adjacent pages on each side** (SQLite's
  `balance_nonroot` rewrites at most the page and two siblings), plus the **ancestors** of all of these.
- For a new source the range is empty and begins past the last key, which gives the right edge with up to two left siblings per
  level.

This still catches a Library-wide churn regression: a journal holding pages tens or thousands of places outside the range fails.

## 14. Rollback, cancellation and crash recovery

**Correctness first.** In every cancel and crash run of the evidence and of this review (21 runs in all: 18 in the evidence, 3
here):
- the main file returned to its exact byte size at `BEGIN`;
- the journal ended at 0 bytes (cancel) or was deleted by recovery;
- the start-up open derived Available (except the harness artefact of C4DR-O01, after a correct rollback);
- the three older snapshots verified.

No partial publication is possible: nothing is committed before `COMMIT`.

**Rollback cost (from the evidence and measured here).**

| Journal | Cancel → rolled back | ms per MiB | Crash → next open | ms per MiB |
|---|---:|---:|---:|---:|
| 0.16 MiB (append) | 0.035 to 0.045 s | – | 0.11 to 0.16 s | – |
| 0.22 MiB (D-52 new source; here) | – | – | **0.125 s** | – |
| 22.3 MiB | 0.58 to 0.76 s | 26 to 34 | – | – |
| 60.0 MiB (D-52 existing source; here, clean prefill) | **1.41 s** | 23 | **1.07 s** | 18 |
| 88.6 MiB | 1.20 to 1.81 s | 14 to 21 | 0.68 to 0.71 s | 7.6 to 8.0 |
| 120.2 MiB (D-52 existing, 2M / 3×2M; B2-built prefill) | 3.09 s | 26 | 1.41 s | 11.7 |
| 177.2 MiB (Library-wide, 2M / 3×2M) | 3.26 to 3.96 s | 18 to 22 | 3.34 s | 18.9 |

**Recovery is not "about 8 ms per MB".** That holds for one cell. The cost per MiB rises to 12 to 19 ms at 120 to 177 MiB and was 18
ms per MiB at 60 MiB under this review's load. Extrapolating at 8 ms per MiB understates recovery (C4DR-O05). The budgets are met in
every measured cell.

**The budgets.**
- **What they are:** 2 s (acceptance cells, from PERF-16), 5 s (worst-case cells; "what a user waits for after Stop") and 5 s
  (recovery, every cell) are acceptance targets, with STOP at 1.5× (3 s, 7.5 s, 7.5 s).
- **Recovery:** 5 s is a reasonable bound next to PERF-08's 1 s clean open.
- **The 2 s figure** is PERF-16's, which C5's Stop Saving responsiveness depends on (CAN-03, OBS-11 "rolls back within PERF-16",
  UI-10). See C4DR-M03.
- **Untested conditions:** all figures are warm OS cache on NVMe. A cold-cache recovery after a real power loss, or a slower drive,
  is not measured; the budgets apply to the reference machine (§15.4).

**C4DR-M03, cancellation semantics.** Four problems:

1. **PERF-16 was narrowed.** It previously applied to every 2M save; it now applies to "the acceptance cells' name families". The
   design review's §14 says PERF-16 "is kept". The edit index lists the row only as "end to end; engine part is PERF-15 (c)".
2. **CAN-03 still says, unqualified, "a save cancellation returns within 2 s (PERF-16)"**, while PERF-15 (c) allows 5 s at the
   engine alone in worst-case cells. Measured there: 3.1 to 4.0 s.
3. **No UI semantics for a Stop that takes more than 2 s** (for example UI-10's "Stopping…" state and what Close does meanwhile).
4. **"At its journal's peak" does not fix the cancel point.** The peak is a plateau that spans the whole in-transaction verification
   (3.9 to 12.2 s at 2M in the evidence). CAN-01d gives the save token **no check inside the verification**. So a Stop pressed early in
   verification waits until "before `COMMIT`". The harness cancels at the end of row insertion, immediately before a token check, so
   PERF-15 (c) measures rollback alone, not the latency the user sees. C4-M02 already requires a token check after verification. The
   specification should bound the check interval inside verification and measure the worst cancel point.

## 15. PERF-01 methodology

| Element | Proposed | Judgement |
|---|---|---|
| Quantity | File rows ÷ (`BEGIN IMMEDIATE` → return of `COMMIT`), verification included | Correct: what the user waits for |
| Warm-up | One unrecorded run of the first cell per session | Adequate |
| Fresh process | Each run a sequential child; interleaved round-robin | Good: spreads drift over cells |
| Cache state | Copied, flushed prefill; OS cache warm, page cache cold | Sound; the 13% difference from in-process prefill is measured (two runs each) and the method is fixed |

**C4DR-M05, the quiet-machine and validity rule.** Three gaps:

1. **"Readable" depends on the API.** The validity rule counts "every other process whose CPU time the benchmark's account can read".
   Measured here, unelevated: the handle-based method the harness uses (`Process.TotalProcessorTime`) reads **255 of 437**
   processes. The performance counter `\Process(*)\% Processor Time` exposes **all 438**, Microsoft Defender's `MsMpEng` included.
   `NtQuerySystemInformation(SystemProcessInformation)`, which Task Manager uses, is likewise readable without elevation. So:
   - the set, and with it every validity decision, depends on an implementation choice the specification does not make;
   - the design review's statement that Defender "does not expose its CPU time to an unelevated account" holds only for the API it
     used;
   - the specification must name the source, and say how it treats processes whose activity the run itself induces (`MsMpEng`
     scanning the Library files, `System`): recorded separately, or excluded from the validity sum with the reason.
2. **No rule for whole sessions.** Nothing prevents discarding a whole session (warm-up plus runs) and starting another until the
   medians pass: retry-until-pass at session level. Every session that passes the quiet check must be reported, and the gate's figure
   must come from a session designated before it starts (for example the first complete one), or from all sessions pooled.
3. **The quiet check runs at the start only.** A session-end check (the same 30 s window) would show background work that started
   mid-session and is invisible to a readable-process rule.

**PERF-01 status.** The specification says PERF-01 is NOT MEASURED until a valid quiet-machine run (§22.5, D-R4, D-R5), and C4's
acceptance requires MET by §15.4's method (§19 C4). Nothing in the amended specification marks PERF-01 MET. **Correct.**

## 16. Acceptance and worst-case split; PERF-01 target and stop threshold

- **Target.** 100,000 rows/s is justified by PERF-02b: 9.5 s minus PERF-02a's 7.0 s leaves 2.5 to 3.2 s for pass V and a 250k
  import, so about 80k to 100k rows/s. Keeping 100k for 1M and 2M imports into Libraries three times their size is conservative.
- **Stop threshold:**
  - **what triggers it:** only acceptance cells, on their median below 50,000 (50,000 exactly is not a STOP);
  - **worst-case cells** are judged by PERF-14's time, T-IMPORT ≤ 60 s, STOP above 90 s (90 s exactly is not a STOP);
  - **cancellation and recovery** are judged by PERF-15 (c) (STOP above 1.5×);
  - **PERF-15 (a)** has no stop: a stray page is a defect, and the budget is MISSED.
  - This is unambiguous.
- **Could a realistic large established source with high churn resemble the worst-case workload? Yes** (§7.3, C4DR-H01):
  - a whole system drive is 21% to 23% distinct;
  - its dictionary is about 20 times the N4 source's;
  - media archives are more distinct still.
  Either the acceptance cells must use an objectively defined distribution that represents such sources, or the specification must
  say plainly, as a reviewed product decision, that high-distinct real sources are bounded only by PERF-14 and PERF-15 (c), and add
  an intermediate high-distinct cell (for example a 2M new source at 25% distinct names) at least as informational. Approving the
  categories as written would accept them because they make the headline target achievable.

## 17. PERF-14 and PERF-16

**C4DR-M04, PERF-14.** PERF-14 budgets the whole saving phase (P5 to P7, pass V included) at 60 s. The amendment holds "the engine
part (T-IMPORT alone) … to the same 60 s in every acceptance and worst-case cell". Problems:

- **Little margin.** The worst-case cells measured 45.4 to 53.3 s under load (single runs): 76% to 89% of the whole budget for the
  engine alone.
- **C5's share is unallowed.** C5 adds pass V (a sequential read of the spool, about 80 B per file), IMP-03's error pass,
  T-OUTCOME, IMP-11's checks and the lease work.
- **The end-to-end worst case is never checked.** C5 confirms PERF-14 only on TEST-P2's real drive and generated trees, not in the
  worst-case name families. A worst-case 2M save could take more than 60 s end to end while C4 reports PERF-14's engine part MET and
  C5 reports PERF-14 MET.
- **Slower drives and antivirus** are outside the reference machine by design. That is acceptable but should be stated.

The engine share must be an explicit part of the budget (60 s minus V, the error pass and T-OUTCOME as projected or measured), or C5
must measure PERF-14 end to end in the worst-case families at 2M and say what happens above 60 s. C4 engine share and C5 end-to-end
budget must not be the same number.

**PERF-16.** See C4DR-M03 (§14).

## 18. Alternatives

- **Hidden staging (rejected; verdict: justified for C4).** Throughput 23,373 rows/s (131,072-row batches, 7 commits) and 10,944
  (16,384-row batches, 60 commits) against about 51k; cumulative journal 798,324,032 B and 2,195,195,168 B against 92.9 MB; peak
  109,840,680 B (above the single transaction's) and 37,071,944 B; after a planted failure following four commits the main file stays
  72.4 MiB larger and the next open derives Damaged. Distinguish:
  - **Inherent to staging without compaction:** committed staged pages stay in the file after a failure; a purge moves them to the
    free list but cannot return them to the volume while 1.1.0 has no `VACUUM`. Any committed intermediate state also needs purge
    and recovery rules and weakens D-47's committed-state check.

    rows; and the throughput and journal-total figures, measured only with the Library-wide dictionary (staging combined with a
    per-source dictionary was not measured).

  bad, and does not claim to.

- **Hashed key (B4), WAL, `ATTACH`, a temporary database, weaker publication (verdict: rejections stand).** Integrity loss for a
