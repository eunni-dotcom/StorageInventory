## 6. ScanSession review

### 6.1 What moved

A line-by-line comparison of v1's `StartScan`/`RunScanAsync`/`CancelScan`/`NewScan` (`bf3fa36`) with
`ScanSession.Start`/`RunScanAsync`/`Cancel`/`Clear` confirms the evidence's table: the bodies are v1's, including the
order of `Progress.Reset()`, `Results = null`, `Stage = Scanning`, the stopwatch and one-second `DispatcherTimer`, the
`Progress<T>` on the UI thread, the optional workbook step, the `finally` that stops the clock, the result, the
exploration load and `CommandManager.InvalidateRequerySuggested()`. The session now owns:

| Responsibility | Owner in v1 | Owner in C2 |
|---|---|---|
| Scanner instance | `MainViewModel._scanner` | `ScanSession._scanner` (one per session) |
| Running task | `MainViewModel._scanTask` | `ScanSession._scanTask` |
| Cancellation | `MainViewModel._scanCancellation` | `ScanSession._scanCancellation` |
| Progress | `MainViewModel.Progress` | `ScanSession.Progress` (re-exposed by `MainViewModel.Progress`) |
| Current stage | `MainViewModel._stage` | `ScanSession.Stage` (`MainViewModel.Stage` is a read-through) |
| Result | `MainViewModel._results` | `ScanSession.Results` |

`MainViewModel` keeps setup state (paths, options, pre-flight, validation) and the commands, and delegates
start/cancel/clear. It no longer holds any scan field.

### 6.2 Behavioural differences, each traced

| Difference | Reachable? | Effect |
|---|---|---|
| `Start` returns `false` when busy instead of returning silently | `MainViewModel.StartScan` keeps v1's `!Preflight.CanScan \|\| IsBusy` guard first | None |
| `Clear` refuses while `IsBusy` | New scan is enabled only in Results. `Stage = Results` is set inside `RunScanAsync`'s final synchronous continuation, which completes the task before any later dispatcher operation (input, command) can run; nothing in that continuation pumps messages | None in any reachable path |
| Change notification goes session → `MainViewModel` | `ScanSession.Stage` raises `Stage`, then `OnSessionChanged` raises `Stage`, `IsSetup`, `IsScanning`, `IsResults` synchronously, then the session calls `InvalidateRequerySuggested`: v1's order. `Results` likewise | None |
| `MainWindow.OnClosing` reads `Session.IsBusy`/`Cancel`/`WhenIdle` instead of the view model's | Same objects and semantics | None |

### 6.3 Lifetime

- **One per app.** `App.OnStartup` creates the only production `ScanSession` and passes it to `MainWindow(session)`;
  `StartupUri` is removed (asserted null). `MainWindow()` without a session creates its own, which only tests and
  designers reach; that is a sound way to keep v1's tests unchanged (judgement call 2).
- **Not owned by views.** The four view code-behinds contain only `InitializeComponent` and the automation peer.
- **Not recreated.** No stage change or New scan creates a session; `MainViewModel` is created once per window.
  `ShellTests.One_session_…` asserts reference identity of the session, page and stage views across Setup → Scanning →
  Results → Setup with one call to Core.
- **Survives re-hosting.** `Replacing_the_Scan_page_view_during_a_scan_…` removes the page view mid-scan, checks that
  the scan is neither cancelled nor restarted, re-hosts a new view that shows the same progress and then the same
  result, with one call to Core. `Closing_another_window_hosting_the_Scan_page_…` shows that a host closing does not
  stop the scan. The exact-head CI log prints "replaced view released: True with the shell open, True once the shell
  closed".
- **Nothing faked.** No lease, `ObservationLease`, `InventoryRun`, save token, Library state or refusal-before-open is
  present or simulated. `Start`'s boolean refusal is a natural seam for C4/C5's refusals.
- **Session owns presentation view models.** `ScanProgressViewModel` and `ResultsViewModel` (with its exploration
  load and report commands) now live in the session (judgement call 7). This is what §14.6 ("existing view models")
  and §14.2 ("owns progress and result") together imply for C2; C5/C8 may want a model/view-model split. Carried
  forward (C2-O07), not a C2 defect.

**Verdict: ScanSession genuinely owns the running scan; ownership and lifetime are sound for C2.**

## 7. Lifetime and weak-event review

`MainViewModel` subscribes with `PropertyChangedEventManager.AddHandler(session, OnSessionChanged, string.Empty)`
(`MainViewModel.cs:42`), never unsubscribes, and has no `Dispose`.

| Question | Analysis |
|---|---|
| Can the session keep a page alive? | No. The manager holds the listener weakly. The session's own fields (scanner, clock, timer, CTS, task, stage, progress, results) hold no reference to `MainViewModel` or any view; `ScanProgressViewModel`, `ResultsViewModel` and `ExplorationViewModel` hold no back-reference; `RelayCommand` uses the weak `CommandManager.RequerySuggested`. Bindings to session-owned objects are WPF's own weak listeners |
| Correctness of the weak subscription | `string.Empty` subscribes to every property. The session raises only on the UI thread (its `RunScanAsync` continuations resume on the WPF synchronisation context, as v1's did), which is where the manager expects delivery |
| Dead targets, cleanup | A collected `MainViewModel` stops receiving; the manager purges dead entries in its scheduled clean-up. No callback can reach a dead target |
| Races with active notifications | Single-threaded delivery; no race beyond v1's |
| Handler accumulation | Impossible in C2 production: exactly one `MainViewModel` exists per session (created in the `MainWindow` constructor), and New scan, stage changes and view re-hosting create none |
| Unsubscribe | Not needed in C2 for the reasons above. If C8 recreates page view models on navigation, each live instance will receive and re-raise notifications until collected; harmless but worth an explicit `Dispose`/unsubscribe then (C2-O07) |

**What the tests prove, and what they cannot.**

- `Repeated_new_scan_cycles_…` proves meaningful production properties: five cycles make exactly five calls to Core
  (no duplicate scans), the elapsed clock stops after each scan (no timer survives), and earlier `ResultsViewModel`s
  are collected (0 of 5 alive on the exact head).
- Its handler-count assertion (`ShellHost.Subscribers`, reflection on `ObservableObject.PropertyChanged`) cannot detect
  duplicate subscribers: with a `WeakEventManager`, the source's invocation list holds **one** manager delegate however
  many listeners exist. "1 session and 1 progress handler each cycle" is constant by construction. Treated as
  supporting evidence only (C2-O03).
- No test creates several `MainViewModel`s over one session and checks delivery counts after collection. Not needed for
  C2 (unreachable), recommended for C8.

**Verdict: no retained pages, controls, callbacks, commands or growth is possible in C2's production object graph; the
test evidence is adequate for C2, with the handler count discounted.**

## 9. TEST-U4 review

### 9.1 Reference and method

- **Reference is v1's and frozen.** The test checks the reference's git object id against the constant `d29fd70…`,
  which I confirmed equals `bf3fa36:src/StorageInventory.App/MainWindow.xaml`. The reference is v1's own markup loaded
  live (two edits that cannot reach the visual tree: drop `x:Class`, name the view-model assembly). It cannot silently
  follow a C2 UI change: the C2 views are separate files, and editing the reference breaks the id check.
- **Same state at the same instant.** Both windows bind one view model and are rendered in one dispatcher operation,
  so the elapsed clock, the indeterminate bar's start and the data are the same.
- **Mask.** The content region is computed from the page host's position and size and must start at x = 200, y = 0
  and equal v1's client area exactly, else the frame fails; the shell image must equal chrome + content exactly. The
  mask therefore covers the whole page and only the navigation column is excluded. A second, unmasked comparison of
  the whole scrollable page (both sides rendered in full, including content below the fold) closes the "outside the
  viewport" gap.
- **Exactness.** Every channel of every pixel; no tolerance.
- **Size, DPI.** Both windows sized so the content regions are equal; both rendered at 96 DPI with the same renderer.
- **Focus, caret, animation.** Strict frames clear keyboard focus in both windows (a process has one keyboard focus);
  Setup frames are re-taken with each window's own source box focused while it renders. Fair to both sides. The
  indeterminate bar starts in the same layout pass in both.
- **Preconditions.** Same window style object, font family, size and foreground at the page root.

### 9.2 Result on the exact head (CI run 36897032954, read independently)

| Theme | Frames | Content region (828 × 749) | Whole page |
|---|---|---|---|
| Light | 8 + 3 focused | 0 differing pixels in all 11 | 0 in all 11 (828 × 749 to 828 × 1092) |
| Dark | 8 + 3 focused | 0 differing pixels in all 11 | 0 in all 11 |

### 9.3 Negative control

`TEST_U4_the_masked_comparison_notices_a_one_word_change_in_the_page` changes "Reports are always new files." to "…new
file." in the reference only. That text is in the Setup stage (v1 line 57; `SetupView.xaml:38`), inside the content
region, and visible in the `setup-ready` frame the control compares. The exact-head log reports **1,285 differing
pixels in the window diff and 1,285 in the page diff**, and the assertion requires both to be non-zero. The unmodified
reference is the two passing TEST-U4 tests. The control is meaningful.

### 9.4 Limits of TEST-U4 (none is a defect)

- **Shared view model.** Both windows run over the C2 `MainViewModel`, so TEST-U4 isolates differences caused by
  markup, hosting, styling and layout. A view-model regression would show identically in both windows and pass
  TEST-U4; that risk is covered instead by the unchanged v1 UI tests and the line-by-line identity of the moved scan
  code (§6.1). This is the right design for "differ only in the shell chrome", but it is the boundary of what TEST-U4
  proves (C2-O04).
- **Theme effect not asserted.** Both themes run through `Application.Current.ThemeMode` (the same mechanism v1's
  `UiSetupTests` use), and both windows share the application, so they always render in the same theme. Nothing
  asserts that the Dark pass actually differs from the Light pass. I could not view the uploaded PNGs (network policy).
  I judge it very unlikely that the Dark pass silently rendered Light, but it is unproven by the test (C2-O04).
- 96 DPI only; the reflowed (screen-limited) layout only (C2-O05).

**Verdict: TEST-U4 is trustworthy for its purpose and passes, light and dark, with a working negative control.**

### 10.2 The transparent peer

`ViewAutomationPeer` subclasses `FrameworkElementAutomationPeer` and overrides only `IsControlElementCore` and
`IsContentElementCore` to return `false`. Assessment:

| Question | Answer |
|---|---|
| Removes only wrapper nodes? | Yes. Children enumeration (`GetChildrenCore`) is inherited unchanged; UIA promotes the children of a non-control element into the control view, so the views' controls appear where v1's were. In the raw view the four wrapper nodes still exist |
| Preserves child controls? | Yes; asserted at every frame in process, and per the evidence's out-of-process dump |
| Stable through stage switching? | WPF caches one peer per element; the views are never recreated by stage changes (asserted), so their peers persist. The peer has no state of its own |
| New lifecycle or race behaviour? | None found. Peer creation, caching, invalidation, children and event raising are the base class's. The default `UserControlAutomationPeer` derives from the same base; the custom peer's only behavioural change is control-view and content-view membership (descriptive properties such as the class name also differ) |
| Could it explain the smoke miss? | No mechanism identified. With the default peers the diagnostic variant passed 11 of 11; with the custom peer 23 of 24. A 1-in-24 versus 0-in-29 difference is not statistically meaningful, and the failing line itself is not established (§11) |

No concrete reproducible failure involving the peer was found; a theoretical preference for default peers is not a
finding.

### 10.3 Binding diagnostics

- **Source.** `BindingErrorRecorder` listens on `PresentationTraceSources.DataBindingSource` at `Warning` (which
  includes WPF's binding `Error` events), after `PresentationTraceSources.Refresh()`, which is what enables binding
  tracing without a debugger. It filters nothing; it only normalises hash codes for comparison.
- **Active during the relevant work.** It is started before the v1 window and the shell are created and stays active
  through all eight frames of each, and a re-host of the Scan page view.
- **Self-test.** `The_binding_diagnostics_are_live` creates a deliberately broken binding and requires the recorder to
  see it; it passes on the exact head.
- **Result (exact head).** "v1 window 0 distinct, shell 0 distinct, 0 not in v1's". The stop condition "a new binding
  error" is not met.

**Verdict: no accessibility or binding regression found. Access-key invocation and screen-reader behaviour are not

The script was run with `powershell -File`, so the error record carries **no line number**. Between the last PASS and

1. `Invoke-ReleaseSmokeTest.ps1:96`: `(Find-Window $leaf).GetCurrentPattern(…WindowPattern…).Close()`, a **second**

C2 leg of run 1, the Explorer step took 7.5 s. Both runners had just built 320,000 files and run the full suite. UI
Automation over the desktop (both lookups) was demonstrably slow on that pair of runners.
