### 2.3 Environment limits

The review ran in a Linux container. There was **no Windows, no .NET SDK and no NTFS/FAT/exFAT media**. So:

- No v1 test was re-run. The baseline counts in spec §1.2 were checked by counting `[Test]` methods: 55 unit
  (11+11+18+13+2) and 93 integration (89 pass + 4 skip locally, 86 + 7 on CI). Both totals match.
- The SQLite probes used Python's `sqlite3` module (SQLite 3.45.1). The behaviours they test (WAL recovery, the
  zero-page WAL deletion, `VACUUM`/`VACUUM INTO`, checkpointing) live in SQLite's pager, WAL and vacuum code, which
  is the same on every VFS. The Windows VFS was not exercised; the claims that depend on Windows specifically are
  marked [UNV] with a gate.
- `learn.microsoft.com` and `sqlite.org` were not reachable. Microsoft documentation was read from its public source
  repositories (`MicrosoftDocs/sdk-api`, `MicrosoftDocs/win32`, `dotnet/docs`, `NuGet/docs.microsoft.com-nuget`);
  SQLite behaviour was read from the SQLite source (`src/pager.c`, `src/vacuum.c`).

## 3. Executive findings

The specification is careful, mostly faithful to the v1.0 code, and its central ideas are right: full snapshots with
shared dictionaries, a single publish transaction as the validity point, attempts kept apart from snapshots by type,
and an anchor-based definition of Unknown. The package facts it quotes are correct. It is **not** ready to authorise
all gates, for these reasons:

1. **D-09 (Library inside a scanned source) is a write-boundary regression, not a labelling question** (REV-B01).
   The capture writes into the very tree it is enumerating. The observation of that subtree becomes a function of
   StorageInventory's own timing (P4: 6,890 different WAL sizes during one capture). The spec also contradicts
   itself: §2 says no invariant is relaxed, and §16.1 says the scanned tree is read-only "always". A replacement
   design that keeps `C:\` saveable, needs no traversal change and keeps the tree write-free during enumeration is
   given in §12.4.
2. **The normative definition of `ProvenAbsent` is unsound on case-insensitive directories** (REV-B02). Three
   concrete counterexamples produce Missing or Added where the correct answer is Unknown, and the brute-force oracle
   (DIFF-P9) would enforce the wrong answer.
3. **Six high findings** need contract changes before their gates: the DLL-pinning rule points at the wrong
   directory and would create a planting risk (H01); the damaged-Library procedures destroy committed data because a
   WAL database is not one file (H02, reproduced); single-writer exclusion is per session and verification is outside
   the publish transaction (H03); identity is never re-checked after traversal (H04); the folder rules contradict the
   truth table (H05); and the audit evolution misses the new native and SQL surface (H06).
4. Fourteen medium findings are real but local: memory use of `temp_store=MEMORY` (reproduced), native file
   creation by SQLite, stall isolation, wall-clock ordering, FAT clock-shift semantics, name-cache integrity,
   lifecycle gaps, WAL growth (reproduced), an unachievable parity test, UI state ownership, identity over-claims,
   automatic drive probing, the dependency boundary and traceability.
5. **C1 can begin** (conditions in §16). C2 and C3 can begin with small conditions. C4 to C13 wait for the revisions.

**Verdict: `SPEC REQUIRES REVISION`** (§18).

## 4. Blocking findings

### REV-B01: the Inventory Library is written inside the tree being enumerated (D-09)

| Field | Content |
|---|---|
| **Severity** | Blocker (C4 path rules; C5) |
| **Affects** | D-09, D-08, LIB-06a/06c, §6.4, §2 ("None is relaxed"), §16.1 (Z1 "Read-only, always"), X-5, SEC-25, UI-07, §10.2 step 4, §11.4 |
| **Evidence** | [SRC] v1's promise: `README.md` "reports can't overwrite anything or be written inside the folder being scanned" and "What StorageInventory writes: only inside the report folder you choose, which must be outside the folder being scanned"; `docs/architecture.md` "Output lives only in a validated folder outside the scanned tree". v1 treats its own output inside the tree as a fault: `ScanEngine.cs:190` throws `OutputInsideScannedTreeException`. [SPEC] §10.2 step 4 writes staging rows *during traversal*; §6.4 "The traversal treats the Library folder as ordinary metadata … Its listed sizes are whatever they are when the folder is listed". [PROBE P4] a listing taken during a 1M-row capture saw 6,890 distinct `-wal` sizes, from 0 to 23.2 MB, and a main file that had not grown yet. [SPEC] LIB-06a blocks only a source that is the Library folder or inside it, so `%LOCALAPPDATA%\StorageInventory` (the Library's parent, containing nothing but the Library) is a valid source. [PROBE P5] closing the last connection checkpoints and deletes `-wal` and `-shm`, and `Pooling=False` (§16.2) makes connection closes frequent |
| **Failure mode** | (1) Every snapshot of `C:\` records a timing-dependent, partial copy of the capture that produced it: totals of a "Complete" snapshot depend on when the traversal reached `%LOCALAPPDATA%`. (2) Every comparison of `C:\` lists `library.sqlite3`/`-wal` among the largest Changed items and the Library folder among the fastest-growing folders; the delta is not a property of the user's storage. (3) A UI query connection that is the last to close during enumeration checkpoints and deletes the side files, so files appear and vanish in the scanned tree mid-listing. (4) Snapshot deletion, backup and migration are not locked out during a scan of a source that contains the Library, even with Save off (only Compact is, and only during a capture). (5) Scanning `%LOCALAPPDATA%\StorageInventory` produces a source made only of StorageInventory's own state. (6) The safety narrative ("the scanned tree is read-only") becomes false for the most common source, and nothing replaces v1's machine-checked idea that our own output inside the tree is a fault |
| **Required correction** | Replace D-09 with the rule set in §12.4: a write-free **enumeration window** (no Library write, maintenance or connection close/checkpoint between enumeration start and end, for any scan whose source contains the Library); capture data spooled **outside the source** (in the validated report folder, create-new, own name, covered by the v1 tripwire) or in capped memory, and imported into the Library after enumeration; the Library subtree **observed, not excluded**, and labelled; a **self-observation tripwire**; sources equal to or inside `%LOCALAPPDATA%\StorageInventory\` blocked; the zone model restated so Z1 and Z3 do not contradict each other |
| **Verification to close** | (a) Integration test: scan a fixture source that contains a fixture Library, Save on; assert that the Library files' sizes and `LastWriteTimeUtc` recorded in the new snapshot equal their values before the run, and that the anchor connection's `PRAGMA data_version` (other connections' commits) and `total_changes()` (its own) did not change during the enumeration window. (b) Audit test: the capture observer's type graph during enumeration references only the spool writer, never `LibraryDatabase`. (c) Preflight tests for the new block code. (d) Revised §2, §6.4 and §16.1 text with no contradiction |

### REV-B02: `ProvenAbsent` is unsound on case-insensitive directories

| Field | Content |
|---|---|
| **Severity** | Blocker (C7). It breaks INV-16, the release-blocking invariant |
| **Affects** | §12.2 (definitions and the soundness argument), DIFF-02 and DIFF-03 rows that use `ProvenAbsent`, DIFF-07, DIFF-P2, DIFF-P9 (the oracle "applies the §12.2 definitions literally"), TEST-D1, TEST-D2 ("case variants" are generated), D-18 |
| **Evidence** | [SPEC] §12.2 defines the anchor as the deepest ancestor that is present **by exact path**, and argues: "The child `c` of `a` … is either absent from that listing, in which case nothing below `c` can exist". [SPEC] §8.4: identity is exact-case, but directories are case-insensitive unless marked otherwise. [INF] In a case-insensitive directory, `a\c` and `a\C` are the same entry, so the absence of the exact name `c` from a complete listing proves nothing when a case variant `C` is present. [SPEC] §12.8 step 1 hints at aligning with DIFF-07 before computing anchors, but the normative §12.2 and the oracle do not |
| **Failure mode** | Counterexamples (full detail in §10.3). **CE-1:** O has `A\Photos\x.jpg`, all Ok. N: `A` is Ok and lists `photos` (a case-only rename), and `A\photos` is Unreadable. §12.2 gives Anchor_N = `A` (Listed) and so **Missing**; the truth is **Unknown (AncestorUnreadable)**. **CE-2:** O: `A` Ok lists `backup`, which is Unreadable; N: `A\Backup\y.txt`. §12.2 gives **Added**; the truth is **Unknown (NotObservableInOlder)**. **CE-3:** O: `A\Backup\…` normal; N: `A\backup` is a junction. §12.2 gives **Missing**; the truth is **Unknown (BehindLink)**. The oracle would fail a correct implementation on these cases, pushing it towards the unsound answer |
| **Required correction** | Restate §12.2 over the **aligned** folder tree, and add an unmatched-variant rule (proposed text in §10.6): anchors descend through DIFF-07-aligned folders, and a Listed folder proves the absence of child `c` only if it holds no **unmatched** child equal to `c` under a conservative case fold. The oracle implements the same definition independently. Add truth-table rows T33 to T36 (§10.4). Restate DIFF-P2 against the corrected predicate |
| **Verification to close** | T33–T36 pass; the TEST-D2 generator produces single-variant case renames combined with Unreadable, Partial and link statuses on either side; the oracle is a brute-force implementation of the corrected definition, and no Missing or Added appears under an unobservable aligned anchor in at least 10,000 generated cases |

## 5. High findings

### REV-H01: SEC-13 pins `e_sqlite3.dll` to the wrong directory

| Field | Content |
|---|---|
| **Severity** | High (C4) |
| **Affects** | SEC-13, §16.3 ("Native DLL planting" row), §5.5 "Native", D-01, D-31, BLD-07 |
| **Evidence** | [SPEC] §16.3: the resolver "loads by full path from the extraction directory (`AppContext.BaseDirectory` for single-file)". [DOC] single-file overview: natives are extracted under `%TEMP%\.net`, and `AppContext.BaseDirectory` is for "files next to the executable". [SRC] `docs/release.md`: v1's natives go to `%TEMP%\.net\StorageInventory\<hash>\`. [PKG] the provider imports `"e_sqlite3"` and registers no resolver of its own |
| **Failure mode** | A resolver built as specified looks for `<folder of the exe>\e_sqlite3.dll`; in a normal download that folder is `Downloads`. If the resolver returns no handle when the file is absent, the runtime falls back to its default probing, so every test passes on a clean machine, yet any `e_sqlite3.dll` placed beside the downloaded exe is loaded in preference and runs in-process: the classic download-folder planting vector. If the resolver throws instead, the Library never opens. The default runtime probing (extraction directory first) has neither problem, so the mitigation as written creates the risk it names |
| **Required correction** | SEC-13: "`e_sqlite3.dll` is loaded only from the single-file extraction directory, never from the executable's folder or the default DLL search order." C4 chooses the mechanism with a Windows probe (Q-11): the runtime's own probing plus a check of the loaded module, or a resolver that takes the directory from the runtime's native search directories. `AppContext.BaseDirectory` must not appear in the Library's loading code (audit rule) |
| **Verification to close** | Extended smoke test: the loaded `e_sqlite3.dll` path is under `%TEMP%\.net\StorageInventory\`; negative case: a dummy `e_sqlite3.dll` planted beside the copied exe is **not** loaded |

### REV-H02: a WAL-mode Library is treated as one file; the damaged-Library actions destroy committed data

| Field | Content |
|---|---|
| **Severity** | High (C4) |
| **Affects** | §6.5 (creation), §6.7 (Missing and Damaged actions), LIB-02, SEC-08, D-28, §6.8 ("Never: deleting any Library file") |
| **Evidence** | [PROBE P1] after a crash with 5,000 committed (`FULL`) rows still in the WAL: a main-file-only copy has no tables; renaming only the main file and creating a new Library makes **SQLite delete** the old `-wal` and `-shm`, and the quarantined file has no tables. [DOC] `pager.c` `pagerOpenWalIfPresent` deletes a WAL when the database has zero pages, which is exactly the state LIB-07 creates (a create-new 0-byte file) |
| **Failure mode** | "Keep a copy" produces an empty or stale copy. "Set aside and start a new Library" loses every committed but not yet checkpointed transaction (after the WAL growth shown in P4, that can be whole snapshots), and SQLite then deletes the only copy. The Missing state's "Create a new, empty Library" does the same when only the main file was removed (by the user, or by antivirus quarantine). A crash between renaming the main file and its WAL could also pair a main file with no WAL, silently reopening an older state |
| **Required correction** | Treat `{db, -wal, -shm, -journal}` as one unit everywhere. (1) Creation refuses while any member of the target name exists: a new state "Leftover database files", with an explicit action. (2) Quarantine renames the main file first, then every present side file to the same quarantine stem, each with `overwrite: false`; creation stays refused until the old names are gone. (3) Drop "Keep a copy" from 1.1.0 (set-aside already preserves everything), or copy every member. (4) SEC-08 and the audit rule name the exact member set. (5) State detection must not trigger a checkpoint on a database it considers damaged (Q-15) |
| **Verification to close** | Library.Tests: crash a child process with committed WAL frames; quarantine; the quarantined set opens with all committed rows; creation refused while leftovers exist; a before/after directory listing shows no file deleted |

### REV-H03: single-writer exclusion is per session, and verification sits outside the publish transaction (D-23)

| Field | Content |
|---|---|
| **Severity** | High (C4, C5) |
| **Affects** | D-23, LIB-10, SEC-19, §6.6 step 6 (recovery at every open), §10.2 steps 7 and 8, LIFE-06 |
| **Evidence** | [SPEC] mutex `Local\StorageInventory.Library.<hash>` (§6.9); recovery purges Staging rows at every open (§6.6); step 7 "Verify the invariants" is a separate read before the step 8 transaction. [DOC] `Local\` objects are per session; a mutex can be created in `Global\` without privilege |
| **Failure mode** | Two instances of the same account in two logon sessions (Windows Server, multi-session Windows, or any configuration that allows a second session per user) both acquire "their" mutex. Instance B's open-time recovery sees A's live capture as Staging, records it as Interrupted and purges its rows. If the purge lands between A's step 7 and step 8, A publishes a snapshot whose rows are partly gone, and the next comparison reports those files as **Missing**. Likelihood on single-session Windows 10/11 is low; the consequence is exactly what the lifecycle must make impossible |
| **Required correction** | (1) Exclusion visible across sessions: an exclusively held lock file in the per-user Library directory (recommended), or a `Global\` mutex (squattable by other local accounts, but only as a denial of service). (2) Recovery purges Staging rows only while holding that lock. (3) Step 7 runs inside the publish transaction (`BEGIN IMMEDIATE`; verify; update; commit). (4) Staging rows carry an owner token (capture GUID, process start time) for diagnostics |
| **Verification to close** | Concurrency test: a second `LibrarySession` on the same path (simulated second session) cannot acquire the writer lock and cannot purge; a fault-injection test deletes staging rows between verify and commit and shows the publish fails |

### REV-H04: source identity is never re-verified after traversal

| Field | Content |
|---|---|
| **Severity** | High (C5; C3 provides the capture function) |
| **Affects** | §7.5, §10.2 (evidence only at step 1), LIFE-06, ID-03 to ID-06, D-21 |
| **Evidence** | [SRC] `ScanEngine.cs:80` opens every folder by path string; no handle on the root is held across the scan. `InventoryScanner.cs:50` scans `validation.RootFullPath`, the normalised input, not the canonical path, so a SUBST or mapped letter is re-resolved on every listing. [SPEC] §7.5 ID-05 itself cites clones and rotating drives with identical layouts |
| **Failure mode** | Rotating backup drives A and B share a folder layout. A scan of `E:` (drive A) starts; the user swaps to B, or a SUBST or mapped letter is re-pointed. Later folders are listed from B with status Ok. Files on A that are not on B are then **Missing** in the next comparison of A's source, B's files are **Added**, and the snapshot is published under A's Strong identity |
| **Required correction** | Hold a 0-access handle to the root for the whole scan (the v1 `NativeMethods` pattern). After enumeration, re-read the identity evidence through that handle **and** through a fresh open of the path (filesystem type, serials, root file ID, canonical root). ## 6. Medium findings

Each finding lists severity, affected items, evidence, failure mode, required correction and verification.

**REV-M01: `temp_store=MEMORY` puts `VACUUM`'s transient database in RAM.**
Affects D-03, SEC-05, SREQ-09, SCH-09, future index-building migrations (C4). Evidence: [PROBE P3] peak RSS
117 MB (MEMORY) against 15 MB (FILE) for a 98 MB result; [DOC] `vacuum.c` attaches an anonymous temporary database.
Failure: at the spec's own projection (6.5 GB after 50 snapshots of a 2M-file drive, §15.2), Compact needs several
GB of RAM or fails; an index added by a later migration sorts in memory as well. Correction: `temp_store=FILE` with
SQLite's temporary directory set to the Library folder (`sqlite3_win32_set_directory`, exposed by the provider [PKG];
set after Microsoft.Data.Sqlite's static constructor, which may call the same function), or forbid plain `VACUUM`.
Verification: a test watches `%TEMP%` and the Library folder during Compact and during an index build; a memory
ceiling assertion in the C10 benchmark.

**REV-M02: SQLite creates files natively that the rules and lists do not cover.**
Affects LIB-02, SEC-02, SEC-06, §6.8 (backups "checked not to exist first"), §9.6, §16.2 (C4). Evidence: [PROBE P2]
`VACUUM INTO` a missing path creates the file natively; a pre-created 0-byte target works; `-journal` files appear
for the Library and for each backup; [DOC] `vacuum.c` opens the target with `SQLITE_OPEN_CREATE`. Failure: SEC-06
("the database file is created only with `FileMode.CreateNew`") is false for backups and pre-migration backups;
LIB-02's owned-file list is incomplete; a power loss mid-backup leaves a file with a valid-looking backup name.
Correction: create every backup target with `FileMode.CreateNew` in `LibraryStore`, then `VACUUM INTO` that empty
file; name it `.partial` until verified, as v1 does for workbooks; add `-journal` members to LIB-02; add a runtime
owned-file-set test. Better still: no backup or migration exists in 1.1.0 (schema 1 is the first), so SREQ-05 can
move to 1.1.x and 1.1.0 need not create any backup file at all (§16B). Verification: the owned-file-set test runs
after every lifecycle scenario.

**REV-M03: isolation covers exceptions but not stalls.**
Affects SINK-04, SINK-05, SINK-06, D-11, REQ-13 (C1 for exception classes; C5 for stalls). Evidence: [SPEC] §11.4
"When the channel is full, the scanning thread blocks"; nothing says the blocked write observes the scan's
cancellation token, and there is no progress watchdog. [SRC] `ScanEngine.IsReadFailure` never swallows
`OperationCanceledException` or `OutOfMemoryException`, but the fan-out's handling of those from an isolated observer
is not specified. Failure: a slow or stuck Library writer (antivirus locks, `SQLITE_BUSY` retries, a stalled disk)
holds the critical report path hostage, and Cancel does nothing while the thread is blocked. Correction: the blocking
write takes the scan's token; a writer that makes no progress for a set time faults itself and releases the scan;
the fan-out's rules for `OperationCanceledException` and `OutOfMemoryException` are stated. The §12.4 spool design
removes the writer thread during traversal and with it most of this finding. Verification: fault-injection tests with
a stalled writer: Cancel returns within the v1 bound; reports are byte-identical.

**REV-M04: "older" and "newer" follow the wall clock.**
Affects DIFF-01, HIST-01, the History order (C6, C7). Evidence: [SPEC] §12.1 "ordered by `finished_utc`". Failure: a
clock set back (a dead CMOS battery, manual change, a VM restore) swaps the order, so Added and Missing swap as well.
Correction: capture order is the authority (a monotonic per-Library sequence, for example `snapshot_id`); timestamps
are displayed and a clock anomaly is flagged. Verification: unit test with inverted timestamps.

**REV-M05: DIFF-05 turns an undecidable case into "Unchanged".**
Affects DIFF-05, D-13, T28, Q-03 (C7). Evidence: [SPEC] same size and exactly ±1 hour on FAT/FAT32 gives Unchanged.
Failure: a genuine rewrite of the same size is reported Unchanged; offsets other than one hour (time-zone changes,
+5:30 or +5:45 zones) are reported Changed; exFAT written by devices without the UTC-offset field behaves like FAT
but is excluded. Correction: a change-status of **Indeterminate (PossibleClockShift)**, counted separately and never
as Unchanged, for any whole-quarter-hour offset up to ±14 h on FAT, FAT32 and exFAT until Q-03 proves exFAT safe.
Verification: T28 revised, plus offsets of 0:30, 5:45 and −3:00.

**REV-M06: name-cache lifetime and name integrity.**
Affects §11.4, SCH-08, Q-07 (C5). Evidence: [SPEC] an LRU name cache backed by `name`; `name_id` is a rowid; no
foreign keys on `file_obs`; §9.5 checks folder references but not `name_id`. [INF] after a rolled-back batch, a
cached `name_id` can point to nothing, or to a different name that later reuses the rowid. Failure: if a cache
outlives a rollback (reused across captures, or a retry within one), files are stored under the wrong name, silently.
Correction: the cache belongs to one capture and is discarded on any rollback; add to §9.5 "every `file_obs.name_id`
and `folder_path.name_id` exists" and "every non-root `folder_obs` has its parent's `folder_obs` in S". Verification:
fault-injection test: roll back a batch, continue, and assert the invariants.

**REV-M07: lifecycle gaps.**
Affects §6.6, §6.8, §10.2, §10.3, `AttemptOutcome` (C5, C6). Evidence: [SPEC] open-time recovery covers Staging only;
there is no rule for a snapshot left in `Deleting`; recovery failure (for example the disk is still full) is
unspecified; the outcome table has no row for Cancel during "Saving to History"; volume and source rows and the ID-04
answer are committed at step 2 and survive a cancelled capture; backups have no partial state. Failure: invisible but
permanent rows, sources with no snapshot shown in Sources, a Library that fails to open because recovery cannot
write. Correction: resume `Deleting` at open; recovery is best effort and never makes the Library unopenable (saving
disabled until it succeeds); an outcome row and code for "save cancelled"; create volume and source rows in the
publish transaction, or hide sources that have no published snapshot; `.partial` backups. Verification: TEST-T1
gains these rows.

**REV-M08: WAL growth and its high-water mark.**
Affects §5.6, §10.2 step 9, PERF-03, D-03 (C4, C5). Evidence: [PROBE P4] with one reader open during a 1M-row capture
nothing could be checkpointed, and the WAL reached 23.2 MB; after the reader closed, a PASSIVE checkpoint left the
WAL file at 23.2 MB; only TRUNCATE shrank it. Failure: a 2M-file capture with a History page open leaves a WAL of
roughly one snapshot (about 130 MB) on disk permanently; after a crash, opening the Library replays it. With D-09 that
file also lands in the next `C:\` snapshot. Correction: `journal_size_limit`, a TRUNCATE checkpoint after publish and
when idle, and readers that do not hold long transactions during a capture. Verification: C10 measures the WAL size
after capture with the UI open.

**REV-M09: TEST-H2 (Library and CSV browsing return "the same rows in the same order") cannot pass.**
Affects §13.4, TEST-H2, REQ-08, §9.2 (C6). Evidence: [SRC] v1 breaks size ties by discovery order:
`ReportWriters.cs:19` (folders by index) and `:77` (files by sequence). Schema 1 stores neither a folder discovery
index nor a file sequence, and `path_id` follows the *first* snapshot's order. Failure: ties are common (0-byte files,
empty folders), and the 2,000-folder and 1,000-file cut-offs fall inside them; the test either fails or gets weakened
ad hoc. Correction: store a per-snapshot discovery ordinal (4 bytes per row; measure the cost), or redefine the parity
as "equal row sets above the tie boundary, ties ordered by path" and document it. Verification: a parity fixture with
many equal-size items.

**REV-M10: the UI decomposition leaves the ownership of long-lived state undefined.**
Affects §14.1, UI-01, UI-02, C2, C8. Evidence: [SRC] `MainViewModel.Scanning.cs:13` owns the scanner, and lines
59–101 own the cancellation source, the task and the results; `MainWindow.xaml.cs:31` waits on it when closing.
[SPEC] "one view model per page, and a small navigation service"; UI-02 requires the scan to survive navigation.
Failure: a per-page view model either kills the scan on navigation or duplicates it. Library state (Available,
Damaged, In use) changes during a session with no defined propagation; a Compare that takes 10 s and 200 MB has no
defined lifetime when the user navigates away. Pages that construct Library services directly can only be tested
against real databases. Correction: app-lifetime services with interfaces: `ScanSession` (scan, cancel, progress,
result, save outcome), `LibrarySession` (state as an observable value), `ICatalogue`, `ICompareService` and
`ISourceStatus`, with fakes for page tests. Cancel and close during "Saving to History" need specified behaviour. C2
should already move the scan out of `MainViewModel` into `ScanSession` to avoid rework in C8. Verification: TEST-U1
gains "navigate away and back during a scan", and "Library becomes Damaged while Compare is open".

**REV-M11: identity claims are stronger than the evidence.**
Affects §7.3 to §7.6, ID-05, ID-06, D-21 (C3). Evidence: [DOC] the NTFS root directory is MFT record 5 on every
volume, so its file ID does not tell volumes apart (the full 128-bit value on two volumes is for C3 to confirm,
Q-13). [SRC] `PathPolicy.cs:118` blocks any source whose path passes through a reparse point, which includes a
folder mount point, yet §7.6 describes folder-mounted sources as supported. [SPEC] `root_key` is case-folded while
item identity is exact-case (§8.4). Failure: ID-05's second trigger (a different root file ID *and* a different
capacity) never fires for whole-volume NTFS sources, so a clone that is not mounted at the same time merges
silently; "never silent merges" (ID-06) is not true for clones; in a case-sensitive parent, `\Media` and `\media` are
two folders that become one source. Correction: state plainly that clones are indistinguishable unless mounted
together; remove or reword the root-file-ID heuristic (it works for subfolder sources); keep folder-mount sources
blocked and correct §7.6; make `root_key` exact-case, with a case-insensitive key used only to *suggest* a match.
Verification: C3 records root file IDs from two NTFS volumes; TEST-I3 includes a clone case whose expected result is
"merged (documented limitation)".

**REV-M12: automatic drive probing at startup is new automatic I/O.**
Affects REQ-04, ID-07, D-32 (C8). Evidence: [SPEC] §7.7 reads identity from every ready fixed and removable drive at
startup and on refresh; the test matrix has no test for ID-07 or D-32. [SRC] v1 touches only the paths the user
chooses. Failure: sleeping external disks spin up at every start; a slow drive delays the Sources page; the "never
network or optical" promise is not machine-checked. Correction: probe on demand (opening a source, or a "Check
drives" action) in 1.1.0 and consider an automatic sweep in 1.1.x; a unit test with a fake drive list proves that
network and optical drives are never probed. Verification: that unit test.

**REV-M13: the dependency boundary is drawn around the wrong code.**
Affects D-02, D-10, SINK-02 (C1, C4, C7). Evidence: [SPEC] D-10 puts "persistence, comparison, history" in the
package-referencing assembly; §11.2 makes `IScanObserver` **public** in Core in C1. [SRC] `IScanSink.cs` says it
"becomes public only when a second real consumer exists", and the roadmap puts the public integration contract in
1.2. [INF] with a plain `ProjectReference`, App receives the SQLite packages at compile time. Failure: the diff engine,
which carries the release-blocking invariant, can only be tested with SQLite underneath; App code can reference
`SqliteConnection` and only a text rule stops it; a public observer API is frozen before its 1.2 design. Correction:
keep comparison, history and identity semantics in package-free code (Core or a new package-free assembly) working on
row streams, with `StorageInventory.Library` reduced to the SQLite adapter; package references with
`PrivateAssets="compile"`, so App gets runtime assets only; `IScanObserver` internal, with `InternalsVisibleTo`
until 1.2. Verification: a reflection audit shows the diff assembly references no SQLite assembly, and App does not
reference `Microsoft.Data.Sqlite` at compile time.

**REV-M14: traceability gaps.**
Affects §3.2, §18, §19 (all gates). Evidence: [SPEC] §3.2 says every SHOULD "has its own acceptance criteria in its
gate", but only SREQ-01 to SREQ-03 have a gate (C9); the "Covers" column uses wildcards (`UI-*`, `HIST-*`, `LIFE-*`,
`DIFF-*`, `SEC-*`, `PERF-*`, `BLD-*`); no test covers ID-07/D-32, UI-02, REQ-04's capacity and free space, REQ-07's
top-N lists, §6.8's deletion scopes, or cancellation while blocked (SINK-05); REQ-01 lists four Library states,
§6.7 defines eight; ID-04 is cited three times but never stated; SEC-05's check runs only inside a local benchmark.
Correction: a requirement-to-test table without wildcards; gates and acceptance criteria for every SREQ kept in
1.1.0 (or an explicit move to 1.1.x); REQ-01 aligned with §6.7; ID-04 written out. Verification: a traceability
check (each MUST has at least one named test).

## 10. Unknown/Missing audit

### 10.1 Method

Each rule in §12 was checked against the v1 traversal that produces the data (`ScanEngine`, `FolderAggregator`), then
attacked with the scenarios the brief lists. The soundness argument of §12.2 was re-derived from first principles.

### 10.2 What the v1 data does and does not prove

- [SRC] `FolderScanStatus.Ok` means the listing enumerated to the end without an exception (`ScanEngine.cs:94–126`),
  with `IgnoreInaccessible = false` and `AttributesToSkip = 0`. So Ok is a complete listing **of names as the
  directory reported them at that moment**. This supports `Listed`.
- [SRC] A folder deleted between discovery and listing becomes `Unreadable (NotFound)`, so its contents are Unknown,
  not Missing. Conservative and acceptable.
- [SRC] A folder that became a link after being listed becomes `ReparsePointSkipped` with updated attributes
  (`BecameReparsePoint`). `OnFolderDiscovered` values are therefore provisional; only the finalised record counts
  (§14A).
- [DOC] Listing metadata on NTFS may lag (O06). This affects Changed and Unchanged, never existence.
- [INF] **The gap:** "complete listing proves absence of an exact name" holds only in a case-sensitive directory.
  In the default case-insensitive directory it proves absence of every case variant **only if none is listed**
  (REV-B02).

### 10.6 Proposed normative text for §12.2 (for the revision task)

> **Alignment first.** Folders of O and N are aligned by `path_id`, then by DIFF-07 (same type, equal under the
> fold F, unique among the *unmatched* children on both sides). Anchors and `ProvenAbsent` are evaluated on this
> aligned tree.
>
> **Case-aware absence.** Let `a` be the deepest aligned, present proper ancestor of item `p`, and let `c` be the
> child of `a` on the path to `p`. `p` is proven absent in S only if `a` is Listed in S **and** one of these holds:
> (i) `a` has no **unmatched** child equal to `c` under F; (ii) `a` has two or more children equal to `c` under F
> (the directory was case-sensitive when it was listed, so exact absence is proof); (iii) the only such child is a
> file and `p` lies strictly below `c`. A child counts as matched only if it is matched to an item of the same type.
> Otherwise `p` is Unknown with the reason from the anchor, or `CaseAmbiguous`.
>
> **F** is the union of `StringComparison.OrdinalIgnoreCase` and per-code-unit `ToUpperInvariant` equality (Q-14).
> A wider F only ever produces more Unknown, never more Missing.

### 11.6 Full-snapshot scaling (D-07)

**Measured** (§15.1: synthetic trees, proxy engine, TEXT names, writes alone): 61 to 64 B per file observation;
2M-row write about 10 s; compare of 2 × 2M in 3.3 s; delete 3.1 s; `VACUUM` 4.8 s at 269 MB.

**Projected** (linear, not measured):

| Snapshots of a 2M-file source | Library size | Of a 250k-file source |
|---|---:|---:|
| 10 | ~1.3 GB | ~0.15 GB |
| 50 | ~6.5 GB | ~0.8 GB |
| 100 | ~13 GB | ~1.5 GB |

- **Indexes:** `file_obs` and `folder_obs` are clustered `WITHOUT ROWID` tables with no secondary index, so index
  overhead grows with distinct names and paths, not with snapshots. The `name` `UNIQUE` index stores each name twice.
- **Fill factor:** `snapshot_id` leads the key, so each snapshot appends at the right edge. Within a snapshot,
  traversal order is not `(folder_path_id, name_id)` order once folders have been added or renamed, so pages split
  and fill below 100% [INF]. The probe's figures may be optimistic if it inserted in key order (not stated).
  Mitigation: import in key order (natural with the §12.4 spool).
- **Deletion and `VACUUM`:** deletion frees pages without shrinking the file; later snapshots reuse them (fine on
  SSD, scattered on HDD). `VACUUM` needs free space about equal to the Library and, as specified, RAM of the same
  size (M01). Deleting a 2M-file snapshot also pushes about a snapshot's worth of pages through the WAL (M08).
- **Startup:** open time does not grow with size (no integrity check), except WAL replay after a crash (M08).
- **Backups:** `VACUUM INTO` doubles the disk space on the system drive, which argues for moving SREQ-05 to 1.1.x.
- **When to reconsider delta storage** (triggers the app can observe locally, since there is no telemetry):
  (1) a real traversal-order capture costs more than 90 B per file observation (C5/C10); (2) the Library exceeds
  10% of its volume's capacity or 20 GB, which the app shows as a warning and users can report; (3) comparisons of
  sources over 1M files show at least 95% Unchanged across 10 consecutive snapshots (deltas would save ten times or
  more); (4) capture time misses PERF-02 because of write volume.

## 12. Inventory Library and write-boundary audit

### 12.1 What D-09 changes

Both statements cannot be true.

### 12.4 Recommended rule set (replacement for D-09 and §6.4)

1. **Enumeration window.** For any scan whose canonical source contains the canonical Library folder (Save on or
   off), StorageInventory performs no Library write, no maintenance (delete, compact, backup, migrate), no
   checkpoint and no Library connection close between enumeration start and enumeration end. A session-lifetime
   **anchor connection** is held so that other connections never close last.
2. **Out-of-source capture.** During enumeration the capture observer appends only to a private, versioned spool
   file created with `FileMode.CreateNew` in the validated report folder, named with the run ID and added to the
   run's own names (so the v1 tripwire covers it). After enumeration and the v1 reports, `InventoryRun` imports the
   spool into Staging (in primary-key order), verifies inside the publish transaction and publishes. The spool is
   deleted by the existing three-proof rule on success and listed as an incomplete artefact otherwise. A capped
   in-memory spool (A5) is an allowed optimisation. One code path for every source keeps testing simple; a
   direct-write fast path is allowed only if C10 shows it is needed and only when the Library is provably outside
   the source.
3. **Observed, not excluded.** The traversal treats the Library folder as ordinary metadata (v1 reports and parity
   unchanged). The snapshot records `library_inside_source`, the Library's root-relative path and a pre-enumeration
   fingerprint of the Library files (size and `LastWriteTimeUtc`). The UI labels the folder.
4. **Self-observation tripwire.** Fingerprint the main database file before and after enumeration. Any difference
   makes the capture `NotEligible (LibraryChangedDuringScan)`.
5. **App-data root block.** A source equal to or inside `%LOCALAPPDATA%\StorageInventory\` is blocked (a new
   `PathIssue` code), extending LIB-06a.
6. **Zone model.** Z1 is read-only, with one exception: Z3 may be written outside the enumeration window of any scan
   that contains it. §2 lists this as a stated relaxation of the v1 "no writes inside a source" promise, with the
   rules above as its narrower replacement, and README's "What StorageInventory writes" names the Library.

clone limitation stated in the UI's identity help, and removal of the ineffective root-file-ID trigger for volume

| Power loss before publish | `NORMAL` batches may roll back; the database stays consistent; Interrupted | Yes |
| Power loss after publish | Durable | Yes (WAL + `FULL`). The publish commit's sync of the WAL also makes the earlier `NORMAL` staging frames durable |
| Disk full during capture | Batch rolls back; purge now or at next open | Partly: the purge itself needs WAL space; recovery failure at open is unspecified (M07) |
| `SQLITE_BUSY` | Snapshot failure, no retry loop | Yes; a stall before the timeout is M03 |
| WAL or journal leftovers | Not addressed | **No**: creation and quarantine mishandle them (H02) |
| Schema migration failure | Rolls back; backup kept; Incompatible | Yes; backups must be created create-new (M02). Not exercised until schema 2 |
| Report succeeds, snapshot fails | Reports valid; SnapshotFailed | Yes (LIFE-05) |
| Snapshot would succeed, report fails | No snapshot (D-06) | Yes (O09) |
| Cancellation before traversal (identity prompt) | Nothing, or purge | Yes, but volume and source rows committed at step 2 survive (M07) |
| Cancellation during traversal | Purge; attempt | Yes, if the blocked channel write observes the token (M03) |
| Cancellation during v1 report writing | Scan Cancelled; purge | Yes |
| Cancellation during "Saving to History" | **Not specified** | No (M07) |
| Exception after enumeration, before publication | Isolated observer faults; purge | Yes |
| Incomplete scan | Published Incomplete | Yes |
| Second app instance, same session | "In use"; runs without history | Yes |
| Second instance, other session | Both writers; recovery can purge a live capture | **No (H03)** |
| Library unavailable mid-run | Treated as a write error | Yes |
| Volume or letter swapped mid-scan | Published under the old identity | **No (H04)** |
| Snapshot in `Deleting` at a crash | **Not specified** | No (M07) |

**Can an invalid observation become eligible for comparison?** As specified, yes, through H03 (rows purged between
verify and publish), H04 (another filesystem observed under the source's identity) and, if a cache outlives a
rollback, M06 (wrong names). D-09 adds timing-dependent values rather than invalid rows. With H03, H04, M06 and B01
corrected, no path remains that this review could find.

### 14A. Scanner and sink architecture audit

| Concern | Finding |
|---|---|
| Lifecycle ambiguity | `OnFolderDiscovered` carries attributes and a reparse flag that can change before listing (`BecameReparsePoint`); only `OnFolderFinalised` values are authoritative. State this in SINK-02. §10.2 lists folder insertion (step 6) after the reports finish (step 5), while SINK-03 delivers `OnFolderFinalised` before `OnScanEnded`, which is before the v1 report writing ends; clarify when the rows are buffered or written |
| Order-dependent sinks | The contiguity guarantee (SINK-03 #3) holds for `OnFile` runs per folder; `OnFolderDiscovered` for children and `OnError` for entries interleave with them. Say "contiguous with respect to other folders' files" |
| One sink corrupting another | Records are immutable (`readonly record struct`, sealed records); `in` parameters. No path found |
| Back-pressure | The blocking channel lets the isolated observer stall the critical path (M03). The §12.4 spool removes it |
| Transaction duration | 50,000-row batches are short; the capture-long Staging row is fine. Move verification into the publish transaction (H03) |
| Memory growth | Channel (about 6 MB), name cache (tens of MB), `folderIndex → path_id` (O(folders)): within PERF-11. With A5 the spool is O(files) and needs a cap |
| Duplicate observation | A file reparse point produces both `OnFile` and an informational `OnError`: expected, and already in v1's counts |
| Error-domain confusion | The v1 `OutputGuardSink` turns `IOException` into `ReportWriteException`; it must wrap only the critical observer, or a Library I/O error fails the scan as `OutputError` (TEST-O3 must cover it); OCE and OOM handling must be stated (M03) |
| Public contract | `IScanObserver` public in C1 is premature (M13) |

Reports and snapshots do come from one observation. The only intended coupling is D-06. The unintended ones are
stalls (M03) and the error guard.

### 14B. UI architecture audit

The page list separates the concerns the brief names: Scan (setup, progress, results as v1's stages), Sources,
History, Compare, Browse, Search and Settings/About. The weak point is **state ownership**, not page separation
(M10):

- Scan state must live in an app-lifetime `ScanSession`, not in a page view model (UI-02). `MainViewModel` owns it
  today (`MainViewModel.Scanning.cs:13`, `:59`).
- Library state must be an observable service value that every page reacts to (Available to Damaged mid-session).
- Compare results (up to 200 MB) need a lifetime tied to the page, with cancellation on navigation.
- Online probing (ID-07) updates Sources asynchronously; with M12 it becomes on demand.
- `PublishedSnapshotId` can be constructed only by the catalogue; page tests need a test factory
  (`InternalsVisibleTo`) or a fake catalogue.
- v1 UI tests drive real windows on an STA thread (`UiHost`); page view models that depend on interfaces can also be
  unit-tested without WPF.

C2's "pixel-compared against v1" will necessarily differ once a navigation list exists; the acceptance should say
"only the shell chrome differs".
