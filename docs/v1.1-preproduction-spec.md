> depends on them starts. Nothing here changes v1.0 behaviour. v1.0 is described by the code on `main` and by the

| | Question it answers |
|---|---|
| **v1.0** | "What exists on this storage right now?" |
| **v1.1** | "What existed before, what exists now, what changed, and **what can we actually prove?**" |

### 1.4 Native API surface (v1.0)

There are exactly **two** P/Invokes, both in `src/StorageInventory.Core/Paths/NativeMethods.cs`. They are enforced by
`The_only_native_calls_are_two_read_only_kernel32_functions`:

- `kernel32!CreateFileW` with `desiredAccess = 0` and `FILE_FLAG_BACKUP_SEMANTICS`, to get a directory handle only;
- `kernel32!GetFinalPathNameByHandleW`, for the canonical location used by the alias checks.

### 1.5 Write, delete, rename and launch surface (v1.0)

| Capability | Only location | Guard |
|---|---|---|
| Create a directory | `ReportRun.EnsureOutputFolder` | Validated output folder only |
| Create a file | `ReportRun.CreateNew` (`FileMode.CreateNew`) | Only this run's six names, only directly in the output folder, and the folder is re-checked for being a reparse point |
| Delete a file | `ReportRun.DeleteOwnTemporaryFile` | Three proofs: created by this run, in the output folder, and exactly the temporary name |
| Rename a file | `ReportRun.PublishOwnWorkbook` (`File.Move(..., overwrite: false)`) | Same three proofs |
| Launch a process | `ReportOpener.Open` (ShellExecute) | Allow-list of this finished run's three CSVs, its workbook and its folder, and only on an explicit click |

### 1.6 Public contracts (v1.0)

- **`IStorageInventoryScanner`** has the single method `ScanAsync(StorageScanOptions, IProgress<StorageScanProgress>?, CancellationToken)`. It
  never faults for scan, output or cancellation problems.
- **`StorageScanOptions`** (`RootPath`, `OutputPath`, `SortFiles`, `ReparsePoints`, `ProgressInterval`) and
  `StorageScanProgress`.
- **`StorageScanResult`** has private constructors and the factories `ForFinishedScan`, `ForCancelled` and
  `ForFailed`. Its invariants:
  - `Finished` ⇔ `Complete | Incomplete`;
  - `Reports != null` ⇔ `Finished`;
  - `Complete` ⇔ `root.SubtreeComplete`.
- **Records** (`src/StorageInventory.Core/Records.cs`): `FileInventoryRecord` (raw values, UTC, bytes), `FolderInventoryRecord`
  (`Status`, `StatusReason`, `SubtreeComplete`), `ScanErrorRecord`, `ScanTotals`, `ReportSet`, `PhaseTimings` and `ScanFailure`.
- **Enums** (`ScanEnums.cs`): `ScanCompletionState`, `ScanErrorType` (the names match the PowerShell reference), `FolderScanStatus`,
  `ScanFailureKind`, `ReparsePointPolicy` (whose only value is `NeverFollow`) and `ScanPhase`.
- **Path policy:** `PathPolicy.Validate` returns `PathValidationResult` and `PathIssue`s with stable codes.
- **Reports:** `ReportCsvReader`, `ReportExplorer` (reads **CSV reports**), `WorkbookExporter` and `FileTypeCatalog`.
- **Internal seam:** `Scanning/IScanSink` has `OnFile(in FileInventoryRecord, int folderIndex)` and `OnError(ScanErrorRecord)`. It has **no
  lifecycle and no folder-discovery callback**; the folder table exists only inside `ScanEngine.Folders` (see §11).

### 1.7 Persistence and other behaviour (v1.0)

- **Nothing is persisted** apart from the reports the user asks for. There are no settings, registry entries, logs or caches, and the audit
  forbids `IsolatedStorage` and `Properties.Settings`.
- **Reproducibility:** as §1.3. The app's version is `1.0.0` everywhere.
- **The results screen depends on the CSV reports.** `ExplorationViewModel` → `ReportExplorer` reads `scan.Reports`. This
  matters for any "snapshot-only" scan (§3, D-24).

### 1.8 Discrepancies found and how they are resolved

| # | Finding | Resolution |
|---|---|---|
| X-1 | `docs/architecture.md`, "File identity", says NTFS file IDs "can change after defragmentation of some file systems or on copy". Microsoft's documentation says **NTFS** file IDs stay the same until the file is deleted. **FAT** file IDs derive from the directory entry's position, so they can change after third-party defragmentation or some renames. ReFS 64-bit IDs are not unique. | Correct `docs/architecture.md` in gate C3 (§8 has the evidence). The request's framing is otherwise consistent |
| X-2 | `IScanSink` has no lifecycle, and folders are never announced to sinks. A snapshot writer cannot key file rows to folders without that. | Resolved by the C1 sink redesign (§11) |
| X-3 | The roadmap says "Persistent index: SQLite or equivalent, introduced only once snapshots need it". The request asks SQLite to *earn* the decision. | §5 does the comparison. Consistent |
| X-4 | The request expects "the WPF app state machine" to be larger than it is. `MainWindow.xaml` is 388 lines, and the stages are `AppStage { Setup, Scanning, Results }`. | The decomposition is still needed before adding more screens (C2), but it is modest |
| X-5 | The default Library location (`%LOCALAPPDATA%`) lies **inside `C:\`**, the most common scan source. v1's rule "outputs are never inside the scanned tree" cannot hold for the Library without making `C:\` unscannable. | This needs an explicit, reviewed exception: D-09, §6.4 |

## 2. v1.0 invariants

All of these are `CONFIRMED` (enforced by v1 code and tests) and remain in force in v1.1 unless a decision in §20 says
otherwise. **None is relaxed by this specification.**

| ID | Invariant | Evidence (v1.0) |
|---|---|---|
| INV-01 | The contents of scanned files are never opened or read. Only listing metadata is used | `ScanEngine` (`FileSystemEnumerable`), `SecurityAuditTests` |
| INV-02 | Scanned files and directories are never created, changed, moved, renamed or deleted, and their attributes and timestamps are never set | `SecurityAuditTests.File_creation_happens_only_in_ReportRun`, `Deletes_and_renames...` |
| INV-03 | Reparse points are never followed during traversal (`NeverFollow` is the only policy), and folders are re-checked just before they are entered | `ScanEngine.BecameReparsePoint`, `ScanEngineTests` |
| INV-04 | No administrator rights (`asInvoker`) and no elevation requests | `The_app_never_asks_for_elevation` |
| INV-05 | No telemetry, analytics, crash reporting, auto-update or automatic network activity. A network location is touched only if the user chooses it | `No_network_registry_dynamic_code_or_persistence_APIs` |
| INV-06 | No accounts, cloud services, registry writes, services, scheduled tasks or startup entries | same |
| INV-07 | Existing user files are never overwritten: creation is create-new only, and renames never replace | `ReportRun`, no-clobber race tests |
| INV-08 | Reports are never written inside the scanned tree (checked by validation before the run and by a tripwire during it) | `PathPolicy`, `OutputInsideScannedTreeException` |
| INV-09 | Incompleteness is explicit: per folder (`Status`, `SubtreeComplete`) and per scan (`ScanCompletionState`) | `FolderAggregator`, `StorageScanResult` factories |
| INV-10 | Cancelled or failed output is never presented as valid: there are no `Reports`, and created files are listed as incomplete and never deleted silently | `StorageScanResult.ForCancelled/ForFailed` |
| INV-11 | CSV reports are human and external-tool exports. They are **not** the internal persistence contract | `docs/architecture.md` "Reports vs snapshots" |
| INV-12 | The v1 report format (columns, formula guard, encoding, ordering) matches the PowerShell reference line for line | `ParityTests` |
| INV-13 | Scanning uses bounded memory: files are streamed, and memory grows with the folder count plus a 24-byte-per-file sort index | `CsvReportSink`, `docs/benchmarks/native.md` |
| INV-14 | Core has no UI, process, network or registry dependency | `Core_has_no_UI_process_or_network_dependencies` |
| INV-15 | The build is reproducible: a clean publish gives a byte-identical exe | `docs/release.md` |
| INV-16 | **UNKNOWN MUST NEVER COLLAPSE INTO MISSING.** Absence is evidence only where the observation proves the location was fully observed | `docs/integration-consumers.md`, `docs/roadmap.md` (v1 preserves the data; v1.1 must enforce it mechanically, §12) |

The **scanned tree stays read-only**. The only new writable surface in v1.1 is the **Inventory Library** (§6), which
StorageInventory owns. The owned write surfaces are therefore:

1. the scanned tree: read-only, as in v1;
2. the report output folder: create-new only, as in v1;
3. the Library: owned, transactional, and never destroyed automatically (§6).

## 4. Non-goals and deferred work

### 4.1 Permanent non-goals (unchanged from `docs/roadmap.md`)

- Reading, hashing or fingerprinting file contents; thumbnails, previews or media interpretation (EXIF and similar);
  perceptual hashing.
- Duplicate judgement, classification or organisation of content.
- Moving, renaming or deleting user files, and cleanup automation.
- Telemetry, analytics, crash reporting, accounts, cloud sync and auto-update.
- Requiring administrator rights.

### 4.2 Deferred beyond v1.1.0

| Item | Why deferred | Revisit when |
|---|---|---|
| A user-chosen or movable Library location; multiple Libraries | Needs persisted settings and a safe "move Library" operation (§6.2) | 1.1.x, after the Library has shipped |
| Move/rename detection and per-file IDs | §8 | A reviewed ID-capable enumeration design exists (1.2 candidate) |
| Automatic retention | Destructive policy | Real Library sizes are reported by users |
| Scheduled or background scans; USN journal; file watchers | INV-06; no measured need | Full scans are shown to be too slow for real users |
| Cross-snapshot search and a query language | No proven need | After SREQ-01 ships |
| Merging histories across a reformatted volume | Identity semantics (§7.6) | User demand |
| Delta or deduplicated snapshot storage | Full snapshots measured at about 64 B per file observation (§15) | A Library passes the budget in PERF-09 |
| Regenerating v1 CSV reports from a stored snapshot | Parity risk: `FullPath`, local-time rendering | 1.2 |
| A public integration contract, NDJSON export and a CLI | Roadmap 1.2 and later | 1.2 |
| Library encryption | Needs a non-default SQLite build (SQLCipher); licensing and key handling | On request |
| "Show in Explorer" for historical items | It would launch paths read from the database (SEC-15) | Never for untrusted DB content; possibly for live verified paths in 1.2 |

## 5. Persistence ADR

**ADR-001: the v1.1 persistent store.** Status: **PROPOSED** (D-01). It changes the v1.0 dependency policy, so it
needs explicit approval.

### 5.1 Context and constraints

- **v1.0's dependency posture:** zero package references, a two-package allow-list for runtime packs, byte-identical
  builds, and a machine-checked audit of every write and native API (§1.3–1.5).
- **The workload (measured and projected, §15):**
  - 2,000,000 file observations and about 470,000 folders per snapshot on a real system drive;
  - tens of snapshots per source;
  - these queries:
    - ordered comparison of two snapshots;
    - aggregates per snapshot;
    - top-N by size;
    - substring search over names;
    - per-folder totals over time.
- **Integrity:** a partial snapshot must never be visible (§10). A crash or power loss must never corrupt earlier
  snapshots.
- **Privacy:** the store holds file names, paths, sizes and timestamps (§16).

### 5.2 Candidates

| | Candidate | Packages (exact) | Native code shipped | Licences |
|---|---|---|---|---|
| **A** | **SQLite via `Microsoft.Data.Sqlite.Core` plus SQLitePCLRaw, with the provider set explicitly** | `Microsoft.Data.Sqlite.Core` 10.0.12, `SQLitePCLRaw.core` 2.1.12, `SQLitePCLRaw.provider.e_sqlite3` 2.1.12, `SQLitePCLRaw.lib.e_sqlite3` 2.1.12. Transitive: `System.Memory` 4.5.3 from SQLitePCLRaw.core's netstandard2.0 group, expected to be pruned by the .NET 10 SDK *(not verified)* | `e_sqlite3.dll` (win-x64) | MIT (Microsoft.Data.Sqlite); Apache-2.0 (SQLitePCLRaw); SQLite is public domain |
| B | SQLite via the `Microsoft.Data.Sqlite` metapackage (bundle) | A's packages plus `SQLitePCLRaw.bundle_e_sqlite3` 2.1.12 | same | same |
| C | SQLite via **Windows' `winsqlite3.dll`** (`SQLitePCLRaw.provider.winsqlite3`, or our own P/Invoke) | `SQLitePCLRaw.core` and `provider.winsqlite3` 3.0.5, or none | none (it's an OS component) | Apache-2.0 / OS |
| D | Our own P/Invoke to a bundled `e_sqlite3.dll` (no ADO.NET layer) | `SQLitePCLRaw.lib.e_sqlite3` only | `e_sqlite3.dll` | Apache-2.0 / public domain |
| E | `System.Data.SQLite` 2.0.4 | `System.Data.SQLite` (and its interop native) | `SQLite.Interop.dll` / native | The nuspec carries no licence metadata *(not verified further)* |
| F | **ESENT** (`esent.dll`, part of Windows) via `Microsoft.Database.ManagedEsent` 3.2.0 or our own P/Invoke | 1 or 0 | none (OS) | MIT (ManagedEsent) |
| G | **Custom immutable snapshot files** (sorted binary rows plus a manifest per snapshot) | none | none | ours |
| H | LiteDB 5.0.21 | `LiteDB` | none | MIT |

The package facts come from the nuget.org v3 API, queried in this task (versions, dependency groups and licence
expressions). Microsoft's documentation on custom SQLite versions confirms how bundles and providers fit together. It
lists `bundle_winsqlite3` as using "winsqlite3.dll, the system SQLite library on Windows 10".
SQLitePCLRaw's `v3.md` records that **`bundle_winsqlite3` was removed in 3.0**, and that `lib.e_sqlite3` is replaced by
`SourceGear.sqlite3` in 3.x. `Microsoft.Data.Sqlite` 10.0.12 still depends on SQLitePCLRaw **2.1.12**.

| Maintenance burden | Low: a mature engine, and Microsoft maintains the ADO.NET provider | medium: behaviour differs between OS builds | high | high |

### 5.4 Decision

**Choose A**: SQLite through `Microsoft.Data.Sqlite.Core` 10.0.12, with SQLitePCLRaw 2.1.12 (`core`,
`provider.e_sqlite3`, `lib.e_sqlite3`) and the provider set **explicitly** at startup
(`SQLitePCL.raw.SetProvider(new SQLite3Provider_e_sqlite3())`) rather than through the bundle's batteries
initialiser.

Reasons:

1. **The engine version is pinned and the same everywhere.** CI, contributors and users run the same SQLite, so behaviour and
   test results carry over. Option C cannot promise this.
2. **SQL makes the MUST scope simple and fast.** The measured diff, top-N, search and aggregate timings (§15) all
   meet the budgets without custom indexes or custom storage code. Options F and G would put a storage engine inside
   the product's safety perimeter.
3. **Durability and corruption behaviour are documented** by SQLite (WAL, `synchronous`, `integrity_check`), so the
   lifecycle in §10 can rest on published guarantees.
4. **The dependency stays contained.** It lives only in a new assembly, `StorageInventory.Library`. Core keeps its
   zero-package, no-network, no-UI rules (SEC-01).

Rejected:

- **B:** the bundle only adds an initialiser that relies on reflection. A has the same engine with one fewer package.
- **C:** the engine is unpinned and differs by OS build; no documented app-level support was found; SQLitePCLRaw
  dropped the bundle. This stays the fallback if a bundled native DLL is ever unacceptable. It would keep the build
  free of native files, but INV-15 would then cover only our code and not the engine.
- **D:** more of our own unsafe interop code, to save one managed layer. A is safer to review.
- **E:** unclear licence metadata, and a non-standard native layout.
- **F:** the ISAM API has no query language, so we would write and own large amounts of unsafe interop.
- **G:** we would own format design, integrity checking, indexing and search. It is attractive for a future export
  format (1.2), but not for the store.
- **H:** unproven at 100M-record scale and a weaker query model. It would also be a third-party managed dependency
  for no gain over A.

## 6. Inventory Library model

The **Inventory Library** is StorageInventory's own persistent state: one SQLite database plus the side files SQLite
manages itself. It is private data, because it holds file names, paths, sizes and timestamps, exactly like the reports
(§16).

### 6.1 Location and ownership

| ID | Rule | Status |
|---|---|---|
| LIB-01 | **Default and only location in v1.1:** `%LOCALAPPDATA%\StorageInventory\Library\`, resolved with `Environment.GetFolderPath(SpecialFolder.LocalApplicationData)`. LocalAppData does not roam and is outside OneDrive's Known Folder Move, which covers Desktop, Documents and Pictures *(scope not re-verified in this task)* | PROPOSED (D-08) |
| LIB-02 | **Owned files, and nothing else:** `library.sqlite3`; SQLite's own `library.sqlite3-wal` and `library.sqlite3-shm`; user-requested backups `library.backup-<yyyyMMdd_HHmmss>-<6hex>.sqlite3`; pre-migration backups `library.pre-schema-<N>-<yyyyMMdd_HHmmss>.sqlite3`; quarantined damaged files `library.damaged-<yyyyMMdd_HHmmss>.sqlite3` (§6.7). **Reports never live in the Library** | DECIDED |
| LIB-03 | **Visibility:** the Home status area and Settings/About show the Library's full path and size. "Open Library folder" is added to the launch allow-list and runs only on an explicit click (SEC-14) | DECIDED |
| LIB-04 | The Library code is **location-agnostic**: every Library API takes an explicit path. Only the App resolves the default, so tests use `%TEMP%` fixtures | DECIDED |
| LIB-11 | A user-chosen or movable location and multiple Libraries are **deferred** (§4.2). They need persisted settings, which v1.0 does not have and v1.1 does not add | DEFERRED |

### 6.2 Why a fixed location in v1.1

A user-chosen location needs a persisted pointer to it (a settings file) plus a safe move operation. Each is a new
write surface and a new failure mode:
- a dangling pointer;
- a Library on a sync folder or network share;
- half-moved databases.

The fixed location keeps v1.1's write boundary to exactly one directory tree. The trade-off is disk space on the
system drive (about 130 MB per 2M-file snapshot, §15), which REQ-11 (deletion) and the size display (LIB-03) mitigate.

### 6.3 Path restrictions

The Library path is validated with the same machinery as the report folder (`PathPolicy`) before every open.

| ID | Condition | Result |
|---|---|---|
| LIB-05a | Network location (UNC or mapped drive) | **BLOCKED**: SQLite's WAL mode "does not work over a network filesystem" (sqlite.org/wal.html) |
| LIB-05b | A reparse point anywhere in the Library path (for example a profile relocated with a junction) | **BLOCKED**, as for report folders; Q-05 tracks the user-experience impact |
| LIB-05c | Inside a OneDrive root (the same environment variables `PathPolicy` uses) or another known sync root | **BLOCKED** in v1.1. Sync engines copy live `-wal` files and create conflicting copies |
| LIB-06a | The **source** equals the Library folder or lies inside it | **BLOCKED**. New `PathIssue` code `SourceInsideLibrary` |
| LIB-06b | The **report folder** equals the Library folder or lies inside it | **BLOCKED**. New code `OutputInsideLibrary`: the Library directory is exclusively StorageInventory's |
| LIB-06c | The **Library lies inside the source** (for example, the source is `C:\`) | **ALLOWED** under the rules of §6.4 (D-09). An informational preflight issue `LibraryInsideSource` says so |
| LIB-06d | The Library lies inside the report folder | Allowed (harmless: reports are create-new and have different names) |

### 6.4 The Library inside a scanned source (D-09, PROPOSED)

Scanning `C:\` with the default Library is the common case, and it needs an explicit, reviewed rule.

- **INV-08 is unchanged for reports.** A report folder inside the source is still blocked.
- **The one exception to "nothing is written inside the scanned tree"** is StorageInventory's own Library files,
  written by the capture that is running. No user file is ever touched, so INV-01 and INV-02 still hold.
- **The traversal treats the Library folder as ordinary metadata.** It is not skipped: skipping it would hide real disk
  usage and diverge from the PowerShell reference. Its listed sizes are whatever they are when the folder is listed.
- **The snapshot records it:** `library_inside_source = 1` and the Library's root-relative path. The UI labels that
  folder "StorageInventory Library (app data)" in results, history and comparisons, so its own growth is never
  mistaken for user data.
- **The v1 tripwire is not triggered.** It matches this run's *report* file names, and Library file names are different.
- **Rejected alternative:** requiring the Library to be outside every source. It would make scanning the system drive
  impossible with the default location.

### 6.5 Creation (LIB-07)

1. The Library is created **on first use**: the first scan whose "Save to History" option is on, after preflight has
   shown the Library path.
2. The directory chain is created with `Directory.CreateDirectory`, only in `LibraryStore`, and only for the validated
   Library path.
3. The database file is created with **`FileMode.CreateNew`** as a 0-byte file, then closed. SQLite treats an empty file
   as an empty database. This keeps creation under the same create-new discipline as reports: the SQLite connection
   **never** uses a create mode (SEC-06).
4. The schema, `application_id`, `user_version` and `library_info` are written in **one transaction**. If it fails,
   the file stays a 0-byte or schema-less file. On the next attempt, a file that is **empty, or has
   `application_id = 0`, `user_version = 0` and no tables**, is treated as uninitialised and initialised again.
5. Any other file at that path, one with content that isn't a Library, is refused and never overwritten (§6.7).

### 6.6 Opening (LIB-08)

Every open performs these checks, in this order:
1. Path validation (§6.3).
2. `application_id = 0x53494E56`.
3. `user_version` is supported (§9.6).
4. **Schema fingerprint:** the rows of `sqlite_schema` exactly match the expected set for that version, so there are
   no extra tables, views or triggers (SEC-17).
5. The single-instance mutex is acquired (LIB-10).
6. Staging rows left by an interrupted capture are recovered (§10.3).

`quick_check` is **not** run at every open. It takes 2.5 s per about 4M rows (§15) and grows with the Library. It runs
on demand (SREQ-05), and after an SQLite error that reports corruption.

### 6.7 Library states and failure handling

| State | Detected by | Behaviour | Never |
|---|---|---|---|
| **Not created** | No file at the default path | Scans work as in v1. The Library is created on the first save (§6.5) | — |
| **Available** | All checks pass | Normal | — |
| **Missing** | The folder exists but the DB is gone, or a previously shown Library disappeared | "The Library was not found at <path>." Saving is disabled, and there is an explicit "Create a new, empty Library" action | Recreate silently |
| **Unavailable** | Path blocked (§6.3), I/O error, access denied | Explained with the path. Scans still run, but without saving | Fall back to another location |
| **In use** | Mutex held by another instance | "The Library is open in another StorageInventory window." Scans still run, but without saving | Open a second writer |
| **Incompatible** | `user_version` newer than supported | "This Library was created by a newer StorageInventory (schema N). Update the app." Read-only access is **not** attempted | Downgrade or modify it |
| **Not a Library** | Wrong `application_id`, or an unexpected schema fingerprint | "The file at <path> is not a StorageInventory Library or has been modified." Refused | Overwrite, repair or delete it |
| **Damaged** | `SQLITE_CORRUPT` / `SQLITE_NOTADB`, or a failed `quick_check` | Saving disabled. Two explicit actions (below) | Delete it; recreate it silently |

The two actions for a damaged Library:
- **"Keep a copy"**: a byte copy made with create-new semantics.
- **"Set aside and start a new Library"**: the damaged file is renamed to `library.damaged-<timestamp>.sqlite3` with
  `File.Move(overwrite: false)`, then a new Library is created. This is the only rename the Library ever performs, and
  it is audited (SEC-08).

### 6.8 What may delete StorageInventory-owned data

| Operation | Trigger | Scope | Safeguards |
|---|---|---|---|
| Delete a snapshot (REQ-11) | User, with confirmation | The rows of one **published** snapshot | Two-phase: state goes Published → Deleting, then rows are deleted, then the snapshot row. `synchronous=FULL`. Other snapshots are never touched |
| Purge a staging capture | Automatic, on cancel, failure or recovery | Rows of snapshots in state **Staging** only, never published data | The SQL is constrained to `state = Staging AND snapshot_id = ?` (SEC-07) |
| Delete a source (SREQ-06) | User, with confirmation naming the snapshot count | That source's snapshots, paths and attempts | As for snapshot deletion, repeated per snapshot |
| Compact (SREQ-09) | User | Unreferenced `name` and `folder_path` rows; `VACUUM` | Runs only when no capture is active |
| **Never** | — | Deleting any Library file; automatic retention; deleting on incompatibility or corruption; deleting reports | — |

Backups (SREQ-05) use `VACUUM INTO` a **new** path that is first checked not to exist. They are never deleted
automatically.

### 6.9 Concurrency (LIB-10)

- **One process per Library:** a named mutex `Local\StorageInventory.Library.<first 16 hex chars of SHA-256 of the
  canonical Library path>` is held while the Library is open. It is a kernel object, not a file, and it is released
  automatically if the process dies.
- **One capture at a time**, as v1 already runs one scan at a time. Readers (the UI) may query published snapshots
  during a capture: WAL allows readers alongside the writer, and readers only ever see `state = Published`.

## 7. Storage and source identity

### 7.1 Concepts (kept separate)

| Concept | Meaning | Is it identity? |
|---|---|---|
| **Volume identity** | Evidence that two observations were of the same filesystem volume: filesystem type plus serial numbers | Yes, with a confidence level |
| **Source identity** | Volume identity **plus the root's location inside the volume** (`\` for a whole volume, `\Media\Music` for a folder); for network sources, the canonical share root plus the path | Yes. This is what snapshots belong to |
| **Observed location** | The drive letter or mount point, and the path as entered, at scan time | **No.** Recorded per snapshot for audit and display |
| **Display label** | The volume label or a user-given name | **No** (labels change) |

### 7.2 Evidence captured at each scan (read-only)

The evidence comes from one directory handle on the canonical source root, opened like v1's `NativeMethods`
(`desiredAccess = 0`, `FILE_FLAG_BACKUP_SEMANTICS`):

| Call | Returns | Probe result on this machine (NTFS `C:\`) |
|---|---|---|
| `GetVolumeInformationByHandleW` | Filesystem name, 32-bit serial, label, filesystem flags | `NTFS`, `0xFE561879`, flags `0x03E72EFF`; works with **0 access** |
| `GetFileInformationByHandleEx(FileIdInfo)` | `FILE_ID_INFO`: 64-bit volume serial and 128-bit file ID of the root directory | `VolumeSerialNumber = 0x1AFE5644FE561879`, whose low 32 bits equal the 32-bit serial; works with **0 access** |
| `GetVolumePathNameW` | Mount point of the volume that contains the root (`E:\`, or a folder mount such as `C:\Mounts\Backup\`) | `C:\` |
| `GetDiskFreeSpaceExW` | Capacity and free bytes | (not probed) |
| Existing `PathPolicy` canonical root (`GetFinalPathNameByHandleW`) | Canonical root: SUBST and mapped drives resolved, UNC as `\\server\share\...` | v1 behaviour |

**Not used for identity:** `GetVolumeNameForVolumeMountPointW` (the `\\?\Volume{GUID}\` name). The mount manager
assigns it per machine, so a removable drive gets different GUIDs on different PCs. It may be recorded as a per-machine
observation, but it is never matched on.

### 7.3 Identity confidence (ID-01)

| Level | When | Automatic matching |
|---|---|---|
| **Strong** | NTFS or ReFS, local, with a non-zero 64-bit serial from `FileIdInfo` | Yes, on (filesystem type, 64-bit serial) plus the root key |
| **Moderate** | FAT, FAT32 or exFAT, local, with a non-zero 32-bit serial (the 64-bit value is unavailable or just the 32-bit one) | Only if the filesystem type, 32-bit serial, **label and capacity (±1%)** all match. Otherwise the user is asked (ID-04) |
| **PathOnly** | Network sources; UDF or optical media; unknown filesystems; serial unavailable or 0 | Only by canonical path, and **always shown as "identified by location only"**. A drive letter alone is never a path identity (ID-03) |

The level is stored with every snapshot. A comparison shows it: "Compared on the basis of location only."

### 7.4 Source keys (ID-02)

- **Local sources:** `(volume_id, root_key)`. `root_key` is the root's path within the volume, case-folded with the
  same folding used for matching (§8.4), with no trailing separator except for the volume root `\`.
- **Network sources:** `(network_root_key, root_key)`. `network_root_key` is the case-folded canonical
  `\\server\share`. **Different server spellings are different sources** (`\\nas`, `\\nas.local`, `\\192.168.1.5`).
  StorageInventory does not resolve names (INV-05). Linking them is DEFERRED.

### 7.5 Matching algorithm (ID-03 to ID-06)

For every scan with "Save to History" on:

1. Collect the evidence (§7.2). If collection fails, the confidence is `PathOnly`, and the snapshot is still saved
   (the evidence failure is recorded).
2. **Strong:** find volumes with the same filesystem type and 64-bit serial.
   - Exactly one → use it.
   - None → create a new volume.
   - **More than one** (clones) → ambiguity (ID-05).
3. **Moderate:** find volumes with the same filesystem type and 32-bit serial.
   - Label and capacity also match exactly one → use it.
   - Otherwise ask: "Is this the drive last seen as *E: 'Backup'* on *date*?" The answers are **Yes** (use it), **No,
     it's a different drive** (create a new volume) and **Don't save this scan**.
4. **PathOnly:** match on the canonical root path.
   - Network sources use `network_root_key`.
   - Local PathOnly volumes (for example UDF) are always new, unless the user explicitly picks an existing source.
5. Find the source with the same `(volume, root_key)`, or create it.
6. Record the observed location (mount point, label, capacity, free space, root directory file ID) on the snapshot.

**ID-05 (clones).** If two currently mounted volumes report the same Strong or Moderate identity, or if a volume's
identity matches a source whose last snapshot shows a different root directory file ID *and* a different capacity,
StorageInventory **asks** the user and never assigns silently. Disk cloning and VHD copies reproduce serials.

**ID-06 (never silent merges).** A snapshot is never attached to an existing source on evidence weaker than this table
allows. The user can always choose "Treat as a new source".

### 7.6 Edge cases

| Case | Outcome |
|---|---|
| Drive letter changes (`E:` → `F:`) | Same Strong or Moderate identity, so the **same source**. The observed location records the new letter |
| Offline removable drive | The source is shown **Offline**, with when and where it was last seen. History and browsing work from the Library (REQ-08) |
| Drive reformatted | A new serial means a **new volume and a new source**. The history is not merged; merging is DEFERRED. If the label matches, the UI shows "Possibly the same drive (reformatted?)" as information only |
| Volume resized | A Strong identity is unchanged. The capacity difference is noted in the snapshot |
| Volume label changed | Identity unchanged, and the display name is updated unless the user renamed it |
| Source folder deleted and recreated (NTFS) | Identity unchanged: the path within the volume is what identifies the source. The root directory's file ID differs, so the comparison warns "The source folder was recreated since the older snapshot". It is information, not a class change |
| SUBST or mapped drive | Resolved to the canonical root by `PathPolicy` before identity is computed |
| Folder-mounted volume (`C:\Mounts\X`) | `GetVolumePathNameW` returns the mount folder, so the root key is relative to that volume, not to `C:` |
| Identity calls fail (for example on some network providers) | `PathOnly`, with the reason stored |
| Optical media (UDF) | `PathOnly`. Discs are rarely compared, and serials are per disc |

### 7.7 Online detection for the Sources view (ID-07)

- **When:** at startup and on refresh.
- **Which drives:** only mounted **local fixed and removable** drives (`DriveType.Fixed` or `Removable`, and
  `IsReady`).
- **How:** each drive's identity is read with the same calls, with a per-drive timeout of 2 s.
- **Never probed automatically:** network drives and optical drives. Their sources show "Not checked" until the user
  scans. This avoids network traffic (INV-05), spinning up optical media, and long hangs.

### 7.8 New native API surface (ID-08, SEC-12)

| Function | Access | Purpose |
|---|---|---|
| `kernel32!GetVolumeInformationByHandleW` | On the existing 0-access handle | Filesystem type, 32-bit serial, label, flags |
| `kernel32!GetFileInformationByHandleEx` (class `FileIdInfo` = 18 **only**) | On the existing 0-access handle | 64-bit volume serial; root directory file ID |
| `kernel32!GetVolumePathNameW` | No handle | Mount point |
| `kernel32!GetDiskFreeSpaceExW` | No handle | Capacity and free space |

All four are read-only queries. The 0-access requirement was verified on NTFS in this task. FAT, exFAT, UDF and
network behaviour must be verified on real media in C3 (Q-02).

## 8. File identity analysis

### 8.1 Facts

| Topic | Fact | Source |
|---|---|---|
| NTFS | "A file keeps the same file ID until it is deleted." IDs survive renames and moves within the volume | Microsoft Learn, `BY_HANDLE_FILE_INFORMATION` remarks |
| Reuse | "File IDs are not guaranteed to be unique over time, because file systems are free to reuse them." (NTFS includes a sequence number in its 64-bit ID) | same |
| FAT | "The file ID is generated from the first cluster of the containing directory and the byte offset within the directory of the entry for the file." It can change after third-party defragmentation, or after a rename to a longer name | same |
| ReFS | 128-bit identifiers. "The 64-bit identifier … is not guaranteed to be unique on ReFS" | same |
| Copies | A copy is a new file with a new ID. Restore-from-backup and sync tools usually create new files | (general filesystem behaviour) |
| `ReplaceFile` | The replacement's ID is retained, not the replaced file's | Microsoft Learn |
| Hard links | All links to a file share one ID. v1 counts each link as a file (documented limitation) | Microsoft Learn; `README.md` |
| Network (SMB) | IDs come from the server's filesystem, or are synthesised. There is no portable guarantee | *(not verified)* |
| Collection cost | `FileSystemEnumerable` (v1's enumerator) **does not return file IDs**. There are two options: open every file (2M handle opens on the reference drive), or change enumeration to `GetFileInformationByHandleEx(FileIdBothDirectoryInfo / FileIdExtdDirectoryInfo)` on directory handles, which replaces the scanner's core and affects PowerShell parity | v1 code; Win32 documentation of the information classes |
| Metadata-only? | Reading an ID with 0 access is metadata-only (verified for directories in this task). A per-file open is still a new kind of interaction with every scanned file (antivirus hooks, cloud-placeholder handling) | Probe (§7.2) |

### 8.2 Decision (D-15, D-16)

- **Move and rename detection: DEFERRED.**
  - It cannot be proven portably: FAT and network IDs are unreliable, IDs get reused, and copies get new IDs.
  - Collecting IDs at all needs either a per-file open or a new enumeration core. Both deserve their own reviewed
    design, with parity implications.
  - Path-based diffing reports **Missing + Added** for a move. That is honest. A guessed "Moved" is not.
- **No per-file ID column in schema 1.** A later schema version adds it through a migration (§9.6). A nullable column
  for data that is never collected would be dead weight.
- **Collected in v1.1:** only the root directory's file ID, per snapshot (§7.6), as information.

### 8.3 Hard links (D-17)

Each link path is its own observation, as in v1. A comparison classifies each path independently. Documentation must
keep saying that sizes are per link and are not deduplicated.

### 8.4 Name case and identity (D-18)

- **Item identity within a source** is the exact, case-preserving name path, compared **ordinally**.
- **Why:** NTFS directories can be marked case-sensitive (for example by WSL), and then `a.txt` and `A.txt` coexist.
  v1 already records them as two files. Case-folded keys would collide and fail the capture.
- **Case-only renames** are matched by a constrained fallback (DIFF-07).

## 9. Persistent schema

### 9.1 Principles (SCH-01 to SCH-06)

- **SCH-01 Raw values only.**
  - Sizes are bytes.
  - Timestamps are **UTC .NET ticks** (100 ns since 0001-01-01; `NULL` means invalid or unrepresentable, as in v1
    records).
  - Attributes are the raw `FileAttributes` integer.
  - Status, type and error values are stable integer codes (§9.4).
  - **No CSV columns** (no KB/MB units, local times, percentages, categories or formula guard).
- **SCH-02 Identity never depends on a drive letter.** Paths are root-relative. The observed location is stored
  separately (§7.1).
- **SCH-03 Full snapshots.** Every published snapshot contains every file and folder observation. No deltas (D-07).
- **SCH-04 Shared dictionaries.**
  - Names are interned library-wide (`name`); folder paths are interned per source (`folder_path`). Snapshots of a
    source share path IDs, so comparisons join on integers.
  - This is not delta storage: each snapshot still has one row per observed item.
- **SCH-05 Versioned from day one:** `PRAGMA user_version = 1` and `application_id`.
- **SCH-06 Invariants can be checked in the database** (§9.5) by "Verify" and by tests.
- **SCH-10 Filesystem-derived strings are stored as exact UTF-16LE BLOBs, never as SQLite `TEXT`.** That covers names,
  paths, labels, and messages that can embed a path.
  - **Why:** NTFS names can contain unpaired surrogates. v1 scans them, and v1's CSV and XLSX writers render them as
    U+FFFD. SQLite `TEXT` is UTF-8, so storing such a name as `TEXT` would be lossy: two distinct names could collide
    on a primary key and fail a capture. BLOB storage round-trips every name exactly.
  - **Consequence for search:** case-insensitive matching and substring search run in .NET over decoded strings
    (§13.5), not in SQLite's `LIKE`, which only folds ASCII case.
  - **Consequence for paths:** full relative paths are rebuilt from the `folder_path` parent chain rather than stored.
    The chain is loaded anyway for display and comparison.
  - **Exempt fields:** fields that are display-only and never used for identity or matching may stay `TEXT`, where
    lossy rendering of an unpaired surrogate is harmless. These are user-editable display names, attempt messages,
    version strings and the filesystem type name.

### 9.2 Tables (schema version 1)

```sql
PRAGMA application_id = 1397313110;          -- 0x53494E56 'SINV'
PRAGMA user_version  = 1;

CREATE TABLE library_info (
  singleton               INTEGER PRIMARY KEY CHECK (singleton = 1),
  library_id              TEXT    NOT NULL,   -- random GUID, fixed for the life of the Library
  created_utc             INTEGER NOT NULL,
  created_app_version     TEXT    NOT NULL,
  last_opened_app_version TEXT    NOT NULL
) STRICT;

CREATE TABLE volume (
```

**Foreign keys** are declared on the dictionary and catalogue tables. They are deliberately **not** declared on
`file_obs` and `folder_obs`. The probe's insert rates (§15) were measured without them, and integrity is guaranteed by
three things:
- the capture writer, which inserts only IDs it has just interned;
- the invariant checks in §9.5, run in tests and by "Verify";
- the published-only views.

C4 measures the cost of declaring them. If it is under 10%, they are declared (Q-07).

### 9.3 Indexes (conceptual justification)

| Index | Serves | Measured without extra indexes (§15) |
|---|---|---|
| `file_obs` PK `(snapshot_id, folder_path_id, name_id)` | Ordered comparison merge, per-folder browsing | 2M × 2 merge in 3.3 s |
| `folder_obs` PK `(snapshot_id, path_id)` | Folder alignment, folder growth | — |
| `snapshot_by_source` | History timeline | trivial |
| `name.utf16 UNIQUE` | Interning. Names-first search scans the distinct-name dictionary in .NET | 0.56 s substring search over 2M files (probe: SQL LIKE over the names, then files by name ID; the .NET scan of about 250k names is expected to be faster, and is measured in C9) |
| **Not added in 1.1:** `(snapshot_id, size_bytes)` or `(snapshot_id, name_id)` on `file_obs` | Largest-N already takes 0.43 s, and names-first search 0.56 s | Revisit only if PERF budgets fail |

### 9.4 Stable codes (SCH-07)

Codes are **explicit integers mapped in code**, never enum ordinals. They are append-only. A test asserts the mapping
table, so reordering a C# enum can never change stored meaning.

| Type | Codes |
|---|---|
| `SnapshotState` | 0 Staging, 1 Published, 2 Deleting |
| `ScanCompletionState` (stored) | 0 Complete, 1 Incomplete. Cancelled and Failed are never stored on a snapshot |
| `FolderScanStatus` | 0 Ok, 1 Unreadable, 2 Partial, 3 ReparsePointSkipped |
| `ScanErrorType` | 1 AccessDenied, 2 NotFound, 3 PathTooLong, 4 IOError, 5 InvalidPath, 6 InvalidTimestamp, 7 UnexpectedError, 8 ReparsePointSkipped, 9 ReparsePointFile |
| `IdentityConfidence` | 1 Strong, 2 Moderate, 3 PathOnly |
| `SourceKind` | 1 LocalVolume, 2 Network |
| `AttemptOutcome` | 1 Cancelled, 2 ScanFailed, 3 SnapshotFailed (the scan finished, but saving failed), 4 Interrupted (found as staging at the next open), 5 NotSaved (the user declined an identity prompt) |
| `scanner_contract` | 1 = v1.0 traversal and metadata semantics (NeverFollow, the v1 completeness rules, UTC ticks) |

### 9.5 Database invariants for published snapshots (SCH-08)

For every published snapshot S of source X:

1. There is exactly one `folder_obs` row for the root `folder_path` of X.
2. Every `folder_obs.path_id` and every `file_obs.folder_path_id` refers to a `folder_path` row of source X that has a
   `folder_obs` row in S.
3. For every folder: `direct_files` equals its `file_obs` count, and `direct_bytes` equals their summed size.
4. S's totals match the data:
   - `files` = `count(file_obs)`;
   - `bytes` = `sum(size_bytes)`;
   - `folders` = `count(folder_obs)`;
   - the root's `total_*` values equal the snapshot totals.
5. Completeness matches the root: `completeness = Complete` ⇔ the root's `subtree_complete = 1`, mirroring
   `StorageScanResult.ForFinishedScan`.
6. No `folder_obs` with status `ReparsePointSkipped` has child folders or files in S.
7. A folder with status `Unreadable` or `Partial` has `subtree_complete = 0`, and so does every ancestor.
8. `scan_errors` equals the count of `scan_error` rows whose type is not informational.

These are the Library-side mirror of `FolderAggregator.Verify`. A capture that would violate them is not published
(LIFE-06).

### 9.6 Versioning and migration rules (SCH-09)

1. `user_version` is the schema version, and `snapshot.schema_version` records the version each snapshot was written
   under.
2. An app supports opening schema versions `1..N` (its own is N). Older Libraries are **migrated forward** as follows:
   - after an explicit prompt;
   - after a **pre-migration backup** (`VACUUM INTO` a new file, §6.1);
   - in **one transaction** per version step, with `synchronous=FULL`.
3. A migration failure rolls back. The backup and the original file remain, and the Library is reported
   "Incompatible (migration failed)" with the backup's path.
4. **A newer schema is never opened**, and there is never a downgrade (§6.7).
5. Migrations only **add** (tables, nullable columns, codes). A destructive change needs a new major version with an
   export path.
6. Each schema version has a frozen fingerprint test (§6.6) and a migration test from every earlier version's fixture
   database (TEST-M*).

## 10. Snapshot lifecycle

### 10.1 States

```
               begin capture (after preflight, before traversal)
   (none) ─────────────────────────────────────────────▶ Staging  ── rows written in batches, invisible to readers
                                                             │
         scan Finished (Complete/Incomplete) + reports OK    │  anything else (cancel, fail, crash, snapshot error)
         + invariants hold + publish txn commits (FULL)      │
                     ▼                                       ▼
                 Published ──(user deletes)──▶ Deleting ──▶ (rows gone)      purged; AttemptOutcome recorded
```

**The validity point (LIFE-01)** is the moment the publish transaction commits. That transaction sets `state = 1`,
`completeness`, `finished_utc`, `published_utc` and the totals, with `synchronous = FULL`. Before it commits, nothing
of the snapshot is visible (LIFE-02: every reader uses `published_snapshot`, and every service API accepts only
`PublishedSnapshotId`, a type that only the catalogue can construct).

### 10.2 Capture steps

| # | Step | Transaction |
|---|---|---|
| 1 | Preflight: Library state (§6.7), path rules (§6.3), identity evidence (§7.2) | read-only |
| 2 | Resolve or create the volume and source. A user prompt, if one is needed (ID-04), comes **before** traversal | 1 short transaction (`FULL`) |
| 3 | Insert the `snapshot` row with `state = Staging` | same |
| 4 | Traversal: intern names and folder paths; insert `file_obs` and `scan_error` rows in batches (the probe used 50,000 rows per transaction) | many short transactions (`NORMAL`) |
| 5 | Traversal ends and v1 finishes its reports. `StorageScanResult` is Finished | — |
| 6 | Insert `folder_obs` (aggregated) and `snapshot_extension_total` | batches (`NORMAL`) |
| 7 | Verify the invariants for this snapshot (§9.5), with aggregate SQL | read |
| 8 | **Publish**: `UPDATE snapshot SET state = 1, …` | **1 transaction (`FULL`) = the validity point** |
| 9 | Checkpoint the WAL (`PASSIVE`) | — |

### 10.3 Outcome table (LIFE-03)

| Situation | CSV reports (v1) | Snapshot | Attempt record | User sees |
|---|---|---|---|---|
| Scan **Complete** | Valid | **Published** (`completeness = Complete`) | — | "Saved to History" |
| Scan **Incomplete** (finished, some folders unreadable) | Valid | **Published** (`completeness = Incomplete`). Per-folder status lets later comparisons use Unknown correctly (D-05) | — | "Saved to History (incomplete: N folders could not be read)" |
| **Cancelled** | Listed as incomplete (v1) | Staging rows purged | `Cancelled` | "Not saved: the scan was cancelled" |
| **Failed**: invalid paths | Nothing created (v1) | No staging row was ever created | `ScanFailed` (only if identity was established) | v1 message |
| **Failed**: report write during traversal (a critical observer, §11.3) | Incomplete (v1) | Purged | `ScanFailed` (`OutputError`) | v1 message, plus "Not saved" |
| **Failed**: report write after traversal (Folders or sorted Files) | Incomplete (v1) | Purged: a snapshot is never published unless the scan Finished (D-06) | `ScanFailed` | v1 message, plus "Not saved" |
| **Failed**: internal consistency or tripwire | Withheld (v1) | Purged | `ScanFailed` | v1 message |
| **Snapshot write error** (disk full, I/O, `SQLITE_FULL`) during traversal | **Unaffected, still valid** (the observer is isolated, §11.3) | The capture stops, and the batch in progress rolls back. Staging rows are purged (or at the next open, if purging fails) | `SnapshotFailed` | "Reports saved. The scan could not be saved to History: <reason>" |
| Snapshot invariants fail at step 7 | Valid | Purged. **Not published** | `SnapshotFailed` (`InternalConsistency`) | same, with "internal check failed" |
| Publish transaction fails (step 8) | Valid | Rolled back, so the snapshot is still Staging, then purged | `SnapshotFailed` | same |
| **App crash** anywhere before step 8 commits | Whatever v1 produced (possibly incomplete files) | Left as Staging. At the next open: `Interrupted` recorded, then purged | `Interrupted` | At the next start: "A scan of X on <date> was interrupted and not saved" |
| **Power loss** before step 8 | as above | WAL with `NORMAL` may lose recent staging batches; the database stays consistent (sqlite.org). Recovered as Interrupted | `Interrupted` | as above |
| Power loss after step 8 commits | — | **Published and durable** (`FULL`) | — | — |
| Library locked or in use at step 1 | Unaffected | Not attempted | none (the Library can't be written) | "Not saved: the Library is open in another window" (preflight warning) |
| Library unavailable, damaged or incompatible at step 1 | Unaffected | Not attempted | none | Preflight warning; the "Save to History" option is disabled with its reason |
| Library becomes unavailable mid-capture | Unaffected | The observer fails, and it is treated as a snapshot write error | Best effort | as for a write error |
| `SQLITE_BUSY` beyond the timeout | Unaffected | Treated as a snapshot write error | `SnapshotFailed` | as above |

**LIFE-04:** a new capture never updates or deletes rows of any other snapshot. Every write statement in the capture
path is scoped to its own `snapshot_id`, and purges are scoped to `state = Staging` (SEC-07). **An older valid
snapshot therefore can never be lost because a newer attempt failed.**

**LIFE-05:** the Save-to-History outcome never changes `StorageScanResult`. The CSV reports keep v1's authority over
their own outcome.

**LIFE-06:** a snapshot is published only if the scan's `StorageScanResult.Finished` is true **and** the §9.5
invariants hold for the staged rows.

### 10.4 Attempts versus snapshots (D-12)

- **The two concepts are separate.** Cancelled, failed, snapshot-failed and interrupted captures are **`scan_attempt`
  rows**: timestamps, outcome and message, never observations.
- **Attempts carry no filesystem data.** They reference no file or folder rows (staging rows are purged), so they
  cannot take part in comparisons.
- **The type system enforces this:** diff and history services take `PublishedSnapshotId`, and no path exists from an
  attempt to that type.
- **The History view shows attempts inline,** with a distinct style ("Scan cancelled", "Not saved"), so completeness
  history is honest.

## 11. Scanner and sink architecture

### 11.1 Goal

One filesystem traversal feeds every consumer. There is no second scan for persistence (SINK-01). The target shape:

```
ScanEngine ──▶ ObserverFanOut ──┬──▶ CsvReportSink          (critical: failure aborts the scan, exactly as v1)
                                └──▶ SnapshotCaptureObserver (isolated: failure disables it, scan continues)
                                        │  bounded channel
                                        ▼
                                  SnapshotWriter (own thread, own connection, own transactions)
```

### 11.2 Observer contract (SINK-02, public in Core from C1)

```csharp
namespace StorageInventory.Core.Scanning;

public interface IScanObserver
{
    void OnScanStarted(in ScanStartInfo start);                        // once, first
    void OnFolderDiscovered(in FolderDiscovery folder);                // index, parentIndex (-1 root), name,
                                                                       // relative path, attributes, timestamps,
                                                                       // isReparsePoint
    void OnFile(in FileInventoryRecord file, int folderIndex);         // v1 record, unchanged
    void OnError(ScanErrorRecord error);                               // v1 record, unchanged
    void OnFolderFinalised(in FolderInventoryRecord folder, int index);// after aggregation, every folder once, index order
    void OnScanEnded(in ScanEndInfo end);                              // exactly once, last, on EVERY path
                                                                       // (finished, cancelled, failed, exception)
}
```

`IScanSink` (internal) is retired. Its two methods are kept, unchanged, inside `IScanObserver`.

**Ordering guarantees (SINK-03).** Each is enforced by a test observer that asserts them on every fixture:

1. `OnScanStarted` comes before everything else, and `OnScanEnded` after everything else, exactly once each.
2. `OnFolderDiscovered(i)` comes before any `OnFile(…, i)`, and before `OnFolderDiscovered(j)` for any child `j` of `i`.
   `parentIndex < index` always holds.
3. All `OnFile` calls for folder `i` form **one contiguous run**, because files are emitted while that folder is being
   listed and listings never interleave (v1 `ScanEngine` behaviour, now a contract).
4. `OnFolderFinalised` is called exactly once for each discovered folder, in ascending index order, only if traversal
   and aggregation finished, and before `OnScanEnded`.
5. Call order is identical to v1's `IScanSink` order, so the report bytes stay unchanged (INV-12).

### 11.3 Fan-out and failure isolation (SINK-04, D-11)

| Observer class | Examples | If it throws |
|---|---|---|
| **Critical** | `CsvReportSink` (v1 reports) | The exception propagates and aborts the scan, exactly as v1 (`ReportWriteException` → `OutputError`) |
| **Isolated** | `SnapshotCaptureObserver` | The fan-out catches the exception and marks that observer **faulted** (no further calls except `OnScanEnded`). Its failure is recorded for the `SnapshotCaptureResult`. The scan continues |

Rationale: the v1 report outcome keeps its v1 semantics, so REQ-13 and REQ-14 hold. A snapshot failure must never
destroy a valid report run that the user asked for.

### 11.4 Threading and back-pressure (SINK-05)

- Callbacks arrive on the scanning thread, as in v1.
- `SnapshotCaptureObserver` does no database I/O on that thread. It copies each record into a **bounded channel**
  (PROPOSED capacity 16,384 records). A dedicated writer thread drains the channel into batched transactions.
- **When the channel is full, the scanning thread blocks.** This is deliberate back-pressure: memory stays bounded
  (INV-13), and a slow disk slows the scan rather than exhausting RAM.
- **Name interning** uses an in-memory cache bounded by count (PROPOSED 262,144 entries, LRU), backed by the `name`
  table. Folder paths are interned when `OnFolderDiscovered` fires. The per-scan `folderIndex → path_id` array is
  O(folders), the same order of memory v1 already holds in `FolderState`.

### 11.5 Cancellation and transactions (SINK-06)

- The scan's `CancellationToken` is shared. On cancellation, the writer rolls back its open batch, `OnScanEnded`
  reports Cancelled, and the orchestrator purges staging and records the attempt.
- **Transaction ownership:** only `SnapshotWriter` owns a connection and transactions for a capture. The scanner,
  report sink and UI never write to the Library.

### 11.6 Results and API compatibility (SINK-07)

- `IStorageInventoryScanner`, `StorageScanOptions` and `StorageScanResult` are **unchanged**. v1 callers and tests
  compile and behave identically.
- `InventoryScanner` gains an overload:
  `Scan(StorageScanOptions, IProgress<StorageScanProgress>?, CancellationToken, IReadOnlyList<IScanObserver> additionalObservers)`.
  Its semantics: every additional observer is **isolated**, and the report sink is always critical.
- **New in `StorageInventory.Library`** (a new assembly, D-10):
  - `InventoryRun.RunAsync(InventoryRunOptions, IProgress<InventoryRunProgress>?, CancellationToken)`;
  - the result `InventoryRunResult { StorageScanResult Scan; SnapshotCaptureResult Snapshot; }`;
  - `SnapshotCaptureResult` has `Outcome` (`NotRequested | Published | NotEligible | Failed | Declined`), plus
    `SnapshotId?`, `SourceId?`, `Failure?` (kind and message) and `Timings`.
- `ScanPhase` gains an appended value `SavingSnapshot` for steps 6–8 of §10.2. Appending is compatible, and the v1 UI
  maps unknown phases safely.
- **The PowerShell reference** keeps its authority over v1 traversal and report semantics. **Persistence is not
  reimplemented in PowerShell** (D-19). Parity tests keep running on the refactored scanner (C1 acceptance).

## 12. Diff semantics and truth table

### 12.1 Scope and preconditions (DIFF-01)

- **Only published snapshots of the same source are compared:** `Compare(PublishedSnapshotId older, PublishedSnapshotId newer)`,
  with `older.source_id == newer.source_id`. Comparing across sources is refused (DEFERRED: user-asserted links).
- **"Older" and "newer" are ordered by `finished_utc`.** The API normalises the order and states it in the result.
- Comparing a snapshot with itself is valid (DIFF-P5).

### 12.2 Definitions

For a snapshot `S`, a **folder path** `f`, and an **item** `p = (parent folder path q, exact name n)`:

- `PresentFolder_S(f)`: `folder_obs(S, f)` exists, including folders with status `ReparsePointSkipped`, which are
  present as entries.
- `PresentFile_S(p)`: `file_obs(S, q, n)` exists.
- `Listed_S(f)`: `PresentFolder_S(f)` **and** `status(S, f) = Ok`, meaning the folder's listing was complete, so the
  set of its direct children is fully known.
  - `Partial`, `Unreadable` and `ReparsePointSkipped` are **not** Listed.
- `Anchor_S(p)`: the **deepest proper ancestor folder** of `p` with `PresentFolder_S`. The root is always present in a
  published snapshot.
- `ProvenAbsent_S(p)`: `p` is not present in S (as the item type in question) **and** `Listed_S(Anchor_S(p))`.

**Soundness argument.** Let `a = Anchor_S(p)`. If `a` is Listed, its direct children are known completely. The child
`c` of `a` on the way to `p` is either absent from that listing, in which case nothing below `c` can exist, or present
as a **file**, in which case `c` cannot contain `p`. If it were present as a folder, `a` would not be the deepest
present ancestor. Either way `p` provably does not exist in S. **If `a` is not Listed, absence proves nothing.**
This is INV-16, made mechanical.

`Unobservable_S(p)`, the Unknown reason, is `Anchor_S(p)` together with its status:

| Status of the anchor | Unknown reason |
|---|---|
| `Unreadable` | `AncestorUnreadable` |
| `Partial` | `ListingIncomplete` |
| `ReparsePointSkipped` | `BehindLink` |

### 12.3 File classification (DIFF-02). `O` is the older snapshot, `N` the newer.

| O | N | Class | Notes |
|---|---|---|---|
| file | file | **Changed** if the metadata differs (DIFF-04), else **Unchanged** | Case-fallback matches (DIFF-07) are included |
| file | absent, and `ProvenAbsent_N` | **Missing** | "Last seen": O (REQ-16) |
| file | absent, and **not** `ProvenAbsent_N` | **Unknown** (`NotObservableInNewer`, with the reason from the N anchor) | **Never Missing** |
| file | a folder with the same path | **Missing** (`ReplacedByFolder`) | Proven: N observed a folder there |
| absent, and `ProvenAbsent_O` | file | **Added** | |
| absent, and **not** `ProvenAbsent_O` | file | **Unknown** (`NotObservableInOlder`, with the reason from the O anchor) | Present now, but we can't say it is new |
| a folder with the same path | file | **Added** (`ReplacedFolder`) | |

### 12.4 Folder classification (DIFF-03)

Folders get an **existence class** plus a **content delta** with a certainty level:

| O | N | Existence class |
|---|---|---|
| folder | folder | **Present**. The content delta is computed |
| folder | absent, and `ProvenAbsent_N` | **Missing**. All of its O descendants are Missing too (proven by the same anchor) |
| folder | absent, and not proven | **Unknown** (with the reason); all O descendants Unknown |
| absent, and `ProvenAbsent_O` | folder | **Added** (all N descendants Added) |
| absent, and not proven | folder | **Unknown** (`NotObservableInOlder`); its N descendants Unknown |
| folder | file (same path) | **Missing** (`ReplacedByFile`); descendants Missing |
| file | folder | the folder is **Added** (`ReplacedFile`) |

The content delta of a Present folder uses `total_bytes`, `total_files` and `total_subfolders`:

| Certainty | Condition |
|---|---|
| **Exact** | Both sides have `subtree_complete = 1` |
| **LowerBoundOnly** | Either side is incomplete. Both values are lower bounds, so the difference is **not** a bound in either direction; the UI shows it as "not comparable (incomplete)" with both values (D-20) |
| **NotObserved** | Either side has status `ReparsePointSkipped`: links are never entered, so there are no contents on either side |

A Present folder is **Changed** when an Exact delta is non-zero, **Unchanged** when an Exact delta is zero, and
**Unknown** otherwise. That gives folders the same five externally understandable classes. The reason
`TotalsNotComparable` or `NotObserved` explains the Unknown.

### 12.5 What "Changed" means for files (DIFF-04, D-13)

| Field | Effect |
|---|---|
| `size_bytes` differs | **Changed** (flag `Size`) |
| `modified_utc` differs (`NULL ≠ value`; `NULL = NULL`) | **Changed** (flag `Modified`) |
| `created_utc` differs | Stays **Unchanged**, informational flag `Created` |
| `attributes` differ | Stays **Unchanged**, informational flag `Attributes` (the Archive bit changes on every backup, for example) |
| Only the name's case differs (DIFF-07 match) | Stays **Unchanged**, informational flag `NameCase` |
| `accessed_utc` differs | **Ignored entirely.** Last-access updates are lazy, often disabled, and NTFS resolution is coarse. It is not evidence of change |

Why: "Changed" should mean "the filesystem reports different content length or a newer write". Everything else is
metadata that users can inspect through the flags without it inflating the Changed count.

**DIFF-05 (FAT timestamps), PROPOSED.** FAT and FAT32 record times in local time. A timezone or DST change can shift
the reported UTC time by whole hours without any content change *(documented behaviour; not re-verified in this
task)*.
- **Rule:** on sources whose `fs_type` is `FAT` or `FAT32`, a file whose size is equal and whose `modified_utc`
  differs by exactly ±1 hour stays **Unchanged**, with the flag `PossibleClockShift`.
- **exFAT** stores UTC offsets, so the rule does not apply to it unless C7 testing on real media shows otherwise (Q-03).

### 12.6 Reparse points (DIFF-06)

| Situation | Result |
|---|---|
| Link folder in both O and N | Existence **Present**, content **NotObserved** (never entered). Shown as "Link (not followed)" |
| A normal folder in O is a link folder in N | The folder is Present, but content is NotObserved. Its O descendants: the N anchor is the link folder (status `ReparsePointSkipped`, not Listed), so they are **Unknown (`BehindLink`)**, **never Missing** |
| A link folder in O is a normal folder in N | Its N descendants are **Unknown (`NotObservableInOlder`, `BehindLink`)** |
| File reparse points (for example symbolic-link files) | Ordinary file observations (their listed size), compared like any file |

### 12.7 Case-only renames (DIFF-07)

Within one aligned parent folder pair, an unmatched O child and an unmatched N child are matched as the same item when:
- they are the same type;
- their names are equal under `StringComparison.OrdinalIgnoreCase`;
- the pair is **unique** on both sides.

Matched folders align their whole subtree. In all other cases, exact-name identity applies. A case-sensitive directory
holding both `a.txt` and `A.txt` in either snapshot never uses the fallback.

### 12.8 Algorithm (DIFF-08, bounded memory)

1. **Folder alignment (O(folders) memory).**
   - Load `(path_id, parent, name_id, status, subtree_complete, totals)` for both snapshots. That is at most about 470k
     rows each on the reference drive, the same order as v1's in-memory folder table.
   - Align by `path_id`, then apply DIFF-07 for folders that remain unmatched.
   - Compute `Listed` and each side's anchor for every folder that is unmatched.
2. **File merge (streaming).**
   - Read `file_obs` for both snapshots ordered by `(folder_path_id, name_id)` (the primary-key order; measured 3.3 s
     for 2 × 2M).
   - Merge per aligned folder pair. Folders remapped by case alignment are read with keyed seeks.
   - Buffer unmatched items only within one folder pair, for DIFF-07.
   - Classify each item with §12.3, using the anchor lookups from step 1.
3. **Output.**
   - A summary: count and bytes per class and reason; flag counts.
   - Top-N heaps: largest Added, largest Changed by absolute size delta, largest Missing, largest Unknown.
   - An in-memory list of **non-Unchanged** items, capped at PERF-06. Beyond the cap, the UI shows the summary and top-N
     lists, and says the full list is available through export (SREQ-08).
   - Comparison results are **not persisted** in the Library (D-14), so there is no new write surface.

### 12.9 Truth table (DIFF-09)

"Complete" and "Incomplete" describe the whole snapshot; the per-location rules above do the real work. Each row is a
required test case (TEST-D*).

| # | Scenario | Older | Newer | Expected |
|---|---|---|---|---|

| T2 | complete → complete, size changed | file | size differs | Changed {Size} |

| T32 | hard link: two paths to the same file | 2 paths | 1 path removed, parent Listed | the removed path Missing; the other Unchanged (D-17) |

### 12.10 Properties (DIFF-P*, property-based tests over generated trees)

- **DIFF-P1 Partition:** every item present in O or N gets exactly one class.
- **DIFF-P2:** Missing ⇒ `ProvenAbsent_N`. Added ⇒ `ProvenAbsent_O`.
- **DIFF-P3 Monotonicity:** making any folder in N *less* observable (Ok → Partial or Unreadable, or the folder
  becomes a link):
  - never turns an Unknown into Missing, and never turns Missing into Added;
  - can only move items from Missing to Unknown;
  - never changes the class of an item present on both sides.
- **DIFF-P4 No Unknown between complete snapshots:** if both snapshots are Complete and no folder in either is a link
  that was a folder in the other, the Unknown count is 0.
- **DIFF-P5 Self-comparison:** `Compare(S, S)` is all Unchanged.
- **DIFF-P6 Duality:** `Added(O→N)` equals `Missing(N→O)` as path sets. Changed is symmetric. Unknown reasons swap
  their direction.
- **DIFF-P7 Conservation:**
  - `|O files| = Unchanged + Changed + Missing + Unknown_oldSide`;
  - `|N files| = Unchanged + Changed + Added + Unknown_newSide`.
- **DIFF-P8 Location independence:** changing the mount point or drive letter between the snapshots does not change
  any result.
- **DIFF-P9 Oracle agreement:** on generated trees of up to 2,000 items, the algorithm equals a brute-force oracle that
  applies the §12.2 definitions literally (the same approach as v1's `AggregationFixtureTests`).

## 13. History, analytics and search

Everything in this section is **metadata arithmetic over published snapshots**. There is no content analysis (§4.1).

### 13.1 Totals over time (HIST-01, REQ-09)

- **Series:** bytes, files and folders per published snapshot of one source, taken from the snapshot's totals.
- **Incomplete snapshots:**
  - their points are drawn and labelled **"at least"** (lower bounds);
  - the chart never joins complete and incomplete points into one line without marking the difference.
- **Attempts** (cancelled, failed, interrupted) appear as markers with no value.
- **Capacity and free space** at each scan are shown as a separate series. They are the volume's, not the source's
  (for a subfolder source that matters).
- **Accessibility:** every chart has an equivalent data table (UI-09).

### 13.2 Growth (HIST-02, REQ-10, SREQ-02)

- **Folder growth** between two snapshots comes from the §12.4 folder alignment.
  - Top-N folders by absolute Exact delta, split into grew and shrank.
  - A separate count of folders whose delta is "not comparable (incomplete)", with a way to list them.
  - **Never** rank a folder on a non-Exact delta.
- **"Fastest-growing over a period"** is the delta between the first and last published snapshots in the period
  (Exact only). A per-day rate may be shown as delta ÷ elapsed time, labelled as an average between two
  observations, not a measured rate.
- **File-count growth** works the same way, using `total_files`.
- **Extension and category growth** (SREQ-02) uses `snapshot_extension_total`, with categories from v1's
  `FileTypeCatalog`. An incomplete snapshot's per-extension totals are lower bounds and are marked as such.
- **Bytes and files added between observations** use the comparison summary (Added and Changed bytes).
- **Largest additions and changes** use the comparison's top-N lists (REQ-07).

### 13.3 Last seen (HIST-03, REQ-16, SREQ-10)

- **MUST:** in a comparison, every **Missing** item shows "last seen: <older snapshot date>". That is exact: the older
  snapshot observed it.
- **SHOULD:** "last seen anywhere" for one path searches older published snapshots of the source, newest first, and
  stops at the first observation. If it passes a snapshot where the path's anchor was not Listed, it says "possibly
  present later (not observable on <date>)" rather than claiming a gap.

### 13.4 Offline browsing (HIST-04, REQ-08)

`LibraryExplorer` serves the v1 results tabs from a published snapshot. For each tab, it gives the same answer as
v1's `ReportExplorer` does from the CSV reports of the same run:

| Tab | Query |
|---|---|
| Overview (largest top-level folders) | `folder_obs` at depth 1, ordered by `total_bytes` |
| Largest folders | `folder_obs` ordered by `total_bytes` descending, with a limit (`ExplorationViewModel.FolderLimit` = 2000) |
| Largest files | `file_obs` ordered by `size_bytes` descending, with a limit (1000). Measured at 0.43 s for 2M files without an extra index |
| File types | `snapshot_extension_total` plus `FileTypeCatalog` |
| Errors | `scan_error` in `seq` order, with counts by type |

**Parity test (TEST-H2):** for every fixture scan with Save to History on, `ReportExplorer` over the CSVs and
`LibraryExplorer` over the snapshot return the same rows in the same order, apart from the documented presentation
differences such as local-time rendering. This is what lets v1's results screen move onto the Library later
(SREQ-04) without regressing.

**When the source is offline,** browsing works from the Library alone. Actions that need the live filesystem are
unavailable, and the UI says why. v1.1 has only one such action: opening the report files, if they still exist, via
the v1 allow-list.

### 13.5 Search (SRCH, SREQ-01): a filter model, not a language

| Filter | Semantics |
|---|---|
| Source; snapshot (default: latest published) | Exactly one snapshot per search in v1.1. Cross-history search is DEFERRED |
| Name contains | Case-insensitive (`OrdinalIgnoreCase`) substring match on the decoded name |
| Path contains | Case-insensitive substring match on the rebuilt folder path |
| Extension | Exact match on `ExtensionOf(name)`, case-insensitive |
| Size range | Inclusive, in bytes. The UI accepts KB, MB and GB and converts with 1024 units, as v1 does |
| Modified between | UTC bounds converted from local dates. Items with `NULL` modified times are excluded, with the count shown |
| Status relative to a reference snapshot | **DEFERRED** (it needs a stored comparison) |

**Execution (SRCH-02):**
1. Match names in .NET over the name dictionary. That is about 250k distinct names for 2M files, and it is Unicode-correct.
2. Match folder paths in .NET over the loaded folder table.
3. Put the matching IDs into an **in-memory** temporary table (`temp_store = MEMORY`).
4. Filter `file_obs` for the snapshot by those IDs and the numeric bounds.

**Results** are paged, and each page is bounded (PERF-04 sets the budget). There is **no free-text query language
and no SQL typed by users** (SEC-04).

### 13.6 Age cohorts (SREQ-03)

- **Cohorts:** "Not modified in 1 / 2 / 5 / 10 years, according to the file's modified date", counting files and
  bytes.
- **Mandatory wording:** "Modified dates are set by the programs that write files. Copying, restoring or syncing can
  keep old dates or set new ones, so a file's modified date does not prove when it was last used."
- **Created and last-access dates are never used for cohorts.** Created dates change on copy, and last-access updates
  are lazy or disabled.

### 13.7 When a volume is offline (HIST-05)

- All history, comparison, browsing and search features work from the Library alone.
- The source card shows **Offline** and "last seen <date> as <mount point>".
- **Scan is unavailable**, with the reason.
- **Online state is never cached as truth:** it is re-checked (ID-07) at startup and on refresh.

## 16. Security and privacy threat model

### 16.1 Zones

| Zone | Trust | Write policy |
|---|---|---|
| **Z1: the scanned tree** | The user's data | **Read-only, always** (INV-01, INV-02). Metadata-only listing. No handles to files, and only 0-access handles to directories |
| **Z2: the report folder** | Chosen by the user | Create-new only, outside Z1 (v1 unchanged) |
| **Z3: the Library** | Owned by StorageInventory; **contains private data** | Transactional writes; creation, deletion and renames under the rules of §6; never on a network or sync location |

### 16.2 New capabilities inventory (everything v1.1 adds that can write, delete, launch or call native code)

| Capability | Where (only) | Zone | Guard |
|---|---|---|---|
| Create the Library directory | `LibraryStore.EnsureLibraryFolder` | Z3 | The validated Library path (§6.3) |
| Create the database file | `LibraryStore.CreateEmptyDatabase` (`FileMode.CreateNew`) | Z3 | Never overwrites; SQLite never creates files itself (SEC-06) |
| Open or write the database | `LibraryDatabase` (`SqliteConnection`, `Mode=ReadWrite`, `Pooling=False`) | Z3 | Checks at open (§6.6); SQL constants only (SEC-04) |
| SQLite side files (`-wal`, `-shm`) | The SQLite engine | Z3 | Documented engine behaviour (sqlite.org/wal.html). Created and deleted by SQLite next to the database only |
| Delete rows | `LibraryMaintenance` | Z3 | State-scoped SQL predicates (SEC-07) |
| Back up and migration backup (`VACUUM INTO`) | `LibraryMaintenance` | Z3 | The target is checked not to exist first. Timestamp plus random name |
| Rename (quarantine a damaged database) | `LibraryStore.QuarantineDamaged` (`File.Move(overwrite:false)`) | Z3 | On explicit user action only |
| Schema migration | `LibraryMigrator` | Z3 | Backup, then one transaction, `FULL` |
| Launch: open the Library folder | `ReportOpener`, extended allow-list | Z3 | Explicit click; the exact validated Library directory |

### 16.3 Threats and mitigations

| Threat | Mitigation | ID |
|---|---|---|
| Crafted file names (quotes, `%`, `_`, control characters, unpaired surrogates, very long names) | Always bound as parameters; stored as exact UTF-16 BLOBs; never interpolated into SQL; displayed as text only | SEC-04, SCH-10, SEC-22 |
| SQL injection through the search UI | No user SQL. Filters become parameters, and name matching happens in .NET | SEC-04 |
| Database path substitution: the Library folder or file replaced by a link or junction | Path validation before every open (a reparse point anywhere in the path blocks); a re-check before `CreateNew`, the same pattern as `ReportRun.CreateNew`. **Residual:** a swap in the window between check and open (same class as v1's documented folder-swap race). SQLite's `SQLITE_OPEN_NOFOLLOW` would close it for the final component; whether Microsoft.Data.Sqlite can pass it is Q-06 | SEC-02, Q-06 |
| Source, Library or report aliasing (SUBST, 8.3 names, case, mapped drives) | Canonical-location checks (`GetFinalPathNameByHandleW`, v1) extended to the Library in both directions (LIB-06) | SEC-26 |
| The Library inside the scanned source | Explicit rule D-09 (§6.4). Only Library files are written; the report tripwire is unchanged | SEC-25 |
| Corrupt database | Errors mapped to Damaged; the file is never deleted or silently recreated; explicit quarantine | §6.7 |
| Tampered database: hostile values | `application_id`; schema fingerprint (no unexpected triggers or views); `trusted_schema=OFF`; codes range-checked on read (an unknown code is a data error, not a crash); bounded reads; **no path read from the database is ever launched, opened or used as a filesystem path** | SEC-15, SEC-16, SEC-17 |
| Partial migration | Transactional per step; backup first; "Incompatible (migration failed)" state | SCH-09, SEC-20 |
| Native DLL planting or search-order hijack of `e_sqlite3.dll` | A `NativeLibrary.SetDllImportResolver` on the provider assembly loads by **full path** from the extraction directory (`AppContext.BaseDirectory` for single-file) and never through the default search order. The smoke test asserts the loaded module's path. **Residual:** a same-user attacker who can write `%TEMP%\.net\…` already controls the user's session (documented, as for v1's WPF natives) | SEC-13, SEC-24 |
| Dependency supply chain | Exact package IDs and versions; `packages.lock.json` content hashes, locked mode in CI and Publish; source mapping refuses everything else; licences reviewed | SEC-10, BLD-02 |
| SQLite temporary files written outside the Library (for example `%TEMP%`) | `PRAGMA temp_store = MEMORY`; queries designed to use primary-key order (no large unindexed sorts); verified by a test that watches `%TEMP%` for `etilqs_*` files during the benchmark scenarios | SEC-05 |
| Privacy leakage | The Library is private data (README, Settings). No upload, and no network or sync location (LIB-05). Comparison export (SREQ-08) carries the same warning as reports. No telemetry | SEC-18 |
| Cloud-synced Library | Blocked (LIB-05c) | LIB-05 |
| Cancellation or crash during capture | Staging, invisible, purged; attempts recorded (§10) | LIFE-* |
| Concurrent instances | A named mutex per Library; the second instance runs without history | LIB-10, SEC-19 |
| Concurrent scans | Only one scan at a time (v1) | LIB-10 |
| Database locking (`SQLITE_BUSY`) | `busy_timeout`; treated as a snapshot failure, never retried in a loop | §10.3 |
| Denial of service from a huge Library | Bounded reads everywhere; the comparison list cap (PERF-06); paging | PERF-06 |
| Extension loading or unsafe pragmas | Extensions never enabled; pragmas are constants | SEC-17 |

### 16.4 How `SecurityAuditTests` must evolve (SEC-30)

No rule is deleted. Each broadened rule is replaced by an **equally narrow, exact** rule.

| v1 rule | v1.1 replacement |
|---|---|
| `File_creation_happens_only_in_ReportRun` | `FileMode.CreateNew` only in `ReportRun.cs` **and** `LibraryStore.cs`. `Directory.CreateDirectory` only in those two files. Still no overwriting modes and no `File.Write*` APIs anywhere |
| `Readers_only_ever_open_files_for_reading` | Unchanged, plus: the `SqliteConnectionStringBuilder` `Mode` is only ever `ReadWrite`, and `ReadWriteCreate`, `Memory` and shared cache never appear |
| `Deletes_and_renames_happen_only_in_ReportRun…` | `File.Delete` only in `ReportRun.cs` (the Library never deletes files). `File.Move` only in `ReportRun.cs` and `LibraryStore.QuarantineDamaged`, both with `overwrite: false`. Still no folder deletion anywhere |
| (new) `Sql_is_constant_and_parameterised` | SQL command text only in `Library/Sql/*.cs` constants. No `$"` or `+` building of command text. Every `DELETE` includes `snapshot_id` and a `state` predicate, or is in the reviewed maintenance list. No `DROP` outside migrations |
| (new) `Library_database_access_only_in_LibraryDatabase` | `SqliteConnection` is constructed only there. `PRAGMA trusted_schema=OFF`, `temp_store=MEMORY` and `foreign_keys=ON` are asserted at open |
| `Process_launching_happens_only_in_ReportOpener` | Unchanged location. The allow-list test gains the Library folder and still rejects any path that comes from Library data |
| `No_network_registry_dynamic_code_or_persistence_APIs` | Unchanged for all assemblies. `IsolatedStorage` and `Properties.Settings` stay forbidden: the Library is the only persistence. `StorageInventory.Library` must not reference `System.Net.*` |
| `The_only_native_calls_are_two_read_only_kernel32_functions` | **Exactly six** P/Invokes, all `kernel32` (the two existing ones plus `GetVolumeInformationByHandleW`, `GetFileInformationByHandleEx`, `GetVolumePathNameW` and `GetDiskFreeSpaceExW`). `GetFileInformationByHandleEx` is called only with the `FileIdInfo` constant. `CreateFile` stays at desired access 0 |
| `Core_has_no_UI_process_or_network_dependencies` | Unchanged for Core. **New:** Core references no `Microsoft.Data.Sqlite` or `SQLitePCL*`. `StorageInventory.Library` references no UI or process assemblies |
| `The_app_never_asks_for_elevation` | Unchanged |
| `No_package_references_anywhere` | Becomes **`Package_references_are_exactly_the_approved_set`**: `<PackageReference>` only in `StorageInventory.Library.csproj`; the (ID, version) set equals the ADR list exactly; `packages.lock.json` is present and its package set equals the allow-list; no floating versions |
| (new) `Native_files_in_publish_are_exactly_expected` | The files in the single-file bundle and the extracted natives are exactly v1's WPF natives plus `e_sqlite3.dll` (asserted by the release smoke test) |
