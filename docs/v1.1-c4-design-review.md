## 2. Verdict summary

C4-B01 is **reproduced and explained** (§4, §5). The rollback journal of the one-transaction import is not a fraction of the snapshot.
Its pages are the pages of the name dictionary's `UNIQUE` index into which new names are inserted: about one 4 KiB page per new name,
until every leaf of the dictionary region the names fall into has been touched. The C4 benchmark's names all sorted past the end of
that index, so nothing existing was touched and the journal was 0.19 MB at every scale. The same mechanism makes the import slow in a
large Library: names the dictionary does not already cache are probed in a large B-tree, which costs the same for lookups of names it
holds as for insertions.

**Decision (D-52, §11):** keep T-IMPORT as one rollback-journal transaction and keep its atomic publication. **Make the name
dictionary per source** (`UNIQUE (source_id, utf16)`), as folder paths already are: a new source's names then occupy a key range that
no existing page holds, so the first snapshot of a new source journals only a fixed handful of pages whatever the Library holds
(measured: 0.24 MB instead of 88.7 MB), and any other import touches only its own source's dictionary. **PERF-15's "≤ 5% of the
snapshot's size" is replaced** by a structural bound on what the journal may contain, a rollback-cost budget, and a space preflight and
guard (IMP-11) that C5 wires. **PERF-01 is restated** with a measurement method, acceptance and worst-case cells, an accepted statistic and
a separate stop threshold. **Rejected:** the prepared hidden-staging alternative (§11.3: it does not reduce the dictionary cost that
caused the miss, and after a failure on a full disk it would leave the staged rows' space taken), and key-ordered interning, which was
prototyped and moved the cost into verification instead of removing it (§10.2).

Final line: §19.

## 3. Method

### 3.1 Harness

A scratch harness (`DesignReviewBench.cs`, kept as `docs/evidence/c4-design-review/harness.patch`; it applies to `035dc90`) runs the
production T-IMPORT unmodified (`LibrarySession.ImportSnapshotAsync` → `SnapshotImporter`) from the C4 test executable:

- **Fresh process per run.** The orchestrator starts one child process per measured import (`--benchmark dr child …`) at High priority,
  as the C4 benchmark does.
- **Prefill.** Three snapshots in two sources before the measured import, exactly as C4's TEST-P1: source A (`p1`, `p3`) and source B
  (`p2`), each of *P* files; the target is the fourth snapshot, of source A (or of a new source C where stated). Folder trees, sizes and
  times are the C4 generator's (`SyntheticSnapshot`), byte for byte; only file names vary by family (§3.2). To save time each
  (family, *P*) prefill is built once by the same production code in its own process and **copied** into each run's fresh Library
  directory, which is then flushed to disk (`FlushFileBuffers`) and opened through the normal start-up open (LIB-08) before the import.
  The `prefillcheck` cells (§4.5) compare this with the C4 method of prefilling inside the measuring process.
- **Journal through a live handle.** A sampler thread opens `library.sqlite3-journal` with `FileShare.ReadWrite | FileShare.Delete`
  and reads `Length` from the handle in a loop with `Thread.Sleep(1)`, which Windows' default timer resolution turns into about one
  sample every 15.6 ms (61 to 64 samples per second, recorded per run; the review's replay had the same limit). The exact length is also
  read through a handle at the end of row insertion. A `TRUNCATE` journal only grows during a transaction, so the sampled peak can miss
  only what the last interval before `COMMIT` added; in all 92 normal runs it was at or above the exact length at the end of insertion,
  by about three pages (the final statements'), so the peak was captured. A second sampler reads `FileInfo.Length` as C4 did, for
  comparison; the importer's own figure (`FileInfo` every 16,384 rows) is recorded too.
- **Sizes through handles.** The Library size before and after is the main file's length through a handle, never a listing.
- **Journal composition.** In the `analyse` runs, the journal is copied through a handle at the end of row insertion (before
  verification and the three final statements, which add a handful of catalogue pages), a copy of the main file is taken before the
  import, and every journal record's page number is attributed to the B-tree that owned that page before the transaction. The
  shipped engine has no `dbstat` (its compile options were read from the DLL), so a 200-line read-only B-tree walker
  (`PageOwnership`, sqlite.org/fileformat2.html) does it. The journal's own structure is parsed too: segments, which segments were
  synced, sector size, records, repeats.
- **Machine load.** Every run samples `GetSystemTimes` every 250 ms and subtracts its own CPU time: "other load" in the tables is the
  share of the whole machine (16 logical CPUs) not used by the run, mean and 95th percentile; it includes kernel and anti-malware work the
  run itself causes (§3.3). Each plan also records the other readable processes' CPU over three seconds at its start and end (names
  withheld in the committed logs; totals only).
- **Cancellation and crash.** `cancel` runs cancel the import's token at the end of row insertion, when the journal is at its peak,
  and time how long `ImportSnapshotAsync` takes to return rolled back. `crash` runs kill the child process there (`TerminateProcess`);
  a second process then times the next start-up open (hot-journal rollback, LIB-08) and verifies the older snapshots.
- **Pristine and probe builds.** *Pristine* builds are the unmodified `src/` of `035dc90` plus the harness; every reproduction,
  distribution, size, cancel, crash and method cell ran on one. Three were made as plans were added (`bin-pristine`, `bin-pristine2`,
  `bin-pristine3`); they differ only in the harness's list of plans and families and in passing the run's environment to the recovery
  process; the committed `harness.patch` is the last. *Probe* builds add environment-gated design variants in `src/`
  (`docs/evidence/c4-design-review/probes.patch`, never committed to `src/`) and ran only the cells labelled "probe" or naming a
  variant (`persource`, `chunked`, `presort`, `cache`, `batched`). Every build ran at idle priority, with two build nodes, while other
  cells were measuring; the runs whose measured import overlapped a build window are marked in their tables.

## 5. Mechanism

### 5.1 What T-IMPORT writes

T-IMPORT writes into two kinds of B-tree (§9.2):

- **Append-shaped trees**, whose new keys are all larger than every existing key: `file_obs`, `folder_obs`, `scan_error` and
  `snapshot_extension_total` (each key starts with the new snapshot's id, which is always the largest, SCH-11), `snapshot` (rowid =
  `snapshot_id`), and the `name` and `folder_path` tables themselves (rowid = largest + 1).
- **Content-keyed trees**, whose new keys fall wherever their content sorts: the name dictionary's `UNIQUE` index
  (`sqlite_autoindex_name_1` on `name.utf16`), `folder_path_child` (`source_id, parent_path_id, name_id`), and one or two entries of the
  small catalogue indexes (`snapshot_by_source`, `scan_attempt_by_source`, the source and volume keys).

### 5.2 What the rollback journal holds

In rollback-journal mode, before the first change to a page that existed when the transaction began, SQLite appends that page's
original image to the journal as a record of 4 + page size + 4 bytes (4,104 bytes here). A page is journalled at most once per
transaction; a page allocated past the original end of the file is not journalled (a rollback truncates the file instead); a free-list
leaf page that is reused is not journalled either ([E-3]: 0.1 MB when re-importing into freed pages). Records are grouped in segments,
each preceded by a 512-byte header (the sector size this VFS reports); a segment's magic number and record count are written only when
the journal is synced, so the last, unsynced segment of a live journal has an all-zero magic (sqlite.org/fileformat2.html §4; measured:
every analysed journal has exactly this layout).

**Measured in every analysed journal:** zero repeated page numbers; 4,104 bytes per distinct page plus the segment headers; exactly
two segments, one synced. The peak journal is therefore *J* = (journalled pages) × 4,104 B plus 1.1 to 1.3 KiB of segment headers and
sector padding, and the question is only which existing pages an import changes.

### 5.3 Why the C4 benchmark measured 0.19 MB

In C4's generator, the unique half of the target's file names is `file_target_<folder>_<k>`; the prefill's are `file_p1_…` to
`file_p3_…`, and the shared half is `common_<n>` (5,000 names, all already in the dictionary and held in the importer's name cache). In
UTF-16 byte order `file_t…` sorts after every existing name, so all 500,000 new names are inserted past the right edge of the name
index: SQLite appends them to its rightmost leaf and grows the tree with **new** pages, which are not journalled. Only the existing
pages on the rightmost root-to-leaf path of each growing tree are journalled once. Folder paths behave the same way: the target tree
repeats `p1`'s first folders exactly (same paths, found, not inserted), and its additional folders hang under existing parents in one
contiguous block of source A's key range.

**Measured (`analyse append 1M/3000k`):** 40 journalled pages in total: 10 of `file_obs`, 10 of the name index, 10 of `folder_obs`, 5 of
the `name` table and one each of five catalogue trees; 165,384 bytes. The same 40 to 48 pages appear at every target size, which is why
C4 measured 0.19 MB at 1M, 2M and 10M rows: **the C4 workload is append-only in every B-tree**, a best case the specification's own
text describes ("an appending import journals almost nothing", §5.8) and G0-O03 asked C4 to go beyond.

### 5.4 Why interleaved names change the result

A new name that sorts *between* existing names is inserted into the existing leaf that covers its position, and that leaf is journalled
the first time this happens. With *N* new names falling at random positions in a dictionary region of *E* leaves, the number of distinct
leaves touched is about *E*·(1 − e^(−*N*/*E*)), plus the parents of the leaves that split: **about one 4 KiB page per new name while
*N* ≪ *E*, and the whole region once *N* ≫ *E***. Measured:

| Cell | New names *N* | Name-index pages *E* (before) | Name-index pages journalled | Other pages journalled | Journal |
|---|---:|---:|---:|---:|---:|
| append 1M/3000k (control) | 499,571 | 20,373 | 10 (right edge) | 30 | 0.16 MB |
| hash 1M/750k | 499,572 | 5,859 | 5,662 (96.6%) | 37 | 22.3 MB |
| hash 2M/750k | 998,419 | 5,859 | 5,662 (96.6%) | 37 | 22.3 MB |
| hash 1M/3000k | 499,571 | 22,811 | 22,611 (99.1%) | 30 | 88.6 MB |
| hash, new source, 1M/3000k | 499,571 | 22,811 | 22,611 (99.1%) | 47 | 88.7 MB |
| mixed 1M/3000k | 349,617 | 16,794 | 16,181 (96.3%) | 30 | 63.5 MB |
| real 1M/3000k | 107,967 | 1,010 | 591 (58.5%) | 32 | 2.4 MB |
| rescan 1% 1M/3000k | 10,187 | 22,811 | 9,928 (43.5%) | 30 | 39.0 MB |

(The 3.4% of the hash index never touched is the `common_` and `dir` range, where no `img…` name falls. Analysis rows: §4.4.)

**Consequences.** (1) The journal does not depend on the snapshot's size: the same 22.3 MB at 1M and 2M rows into the same Library,
because the snapshot's own pages are all new. (2) It depends on the number of *new* dictionary entries and on the size of the dictionary
region they fall into, and that region today is the **whole Library's** name dictionary: a new source's first snapshot (hash, new source)
journals exactly as much as the next snapshot of an existing source, because names are library-wide (SCH-04). (3) Every other B-tree contributes a
fixed 30 to 50 pages. So, with *K* ≈ 50 pages: **J ≈ (min(N_new, E_region) + K) × 4,104 B**.

### 5.5 Why throughput falls in a larger Library

- **The import is CPU-bound.** In every run the process's CPU time equals the import's wall time within a few percent (for example
  18.6 s of CPU for an 18.7 s import); there is no I/O wait to speak of.
- **It is not journal syncs.** Every analysed transaction synced its journal exactly once: SQLite's page cache spills new
  (unjournalled) pages, which need no sync, in preference to journalled ones.
- **The cost scales with the dictionary, not the snapshot.** The `files` phase of a hash 1M import takes 7.3 to 8.2 s into the 750k
  Library and 13 to 19 s into the 3M one, while the append control takes 4.3 to 6.9 s at both sizes.
- **Lookups pay it too.** The 1% re-scan inserts only 10,187 names but looks up about 990,000 existing ones, which do not fit the
  importer's 262,144-entry name cache, and runs at 55k to 73k rows/s in the 3M Library.

**Inferred:** each name that is not in the name cache costs a random root-to-leaf probe of a B-tree of 20,000+ pages (90 MB, larger
than the CPU's caches and than the 64 MiB page cache), visited in shuffled order. [E-3] measured the same effect on the observation
table (shuffled order 2.3 to 2.9 times slower than key order), which is why IMP-03 sorts observation rows; the name dictionary is the
one structure the importer still visits in shuffled order. The design probes (§10.2) tested this inference. A 256 MiB page cache made
the same import about 1.5 times as fast and needed no journal sync, which confirms the cost of probing an index larger than the cache.
Interning in key order did not help, because it moved the cost into the in-transaction verification. Shrinking the dictionary each
import works in (per source) bounds the cost by the source.

### 5.6 The sampler was not the cause

On this machine `FileInfo.Length` agreed with the handle's length for the journal in every run (the review's control showed the same).
The 0.19 MB figure was a property of the workload, not of the measurement. Reading sizes through a handle stays the rule
(OBS-04 (c)): the C4 evidence itself recorded a stale directory size for the main file after a rollback.

bounded by its own dictionary: 3.09 s to cancel and 1.41 s to recover 120 MB at 2M into the 6M Library, 0.08 s to cancel a 1% re-scan of

## 9. Re-deriving what PERF-15 protects

**What the frozen text says.** PERF-15: "Peak journal during an import ≤ 5% of the snapshot's size", basis "0.0–0.1 MB for 1M rows
[E-3], measured on one `file_obs`-shaped table only". The specification leans on that figure in four places, which are what PERF-15 was
protecting:

| Where | What it relies on | Product property |
|---|---|---|
| §15.2 "Transient disk needs. Import: almost no journal, plus the snapshot's own growth" | the transient space of a save ≈ the snapshot's growth | **free-space safety** of the Library's volume, usually the system drive |
| CAN-03, PERF-16 "rolling back an appending import is cheap because appended pages are not journalled" | rollback copies little back | **cancellation and failure latency** |
| O21, LIFE-11, PERF-08 (open ≤ 1 s) | a hot journal after a crash is small | **recovery cost at the next start** |
| §5.9 "Appended pages are not journalled; peak journal 0.0–0.1 MB for 1M rows" | journal writes are negligible | **write amplification** (bytes written and synced per save) |

**Why "≤ 5% of the snapshot's size" is the wrong metric.** The measured mechanism (§5.4) gives J ≈ (min(N_new, E_region) + K) × 4 KiB.
Its denominator is not the snapshot:

- it is **unattainable for small snapshots with new names**: each new name costs one 4 KiB journal page against about 130 B of growth,
  so a snapshot whose names are mostly new can journal 30 times its own growth once the dictionary is large enough; the 5% re-scan
  measured 110% (§6);
- it is **trivially met by large snapshots in small Libraries**, which is the C4 benchmark's case;
- it **maps to no product limit**: the user's disk has a number of free bytes, not a ratio; rollback time depends on journal bytes, not on
  the ratio. A larger percentage would only move the line, and every percentage fails at one end of the matrix.

**What replaces it (adopted, §11 and §16):**

1. **A structural bound, tested.** The journal of T-IMPORT may contain only (a) pages of the `name` and `folder_path_child` indexes that
   hold an entry of the *target source*, with the pages bordering that range and their ancestors (for a new source, only the indexes'
   right edge), (b) the right edge of each append-shaped tree, with the up to two left siblings per level that SQLite's rebalancing
   rewrites (about 10 pages per tree measured at 1M rows), and (c) the few catalogue pages the import changes, page 1 and free-list trunk
   pages. TEST-P1 attributes every journalled page of one cell per family to its B-tree and fails on anything
   else. A regression that adds a content-keyed index over observation rows, or that journals observation pages, is caught by
   construction rather than by a ratio.
2. **Free-space safety, enforced where it can be.** IMP-11 (C5 wires it; C4 provides the hook): before T-IMPORT the Library's volume
   must have room for the projected growth, the projected journal and a margin; during T-IMPORT a guard checks the volume every 4,096 rows
   and rolls back before the free space falls below the margin. A rollback needs no space and returns all of it (the main file is truncated
   to its size at `BEGIN`, the journal to 0 bytes), so the guard turns "the system drive fills up" into "this save fails cleanly".
3. **Rollback cost, budgeted in time.** Cancelling at the journal's peak returns rolled back within 2 s in the acceptance cells and 5 s in
   the worst-case cells, and the next start-up open after a crash at that point finishes within 5 s in every cell. 2 s is PERF-16's
   own figure; 5 s keeps a worst-case cancellation within what a user waits for after pressing Stop. Measured with D-52's dictionary on
   this loaded machine (§8): 0.08 s to cancel the acceptance re-scan cell at 2M; 3.09 s to cancel and 1.41 s to recover the worst-case
   interleaved cell at 2M into 6M files. C4's mechanics needed 3.3 to 4.0 s and 3.3 s there.
4. **Write amplification is reported, not budgeted.** It is bounded by (1) and paid for by (2) and (3); TEST-P1 records journal bytes per
   imported row so a change is visible.

With per-source dictionaries (§11), (1) also bounds the journal by the **target source's** own dictionary, so adding a source never pays
for the dictionaries of the others, and the first snapshot of a new source journals only the fixed *K* pages.

## 10. Candidate designs

### 10.1 The three designs the brief names, and what each changes

- **A. Keep C4's one-transaction import; revise the criteria.** No code change; PERF-15 rewritten around the mechanism; PERF-01
  restated; IMP-11 added.
- **B. Keep one transaction; change import or schema mechanics to reduce existing-index page churn.** Variants evaluated:
  **B1** per-source name dictionary (`UNIQUE (source_id, utf16)`); **B2** key-ordered interning of each chunk's names (an ordered sweep
  of the dictionary instead of random probes; the same principle IMP-03 already applies to observation rows); **B3** a larger import page
  cache; **B4** a smaller dictionary key (a hash column indexed instead of the name). B1 and B2 were prototyped and measured alone and
  together (§10.2); B3 was measured; B4 was assessed on paper.
- **C. The prepared hidden-staging alternative.** Import in several committed batches into a snapshot left in `state = 1` (hidden),
  verify, then publish with one small transaction. A probe committed the same importer's work every 131,072 or 16,384 file rows (§10.2).

Not evaluated further, as the brief requires: WAL (D-37: a read writes `-shm`, breaking INV-17's no-write reads, and the WAL grows to
the snapshot's size, so the transient space would be larger, not smaller), `ATTACH` or an external temporary database (REV-M02, A6 in
§6.5: a second file family, temporary-storage review), a new package, or a weaker publication (anything but one `COMMIT` as the
validity point).

### 10.3 Evaluation

| Criterion | A: C4 mechanics, new criteria | **B1: per-source name dictionary, new criteria (chosen)** | C: hidden staging, batched |
|---|---|---|---|
| **Atomic visibility** | One `COMMIT` is the validity point (LIFE-01, CONC-04) | Same | Staged rows are committed and visible to every connection as `state = 1`; correctness then rests on every reader filtering by state and on `PublishedSnapshotId` (LIFE-02). The committed-state check of LIB-08 step 7 ("a committed `state ≠ 2` row means a defeated commit → Damaged", D-47) can no longer tell damage from an interrupted staging and must be weakened |
| **Crash recovery** | SQLite's hot-journal rollback at the next open; cost ∝ journal (0.7 s for 89 MB, 3.3 s for 177 MB) | Same mechanism; the journal of a new source's import is the fixed few pages, any other bounded by its source's dictionary | Each batch's hot journal is small, but the committed staged rows of an interrupted import must be **purged** at the next open: a T-DELETE-sized write transaction (C4: 128 MB journal for a 2M snapshot) inside the start-up Open lease, which can itself fail on a full disk ("recovery pending"); `c0c031f`'s purge rules (REV-H03) come back |
| **Cancellation** | Rollback ∝ journal: 1.2 to 1.8 s at 89 MB, 3.3 to 4.0 s at 177 MB (§8) | Same mechanism, smaller journals in the common cases | Stop between batches is quick, but the staged rows remain: either a purge now (seconds, journal ≈ staged size) or a deferred purge (a new pending state) |
| **`SQLITE_FULL`** | Rollback returns all space (main file truncated to its size at `BEGIN`) | Same | The failing batch rolls back, the **earlier batches' pages stay in the file**; a purge only moves them to SQLite's free list (no `VACUUM` in 1.1.0), so a save that ran out of space leaves the drive **fuller** than before (probe: a failure after four commits left the file 72.3 MB larger, §10.2) |
| **Temporary disk amplification** | G + J, J up to the whole Library's name index (89 MB at 3M files, 177 MB at 6M) | G + J, J = 0.2 MB for a new source; for a known source up to that source's dictionary range | G + one batch's J, but each batch re-journals the dictionary leaves its names touch: 798 MB written in 7 commits and 2.2 GB in 60, against 89 MB in one; at 7 commits the peak was not even lower (105 MB) (§10.2) |
| **C5 free-space preflight** | J's projection must cover the whole Library's name dictionary (an aggregate over every source's names), and grows with every source added | J's bound = the target source's footprint, one read-only aggregate (IMP-11); zero for a new source | Needs G + J_batch, plus the purge's own journal for the failure path |
| **Rollback latency** | Grows with the Library | Grows with the source's dictionary only | Small per batch; the purge is the real cost |
| **Schema and state complexity** | None | One column and a two-column `UNIQUE` on `name`; invariant 4 gains the source; the name cache is per source; IMP-11's guard hook; no new state | A committed intermediate state, a purge transaction, new recovery rules, a weaker committed-state check, more lifecycle tests (TEST-T1 rows, W2 pause points) |
| **Security surface** | None new | None new (same SQL surface, constant statements; IMP-11 reuses an existing read-only native call) | A committed partial snapshot is a new tamper and crash surface (CONC-10, D-47) |
| **Performance** | Realistic names: 118k to 164k rows/s. **B2 (key-ordered interning)** is not adopted: alone, it left whole-import throughput unchanged or lower (§10.2) because the cost moved from
insertion into the in-transaction verification; with B1 it added nothing beyond B1's own effect within the run-to-run spread. **B3 (larger cache)** is the strongest single lever measured: at the interleaved 1M / 3×1M cell a 256 MiB cache made the import about 1.5 times as fast (73k to 77k against 47k to 53k rows/s) and needed no journal sync at all, while 16 MiB made it about 30% slower (33k to 36k) with seven syncs; it confirms that the large-Library slowdown is the name index outgrowing SQLite's page cache. But it raised the working set by 322 MB at 1M rows, beyond PERF-11b's 300 MB at 2M, so it is not adopted; it is the first prepared alternative should a worst-case cell miss PERF-14 (§15.4). **B4 (hash key)** shrinks the index by a constant factor (an 8-byte key instead of a 40 to 100-byte name),
so the journal and the probes shrink by the same factor, but the dictionary's uniqueness would no longer be a constraint of the schema
(a hash collision needs a second lookup by bytes, and `UNIQUE` on content goes away): an integrity loss for a constant factor, not
adopted; kept as a prepared alternative for a future stop (§15.4).

## 11. Decision

### 11.1 Chosen design (D-52)

1. **T-IMPORT stays one `BEGIN IMMEDIATE` transaction in rollback-journal (`TRUNCATE`) mode**, with `synchronous=FULL`, verification
   inside, and the three final statements before `COMMIT` (IMP-02, IMP-05, IMP-06 unchanged). Atomic publication, crash recovery by
   SQLite's hot-journal rollback, and `SQLITE_FULL` returning every byte all stay exactly as specified.
2. **The name dictionary is per source** (B1): `name (name_id, source_id NOT NULL REFERENCES source, utf16, UNIQUE (source_id, utf16))`.
   Folder paths already were. A new source's names form a new key range, so its first import journals no existing dictionary page; a
   later import journals at most its own source's range. Comparisons pair snapshots of one source only (DIFF-01), so integer joins on
   `name_id` are unaffected; search matches the source's names (SRCH-02).
3. **Interning is otherwise unchanged** (IMP-03): names are interned run by run, as C4 does, through a name cache that is per capture and
   per source (IMP-04).
4. **PERF-15 is replaced** (§9): (a) what the journal may hold, asserted page by page in TEST-P1; (b) IMP-11's space preflight and guard;
   (c) a rollback-cost budget in time. **PERF-01 and §15.4 are restated** with a method and outcome classes (§12).

### 11.2 Why this and not the others

- **Not A alone:** A is correct, and on realistic names it is as fast as B1 (§10.2). Its weakness is structural: the journal, the
  rollback and the recovery of every import, a new source's first included, grow with the name dictionaries of *all* sources. The first
  snapshot of a new source with unfamiliar names journalled 88.7 MB at the 3M-file Library, exactly what a known source's did, and the
  6M-file Library's 177 MB took 3.3 to 4.0 s to cancel and 3.3 s to recover. That term has no bound but the Library's history, and it is
  the G0-O03 case. A with revised budgets would pass the matrix today and drift out of it as Libraries grow, without anything to say so.
- **Not C:** staging bounds the size of each journal but not the dictionary work that caused C4-B01, and it trades a transient,
  self-returning journal for committed rows that a failure leaves behind: on a full disk the staged pages stay in the file. It also brings
  back the recovery and purge rules the repaired architecture removed (REV-H03) and weakens D-47's committed-state check. Its one benefit,
  a smaller peak journal, is delivered by B1 for the common cases without any of that.
- **B1:** it removes the cross-source cost structurally: the G0-O03 case, "a Library that already holds other sources", becomes
  append-shaped for a new source, and a known source pays only for its own dictionary. It changes neither the transaction model, nor the
  side-file model (§6.3), the interlock, the leases or the security surface, and it makes IMP-11's journal projection a cheap, exact-scope
  aggregate.
- **Not B2:** measured not to help (above).

### 11.3 Alternatives rejected (summary)

| Alternative | Reason |
|---|---|
| Revised percentage for PERF-15 | Wrong denominator (§9); any percentage fails at one end of the matrix |
| A alone with revised budgets | Cost and journal grow with the whole Library; stop-threshold cells; no cheap preflight bound |
| C, hidden staging (the prepared alternative) | Does not reduce the dictionary cost; leaves a failed save's space in the file; purge and recovery rules; weaker D-47 |
| B2, key-ordered interning | Moved the cost into verification; no net gain alone or with B1 (§10.2) |
| B3, a larger page cache | About 1.5 times as fast at the interleaved 1M / 3×1M cell, but +322 MB of working set at 1M rows, beyond PERF-11b; the first prepared alternative (§15.4) |
| B4, a hashed dictionary key | Constant factor only; loses `UNIQUE` on content; kept for a future stop |
| WAL, `ATTACH`, external temporary database, a new package, weaker publication | Excluded by D-37, REV-M02, BLD and LIFE-01; not needed |

## 12. PERF-01 decision (resolves C4-H02's methodological part)

**The ambiguity.** PERF-01 said "≥ 100,000 file rows/s in key order" and §15.4 said "a fresh process per run, warm cache, … the
Library on the same SSD" and "stop if missed by more than 50%". Nothing said which statistic, how many runs, what counts as a quiet
machine, which runs may be discarded, which data, which Library size, or what a miss smaller than 50% means. C4 reported "met on the
median" over a subset; the review could not say "met" or "missed" (`PERF-01 EVIDENCE INCONCLUSIVE`). The revised authority (§15.3 and
§15.4 of the specification, §16 below) fixes each point:

| Point | Decision | Why |
|---|---|---|
| **What is measured** | File rows ÷ (time from `BEGIN IMMEDIATE` to the return of `COMMIT`), in-transaction verification included | What the user waits for; it is what C4 and this review report |
| **Target** | **≥ 100,000 file rows/s** (unchanged) | Derived, not chosen to fit: PERF-02b allows 1.5 × v1's 6.36 s = 9.5 s until "Saved to History" on the 250k tree; with the reports ready at 6.4 to 7.0 s (PERF-02a), 2.5 to 3.2 s remain for pass V and the import of 250k files, so the import needs 80k to 100k rows/s. PERF-14 (2M in ≤ 60 s) needs only about 40k rows/s and is the worst-case bound |
| **Stop threshold** | A median **below 50,000** rows/s in an acceptance cell | Half the target; below it PERF-02b is missed by seconds and no tuning of constants recovers it, so the design is reviewed |
| **Acceptance cells** | Real-vocabulary names (N4) as the first snapshot of a **new source**, and a 1% re-scan (N5) of such a source into its **existing** source; 1M and 2M files; a Library of three snapshots of the target size in two sources (L2) | The common cases, with the name statistics of real trees: the first save of a source into an established Library, and the periodic save of a known source. Real trees repeat names heavily: about 10% of the harvested names were new to their source (§3.2), and SRCH-02 puts the reference drive at about 250k distinct names in 2M files |
| **Worst-case cells** | Interleaved (N2) and mixed (N3) names into an existing and into a new source, and a 1% re-scan of an all-unique (N2) source, at 2M into L2: bounded by **PERF-14's engine share (≤ 60 s; stop above 90 s)**, not by PERF-01 | A third to a half of the names new and spread over the key space is possible (a media archive, a cache folder) but far from the measured statistics; its user-visible bound is the saving time |
| **Informational cells** | The append control (N1) at every size; 10M rows into three 2M snapshots; the rescan at 5% | Kept so a regression of the best case or of scale is visible; never acceptance evidence |
| **Run count** | **5 valid runs per cell** | The smallest count whose median tolerates two disturbed runs |
| **Warm-up** | One complete, unrecorded run of the first cell at the start of every benchmark session | Loads the binaries and the engine DLL and wakes the SSD from low-power states |
| **Fresh process** | Every run is its own child process, started sequentially by the harness; runs are interleaved round-robin across cells (run 1 of every cell, then run 2 …) | Drift in machine state spreads over all cells instead of biasing one |
| **Cache state** | The run copies its prefilled Library (built once per family and size by a separate process of the same binary) and flushes it to disk immediately before the measured import: the OS cache is warm for the Library, SQLite's page cache is cold (a fresh writer connection, as at a real save) | Matches §15.4's "warm cache" and v1's benchmark; one method only, because prefilling in the measuring process measured about 13% slower (§4.5); cold-cache figures are informational (C10) |
| **Machine record** | CPU model and logical CPUs, RAM, storage model and bus, file system and cluster size, OS build, power plan and AC power, Defender real-time state (no exclusion for the benchmark folder), SQLite version, page and cache size, binary commit | Reproducibility; the review could not tell load from regression |
| **Quiet machine** | Before the warm-up, with nothing of the benchmark running, the machine's whole CPU use over 30 s is at most 5% | Services and anti-malware the account cannot read show up here, and only here |
| **Load record** | Per run, during the measured import: the CPU of every other process the account can read, as a share of the machine (mean, 95th percentile); for information, the machine's whole CPU use less the run's own (`GetSystemTimes`), which also counts kernel and anti-malware work the import itself causes; per session: the other processes' CPU at start and end | The C4 attribution of slow runs to load was an inference with no data. This review learned the difference the hard way (§3.3) |
| **Accepted statistic** | **The median of the 5 valid runs** of each cell; minimum and maximum are reported beside it | The median is robust to an occasional disturbed run; the minimum would measure the machine's worst moment, the maximum its luck |
| **Validity and exclusion** | A run is **invalid** only if the other readable processes' CPU exceeded 10% of the machine (mean) or 25% (95th percentile) during the measured import, or it failed for a recorded environmental reason. Invalid runs stay in the raw table, marked, and are replaced; at most 10 attempts per cell. **No run is ever excluded for its throughput** | Exclusion by a property recorded *before* looking at the result, never by the result |
| **Not enough valid runs** | A cell with fewer than 5 valid runs after 10 attempts is **NOT MEASURED**, which never counts as met | The C4 failure mode was a figure taken from a loaded machine |
| **Hosted CI** | A second environment: the evidence workflow runs the whole matrix once and reports it beside the reference figures. A hosted result never meets or misses a target and never replaces a reference cell. A hosted cell beyond a stop threshold requires that cell to be measured on the reference machine before the gate is accepted | Hosted runners differed 1.5× between two runs of identical code (C4 evidence) and are not the reference machine |
| **Reference machine** | §15.1's: i7-1270P, 32 GB, NVMe SSD, Windows 11, on AC power | The machine every earlier budget was measured on |

**Outcome classes (every budget of §15.3 at its gate).** **MET**: every acceptance cell's median meets the target. **MISSED**: some
acceptance cell's median misses the target, none crosses the stop threshold: the gate is **not** accepted on that budget; the
implementation is improved, or the budget is revised by a reviewed specification change with measured justification (§15.3's
heading). **NOT MEASURED**: as MISSED. **STOP**: a median crosses a stop threshold: the gate stops and the design is reviewed (§15.4).
The specification now says in so many words that a MISSED budget is never reported as met because the stop condition did not fire.

**Applied to the evidence that exists.** None of the C4 or of this review's runs is valid by this method (other readable processes at 12% to 45% of the machine, the
whole-machine figure 28% to 75%), so
**PERF-01 is NOT MEASURED** for the current code. The repaired C4 must measure it on a quiet reference machine (§17). The direction is
visible, though: in the acceptance cells' name families both mechanics ran at 115k to 148k rows/s even on this loaded machine, and in
the worst-case cells 2M files took 45 to 53 s, inside PERF-14's 60 s but not by much (§7, §10.2). The C4 statement "meets PERF-01 on
the median" is withdrawn by this method, not replaced by "met".

## 13. Safety and full-disk implications

- **Atomicity is unchanged.** T-IMPORT stays one `BEGIN IMMEDIATE` … `COMMIT` with `synchronous=FULL` (CONC-04, LIFE-01, LIFE-11).
  Nothing of a snapshot is visible before its `COMMIT`; there is no committed intermediate state, so nothing has to be purged and no
  recovery rule is added.
- **`SQLITE_FULL` stays safe and returns the space.** A failed import rolls back: SQLite copies the journalled pages back and truncates
  the main file to its size at `BEGIN`, then truncates the journal. A rollback writes no new bytes beyond the pages it restores in place.
  C4's hosted run showed it on a really full NTFS volume (2M rows into a 200 MB VHDX: `LibraryFull`, rolled back in 7.07 s, main file
  37.8 MB again, older snapshots verified); every cancel run of §8 shows the main file back at its exact size before and the journal at
  0 bytes.
- **The transient need is G + J**, both measurable before the import: G, the snapshot's growth, from the spool's counts and name bytes;
  J, from the target source's dictionary footprint (zero for a new source, §11). With per-source dictionaries J no longer grows with the
  other sources of the Library.
- **The remaining hazard is the volume itself.** The Library usually lives on the system drive. Without a rule, an import may fill it to
  zero for the seconds before `SQLITE_FULL` and the rollback, and other programs writing at that moment fail. IMP-11 (§16) closes this:
  a preflight before T-IMPORT (and the read-only part at P0) and a guard during T-IMPORT that rolls back before the free space falls
  below a margin, in the style of SPOOL-24.
- **Rejected staging would have made this worse** (§10.3): a failed batched import leaves the committed staging pages in the file, and
  a purge frees them to SQLite's free list without returning them to the volume (no `VACUUM` in 1.1.0), so a save that ran out of space
  would leave the drive fuller than before (measured: a failure after four commits left the main file 72.3 MB larger, §10.2).
- **Deletion (not changed here).** T-DELETE journals about the deleted snapshot's pages (C4: 128 MB for a 2M snapshot) and does not
  shrink the file. A deletion on a nearly full volume fails safely with `SQLITE_FULL`. Applying an IMP-11-style guard to T-DELETE is
  left to C6, which owns the Delete action (observation, not an edit of C6's scope).

## 14. Cancellation and recovery implications

- **Cancellation** rolls back the open transaction; its cost is the journal, 13 to 34 ms per MB (§8; 0.6 to 0.8 s for 22 MB, 1.2 to 1.8 s for 89 MB, 3.3 to 4.0 s for 177 MB). With per-source dictionaries
  the journal of a common save (a new source, or a re-scan of a realistic source) is small, and the worst case
  is bounded by the target source's dictionary. PERF-16 (2 s at 2M, end to end, C5) is kept; the engine part becomes PERF-15 (c)
  (§16).
- **Crash recovery** is SQLite's hot-journal rollback at the next start-up open, inside the start-up Open lease (LIB-08 step 5, O21);
  its cost is the journal too, about 8 ms per MB of hot journal (§8; 0.68 to 0.71 s for 89 MB, against 0.11 to 0.16 s for the append control). PERF-08 (open ≤ 1 s) stays the budget of a clean open; an open that rolls a hot
  journal back is budgeted by PERF-15 (c).
- **No new state.** No staging state, no purge, no "recovery pending" case beyond LIB-08 step 8's existing one; the committed-state
  check (LIB-08 step 7, every committed snapshot has `state = 2`) stays exactly as strong as it is.
- **Open C4 findings that touch this area stay open:** C4-M02 (the token is not checked after verification and before `COMMIT`) must
  be repaired as the review says (§17).

## 15. C5 implications

1. **IMP-11 is a C5 prerequisite** (§16): C5 computes the projections, runs the read-only P0 check and the P5 preflight, and wires the
   guard to `GetDiskFreeSpaceExW` on the Library directory through Core's existing native method (already in the native set, §7.8; the
   Library assembly gains no P/Invoke). A failed preflight or a guard stop records `SnapshotFailed (LibraryFull)` with a
   message that says how much space saving needed (O13), or makes Save to History unavailable at P0 (O24). Its constants are defined
   values confirmed or revised in C5 by Q-24, as SPOOL-24's are by Q-18.
2. **The name bytes of the snapshot** (Σ of the UTF-16 lengths of every file and folder name) feed IMP-11's growth projection. Pass V
   already parses every record's length (SPOOL-23 (3)); C5 sums them there, with no extra read.
3. **The spool's read pattern is unchanged** (IMP-03): runs in `path_id` order, names interned per run; only the dictionary's scope
   changes (the source's names, IMP-04).
4. **PERF-16 end to end** is measured in C5 in the acceptance cells' name families (the budget) and, for information, in the worst-case
   ones, whose engine part PERF-15 (c) bounds at 5 s.
5. **PERF-03 (C5)**: per-source dictionaries store a name once per source that has observed it instead of once per Library. The
   measurements here put a new name at about 2 × its UTF-16 bytes + 25 B (row and index entry; 117 B for the 46-byte interleaved names,
   from the hash and 1% re-scan cells at 1M/3000k) and an existing one at nothing, so the first
   snapshot of a source costs more per file than its re-scans (§6 and §10.2 growth columns: about 110 to 116 B per file for a first snapshot of real
   names, 73 B for a 1% re-scan). C5 reports both when it confirms PERF-03; PERF-03 itself is not changed here.
6. **TEST-T1's "full Library volume" row** is driven through IMP-11's guard as well as through a real full volume.

## 18. Limitations

- **The machine was loaded** (other readable processes at 12% to 45% of its capacity, the whole-machine figure 28% to 75%) throughout; every timing here is comparative, not an
  acceptance figure. Comparisons are made between cells run under similar load, and a probe is compared with the same cell of the
  pristine build run in the same chain.
- **Few runs per cell** (two or three, one for the analysis and probe cells), not five: enough to reproduce, explain and choose; not
  enough to accept.
- **Synthetic trees.** Folder trees, sizes and times are C4's generator; only names vary. The real-vocabulary family uses real names on a
  synthetic tree; no real drive was imported (that is C5's TEST-P2).
- **The probes are prototypes** (`probes.patch`): the per-source dictionary probe skips the schema-fingerprint check and does not change
  invariant 4's statements; the key-ordered probes sort and intern through the existing name cache in an unoptimised way, with their own
  memory (223 to 265 MB above baseline at 1M rows, against 132 to 170 MB for the unmodified importer). They measure the mechanics, not a
  finished design.
- **Warm OS cache only.** A cold cache (a Library not touched for days) would make the dictionary probes read from the SSD; not measured
  (C10).
- **One page size, one cache size** (4 KiB, 64 MiB) except the cache probes.
- **Hosted runner not used** in this review (no workflow was added); the method gives hosted runs a defined, secondary role for the
  repair.
