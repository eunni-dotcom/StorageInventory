## 3. Methodology

1. **Specification first.** The C1-relevant authority above was read before the code.
2. **Code.** Every changed source file was read in full against the base: `InventoryScanner.cs`, `CsvReportSink.cs`,
   `ScanEngine.cs`, the deleted `IScanSink.cs`, the new `IScanObserver.cs`, `ObserverFanOut.cs`, `SpoolFormat.cs`,
   `SpoolWriter.cs`, `SpoolReader.cs`, `VerifiedSpool.cs`, and the unchanged collaborators they depend on
   (`ReportRun.cs`, `FolderAggregator.cs`, `PathPolicy.cs`, `NativeMethods.cs`).
3. **Tests.** Every new and changed test file was read in full, including the test kit's independent format walker.
4. **Windows CI, independently.** The job logs of run
   [36851525750](https://github.com/eunni-dotcom/StorageInventory/actions/runs/36851525750) (the reviewed head
   `7d4a272` itself, which the evidence predates) and of the baseline run
   [36846607962](https://github.com/eunni-dotcom/StorageInventory/actions/runs/36846607962) (`521d0e4`) were pulled and
   parsed: totals, every per-test status line, skip reasons, build warnings, publish size and SHA-256.
5. **Local execution (Linux, supporting evidence only).** The container has no .NET SDK and the .NET download hosts are
   blocked by the environment's egress policy. A toolchain was assembled from official Microsoft NuGet packages
   (`Microsoft.NETCore.App.Runtime.linux-x64` 10.0.12, `Microsoft.NETCore.App.Ref` 10.0.12 with its source generators,
   `Microsoft.NETCore.App.Host.linux-x64` 10.0.12, `Microsoft.Net.Compilers.Toolset` 5.0.0) and `csc` was driven
   directly (`-langversion:latest -nullable:enable -warnaserror+`). The two `kernel32` imports were satisfied by a stub
   whose `CreateFileW` fails, so v1's canonical check reports "unavailable" exactly as v1 handles it. Both the base and
   the head were built this way. Nothing measured on Linux is treated as release-authoritative.
6. **Independent experiments** (details in the sections that use them):
   - Core.Tests on base and head;
   - TEST-O5 baseline regenerated from the base build, plus a second, independent public-API dump that includes custom
     attributes, generic constraints, parameter metadata and defaults;
   - 20 source mutants (the four reported in the evidence plus 16 more) against Core.Tests;
   - a fuzz and hostile-input harness against `SpoolReader.Verify` and `VerifiedSpool` (about 23,000 inputs);
   - fan-out edge probes through `InventoryScanner.ScanObserved` on a real tree;
   - a base-versus-C1 report A/B through the public `InventoryScanner.Scan` only (36 runs), and a timing A/B.

real NTFS tree in CI, and the folder records are compared against the Folders report's rows on every fixture.

### 6.2 Critical versus isolated (SINK-04, SINK-05, D-11)

- Only `CsvReportSink` is critical and only it is wrapped by `OutputGuard` (`new OutputGuard(sink)`, machine-checked).
  A critical IO/UAE becomes `ReportWriteException` → `OutputError`, exactly as v1 (TEST-O4, and the squatter test,
  which produces a real create-new collision on the ScanErrors report).
- An isolated class A exception is caught per callback, recorded once with the original exception (never wrapped),
  and the observer receives nothing more except `OnScanEnded` (TEST-O3 at 15 points; TEST-O4). Class B with the run's
  token set and class C propagate (TEST-O4 at every callback, both at the fan-out and through the pipeline).
- An isolated observer cannot corrupt or interrupt the CSV observer: the critical observer is called first for every
  per-record callback, and an isolated class A exception never leaves the fan-out. The only ways an isolated observer
  can change the scan's outcome are those the specification mandates (class B, class C).
- Failure ordering is deterministic: the isolated observers in list order, the critical observer first for record
  callbacks and for the Finished end, and first in `EndRemaining`.
- Classification (`ExceptionClasses`): class C is `OutOfMemoryException` (which includes `InsufficientMemoryException`)
  and `InsufficientExecutionStackException`, matching CAT-03; class B is `OperationCanceledException` with the run's
  token cancelled, matching CAT-02. Mutants M9 and M10 (§9.4) show both rules are pinned by tests.

### 6.3 The judgement call: isolated observers started before the CSV observer

Each scenario of the review brief was traced in code and, where possible, run:

| Scenario | Outcome | Problem? |
|---|---|---|
| Isolated start succeeds, CSV start fails | `ReportWriteException` → `OutputError`; `EndRemaining(Failed)` ends the isolated observers; a spool writer becomes `Abandoned` (CI test with a real collision) | No |
| Isolated start throws class A | that observer is faulted; the CSV observer starts; the scan is unaffected (probe d: Complete, 1 fault, the observer still ended) | No |
| Isolated start throws class B or C | the scan ends Cancelled or Failed (Unexpected) **before** any CSV report exists, so no incomplete artefacts are listed where v1 would have listed two | Only reachable with a test observer: `SpoolWriter.OnScanStarted` never throws class B, and a class C there is CAT-03's intended outcome. No concrete failure |
| Faulted observer gets the terminal notification | by design (spec: "no further calls except `OnScanEnded`"); `SpoolWriter` stays `Faulted` and never seals (mutant M6 is killed) | No |
| Critical observer fails part-way | the critical observer is called first, so isolated observers never see the record that failed; then `EndRemaining(Failed)` | No |

Pre-cancelled token (probe e): plain and observed scans both return Cancelled with v1's two incomplete artefacts.
**C5 compatibility:** the writer takes its stream at construction, so C5 must create the spool file before
`OnScanStarted`, that is before the first CSV report. That fits SPOOL-04 ("when the run creates its first report file")
and SPOOL-24 check (1), and a later CSV failure simply closes (deletes) the spool. **No concrete failure mode was found;
the ordering is acceptable.**

## 8. Spool format review

**Verdict: PASS.** Code, constants, tests, the evidence's table and SPOOL-20 agree exactly.

| Part | Specification (SPOOL-20) | Code (`SpoolFormat`, `SpoolWriter`) | Pinned by |
|---|---|---|---|
| Header | magic, format u16, flags u16, token 16 B, run ID (u16 len + UTF-16), contract u16, created ticks i64 | 30 + 2·runId + 10 bytes; run ID 1..256 units | `Frozen_layout_of_format_1` |
| File `0x01` | folder i32, name (u16 len), size i64, 3 × ticks i64, attributes i32 | 43 + 2·name bytes | same |
| Error `0x02` | type u8, path (u32 len), message (u32 len) | 10 + 2·(path + message) | same |
| Folder `0x03` | index, parent i32, name, status, reason (0xFF none), subtree u8, attributes i32, 2 × ticks, 6 × i64 counts, largest i64 or null | 90 + 2·name; name length u16 (G0F-O03) | same |
| Run index | (folder i32, offset i64, count i32) per run, emission order | 16 B; offset = the first file record's tag | same |
| Trailer | `0x7F`, counts, totals, two offsets | 113 B: 4 counts, 8 totals in the order files, folders, bytes, scan errors, reparse skipped, file reparse, locally incomplete, affected ancestors; folder-section and run-index offsets | same |
| Digest | SHA-256 of `[0, L − 32)`, last 32 bytes | `IncrementalHash` fed in write order; nothing follows | TEST-SP1 (independent `SHA256.HashData`) |
| Nulls, flags, codes | `i64.MinValue` ticks; reason 0xFF; §9.4 codes | as specified; flags must be 0; codes 1..9 and 0..3 are explicit switches, never ordinals | `Null_encodings_and_stable_codes_are_frozen` |
| Count mapping | (G0F-O03) | error records = ScanErrors + ReparsePointsSkipped + FileReparsePoints | `Frozen_layout_of_format_1` |

Little-endian is explicit (`BinaryPrimitives`, with a big-endian fallback for UTF-16 copies). Integer handling was
checked for overflow: name lengths are bounded before the cast to `u16`; byte totals use `checked` in the writer and a
sign check in the reader; every reader length is widened to `long` before `2 × length`, so no length can overflow;
run counts are checked against `int.MaxValue`; the folder count is capped by the bytes remaining (§9.3). The
evidence's frozen details (G0F-O03) are recorded in `SpoolFormat`'s documentation and pinned by tests: **G0F-O03 is
satisfied.**

**Exact names (item 10).** Writing copies the string's UTF-16 code units (`MemoryMarshal.AsBytes`, no `Encoding`);
reading rebuilds the string from the same units (`new string(ReadOnlySpan<char>)`). No UTF-8 step, normalisation or
case folding exists anywhere in the codec; length fields count UTF-16 code units on both sides. TEST-SP1 round-trips
unpaired high and low surrogates, a reversed pair, a dangling high surrogate after text, a real pair, NFC and NFD,
case variants, `ß`/`ss`, `İ`/`i̇`, U+0345, `NUL`, U+FFFE/U+FFFF, zero-width, tab and a 255-unit name, compared by
code unit; the NTFS test in CI does the same through a real scan. No C7 comparison-key semantics appear in C1.

## 9. Integrity and structural-validation review

**Verdict: PASS, with two test-gap and hardening observations (C1-O01, C1-O02).**

### 9.1 Ordering of pass V (SPOOL-23)

`SpoolReader.Verify` reads the stream once, sequentially, from offset 0: the hashing pass feeds `[0, L − 32)` to
SHA-256 and keeps the last 32 bytes while the structure parser consumes the same bytes. If parsing fails, the stream
is still read to the end, and **a digest mismatch is reported in preference to any structural defect**
(`SpoolReader.cs:111-115`). A `VerifiedSpool` is constructed only after both pass, in `SpoolReader.cs:115`, the only
construction site (machine-checked). There is no API that returns a record, an offset or an index from an unverified
stream: `SpoolVerification.Spool` is null for every defect (asserted in every TEST-SP7 case). V's structural steps
mirror SPOOL-23 (2) to (6) and add closure checks that mirror `FolderAggregator.Verify` and §9.5 (stricter than the
minimum, and unable to reject a writer-produced spool because the writer only receives folders that passed `Verify`).

### 9.2 Swap and TOCTOU

`VerifiedSpool` keeps the stream it was verified on and reads it by seeking. It re-checks the stream length on every
refill and throws `SpoolFormatException` if a record no longer parses, but it does **not** re-hash. A same-length
modification after V is therefore returned as read (probe: a changed name byte after V reads back changed). That is
exactly SPOOL-23's stated model: V is meaningful because, from C5, the stream is the exclusive delete-on-close handle
held since creation; "silent corruption by the storage stack between the two reads is outside the integrity model".
In C1 the stream is the caller's, so nothing more can be claimed, and the evidence does not claim more. SHA-256 here
seals a byte sequence; it does not authenticate a deliberate reconstruction, and neither the code nor the evidence
says otherwise. Two hardening points are C1-O02.

### 9.3 Hostile and corrupt input (item 13)

A harness ran `Verify` on about 23,000 inputs, and on every accepted spool also read the whole record region, every
run, the folders and the errors:

- zero-byte, 1, 30, 184, 185, 186, 187, 300, 4,096 and 1 MiB random buffers, with and without a valid re-seal;
- 3,000 spools with a valid header and a random body biased towards valid tags, re-sealed;
- 20,000 structural mutations of valid spools (multi-byte overwrites, insertions, deletions, duplicated ranges, and
  `i64` fields forced to `long.MaxValue`, `long.MinValue`, `int.MaxValue`, `int.MinValue`, −1, 0, `uint.MaxValue`,
  `ushort.MaxValue`), re-sealed;
- a root claiming `long.MaxValue / 2` subfolders in a tiny file (rejected `FolderSectionInvalid`, no allocation);
- a 10.7 MB re-sealed hostile spool of 250,000 single-file runs (rejected; 32.8 MB allocated in 39 ms, so memory is
  bounded by the input's size, not by any count field).

**Result: 0 unexpected exceptions, 0 rejected results carrying a spool, 0 accepted spools that failed to read back.**
Defects reported: `RecordOutOfBounds` 13,750, `BadRecordTag` 5,834, accepted 1,830 (byte changes inside names, times
or attributes: the documented boundary), `FolderClosureViolation` 503, `FolderSectionInvalid` 439, `RunIndexMismatch`
340, `BadHeader` 90, `RunSplit` 78, `CaptureTokenMismatch` 57, and smaller counts of the rest. Duplicate or missing
trailers, out-of-range tags and codes, impossible hierarchies, duplicate indexes, inconsistent totals and corrupted run
indexes are all rejected with named defects. Names and messages are skipped, not allocated, during V; the only
count-driven allocation (17 bytes per folder) is capped at `remaining bytes / 90`. **The reader fails boundedly.**

### 9.4 TEST-SP7 against the corrected form, and the mutation checks

TEST-SP7 covers every clause of §18.1's corrected text: byte changes at each position class (header, file record,
error record, a run read out of key order, folder section, run index, trailer field, trailer tag, digest) with three
masks; truncation at 14 offsets; 1, 32, 1,000 and 8 bytes appended; zero, shorter-range, longer-range and foreign
digests; then re-sealed structural rewrites (run split; whole records of different folders exchanged, both as
single-record runs and into a multi-record run; run-index entries exchanged; unknown tag; trailer tag in the record
region; out-of-bounds lengths, codes, sizes, ticks and folder index; per-tag counts; folder order and parent
violations; closure violations; each of the eight totals; the result's totals; both offsets, the run count and the
trailer tag; every header field). The documented boundary is **asserted as accepted**: same-folder exchanges (equal and

## 10. Cancellation and failure review

**Verdict: PASS, with C1-M01 and C1-O04.**

### 10.1 Writer finalisation

- The writer seals only when told `Finished` while it is `Writing` (`SpoolWriter.cs:227-246`), only after its own
  counts and statuses equal all eight `ScanTotals` fields, and only after the folder section exists and holds exactly
  `root.TotalSubfolderCount + 1` folders. The digest is computed after `Flush()` of every preceding byte; the state
  becomes `Sealed` only after the digest is written and the stream flushed (`SpoolWriter.cs:270-275`).
- `Cancelled` or `Failed` → `Abandoned`, buffer and hash released, no trailer. Any exception while writing → `Faulted`
  for good. `Sealed`, `Abandoned` and `Faulted` are terminal, so double finalisation is a no-op. No digest can be written
  before success is established, and no exception is swallowed into a valid-looking spool: a partial digest or a
  failed flush leaves the writer `Faulted`, and the bytes fail V.
- The pipeline sends `OnScanEnded(Finished)` only after v1's reports are complete (`InventoryScanner.cs:174`), so a
  cancellation during enumeration, finalisation, the Folders report or the sorted copy yields `Abandoned`
  (`Cancellation_at_every_stage_...`, TEST-O6, `Cancelled_at_any_point_the_spool_never_verifies`).
- **Exception (C1-M01):** if another isolated observer, ended after the writer, throws class B or C during the Finished
  end, the writer is already sealed and V-valid while the scan result becomes Cancelled or Failed (Unexpected). The
  evidence's §8 statement that no cancelled or failed run can yield such a spool is true only with a single isolated
  observer, or with the writer ended last.

### 10.2 Terminal notification

`EndRemaining` ends each started, unended observer in its own guard, critical first, records isolated failures, drops
the critical observer's (the outcome is already v1's), and returns whether a class C occurred. A class C there stops
further notifications (judgement call 5; probe c: a started observer after the thrower was never ended). This is a
narrow deviation from SINK-03 #1's "exactly once", consistent with OBS-13's best-effort release (C1-O04).

### 10.3 Catastrophic failures (item 16)

CAT-03 requires that v1's top-level handler stay unchanged (class C → `Failed (Unexpected)`, never Finished) while the
internal capture entry point also reports `Catastrophic`. C1 does exactly that: the public result is v1's
(`Failed (Unexpected)`, "The scan stopped unexpectedly: …"), and `ObservedScanOutcome.Catastrophic` is set when the
failure, or an exception while ending, is class C (`InventoryScanner.cs:192-195`). Class C is never isolated
(mutant M10 killed) and never wrapped (`OutputGuard` and `Output` map only IO/UAE). C1 implements no Faulted state,
which is correct: the interlock is C4/C5 (OBS-13, CAT-04). One edge: the informational canonical-root lookup runs
before the pipeline's `try`, so a class C there escapes `Scan` as an exception instead of `Failed (Unexpected)` (as
v1's own `PathPolicy.Validate` already does); CAT-04's task-boundary handling covers that in the App. **No loss of
information that later gates require.** Recorded in C1-O04.

### 10.4 `CsvReportSink` lifecycle change (item 17)

- Output validation still precedes any mutation: `PathPolicy.Validate`, `ReportRun.Prepare` (existence of all six own
  names) and `EnsureOutputFolder` run first, unchanged; every create still goes through `ReportRun.CreateNew`, which
  re-checks own name, folder and the reparse-point state of the folder at creation time.
- Collisions fail as before (`ReportPipelineTests.A_report_name_taken_mid_run_is_never_overwritten`, and a real
  collision through `ScanObserved`); the squatter's file is never overwritten or claimed.
- Cancellation before start: unchanged artefacts (probe e; A/B cancelled runs identical).
- Partial outputs: the incomplete-artefact lists and sizes are identical to v1's (A/B).
- `OutputGuard` protects the same boundary as v1's constructor `try`/`catch` plus `OutputGuardSink`.
- The one observable difference is in a rare failure path and is an improvement (C1-O06 (a)).

**The refactor is legitimate.**

## 16. Findings

Counts: **0 blocker, 0 high, 1 medium, 8 observations.**

### C1-M01: a sealed, V-valid spool can coexist with a Cancelled or Failed scan; the evidence overstates the guarantee

- **Requirement and code.** SINK-02 ("`ScanEndInfo` carries the outcome"), SPOOL-07 (seal at `OnScanEnded(Finished)`
  after v1's reports), CAT-02/CAT-03 (class B and C from any observer are never isolated).
  `ObserverFanOut.OnScanEnded` (`ObserverFanOut.cs:112-126`) tells the critical observer and then each isolated observer
  "Finished" in turn; `InventoryScanner.RunNamed` assigns `finished` only after that call returns
  (`InventoryScanner.cs:174-175`). Evidence §8: "No cancelled or failed run can yield a spool that later gates could
  mistake for a snapshot candidate … any other end leaves no trailer and no digest, and V rejects it."
- **Evidence.** Probe (a): `ScanObserved` with `[SpoolWriter, observer that throws OutOfMemoryException in
  OnScanEnded(Finished), recorder]` returns `Failed (Unexpected)`, `Catastrophic = true`, writer `Sealed`, **V passes**,
  the recorder is told `Failed`, and the three complete reports are listed as incomplete. Probe (b): the same with an
  `OperationCanceledException` while the run's token is cancelled returns `Cancelled` with a sealed, V-valid spool.
- **Failure mode.** One observer is told "Finished" while the scan's final outcome is Cancelled or Failed, and a spool
  that passes V exists for a scan that did not finish. In C1 this is harmless (the public path attaches no isolated
  observer; nothing consumes a spool). From C5 the only remaining defences are LIFE-08, IMP-01 and SPOOL-06 (5)
  (eligibility requires `StorageScanResult.Finished`) and CAT-04 (Faulted on class C). A C5 implementation that relied
  on the evidence's stronger statement, for example by deriving eligibility from `writer.State == Sealed` plus V, or
  that attaches any second isolated observer after the writer, could import a cancelled run.
- **Required correction.** (1) Correct the evidence §8 statement (and its table row) and, if wished, the
  `SpoolWriter` remarks: the writer seals only when told Finished, but a later isolated observer's class B or C
  exception during the Finished end can still change the outcome, so eligibility always rests on
  `StorageScanResult.Finished`. (2) Add a test that pins this behaviour (writer plus a later observer throwing class B
  and class C at the Finished end), so C5 cannot silently depend on the stronger property. (3) Record for C5 that the
  spool writer stays the only isolated observer in production, or is ended last; with the writer ended last, an earlier
  observer's class B or C reaches the writer through `EndRemaining` as Cancelled or Failed and it never seals.
- **Verification to close.** The corrected text; the new test passing in CI; C5's entry review confirming that its
  eligibility check reads `StorageScanResult.Finished`.
- **Severity.** Medium, not high: no C1 code path is unsafe, the specification's own layered conditions close the gap,
  and the fix is text plus a test. It is not a merge condition, but it must be closed before C5 starts.

### C1-O01: two of V's closure rules have no isolating test

- **Evidence.** Mutants M19 and M12 remove each rule; all 97 Core tests still pass. The "Unreadable folder with files"

- Related nit: `Random_single_byte_rewrites_are_never_accepted_unless_structurally_identical` asserts nothing about the

### C1-O02: `VerifiedSpool` trusts the verified state without bounding later reads

- **Code.** `VerifiedSpool.Utf16` (`VerifiedSpool.cs:161-173`) allocates `2 × length` bytes before reading; `ReadRun`
  (`:39`) accepts any `SpoolRun` value.
- **Evidence.** After V, a same-length change of one error-message length to `0x30000000` code units made the read
  allocate 1,610,680,104 bytes before failing with `SpoolFormatException`; `0x7FFFFFFF` failed with
  `OverflowException`. A run of another spool passed to `ReadRun` failed with `SpoolFormatException` (bounded).
- **Failure mode.** Only after the stream changes post-V, which SPOOL-23 places outside the integrity model and C5's
  exclusive handle prevents. Under memory pressure, though, such a read could surface as `OutOfMemoryException`
  (class C, so Faulted and a restart in C5) instead of a class A spool error.
- **Correction (hardening).** Bound every length by the verified bytes remaining before allocating; take a run index
  (or check membership) in `ReadRun`.
- **Verification.** The two probes then fail with `SpoolFormatException` and no large allocation.

### C1-O03: observers receive the run's live own-name set

- **Code.** `ScanStartInfo.OwnFileNames` is `run.OwnFileNames` (`InventoryScanner.cs:97`), the same `HashSet<string>`
  the engine's tripwire (`:133`) and `ReportRun.CreateNew`'s own-name check (`ReportRun.cs:50`, `:131-133`) use.
- **Failure mode.** An internal observer could downcast and clear or alter it, disabling the tripwire or breaking report
  creation. No first-party observer does; observers are internal, so this is defence in depth for item 18's "observer
  implementation cannot bypass report output containment".
- **Correction.** Pass an immutable copy (for example `FrozenSet` or `ReadOnlySet`) in `ScanStartInfo`.
- **Verification.** A test that casts `start.OwnFileNames` to `ISet<string>` and expects a failure or an unchanged run.

### C1-O04: class C while ending stops further `OnScanEnded` calls; canonical-root lookup outside the `try`

- **Code.** `ObserverFanOut.EndRemaining` returns at the first class C (`ObserverFanOut.cs:149`);
  `CanonicalRootOrNull` runs before `RunNamed`'s `try` (`InventoryScanner.cs:97`).
- **Evidence.** Probe (c): after a class C at start, a second class C while ending left a started observer never
  ended. A class C from the canonical lookup would escape `Scan` as an exception.
- **Assessment.** Documented judgement call 5, consistent with CAT-03 ("never retried") and OBS-13's "stopping at a
  second class C exception", but a narrow exception to SINK-03 #1's "exactly once". No information is lost:
  `Catastrophic` is set, and the escaping case is caught by CAT-04 at the App's task boundary, exactly as an
  exception from v1's own `PathPolicy.Validate` would be.
- **For C5.** Release the spool handle through `ReportRun`'s ownership (SPOOL-02), never through the writer's
  `OnScanEnded`.

### C1-O05: limits of the source-text audit rules; A-13 has no negative self-test

  `new StreamReader(path)` and similar path-taking constructors. Grep confirms no such use exists today.
- A-21 and TEST-A1 ask for a negative self-test for every rule; the A-13 reflection check has none.
