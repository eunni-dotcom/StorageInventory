## 10. A-25, the lease audit and runtime lease safety (C4-H01, C4-M05, C4-M13, C4-M17)

### 10.0 Summary

The frozen wording is enforced over every first-party assembly and production passes it; two genuine violations still pass the audit (10.2, 10.3). The run-time half of A-25 (OBS-15) is in section 19.

### 10.1 What the audit enforces now

`IlAudit.MutationViolations` (`IlAudit.cs:636-714`) implements the **frozen wording and nothing else by default**: a method has authority if it takes a `MutationLease`, or is private and **every** caller is a method of **its own type that takes a lease** (one hop: `who.All(c => c.Type == unit.Type && c.TakesLease)`, line 670). The three relaxations of the blocked audit (the lease-bound-type exemption, the lease-producer exemption, transitive private authority) survive only as `Options.Relaxed`, used by the negative self-tests that prove each one is load-bearing; `Options.Frozen` is the default and the real-assembly test runs with it. The audit reads **every first-party assembly** (Core, History, Library, App), follows calls through interface and virtual dispatch, keys methods by signature (parameter lists included), decodes `calli` (rejected anywhere), matches the specification's wider primitive list (`BeginTransaction`, `Commit`, the `*Async` execute and open methods, `File.OpenWrite`/`Open`/`OpenHandle`, `FileInfo` and `DirectoryInfo` operations, `StreamWriter(path)`, the engine's own `sqlite3_step`/`prepare`/`open`), and exempts exactly eight read-only signatures (A-25 (d), no wildcard, each shown load-bearing) plus six exact Core report-output methods that A-01 and A-04 themselves allow (`V1ReportOutput`, pinned; the repair record does not mention that list: O06).

**Production passes it, with no invented exemption.** The A-25 agent listed the 72 Library methods that reach a primitive or a leased operation: 63 take a `MutationLease`, one is a private helper whose only caller takes one (`WriterConnection.SetAndReadBack`, called by `Configure`), eight are the allow-listed read-only methods. The formerly problematic path is repaired: **`WriterConnection.Configure(MutationLease lease, bool importCache)` takes the lease and guards it before its first statement** (and `AssertEngine`, `PageCount`, `PageSize`, `BeginCancellationScope` likewise); `NameCache` no longer holds a lease (`Intern(lease, name)`, `LookUp(lease, name)`, `NameCache(writer, lease, sourceId)`); `WriterQueryRunner` is gone (`DelegateQueryRunner` captures the lease in a delegate built by a method that takes it); `RunStartup` and `TryRunMutation` live in the interlock and hand the lease to a lambda **as a parameter**; `ISpaceGuard` is a read-only callback and `ProgressGuard` uses `sqlite3_progress_handler`, which is not a primitive. The only lease-typed fields in the Library are `WriterConnection._openedBy` and compiler closures.

## 13. Cancellation (C4-M02, D-R7, CAN-01d, CAN-03)

- **Order around COMMIT (traced by me in `SnapshotImporter.Run/Execute`).** Rows with `GuardPoint` every 4,096 observation rows; errors and extension totals; token check; `VerifyCounts`; the verification inside a cancellation scope (token between queries, every 65,536 rows of a streamed query, and the engine's progress callback every 20,000 virtual-machine steps); token check and lease check after the verification; the final statements with the `FinalStatements` probe **between** `PublishSnapshot` and `PublishAttempt`; the **final** `GuardPoint` (lease, then the save token, then the space guard), which is the last look at the token; `COMMIT`. ## 14. IMP-11, the space-guard hook (D-R3)

`GuardPoint` implements the primitive of IMP-11 (3): the lease, then the save token, then the exact inputs (`PRAGMA page_count` through the writer, the page size, the main file's and the journal's lengths **through fresh handles** opened with `FileShare.ReadWrite | FileShare.Delete`), `Λ = Math.Max(0L, pageCount * pageSize - main)` in `long` throughout (no `int` cast on any path; page count at most 2³²−2 times 65,536 is far below 2⁶³), the record callback, then the guard. ### 25.1 C4R-M01: no bound on the stretch between two checks inside one big folder (CAN-01d, CAN-03, IMP-11)

- **Requirement.** CAN-01d: the save token is checked "at every IMP-11 check of T-IMPORT (`BEGIN`, every 4,096 inserted rows **of any table**, and the final check)" and "no two consecutive checks are more than 0.5 s apart"; IMP-11 (3): periodic checks "after every 4,096 inserted rows of any table"; CAN-03: detection at most 0.5 s. The brief (§25) says the time cadence must not be inferred from the row cadence.
- **Evidence (code).** `SnapshotImporter.InsertFiles` (`SnapshotImporter.cs:424-450`) interns **every name of a folder first** (`for (i < files.Count) ids[i] = names.Intern(lease, files[i].Name)`, lines 431-435) and only then inserts that folder's rows, and `RowsInserted` (the one place that advances the 4,096-row counter, lines 156-163) is called only for **observation rows** (file, folder, error and extension rows, `SpaceCheck.RowsInserted`'s own documentation says so). The `name` and `folder_path` inserts that D-52 now makes one per (source, name) are tables' rows too but are not counted, and the interning loop contains no token look, no lease check and no space check (only the per-statement lease guard of each statement).
- **Evidence (measured here, my own scratch test in a scratch worktree, never committed; one folder holding N files with names that are all new to the source; `ScriptedSnapshot`, a Create-lease import, the machine otherwise quiet apart from my own mutant builds).**

  | Names in the folder | Largest gap between two IMP-11 checks (BEGIN to the first row check) | Token `MaxGap` |
  |---:|---:|---:|
  | 10,000 | 112 ms | 61 ms |
  | 40,000 | 292 ms | 208 ms |
  | 100,000 | **680 ms** | **570 ms** |
  | 200,000 | **1,282 ms** | **1,254 ms** |

  Cancellation issued 100 ms after `BEGIN`, measured from the cancellation to `ImportSnapshotAsync` returning (detection plus rollback): 20,000 names 100 ms; 100,000 names **474 ms**; 200,000 names **1,079 ms**.

  The importer agent measured the same shape independently on a busier machine (120,000 names: 0.96 s between checks; 150,000: cancel latency 1.02 s). The stretch scales with the folder's name count and needs about 60,000 to 90,000 new names in one folder to pass 0.5 s here.
- **Failure mode and consequence.** A first save of a source with a very large folder (a mail spool, a thumbnail cache, a photo dump of 100,000 files or more) cannot be stopped for one second or more, the space guard cannot fire inside the stretch, and the interval's growth is not bounded by any check either (about twice the name bytes plus index overhead per new name: small for short names, but 120,000 names of 255 characters would write well over 100 MB before the first check, against an `I_L` of at least 32 MiB; this last figure is an estimate, not a measurement). No data is at risk (a cancellation or a guard stop afterwards rolls back as usual); the accepted detection budget and the guard's model are broken for that input. **No test sees it**: `SyntheticSnapshot` folders hold at most a few files, `ScriptedSnapshot` a handful, and the TEST-P1 generator uses the reference drive's small folders, so even a MET gate session would not reveal it (the §15.4 statement is made "in any TEST-P1 cell", the product requirement is not).
- **Required correction.** Count the `name` and `folder_path` rows toward the 4,096-row interval, or chunk the interning of a folder (look at the token, the lease and the space guard every 4,096 interns); add a test with one folder of at least 150,000 new names that asserts the largest gap between two token looks stays under 0.5 s and that a cancellation issued during the interning is detected within it. **Closure evidence:** that test, and the same measurement repeated in the gate session.

### 25.2 C4R-M02: TEST-L9's "exact inputs" and "an unreadable `page_count`" are not pinned (D-R3 as amended)

### 25.3 C4R-M03: the session tooling invalidates, and replaces, a valid run because of its result (§15.4 Validity)

- **Requirement.** §15.4: a run is invalid only if `U` exceeded the run rule or it "failed for an environmental reason recorded in its log (a disk error, a crash of the harness)"; "no valid run is ever discarded or replaced because of its result"; PERF-15 (c) judges a cancellation that does not roll back; the repair record (§7) itself says "a failed save is a valid, missed run and is never replaced".
- **Evidence (code, read by me).** `RecordJson.Validate` (`RunRecord.cs:100-168`) requires `cancel.rollback` for a `cancel` record. `rollback` is null **exactly when the cancelled run published** (`GateRunner.cs:376`: `if (!published) rollback = CheckRolledBack(...)`), that is when the product did not honour the cancellation. `GateBenchmark.RunCell` then exits **3** for a record "not fit as raw evidence" (lines 119-124), and `perf_session.Session.judge` (lines 380-384) turns any exit code other than 0 or −1 into the reason "the harness child failed (exit 3)" with status `invalid`, which `model.needs_run` replaces (at most five more attempts). A timed record with fewer than two IMP-11 checks (a save that fails at `BEGIN`) takes the same path. The Python branch that would report "cancellation was not honoured" as a valid, missed run is therefore unreachable.
- **Failure mode.** A product that ignores the cancellation intermittently (a race that skips a token check) has the offending run recorded as "harness child failed" and replaced by a later, honoured one; a product that always ignores it ends as NOT MEASURED instead of MISSED or STOP. The invalid attempts stay in the raw table, but with a wrong reason, and the cell's figure is decided by the replacements.
- **Required correction.** Let the harness child exit 0 and write the record for a published cancel run (the record then carries `published = true` and the Python judge reports MISSED or STOP by its own rule); reserve exit 3 for a record that cannot be interpreted; add a session self-test with a cancel run that published and one with a save that failed early, asserting a valid run that is never replaced. **Closure evidence:** those tests.

### 25.4 C4R-M04: a gate session can be re-run in place, and its report does not carry a failed negative control (§15.4 Session, Reruns; §19 C4)

- **Requirement.** §15.4: "a new session starts only after a documented objective invalidation … and is declared as such"; the first declared session on the frozen binary is the gate session; the negative control "must FAIL … if it passes, the checker is defective and TEST-P1 fails"; §19 C4's acceptance includes "the negative control failing as required".
- **Evidence (code, read by me).** (a) `perf_session.main` (lines 783-784) refuses to run a session only when `session.json` exists. A session that was **refused** by the pre-session quiet check (`refused.json`, exit 3) or **aborted** (`aborted.json`) has no `session.json`, so `perf_session.py run --session <same directory>` runs it again with `Session.runs = []`, appending to the same `runs.jsonl` and `judgements.jsonl` (duplicate run identifiers and clashing `order` values) with no new manifest and no `--supersedes` record; the refused-then-completed session keeps its `refused.json`, so the report says REFUSED. That is the natural thing to do after a refusal ("quiet the machine and run it again"). The accepted rule is a new, declared session. (b) `Session.finish` writes the status `TEST-P1 FAILED: the negative control did not FAIL` into `session.json` and exits 1, but `perf_session.rebuild` and `perf_report.session_report` never read the control: the report prints "Status: complete" and `PERF-15 (a)` MET beside a control table that shows PASS under the heading "must FAIL" (`model.evaluate` takes no control input). The importer, harness and Python agents confirmed both paths.
- **Failure mode.** (a) A poor first pass of an aborted session is followed by a second pass of the same manifest with only the second reflected in `session.json`; the replayed report and the live record disagree. (b) A defective checker yields a gate report that says MET.
- **Required correction.** Refuse `run` for any session directory that holds `refused.json`, `aborted.json` or `runs.jsonl` (a later attempt needs a new declaration naming the earlier one); let `rebuild`, `outcome` and the report read the control and mark the session and PERF-15 (a) `TEST-P1 FAILED` when it did not FAIL; add self-tests for both. **Closure evidence:** those tests.
